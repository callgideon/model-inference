## 0. The five numbers

1. **A 10 s clip is 2,061 input tokens and ~197 output tokens** (`meas.`
   2026-09-19, [`models/marlin2b/results/notes.md`](../../models/marlin2b/results/notes.md)),
   so at the console's current `$0.10 / $0.30` per 1M prices it bills
   **$0.0002652**. Price source:
   [`apps/app/supabase/migrations/0002_seed_models.sql:18`](../../apps/app/supabase/migrations/0002_seed_models.sql).
2. **That clip costs $0.000397 of GPU time on a 1080p source** at the measured
   1.57 clips/s, on-demand `g6e.2xlarge` at $2.24208/h, **at 100 % utilisation**.
   The API is sold **below marginal cost** today: −49.6 % gross margin at
   `U = 1`, before a single dollar of fixed cost.
3. **The transcode optimization is the whole business.** At the measured 360p
   throughput (3.58 clips/s) the same clip costs **$0.000174** → **+34.4 %** at
   `U = 1`, break-even at **U\* = 65.6 %** on-demand and **41.3 %** on a 1-year
   g6e Instance Savings Plan.
4. **A NAT Gateway would cost more than the inference.** At $0.045/GB of data
   processing [src](https://aws.amazon.com/vpc/pricing/), one 5.5 MB source clip
   pulled through NAT costs **$0.000248** — 94 % of the revenue for that clip, and
   the gateway currently downloads each clip **twice** (once to `ffprobe`, once by
   vLLM). GPU nodes must sit in a **public subnet behind an Internet Gateway**
   (ingress is free); that single decision is worth **$29,443/month** at scenario C.
5. **"No drops" is cheap at scale and expensive at the start.** One hot spare
   GPU adds **+4.3 %** to the monthly bill at 23 GPUs and **+38.9 %** at 3 GPUs.
   Below ~5 GPUs the right answer is a *stopped* warm-pool instance
   (**$16/month**, EBS only [src](https://docs.aws.amazon.com/autoscaling/ec2/userguide/ec2-auto-scaling-warm-pools.html))
   plus a bounded queue, not a hot spare. ⚠️ **Read §6.3's correction box before
   acting on this**: `g6e` cannot hibernate, a stopped instance does not hold
   capacity, and a stopped instance held behind an ODCR bills the full on-demand
   rate — [`04-autoscaling-and-capacity.md` §2.5](04-autoscaling-and-capacity.md)
   reaches the opposite conclusion on the same sources.

## 1. Cost per clip and per 1M tokens

### 1.1 The unit conversion — why this model needs three units, not one

Marlin samples video at **2 fps, 4–240 frames, 200,704 px/frame**, and each
*pair* of frames is one temporal patch of **196 tokens**
([`models/marlin2b/README.md`](../../models/marlin2b/README.md), model card).
Two frames per second, two frames per patch:

```
input_tokens ≈ 196 × video_seconds + prompt_text_tokens

  196 tokens / video-second
  11,760 tokens / video-minute
  705,600 tokens / video-hour

  1M input tokens = 5,102 video-seconds = 85.0 video-minutes = 1.417 video-hours
```

Check against measurement: a 10.1 s clip → 196 × 10.1 = 1,980 + 81 text = **2,061**,
which is exactly what vLLM reported (`meas.` 2026-09-19). The identity holds.

**This is the central economic fact of the product.** The customer sends ~30 bytes
of URL and a one-line prompt; the *model* manufactures 2,061 billable input tokens
from the clip's duration. Three consequences:

| Consequence | Why it matters |
|---|---|
| The customer cannot control the token count except by sending a shorter clip | Token pricing is really duration pricing with extra steps — and a confusing bill |
| Our own configuration sets the token count | The processor default bills **12,221** tokens for the same 10 s clip (5.9× — corrected 2026-09-20: 12,221 ÷ 2,061 = 5.93) at **the same cost to us** (1.47 vs 1.57 clips/s, `meas.`) |
| Revenue is 78 % input tokens | Output pricing barely matters: the `$0.30/1M` output price contributes $0.0000591 of the $0.0002652 |

The second row is a perverse incentive worth stating plainly: **the bug we fixed
(honouring the model's training budget) cut revenue per clip by 4.8× and left our
cost unchanged.** Correct engineering made the margin worse. On the default (wrong)
path the margin at `U = 1` is **+66.9 %**; on the correct path it is **−49.6 %**. A
pricing unit that rewards wasting tokens is the wrong pricing unit (§4.4).

So every number below is reported in three units:

- **$/clip** — the operational unit (one request = one clip).
- **$/1M tokens** — the console's billing unit, on input, output and total.
- **$/video-minute** — the unit the market uses for video understanding
  (TwelveLabs bills its Analyze API input at **$1.75 per hour of video**
  [src](https://www.twelvelabs.io/pricing), fetched 2026-09-20).

### 1.2 Correction: the cost sketch in `results/notes.md` is wrong by 3.6×

[`models/marlin2b/results/notes.md`](../../models/marlin2b/results/notes.md)
("Cost sketch") says one GPU-hour processes "57–129 video-hours → $0.02–0.04 per
video-hour". The video-seconds→video-hours conversion divided by 1,000 instead of
3,600:

```
c=8, 1080p: 1.57 clips/s × 10 s = 15.7 video-seconds per wall second
            × 3600              = 56,520 video-seconds per GPU-hour
                                = 15.7 video-hours per GPU-hour        (not 57)
  $2.24208 / 15.7               = $0.1428 per video-hour               (not $0.02–0.04)

c=8, 360p:  3.58 clips/s → 35.8 video-s/s → 35.8 video-hours per GPU-hour
  $2.24208 / 35.8               = $0.0626 per video-hour
```

⚠️ **One caveat on the 360p line (added 2026-09-20).** The 3.58 clips/s row was
measured on `Big_Buck_Bunny_360_10s_1MB.mp4`, whose prompt was **1,928 tokens**
([`models/marlin2b/README.md`](../../models/marlin2b/README.md) results table), not
2,061 — and since the token budget is `frames × 200,704` with
`frames = clamp(2 fps × duration, 4, 240)`, 1,928 tokens implies a **~9.84 s** clip,
not 10.1 s. So the 360p row is really 35.2 video-seconds per wall second, and
$2.24208 / 35.2 = **$0.0637** per video-hour rather than $0.0626 — about 2 % worse.
Every 360p figure in this document carries that same ~2 % optimism. It changes no
sign and no verdict; it is recorded so the §7.1 re-run fixes it at the source.

The true GPU cost is **$0.063–$0.143 per video-hour**, not $0.02–0.04. Revenue at
the current prices is **$0.0945 per video-hour** (§1.1), which sits *between* the
two — i.e. the sign of the margin is decided entirely by whether the transcode
optimization ships. `models/marlin2b/results/notes.md` should be corrected; the rest
of this document uses the corrected arithmetic.

### 1.5 Instances we have NOT measured — break-even throughput, not invented numbers

We have measurements on exactly one instance type. Rather than estimate clips/s on
L4, A10G or H100 from FLOPS ratios — dishonest for a workload whose bottleneck is
*video decode on the CPU*, not the LM (`meas.`, finding 7 in
[`results/notes.md`](../../models/marlin2b/results/notes.md)) — the useful output is
the **throughput each alternative must hit to beat `g6e.2xlarge`**:

```
break_even_clips_per_s(X) = price_per_hour(X) ÷ ( price_per_hour(g6e.2xlarge) ÷ 3.58 )
                          = price_per_hour(X) ÷ 0.62628
```

| Candidate | On-demand $/h | Must reach | = % of L40S post-transcode throughput | Prior |
|---|---|---|---|---|
| `g6.2xlarge` (L4 24 GB, **same 8 vCPU**) | $0.97760 | **1.56 clips/s** | 44 % | **Most likely win.** If the wall is the 8 vCPUs, an L4 box with the same 8 vCPUs lands near the same clips/s at 44 % of the price. The model is 5.4 GB BF16 — 24 GB is ample. |
| `g5.2xlarge` (A10G 24 GB, 8 vCPU) | $1.21200 | **1.94 clips/s** | 54 % | Same argument at 54 % of the price. |
| `g6e.4xlarge` (same L40S, 16 vCPU) | $3.00424 | **4.80 clips/s** | 134 % | Wins only if doubling vCPUs gives **>+34 %** clips/s. Plausible *before* the transcode fix; unlikely after it. |
| `g6e.8xlarge` (same L40S, 32 vCPU) | $4.52856 | **7.23 clips/s** | 202 % | Needs +102 %. Only if decode is still the wall at 16 vCPU. |
| `p5.4xlarge` (H100 80 GB, 16 vCPU) | $6.88000 | **10.99 clips/s** | 307 % | A 2B model on an H100 is a category error at this scale; relevant only for Qwen3.8-27B / DeepSeek-V4.1-Flash later. |

**Decision rule.** Run `models/marlin2b/bench.py -c 8` on `g6.2xlarge` and
`g5.2xlarge` with the same clips before committing to any reservation. If
`g6.2xlarge` clears 1.56 clips/s, the whole fleet moves to `g6` and every GPU dollar
in §3 drops by up to 55 %. This is a **half-day experiment worth more than every
other optimization in this document**, and it also attacks the capacity problem:
`g6` is a far more widely deployed family than `g6e` in us-east-1 (⚠️ TO BE VERIFIED
by attempting launches in 1a/1b/1c/1f).

The counter-argument: the L40S has several times the L4's BF16 throughput, so if
the transcode fix moves the bottleneck back onto the LM, the L4 falls short. That is
exactly why the rule is *measure, then reserve*.

### 1.6 What the transcode optimization is worth, in money

One change — `ffmpeg` downscale to ≤480p before the clip reaches vLLM; the model
never sees more than 448×448 anyway:

| | 1080p today | post-transcode (360p-equivalent) | Δ |
|---|---|---|---|
| clips/s at c=8 `meas.` | 1.57 | 3.58 | **2.28×** |
| TTFT p50 `meas.` | 3.35 s | 0.66 s | −80 % |
| $/clip @ `U=1`, on-demand | $0.000397 | $0.000174 | −56 % |
| Gross margin @ `U=1` | **−49.6 %** | **+34.4 %** | sign flip |
| Break-even utilisation, on-demand | **149.6 % (impossible)** | **65.6 %** | feasible |
| Scenario C monthly GPU line (1y SP) | $26,517 ⚠️ est. | **$11,629** | **−$14,888/mo** |

Where to do it, cheapest first:

1. **In `apps/infrx-api/gateway.py`, during the download it already performs.**
   The gateway downloads the clip to run `ffprobe` (`video_seconds()`); piping that
   same file through `ffmpeg -vf scale=-2:480 -r 2` costs one more process on a file
   already in page cache, and lets the gateway hand vLLM a **local path or data URL
   instead of the original URL** — which also **removes the second download vLLM
   performs today**. Two wins from one change.
2. **On the L40S's NVDEC/NVENC** rather than libx264 on the contended 8 vCPUs
   (`-hwaccel cuda -c:v h264_cuvid`, `scale_npp`). The hardware is already paid for
   and idle. ⚠️ TO BE VERIFIED that NVDEC decode of arbitrary customer codecs is
   robust enough to be the default path (fall back to CPU on failure).
3. **A separate `c7i` transcode pool** ($0.357/h on-demand, $0.23616/h on a 1y
   Instance SP) only if 1 and 2 leave the GPU starved. At scenario C's 23 clips/s
   mean that is ~3–4 `c7i.2xlarge` ≈ **$260–390/month**, against the **$14,888/month**
   of extra g6e time the untranscoded path costs. Still a clear win, but strictly

### 2.3 Fixed/variable crossover

At the 1y-SP GPU rate the fixed floor ($1,138) equals the marginal GPU cost
($0.00010960/clip at `U=1`, post-transcode) at

```
1,138 ÷ 0.0001096 = 10.4 M clips/month = 341,000 clips/day
```

Below that, **this is a fixed-cost business**: the bill barely moves with traffic and
each extra request is nearly free. Above it, it becomes a variable-cost business and
the per-clip figures of §1.4 dominate.

All three scenarios in §3 sit *below* that crossover. That is the most important
framing for pricing (§4): **at our traffic, revenue must cover a fixed floor, not a
per-token cost.**

therefore "how fast do we get from A to B", not "what does the GPU cost".

### 4.4 Recommended pricing change, and when to make it

**Change the unit, then the number.**

1. **Bill per video-second, not per token**, for video requests. The gateway already
   computes and records `video_seconds` per request
   ([`gateway.py`, `video_seconds()`](../../apps/infrx-api/gateway.py);
   `usage_events.video_seconds`), so the plumbing exists. Tokens stay in the
   response's `usage` object for OpenAI compatibility; they stop being the billing
   basis. This removes the perverse incentive of §1.1 and makes the bill predictable
   from the one thing the customer controls — clip length.
2. **Launch at $0.006/video-minute** = $0.36/video-hour = **$0.001 per 10 s clip**.
   That is a **70 % all-in margin at scenario B**, ~80 % at C, and still **4.9×
   below** TwelveLabs. Publish the token-denominated equivalent for comparison
   shoppers: ≈ **$0.38 / $1.14 per 1M**.
3. **Keep a free tier of 60 video-minutes** (~360 pilot clips). That is $0.07 of
   marginal cost — cheaper than the Supabase rows it writes.
4. **Add a `$0` cached price and make it real.** `usage_events.cached` is currently
   hard-coded `False` ([`gateway.py`](../../apps/infrx-api/gateway.py)). A
   re-request of the same clip + prompt should be served from a result cache and
   billed at zero: it costs an S3 GET ($0.0000004) and buys goodwill (§6.5).

**Triggers to revisit the price** — write them as alarms, not as a calendar
reminder:

| Trigger | Threshold | Action |
|---|---|---|
| All-in cost per clip (CUR ÷ `usage_events`) | > 30 % of price | Raise price or cut cost; margin is heading under 70 % |
| Running GPU utilisation, 7-day p50 | < 35 % for two weeks | Scale-to-zero or consolidate — do **not** raise price to fix idle |
| A cheaper GPU family clears §1.5 break-even | measured | *Lower* price to buy share; the cost basis moved |
| One customer exceeds 20 % of total video-seconds | measured | Negotiate a committed-volume rate above marginal cost, not off list |
| Source-resolution mix shifts above 50 % 1080p+ | measured | Transcode cost rises; re-check §1.6 |
| Qwen3.8-27B goes live | — | Price it separately; its `$/1M` has nothing to do with Marlin's |

### 4.5 What breaks if we do nothing

At the current price each scenario burns money, and on the 1080p path it burns
**more the more successful it is** (−$0.00013 marginal per clip). A pricing bug that
is linear in success is worse than an outage. This is the one item here that should
not wait for the rest of the architecture.

### 5.2 On-Demand Capacity Reservations — the g6e scarcity tax

Today's deployment is pinned to **us-east-1d** because every other AZ returned
`InsufficientInstanceCapacity`. Scale-out *can fail*, which is incompatible with "no
dropped requests". The only instrument for g6e is an ODCR (Capacity Blocks exclude
the G family, §1.3).

AWS is explicit about the cost: *"Capacity Reservations are charged at the
equivalent On-Demand rate whether you run instances in reserved capacity or not"*,
and *"Billing discounts for Savings Plans and Regional Reserved Instances apply to
Capacity Reservations"*, with *"Discounts … preferentially applied to instance usage
before covering unused Capacity Reservations"*
[src](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-reservations-pricing-billing.html)
(fetched 2026-09-20). So an ODCR is a Savings-Plan-coverable standing charge:

| Reserved `g6e.2xlarge` | At on-demand | Covered by 1y NU g6e ISP | What it buys |
|---|---|---|---|
| 1 | $1,636.72/mo | **$1,031.13/mo** | The always-on box cannot be evicted by a capacity crunch |
| 3 | $4,910.16/mo | **$3,093.40/mo** | Scenario B's peak is always launchable |
| 5 | $8,183.59/mo | $5,155.66/mo | B's peak + N+2 |
| 8 | $13,093.75/mo | **$8,249.06/mo** | Scenario C's p50 |
| 23 | $37,644.52/mo | $23,716.04/mo | Scenario C's *peak* — **1.9× the whole modelled C bill** |

**Decision rule — reserve the floor, never the peak:**

```
odcr_count   = ceil(p50_concurrent_gpus)   # capacity you use nearly always
spot + on-demand cover everything above it # priced per hour, may fail to launch
```

At B that is 1–2 reservations ($1,031–2,062/month, fully used, so the "unused
reservation" line is $0). At C it is ~8 — **$8,249/month** of guaranteed capacity,
65 % of the modelled bill, all of it capacity we were buying anyway. Reserving the
*peak* converts a variable cost into a fixed one at exactly the moment the fixed
floor is already the problem (§2.3).

**Reserve in two AZs, not one.** A single-AZ ODCR in us-east-1d pins us to the AZ
that is already constrained. Splitting the reservation costs the same dollars and
removes the correlated failure; the only new charge is $0.01/GB for anything that
crosses AZs
[src](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AWSDataTransfer/current/index.json),
which for a stateless gateway→vLLM path on the same host is $0.

### 6.4 The other direction: what scale-to-zero would save, and why not yet

At scenario A the GPU is **96.8 % idle**. Scaling to zero between requests would cut
$1,031–1,637/month to roughly $60/month of real compute plus warm-pool EBS. The
blocker is the **2–3 minute vLLM boot** (`meas.`, including `torch.compile`): the
first request after an idle gap waits minutes.

```
scale_to_zero_is_acceptable if
     p99_idle_gap > 30 min                 # not thrashing the boot
 and customer_contract_allows_cold_TTFT    # async/batch tier, not interactive
 and queue_holds_the_request               # §6.1 - never a 503
```

The clean product answer is **two tiers**: an interactive tier on the always-warm
GPU at the §4.4 price, and a **batch tier priced ~40 % lower** on scale-to-zero +
spot with a minutes-scale SLA. The batch tier's marginal cost is $0.000080/clip
(spot, `U=1`) and it fills the troughs the interactive tier leaves — the mechanism is
[`07-cost-engineering.md` §2.3](../scaling/07-cost-engineering.md).

### 7.2 The same benchmark on `g6.2xlarge` and `g5.2xlarge` (removes: §1.5, up to 55 % of the GPU bill)

The single highest-value experiment in this document. Break-even is **1.56 clips/s**
on `g6.2xlarge`, **1.94** on `g5.2xlarge`. Half a day of work; up to −$6,389/month at
scenario C, plus better AZ availability.

### 7.3 Where the seconds go (removes: §1.6's "which fix first")

Instrument `gateway.py` to emit four spans per request — `download_s`, `ffprobe_s`,
`transcode_s`, `upstream_s` — into the existing `usage.jsonl` line. Today the only
timings recorded are `ttft_s` and `wall_s` ([`gateway.py`,
`log()`](../../apps/infrx-api/gateway.py)). Without the split we are guessing which
half of "per-request video handling" to optimise.

### 7.4 Real traffic shape (removes: §3's invented scenarios)

From `usage_events` in Supabase, weekly:

```sql
-- peak-to-mean ratio and the utilisation denominator, per day
select date_trunc('day', created_at)                  as d,
       count(*)                                       as clips,
       sum(video_seconds)                             as video_s,
       max(cnt_per_min)                               as peak_per_min,
       count(*)::float / (24*60)                      as mean_per_min,
       max(cnt_per_min) / (count(*)::float / (24*60)) as peak_to_mean
from (select *, count(*) over (partition by date_trunc('minute', created_at)) cnt_per_min
      from usage_events) u
group by 1 order by 1;

-- repeat rate: the value of the result cache (§6.5)
select 1 - count(distinct (org_id, request_fingerprint))::float / count(*) as repeat_rate
from usage_events
where created_at > now() - interval '30 days';

-- source-resolution mix: how much the transcode is worth (§1.6)
select width_bucket(video_seconds, 0, 120, 12) bucket, count(*), avg(latency_ms)
from usage_events group by 1 order by 1;
```

⚠️ `request_fingerprint` does not exist yet. Adding a hash of (clip URL, prompt,
params) to `usage_events` is a one-column migration in
`apps/app/supabase/migrations/` and is the prerequisite for pricing cached hits.
⚠️ Neither does a source-resolution column; the gateway knows it from `ffprobe` and
should record it.

### 7.5 Actual dollars, not modelled dollars (removes: every non-GPU line in §3)

Enable **Cost and Usage Report 2.0** with resource IDs and hourly granularity, tag
every resource `Service=marlin2b`, and reconcile monthly:

```
cost_per_clip_actual = (CUR total where tag Service=marlin2b) ÷ (count(*) from usage_events)
margin_actual        = 1 − cost_per_clip_actual ÷ (sum(cost_usd) ÷ count(*))
```

CUR 2.0 also exposes Capacity Reservation status per line
(`capacity_reservation_capacity_reservation_status` = `Reserved` / `Used` /
`Unused`, with `UnusedBox` as the idle-capacity usage type)
[src](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-reservations-pricing-billing.html),
which is exactly the metric that tells us whether §5.2's "reserve the p50" rule is
sized right. Publish both numbers on an internal dashboard beside GPU utilisation.
Every estimate in this document is a placeholder for that ratio.

## Implications for our system

In order. Each names the file that changes.

1. **Fix the pricing unit and the price** — `apps/app/supabase/migrations/` (a new
   migration updating `models`), `apps/README.md` §F3/§F9, the console Models page,
   `cost()` in [`apps/infrx-api/gateway.py`](../../apps/infrx-api/gateway.py), and
   the docs snippets. Move to **$/video-second** at **$0.006/video-minute** (≈
   $0.38/$1.14 per 1M as the token-denominated equivalent). At $0.10/$0.30 there is
   *no* utilisation at which the current 1080p path is profitable (§4.2), and correct
   token budgeting makes the margin worse (§1.1). This is the only change that is
   linear in success.
2. **Put the GPU nodes in a public subnet behind an Internet Gateway; never NAT** —
   the VPC/ASG template that `apps/infrx-api/deploy/` does not yet contain. NAT's
   $0.045/GB applies to the ingress this workload is made of: **+$1,503/month at
   scenario B, +$29,443 at C with today's double download** (§2.2). If private
   subnets are mandated later, the answer is an S3 Gateway Endpoint plus
   customer-staged clips, not NAT.
3. **Do the transcode inside `gateway.py`, in the download it already performs** —
   `video_seconds()` should return a downscaled local file and hand *that* to vLLM
   instead of the original URL, which also removes vLLM's second download. Worth
   **2.28× throughput, −56 % $/clip, and the sign of the margin** (§1.6); prefer
   NVDEC on the idle L40S over libx264 on the contended 8 vCPUs.
4. **Replace the 429 with a bounded queue** — `apps/infrx-api/gateway.py`. The queue
   costs **$0–18.69/month**, and holding connections costs **$0.008 per 3,000 per
   hour** (§6.1). There is no cost argument for dropping requests. Verify and raise
   the ALB idle timeout in the same change.
5. **Benchmark `g6.2xlarge` and `g5.2xlarge` before buying any commitment** —
   `models/marlin2b/bench.py`. Break-even 1.56 / 1.94 clips/s; upside up to
   **−55 % of every GPU dollar** plus better AZ availability (§1.5, §7.2).
6. **Warm pool of *stopped* instances, not hot spares, below ~5 GPUs** — the ASG in
   `apps/infrx-api/deploy/`. **$16/month** versus **$1,637/month** for the same
   capacity 2–3 minutes later (§6.3). Buy the hot spare once N ≥ ~10, where it costs
   under 5 %. ⚠️ **Contested — corrected 2026-09-20.** The arithmetic holds, the
   mechanism may not: `g6e` cannot hibernate, a `Stopped` instance does not reserve
   capacity in the family that already returns `InsufficientInstanceCapacity`, a
   warm pool cannot coexist with §5.1's spot mixed-instances policy, and a warm pool
   held behind an ODCR bills the full on-demand rate.
   [`04-autoscaling-and-capacity.md` §2.5](04-autoscaling-and-capacity.md)
   recommends the opposite — *reserve and run warm* — on the same primary sources.
   **Resolve this disagreement before writing the ASG template.**
7. **Buy a 1-year No-Upfront *Compute* Savings Plan sized to the floor now; convert

8. **ODCR the p50, not the peak, and split it across two AZs** (§5.2). Savings Plans

9. ~~**Run the elastic tier on spot with a persisted queue** (§5.1). −54 % on elastic
