## 1. What this is

Fact-checked research on taking the single-box Marlin-2B endpoint (`apps/infrx-api/gateway.py` on one `g6e.2xlarge`) to real, paying users on AWS: no dropped requests, a bounded queue that absorbs load while capacity scales up, automatic scale-up/down, caching, and throughput/latency optimization. Ten documents, `01`–`10`, each with its own verification log. **Research date: 2026-09-20**, pinned in every document; AWS prices, quotas and API surfaces move, so re-pin before you build. Every non-trivial claim carries an inline `[src]` or an **⚠️ TO BE VERIFIED** marker.

This tree is scoped to **today's system on AWS**, not the bare-metal target: [`../scaling/`](../scaling/README.md) plans an 8×B300 cluster and its Marlin-2B numbers are `est.`; this tree plans **one L40S, growing to a handful**, and its Marlin numbers are **measured** ([`../../models/marlin2b/results/notes.md`](../../models/marlin2b/results/notes.md), 2026-09-19). Where the two disagree, the measurement wins.

## 4. The documents, 01–10

**[`01-requirements-and-traffic-model.md`](01-requirements-and-traffic-model.md) — requirements, SLOs and traffic model.** Fixes what the API promises and how much hardware that costs. Measured on one L40S at concurrency 8: **1.57 clips/s on 1080p sources vs 3.58 clips/s on 360p** — a 2.3× swing driven entirely by video fetch/decode, not the LM (6% throughput cost for 5.9× the prompt tokens). Capacity: **1 GPU** covers the pilot scenario (S1), **6–10 GPUs** growth (S2), **29–46 GPUs** a 50 req/s burst (S3); scale-up takes **~5–7 min**, so a 5-minute burst must be absorbed by queue plus headroom, not scaling. AWS ALBs default to a **60 s idle timeout**, which a held connection cannot survive through a scale-up.

**[`02-aws-architecture-options.md`](02-aws-architecture-options.md) — AWS architecture options.** Compares five shapes (A–E: single box, ASG behind ALB, SageMaker, EKS/Karpenter, serverless-GPU broker) and picks one for the next 3 months and one for 12. Today's box: `g6e.2xlarge` (1× L40S 48 GB, 8 vCPU) at **$2.24208/h** on-demand, us-east-1; SageMaker real-time/async hosting is **+25%** over EC2 ($2.8026/h). Recommends ALB → gateway fleet → queue → ASG GPU workers now, portable to EKS/Karpenter or the bare-metal cluster later.

**[`03-request-handling-and-queueing.md`](03-request-handling-and-queueing.md) — no-drop request handling.** The request-path design: admission contract, bounded queue with an honest wait estimate, the CPU stage that is the real bottleneck, retries, routing, and a concrete gateway v2. Replaces today's entire overload policy — three lines that 429 above `MAX_INFLIGHT=16` with no queue — with durable admission before acknowledgement and an explicit typed refusal with `Retry-After` when it cannot be met. Sets **three limits, not one**: engine `--max-num-seqs`, a per-worker dispatch gate, and a central burst queue of hundreds.

**[`04-autoscaling-and-capacity.md`](04-autoscaling-and-capacity.md) — automatic scale-up/down with scarce GPU capacity.** Scale on **backlog per replica** and **oldest-queued-request age**, never GPU utilization; target backlog **47** (= 30 s wait × 1.57 clips/s). `g6e` Spot quota is **0** and Spot Placement Score is **1/10** in every AZ that offers it, so the reliable levers are an On-Demand Capacity Reservation, a mixed-instances policy across `g6e.2xl/4xl/8xl` in four AZs, and the queue. Cold start is **~5–8 min** today, cuttable to **~100–200 s** by baking weights and the `torch.compile` cache into the AMI's EBS root. Scale-down: a termination lifecycle hook, slow asymmetric scale-in, `min_size = 1`, no scale-to-zero for the pilot.

**[`05-caching.md`](05-caching.md) — caching at every layer.** Prefix caching (APC) is worth **~1–2%** on distinct clips (~0% for video: the video hash poisons every block hash past the chat-template preamble). vLLM's multimodal processor cache does not cache the slow part — HTTP fetch and frame decode happen before its key exists. The single biggest lever: **transcode once at ingest to ≤480p, cache by content hash** — the measured 2.28× win, and it pays on the *first* request, not a cache hit. No CloudFront (the video flow is ingress, not egress). Pre-signed S3 PUT URLs replace base64 in the request body, but EC2-instance-role-signed URLs are capped at ~6 h, not S3's 7-day ceiling.

**[`06-throughput-and-latency-optimization.md`](06-throughput-and-latency-optimization.md) — making one request faster, one GPU do more.** The GPU runs at **5.8% of its dense BF16 rate** during steady-state video captioning; four CPU cores are the binding constraint, so every recommendation is ordered by how much CPU work it removes from the request path. TTFT grows 4.4× from c=1 to c=8 (0.77 s → 3.35 s) while TPOT grows only 1.33×, meaning whatever congests is ahead of the token loop. Names every file to change: `gateway.py`, `serve.sh`, the systemd units, `bench.py`, the instance type.

**[`07-reliability-observability-operations.md`](07-reliability-observability-operations.md) — reliability, observability, ops.** Metrics/alerts, health/readiness/deploy/rollback, failure handling, security, **eight runbooks**, testing, paging. ALB target-group tuning: `deregistration_delay=900s` (covers a 120 s clip plus queue drain), `least_outstanding_requests` (video requests vary >10× in cost), `slow_start=120s` (absorbs the ~18 s first-`mm_processor_kwargs` penalty). The vLLM boot time of **~2–3 min** everything downstream sizes against is itself ⚠️ **TO BE VERIFIED** — no repo file records a measured boot.

**[`08-cost-model-and-unit-economics.md`](08-cost-model-and-unit-economics.md) — cost model and unit economics.** At the console's current **$0.10/$0.30** per 1M token price, a 10 s clip (2,061 input / ~197 output tokens) bills **$0.0002652** but costs **$0.000397** of GPU time on a 1080p source at 100% utilization — already underwater. At the Growth scenario (200K clips/day) even on a 1-year Savings Plan the API **loses 13.6%** gross margin; NAT Gateway on this ingress-dominated workload would add **+$29,443/month** at Scale scenario, more than the inference itself. Pricing is the one lever here that is linear in success.

**[`09-blueprint.md`](09-blueprint.md) — the assembled system.** No number here is new; every figure is carried from `01`–`08` or one stated multiplication on carried figures. The shape: **ALB → stateless gateway fleet → Valkey queue → queue-pull GPU workers (ASG, multi-AZ, mixed g6e sizes, ODCR floor)**, Supabase for auth/usage, S3 for media and async results. Resolves five cross-document contradictions (fetch timeouts, transcode geometry, worker budget vs. max video length, `max_num_seqs` vs. `MAX_INFLIGHT`, spot economics). Nine of the ten highest-value actions are code in `gateway.py` and flags in `serve.sh` — the AWS work is real but is not where the wins are.

**[`10-implementation-spec.md`](10-implementation-spec.md) — gateway v2, worker, queue, transcode.** An engineering document: module layout, the Redis key schema (ZSET leases, LIST ready queue, two Lua scripts for weighted-fair-queueing), the HTTP API (`POST /v1/chat/completions` sync, `POST /v1/jobs` + `GET /v1/jobs/{id}` + resumable SSE async), the request state machine, media-stage SSRF guard and transcode, the worker loop with heartbeat/reaper/drain, config, metrics, an 11-item failure-handling table, a test plan, and a phased migration off the current 481-line gateway. Resolves four conflicts the research left open (D1–D4), including shipping `ENGINE_MAX_NUM_SEQS=8` / `WORKER_CONCURRENCY=10` until a step-load sweep re-pins them. `REDIS_URL` unset ⇒ in-process queue, so single-box mode keeps working.

## 6. Top 13 open questions across the tree

Deduplicated from each document's own Open-questions section and reconciled against [`09` §10.2](09-blueprint.md#102-open-questions-consolidated) (18 items, the fuller consolidated list — go there for the rest: NVDEC/FLA-Triton feasibility, stream-abort propagation, `uuid`-remap survival, vLLM readiness-vs-listening, response-cache content-storage policy, `expired` billability, the Elastic-IP dependency). Each item below is load-bearing for at least one number above; a `→` note marks where `09`/`10` narrowed or answered a question this list used to leave fully open.

1. **Is every measured throughput figure inflated by vLLM's multimodal processor cache?** All benchmark rows reused one clip; `mm_processor_cache_gb` defaults to 4 GiB. Foundation of every capacity, autoscaling and cost number in the tree. [`01`](01-requirements-and-traffic-model.md#open-questions), [`04`](04-autoscaling-and-capacity.md#open-questions), [`05`](05-caching.md#open-questions), [`06`](06-throughput-and-latency-optimization.md#open-questions), [`08`](08-cost-model-and-unit-economics.md#open-questions) → still fully open; `09` §10.1 K1 makes it Phase 0's B0.1, gating everything downstream.
2. **No end-to-end cold start has ever been measured for Marlin on an L40S.** `InstanceWarmup`, health-check grace period, lifecycle-hook heartbeat are all `est.` on top of an `est.` [`01`](01-requirements-and-traffic-model.md#open-questions), [`02`](02-aws-architecture-options.md#open-questions), [`04`](04-autoscaling-and-capacity.md#open-questions), [`07`](07-reliability-observability-operations.md#open-questions) → still open; `09` §10.2 item 4 makes it Phase 0's B0.4.
3. **The concurrency knee is unknown.** `MAX_INFLIGHT=16`, `--max-num-seqs 32`, only `c=8` ever benchmarked — more concurrency may *reduce* throughput on an 8-vCPU box. [`03`](03-request-handling-and-queueing.md#open-questions), [`04`](04-autoscaling-and-capacity.md#open-questions), [`10` D4](10-implementation-spec.md#decisions-this-spec-makes-that-the-research-left-open) → **narrowed**: `10` D4 ships an interim `ENGINE_MAX_NUM_SEQS=8` / `WORKER_CONCURRENCY=10` (the only measured point, +2) rather than leaving the flags at today's unmeasured 32/16 pending the step-load sweep.
4. **Does throughput scale with vCPU?** The CPU-bound thesis predicts `g6e.4xlarge` is ~1.49× cheaper per clip; unmeasured. [`01`](01-requirements-and-traffic-model.md#open-questions), [`04`](04-autoscaling-and-capacity.md#open-questions), [`06`](06-throughput-and-latency-optimization.md#open-questions)
5. **Does GPU video decode (NVDEC / `pynvvideocodec`) work on L40S with the pinned vLLM image?** Could make the whole CPU-transcode tier unnecessary, or cost more KV than it saves CPU. [`01`](01-requirements-and-traffic-model.md#open-questions), [`02`](02-aws-architecture-options.md#open-questions), [`06`](06-throughput-and-latency-optimization.md#open-questions)
6. **Does transcoding a 1080p source to ≤480p actually reproduce the measured 360p throughput (3.58 clips/s)?** The 360p measurement used a different, smaller source file, not a transcoded one — every margin sign in `08` depends on it. [`03`](03-request-handling-and-queueing.md#open-questions), [`05`](05-caching.md#open-questions), [`08`](08-cost-model-and-unit-economics.md#open-questions) → still fully open; `09` §10.1 K2 makes it Phase 1's exit criterion, measured through the gateway.
7. **What is the throughput of a 120 s clip?** Every capacity number extrapolates linearly in video-seconds from 10 s clips; at 120 s the prompt is 11.5× larger and there is no reason to expect linearity. [`01`](01-requirements-and-traffic-model.md#open-questions), [`03`](03-request-handling-and-queueing.md#open-questions) → still fully open; `09` §10.2 item 3 makes it Phase 0's B0.3.
8. **The real request mix is unknown.** Operation split, clip-length and source-resolution distribution, peak:mean ratio, repeat rate — every one is an assumption today. [`01`](01-requirements-and-traffic-model.md#open-questions), [`08`](08-cost-model-and-unit-economics.md#open-questions)
9. **Does a queued request survive the ALB's idle timeout during a multi-minute scale-out wait?** [`04`](04-autoscaling-and-capacity.md#open-questions), [`08`](08-cost-model-and-unit-economics.md#open-questions) → **narrowed, not closed**: `01`/`02`/`04`/`07` disagreed (180 s vs 900 s vs 600 s); `09` §0.2 R1 settles the design at `idle_timeout=180` with a mandatory SSE keepalive and the 202-upgrade rule, and `09` §0.2 R6 replaces `01`'s "keep N+1 warm" with `async_upgrade_enabled=on` for the 90–170 s scale-out window it actually measures (not "~30 s"). What is left open is empirical: no request has yet been driven through a live ALB to confirm the keepalive survives it — `10`'s test plan item 12 is that measurement.
10. **`g6e` Spot/Savings-Plan economics and multi-AZ capacity are snapshots.** Spot quota is 0 and Spot Placement Score is 1/10 today — account- and day-specific — and ODCR-vs-warm-pool compatibility is inferred, not documented. [`02`](02-aws-architecture-options.md#open-questions), [`04`](04-autoscaling-and-capacity.md#open-questions), [`08`](08-cost-model-and-unit-economics.md#open-questions) → still open; `09` §10.2 item 18 restates it as the largest single-point-of-failure input to `09` §7.
11. **NAT Gateway's per-GB rate was read from the Ohio pricing page, not N. Virginia**, and the regional offer file was too large to pull in session — confirm before quoting the +$29,443/month figure externally. [`08`](08-cost-model-and-unit-economics.md#open-questions)
12. **Product question: can customers be required to upload clips to a presigned S3 URL instead of supplying arbitrary URLs?** If yes, the residual SSRF surface (the error-class oracle, the validate-then-connect rebind window) and most of the egress security-group surface disappear at once. The duplicate download is already gone — commit `0952ca2`. [`07`](07-reliability-observability-operations.md#open-questions) → `09` §10.2 item 13 calls it "the single highest-leverage decision in this program, and it is a product decision, not ours" — still unresolved.
13. **Can a Valkey failover drop an already-acknowledged 202?** Not asked by `01`–`08`; surfaced while writing `09`/`10`'s durable-queue design (the mechanism the whole "no dropped requests" promise now rests on). [`09` §1.2, §10.2 item 17](09-blueprint.md#102-open-questions-consolidated), [`10` F28](10-implementation-spec.md) → **filled with a decision rule, not yet a measurement**: `09` specifies an `aws elasticache test-failover` drill with a known job-id set before the async tier carries real traffic; if any acknowledged id is lost, ship either the SQS async tier (`10` §3.7) or a synchronous Supabase write ahead of the 202, never "rely on the client to retry" (a retry after a lost 202 is a duplicate, not a recovery, under `10`'s D2).
