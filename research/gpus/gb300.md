# NVIDIA GB300 NVL72 (Grace Blackwell Ultra) — inference reference

Research date: **2026-09-19**. Follows [`research/METHODOLOGY.md`](../METHODOLOGY.md).
Markers: `[src]` = primary source link, **⚠️ TO BE VERIFIED** = estimate/unsourced,
`est.` = derived from METHODOLOGY formulas, `meas.` = published measurement.

**Scope note.** GB300 is a *rack*, not a GPU. This document keeps two views
separate throughout:

* **Per-GPU view** — one B300 "Blackwell Ultra" die-pair as configured inside a
  GB300 compute tray (liquid-cooled, **1,100 W**). This is **not** the same operating
  point as the B300 in an air-cooled HGX/DGX B300 node; see §1.
* **Rack view** — the 72-GPU NVLink-5 domain, which is the whole reason GB300
  exists and the only configuration in which EP=72 / wide-EP decode is possible.

### 2.3 What the extra 93 GB/GPU vs GB200 actually buys

GB300's HBM bandwidth per GPU is **identical to GB200's** (8 TB/s; 576 TB/s per
rack on both) [src](https://www.nvidia.com/en-us/data-center/gb200-nvl72/). The
capacity is the delta: 279 vs 186 GB spec (+50 %). So GB300 is *not* a decode
bandwidth upgrade — it is a **concurrency / context-length** upgrade plus an FP4
and attention-throughput upgrade. This is visible directly in SGLang's measured
max decode concurrency at 128K context: **40 req/GPU on GB300 vs 24 req/GPU on
GB200 (1.67×)** [src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/).
Those two are the *theoretical* capacities in that post; the same post's
practical figures are **~36 vs ~20 req/GPU** (1.8×) — plan with the practical
pair [src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/).

### 3.1 The INT8 trap on sm_103 — read this before quoting any INT8 number

An ISA- and source-level audit published on arXiv establishes that INT8 on
Blackwell Ultra is *listed but not usable by default*
[src](https://arxiv.org/html/2608.11693v1):

* Published dense peaks: H200 = 1,979 TFLOPS FP8 / 1,979 TOPS INT8 (1:1);
  HGX B200 = 4.5 PFLOPS / 4.5 POPS (1:1); **HGX B300 = 4.5 PFLOPS FP8 / 150 TOPS
  INT8 (~30:1)**.
* PTX ISA: `tcgen05.mma` qualifier `.kind::i8` is documented for
  `sm_100a … sm_110a` — **`sm_103a` is absent**. B300 falls back to legacy
  warp-level `mma.sync .s8/.u8`, which runs at the throttled ~1/30 rate.
* CUTLASS skips INT8 UMMA kernel generation when targeting `sm_103a`; the only
  SM103-specific generator emits FP4 kernels.
* vLLM ships no Blackwell INT8 GEMM and raises `Int8 not supported on SM<N>` at
  the *first forward pass* — after the weights have already downloaded and loaded.
* SGLang's AOT INT8 support stops at sm_90; no B200/B300 INT8 tuning configs exist.

**Planning rule: treat INT8 and INT4-activations as unsupported on GB300.**
W4A16 (AWQ/GPTQ) is a different matter — see §6.

### 3.2 Attention-specific hardware change (the "2× attention" claim)

NVIDIA markets *"2× higher attention performance"* vs standard Blackwell
[src](https://www.nvidia.com/en-us/data-center/gb300-nvl72/). The mechanism is
concrete and third-party confirmed: the FlashAttention-4 paper states B300/GB300
**"doubled the exponential throughput to 32 ops/clock/SM"** vs B200's 16
[src](https://arxiv.org/html/2603.05451v1). Verda quantifies it as
**10.7 TeraExponentials/s** of SFU `EX2` throughput on B300
[src](https://verda.com/blog/gb300-nvl72-architecture).

This matters because softmax `exp2` on the SFUs is the *actual* bottleneck in
long-context attention — Modal's FA4 teardown documents FA3/FA4 fighting the
same SFU wall on B200 and FA4 resorting to a cubic-polynomial software `exp2` to
dodge it [src](https://modal.com/blog/reverse-engineer-flash-attention-4). On
GB300 that workaround is less necessary. Measured result: SGLang's FMHA kernel
for a 128K prefill runs **205 ms on GB300 vs 277 ms on GB200 (1.35×)**
[src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/) — a real but
sub-2× realisation of the claim.

### 4.3 Standard node / rack topology

```
GB300 NVL72 rack
├── 18 compute trays   × (2 Grace CPU + 4 B300 GPU)      = 36 CPU + 72 GPU
│     └── Grace↔Blackwell over NVLink-C2C (900 GB/s bidir)
├── NVSwitch trays — 72-GPU flat all-to-all, 130 TB/s aggregate
├── 72 × ConnectX-8 SuperNIC @ 800 Gb/s (scale-out)
├── BlueField-3 DPUs (per NVIDIA reference design)
└── 100 % liquid cooled; ~120 kW class rack
```

Rack power: NVIDIA publishes **no** rack-power figure. Operator estimates put
GB200 at ~120 kW and GB300 at **~135–140 kW**
[src](https://www.spheron.network/blog/gb300-nvl72-vs-gb200-nvl72-pricing-availability-2026/).
Verda computes max GPU-only TDP at 72 × 1.4 kW = **100.8 kW**
[src](https://verda.com/blog/gb300-nvl72-architecture) — but that starts from the 1,400 W
per-GPU figure this document no longer uses (§1.1); at the resolved **1,100 W** the GPU-only
draw is 72 × 1.1 kW = **79.2 kW** `est.`, which is what fits inside Lenovo's published
**135 kW TDP / 155 kW peak** rack [src](https://lenovopress.lenovo.com/lp2357-lenovo-nvidia-gb300-nvl72-rack-scale-ai) alongside 36 Grace CPUs, NVSwitch and losses.
Several vendor pages quote a flat "120 kW". ⚠️ Treat any single rack-power number as unverified.

### 4.4 Multi-node considerations

* Within a rack, TP/EP/PP all ride NVLink — METHODOLOGY's "5–15 % comm overhead
  for TP=8 over NVLink" is the right default, and TP=16 was used in production
  by SGLang across trays [src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/).
* Crossing racks drops you to 800 Gb/s/GPU IB — a **~18× bandwidth cliff** vs
  NVLink. For MoE all-to-all this is the dominant design constraint; NVIDIA's own
  framing is that the NVL72 domain is 130 TB/s aggregate all-to-all vs 900 GB/s
  per GPU on an HGX H200 island
  [src](https://developer.nvidia.com/blog/how-nvidia-gb200-nvl72-and-nvidia-dynamo-boost-inference-performance-for-moe-models/).
* TensorRT-LLM lists **GB300 multi-node** as validated only from **1.2.0rc4+**;
  it was beta in 1.1 [src](https://nvidia.github.io/TensorRT-LLM/release-notes.html).

### 5.1 Live gotcha: flash-attn-4 rejects sm_103

As of SGLang v0.5.12-cu130 + `flash-attn-4>=4.0.0b9`, serving on B300 crashed in
warmup with `AssertionError: Only SM 10.x and 11.x are supported` at
`flash_attn/cute/flash_fwd_sm100.py:162` — the arch range check
`sm_100 <= arch <= sm_110f` resolves `sm_110f` numerically *below* `sm_103` on
non-CUDA-13 CuTeDSL builds [src](https://github.com/sgl-project/sglang/issues/25564).
Root-cause fix is [Dao-AILab/flash-attention#2572](https://github.com/Dao-AILab/flash-attention/pull/2572)
(family matching instead of range comparison). Workarounds: pin SGLang
v0.5.11-cu130, or run on sm_100. **Verify your flash-attn-4 pin before standing
up a GB300 fleet.**

### 5.2 Paged KV, FP8/FP4 attention, MLA

* **Paged KV**: supported by FlashInfer (paged + ragged) [src](https://github.com/flashinfer-ai/flashinfer),
  and by all three engines.
* **FP8 KV cache**: production-standard on GB300. MLPerf v5.1 and v6.0 NVIDIA
  submissions used NVFP4 weights + **FP8 KV**
  [src](https://developer.nvidia.com/blog/nvidia-blackwell-ultra-sets-new-inference-records-in-mlperf-debut);
  SGLang's GB300 long-context run used FP8 KV
  [src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/).
* **FP8 attention compute** (not just KV storage): SGLang measured FP8 attention +
  NVFP4 MoE on GB200 at 26,156 prefill / 13,386 decode tok/s/GPU vs 18,471 /
  9,087 for BF16-attention + FP8-MoE — a **1.42× / 1.47×** win
  [src](https://www.lmsys.org/blog/2025-09-25-gb200-part-2/). Expect the same or
  better on GB300.
* **FP4 KV cache**: exists as of 2026-09-10 in FlashMLA for DeepSeek-V4/V4.1
  [src](https://github.com/deepseek-ai/FlashMLA), and DeepSeek-V4.1-Flash ships
  an FP4 (E2M1, one E4M3 scale per 16 channels) main KV cache natively
  [src](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash). Engine-side
  support on sm_103 ⚠️ TO BE VERIFIED.
* **MLA**: native in FlashInfer; DeepSeek's own kernels are the reference.
  DeepSeek-V3.2's sparse-MLA/Indexer path costs **2.7× the kernel time of dense
  MLA** on GB300, per vLLM's measurement
  [src](https://vllm.ai/blog/2026-02-13-gb300-deepseek) — a useful counterweight
  to "sparse attention is free" assumptions.

### 6.1 Practical recipe on GB300 (what every record run actually does)

> **NVFP4 weights + FP8 KV cache + BF16 for norms/router/embeddings.**

MLPerf v5.1: *"extensive use of NVFP4 acceleration across all DeepSeek-R1 and
Llama model submissions … DeepSeek-R1 weights quantized to NVFP4, KV cache
reduced to FP8"* [src](https://developer.nvidia.com/blog/nvidia-blackwell-ultra-sets-new-inference-records-in-mlperf-debut).
Lambda's MLPerf v6.0 GB300 entry: *"FP4 weights, FP8 KV cache"*
[src](https://lambda.ai/blog/lambdas-mlperf-inference-v6.0-hardware-leap-software-maturity-research-breakthrough).
SGLang's GB300 InferenceX result: NVFP4 GEMM for MoE *and* dense layers
[src](https://www.lmsys.org/blog/2026-02-20-gb300-inferencex/).

Accuracy check, measured: SGLang reports LongBench-v2 **57.2 % non-MTP / 56.9 %
with MTP** on DeepSeek-R1-NVFP4 at 128K
[src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/) — i.e. the NVFP4+FP8-KV
recipe is not visibly lossy at long context in that eval.

### 6.2 On "B300 can run NVFP4 and that's a GB300-only win" — it is not

NVFP4 is a **Blackwell-family** format: GB200/B200 (sm_100) run it too, at
720 PFLOPS dense per rack. GB300's advantage over GB200 on NVFP4 is **1.5× rate**
(1,080 vs 720 PFLOPS/rack), not availability
[src](https://www.nvidia.com/en-us/data-center/gb200-nvl72/),
[src](https://www.nvidia.com/en-gb/data-center/gb300-nvl72/). What *is*
GB300-specific: the 2× softmax/SFU attention path (§3.2) and +50 % HBM.

DeepSeek-V4.1-Flash is an FP4-native-KV model
[src](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash) whose 890 B/token
global KV (with the Blackwell FP4-KV kernel) makes it extraordinarily cheap to
serve at 1M context on this rack (§2.4). Two precision facts about it matter on
sm_103 and are routinely stated backwards:

* **The base checkpoint's routed experts are MXFP4** (E2M1 + one E8M0 per 32),
  not NVFP4; non-expert tensors are FP8 with 32×32 UE8M0 scales. Total
  510.29 GB [src](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash),
  [models/deepseek41f/architecture.md](../models/deepseek41f/architecture.md).
* **NVIDIA's NVFP4 build does exist** — `nvidia/DeepSeek-V4.1-Flash-NVFP4`,
  published 2026-09-16 — and it is **larger, not smaller: 527.27 GB vs 510.29 GB**,
  because NVFP4's per-16 E4M3 scales cost more than MXFP4's per-32 E8M0 ones.
  It is accuracy-neutral and has **no published speedup over the base
  checkpoint** ⚠️ [src](https://huggingface.co/nvidia/DeepSeek-V4.1-Flash-NVFP4),
  [models/deepseek41fnvfp4/architecture.md](../models/deepseek41fnvfp4/architecture.md).
  The reason to convert is Blackwell's native NVFP4 tensor-core path, not capacity.
  (Verification-log row 12 recorded this repo as unconfirmed; it is confirmed as
  of the 2026-09-19 sweep and pinned in METHODOLOGY §8.)

## 9. Roofline numbers for inference

### 9.1 Machine balance (per GB300 GPU: 8 TB/s HBM)

| dtype | Dense TFLOPS | Break-even arithmetic intensity (FLOP/byte) | bytes/FLOP |
|---|---|---|---|
| NVFP4 | 15,000 | **1,875** | 0.00053 |
| FP8 / FP6 | 5,000 | **625** | 0.00160 |
| BF16 / FP16 | 2,500 | **312.5** | 0.00320 |
| TF32 | 1,250 | 156.3 | 0.00640 |
| INT8 (throttled) | ~167 | 20.8 | 0.04800 |
| FP64 | ~1.39 | 0.17 | 5.7554 |

`est.` — peak ÷ 8e12 B/s. Interpretation: at NVFP4 a GEMM must reuse every byte
**1,875 times** to be compute-bound. A batch-1 decode step reuses each weight
byte once. **Decode on GB300 is bandwidth-bound until batch ≳ 1,875 at FP4** —
which is exactly why the rack's 72-way NVLink domain (enabling EP-wide batching
across 20 TB of pooled weights and KV) is the architecture, not an accessory.

### 9.2 Decode upper bound

`tokens_per_s = batch / decode_step_time`, `decode_step_time ≥ bytes_read / (8 TB/s × MBU)`

| Bytes read per decode step (per GPU) | MBU 0.50 | MBU 0.65 | MBU 0.80 |
|---|---|---|---|
| 20 GB | 200 steps/s (TPOT 5.0 ms) | 260 (3.85 ms) | 320 (3.13 ms) |
| 120 GB | 33.3 (30.0 ms) | 43.3 (23.1 ms) | 53.3 (18.8 ms) |
| 251 GB (a full usable HBM's worth) | 15.9 (62.8 ms) | 20.7 (48.3 ms) | 25.5 (39.2 ms) |
| 5.6 GB (a 1/72 EP slice of a ~400 GB NVFP4 MoE) | 714 (1.40 ms) | 929 (1.08 ms) | 1,143 (0.88 ms) |

`est.` MBU bands per METHODOLOGY §4 (0.5–0.7 on Blackwell-generation software).
**The 251 GB row is the interactive-SLO boundary:** a model that fills one GB300's
HBM cannot beat ~39–63 ms TPOT single-GPU. Sharding it 72 ways is what buys the
sub-5 ms step times in the last row.

### 10.6 Wide-EP on NVL72 — what EP=72 actually buys

* DeepSeek-R1 has 256 routed experts. At ~4 experts/GPU you need **64 GPUs** to
  hold the routed experts once during decode — which fits inside one NVL72 domain
  and *does not* fit inside an 8-GPU node
  [src](https://developer.nvidia.com/blog/how-nvidia-gb200-nvl72-and-nvidia-dynamo-boost-inference-performance-for-moe-models/).
  This is the single clearest architectural argument for NVL72 over HGX.
* MoE dispatch/combine all-to-all is the cost. DeepEP measures **726 GB/s
  dispatch / 740 GB/s combine over NVLink at EP8 on SM100** (64 SMs, max-perf) vs
  **90 GB/s over RDMA** for EP8×2 [src](https://github.com/deepseek-ai/DeepEP) —
  an **~8× bandwidth cliff** the moment experts spill off the NVLink domain.
  DeepEP V2 supports scale-up domains to **EP2048** and cut SM usage 4×.
  ⚠️ DeepEP publishes **no SM103 row** — GB300 numbers are unverified.
* SGLang on GB200 ran **EP48 for decode** with 2–4 EP ranks per prefill instance,
  reaching 26,156 prefill / 13,386 decode tok/s/GPU on DeepSeek at ISL 2K
  [src](https://www.lmsys.org/blog/2025-09-25-gb200-part-2/). On GB300 it used
  Wide-EP up to 32 GPUs for 128K decode
  [src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/) — i.e. **EP=72 is
  the ceiling, not the operating point**; real deployments pick EP based on
  expert count and load balance, then use the spare GPUs for a second replica or
  for prefill.
* **EPLB** (expert-parallel load balancing) and online rebalancing: referenced by
  NVIDIA's v6.0 Wide-EP stack, but **no published EPLB measurement on GB300** was
  found. ⚠️ TO BE VERIFIED.

### 10.7 Disaggregated prefill/decode on NVL72

* MLPerf v5.1: dedicating disjoint GPU sets to prefill and decode and shipping KV
  over NVLink/NVSwitch gave **nearly 1.5×** throughput per GPU vs aggregated
  serving — note the blog attributes that figure to **GB200 NVL72**, not GB300,
  and does not tie it to the Llama-3.1-405B interactive run specifically
  [src](https://developer.nvidia.com/blog/nvidia-blackwell-ultra-sets-new-inference-records-in-mlperf-debut).
  Carrying it to GB300 is ⚠️ TO BE VERIFIED.
* The NVL72 domain is what makes KV transfer between prefill and decode pools
  cheap — 1.8 TB/s/GPU rather than 800 Gb/s. Off-rack disaggregation is a
  different (much worse) economic problem.
* vLLM tested GB300 disaggregation with `NixlConnector` for KV transfer
  [src](https://vllm.ai/blog/2026-02-13-gb300-deepseek); SGLang uses Dynamo
  [src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/).
* Prefix caching / KV offload: Dynamo's **KVBM** multi-tier KV manager supports
  vLLM and TRT-LLM (🚧 on SGLang); SGLang uses a **HiCache radix tree** with
  KV-aware routing on GB300 [src](https://github.com/ai-dynamo/dynamo),
  [src](https://www.lmsys.org/blog/2026-02-20-gb300-inferencex/). With 17 TB of
  Grace LPDDR5X per rack at 14 TB/s, **host-memory KV offload is unusually
  attractive here** — 900 GB/s per-GPU C2C is ~9× a PCIe Gen5 x16 link.

## 11. Known gotchas

1. **INT8 and INT4-activation are dead on sm_103.** ~1/30 the FP8 rate, no
   `tcgen05` integer path, no CUTLASS kernels, hard failure in vLLM *after weight
   load*. If your pipeline assumes W8A8, it does not run here
   [src](https://arxiv.org/html/2608.11693v1). Migrate to FP8 or NVFP4.
2. **FP64 is ~1.39 TFLOPS/GPU** (rack 100 TFLOPS vs GB200's 2,880). GB300 is
   actively worse than GB200 for any FP64 work
   [src](https://www.nvidia.com/en-gb/data-center/gb300-nvl72/).
3. **flash-attn-4 arch check rejects sm_103** in some builds — crashes at warmup
   with `Only SM 10.x and 11.x are supported`
   [src](https://github.com/sgl-project/sglang/issues/25564). Pin around it until
   [#2572](https://github.com/Dao-AILab/flash-attention/pull/2572) is in your
   release.
4. **FlashMLA and DeepEP publish SM90/SM100 support and perf, not SM103.**
   DeepSeek's own kernels are the reference implementation for MLA and DSA; their
   GB300 status is unverified [src](https://github.com/deepseek-ai/FlashMLA),
   [src](https://github.com/deepseek-ai/DeepEP).
5. **TRT-LLM GB300 multi-node was beta until 1.2.0rc4.** Anything below that is
   single-rack only in practice [src](https://nvidia.github.io/TensorRT-LLM/release-notes.html).
6. **GB300 is 288 GB nominal, ~279 GB usable — size KV from 279, not 288.**
   That is the one convention used throughout this doc and pinned in
   METHODOLOGY §8. NVIDIA publishes only the rack figure, 20 TB ÷ 72 = 277.8 GB
   [src](https://www.nvidia.com/en-gb/data-center/gb300-nvl72/); SemiAnalysis

   Lambda and CoreWeave list 279 GB. Sizing from 288 over-commits by ~3.2 % per
   GPU, ~650 GB per rack. **HGX/DGX B300 is a different number entirely:
   268 GB per GPU, 2,144 GB per 8-GPU node** (AWS P6-B300.48xlarge
   [src](https://aws.amazon.com/ec2/instance-types/p6/); NVIDIA's DGX B300 page

   pins 268 / 2,144). The widely-quoted **270 GB and 288 GB for HGX B300 are
   both wrong**, and HGX B300 figures are **not interchangeable with GB300**
   [src](https://verda.com/blog/gb300-nvl72-architecture).
7. **Engines reserve far more than METHODOLOGY's 10 %.** SGLang's published GB300
   config holds back 25 % [src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/).
   Long prefill chunks and CUDA graphs are the reason; 32K dynamic chunking was
   the tuned choice.
8. **AWS's P6e-GB300 spec table lists 13,320 GB of GPU memory** — the GB200
   number [src](https://aws.amazon.com/ec2/instance-types/p6/) — while AWS's own
   launch note says "close to 20TB". The table appears stale. Don't quota-plan
   from it.
9. **Cloud quota reality: GB300 is quote-only almost everywhere.** Oracle OCI is
   the single exception, publishing **$18.00/GPU-h** on-demand for
   `BM.GPU.GB300.4` (§8.1, [cloud-pricing.md §3.4](../cross-cutting/cloud-pricing.md)).
   No other first-party provider published an on-demand $/GPU-h as of
   2026-09-19. Together sells
   it as reserved capacity only, minimum term 7 days
   [src](https://www.together.ai/gpu/nvidia-gb300-nvl72); AWS routes P6e-GB300
   through sales [src](https://aws.amazon.com/about-aws/whats-new/2025/12/amazon-ec2-p6e-gb300-ultraservers-nvidia-gb300-nvl72-generally-available).
10. **Power/thermal: no NVIDIA rack-power spec exists.** Estimates span 100.8 kW
    (GPU-only TDP) to 140 kW (operator all-in). Liquid cooling is mandatory, not
    optional [src](https://www.spheron.network/blog/gb300-nvl72-vs-gb200-nvl72-pricing-availability-2026/),
    [src](https://verda.com/blog/gb300-nvl72-architecture). Colo contracts written

    path costs 2.7× the dense-MLA kernel time on GB300
    [src](https://vllm.ai/blog/2026-02-13-gb300-deepseek); it wins on asymptotics

12. **Benchmark half-life is about two quarters.** 2.77× on DeepSeek-R1 server
    from v5.1 to v6.0 on identical hardware
    [src](https://developer.nvidia.com/blog/nvidia-platform-delivers-lowest-token-cost-enabled-by-extreme-co-design).
13. **MXFP4 vs NVFP4 rate parity on sm_103 is undocumented.** Both use the

## 12. Comparison hooks

**(a) Decode bandwidth — vs H100 and vs B200.**
Per-GPU HBM bandwidth is **8 TB/s on GB300, 8 TB/s on GB200/B200 in NVL form,
and 3.35 TB/s on H100 SXM** — so GB300 is **~2.4× H100** and **1.0× B200** on the
metric that sets low-batch TPOT. GB300 buys *nothing* over GB200 in raw decode
bandwidth [src](https://www.nvidia.com/en-us/data-center/gb200-nvl72/),
[src](https://inferencex.semianalysis.com/chips/gb300-nvl72). What it buys is
**capacity**: 279 vs 186 GB per GPU (+50 %), which raises how many concurrent
sequences share each weight read — SGLang measured **40 vs 24 concurrent 128K
requests per GPU (1.67×)** [src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/).
Since decode throughput at fixed TPOT ≈ (bandwidth × MBU × batch) / bytes-read,
GB300's win over GB200 in decode is entirely a batching win, and it evaporates
for a small model that already fit comfortably in 186 GB. Against an 8-GPU H100
node the gap is not 2.4× but closer to the 15–25× seen in InferenceX, because
NVL72 also removes the MoE all-to-all penalty (726 GB/s NVLink vs 90 GB/s RDMA
in DeepEP's own table) [src](https://github.com/deepseek-ai/DeepEP).

**(b) FP8 / FP4 prefill — vs H100 and vs B200.**
Dense FP8 per GPU: **GB300 5,000 TFLOPS vs H100 SXM 1,979 TFLOPS (2.5×) vs
B200-in-GB200 5,000 TFLOPS (1.0×) vs HGX B200 4,500 TFLOPS (1.11×,
METHODOLOGY §8)**. H100 has **no FP4 tensor core at all**, so
the FP4 comparison is categorical, not incremental: GB300's 15,000 dense NVFP4
TFLOPS has no H100 equivalent, and on Hopper an FP4 checkpoint must be upcast.
Against the B200 *in a GB200 NVL72* (720 PFLOPS dense ÷ 72), dense NVFP4 is
**15,000 vs 10,000 TFLOPS = 1.5×**; against an **air-cooled HGX B200 (9,000
dense FP4, METHODOLOGY §8) it is 1.67×**. All figures dense, never sparse
[src](https://www.nvidia.com/en-gb/data-center/gb300-nvl72/),
[src](https://www.nvidia.com/en-us/data-center/gb200-nvl72/) — and the second,
less-advertised prefill lever is the **doubled SFU exponential throughput
(32 vs 16 ops/clock/SM)** [src](https://arxiv.org/html/2603.05451v1), which shows
up as a **1.35× FMHA kernel speedup on a 128K prefill**
[src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/). Combined, real
long-context prefill lands at **1.38–1.58× GB200** and **8× H200** measured
[src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/),
[src](https://vllm.ai/blog/2026-02-13-gb300-deepseek). Note the inverse: FP8, BF16
and TF32 rates are *identical* to GB200 — if you are not on FP4, the prefill
upgrade is only the attention kernel.

**(c) Memory per dollar — vs H100 and vs B200.**
On purchase price, GB300 is **$51k–$90k per GPU for 279 GB = 3.1–5.5 GB/$k**;
GB200 NVL72 is $43k–$54k for 186 GB = **3.4–4.3 GB/$k**
[src](https://www.spheron.network/blog/gb300-nvl72-vs-gb200-nvl72-pricing-availability-2026/) —
i.e. roughly a wash at the low capex estimate and worse at the high one, with the
real GB300 argument being tokens per dollar rather than gigabytes per dollar. On
rental, the only comparison with two published numbers is the air-cooled tier:
**Nebius HGX B300 $7.85/GPU-h for 268 GB = 34.1 GB per $/h** (268 GB is the
METHODOLOGY §8 as-deployed pin, from AWS's 2,144 GB node
[src](https://aws.amazon.com/ec2/instance-types/p6/); the earlier 270 GB / 34.4
and 262.5 GB / 33.4 variants both came from unpinned capacity figures), vs **HGX H200
$4.50/GPU-h for 141 GB = 31.3 GB per $/h** and **HGX B200 $7.15 for 180 GB =
25.2** [src](https://nebius.com/prices) — so B300 is the best GB-per-dollar-hour
of the three, narrowly. Against an H100 (80 GB at $6.16/GPU-h on CoreWeave =
13.0 GB per $/h [src](https://www.coreweave.com/pricing)), Blackwell Ultra is
**~2.6× better memory per dollar-hour**, before any throughput advantage. The
decisive number, though, is cost per token: **$0.065–$0.080 per 1M tokens** at
SemiAnalysis's $2.31/chip-h against MLPerf v6.0 DeepSeek-R1 throughput (§8.4),
versus **$1.56 per 1M on H200** at comparable interactivity
[src](https://developer.nvidia.com/blog/nvidia-blackwell-leads-on-new-semianalysis-inferencemax-benchmarks/).

**(d) GB300 (NVL72) vs HGX B300 — same die, two different parts.** Never merge
these two rows; the sizing errors they cause are the most common ones in this
family (METHODOLOGY §8):

| | **GB300 NVL72** (per B300) | **HGX / DGX B300** (per B300) |
|---|---|---|
| HBM as deployed | **288 GB nominal, ≈ 279 GB usable** | **268 GB** (2,144 GB per 8-GPU node; DGX B300 page implies 262.5) |
| HBM bandwidth | 8.0 TB/s | 8.0 TB/s |
| Dense BF16 | **2,500 TFLOPS** | **2,250 TFLOPS** |
| Dense FP8 | **5,000 TFLOPS** | **4,500 TFLOPS** |
| Dense NVFP4 | **15,000 TFLOPS** | **13,500 TFLOPS** |
| TDP | 1.1 kW (§1.1, resolved) | 1.1 kW |
| Scale-up domain | 72 GPUs over NVLink-5 (130 TB/s) | 8 GPUs per baseboard |
| Published on-demand price | OCI $18.00/GPU-h | OCI $15.00/GPU-h; AWS p6-b300 $17.80; Nebius $7.85 |

So GB300's per-GPU advantage over air-cooled HGX B300 is **+11 % on every dense
math rate, +7 % usable capacity, and 9× the scale-up domain** — the domain being
the part that actually decides whether a 256-expert MoE holds its routed experts
once (§10.6). A throughput number measured on one is not transferable to the
other: vLLM measured **GB300 = +14 % prefill / +12 % short-output vs air-cooled
B300** on the same model [src](https://vllm.ai/blog/2026-02-13-gb300-deepseek).
