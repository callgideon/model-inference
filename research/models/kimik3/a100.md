> [`research/METHODOLOGY.md`](../../METHODOLOGY.md). Pinned inputs from
> [METHODOLOGY §8](../../METHODOLOGY.md#8-pinned-inputs-converged-values-from-the-fact-checked-docs).

## 0. Verdict

1. **Not runnable today.** No engine ships a Kimi-K3 A100 path: `vllm serve`'s
   recipe API returns **404** for `hw/a100.json`, SGLang's `supportedHardware` is
   `[b300, gb300, b200, gb200, h200, h100, mi350x, mi355x, a3]`, and TensorRT-LLM
   scopes K3 to **SM100 only** ([architecture.md §8.1–8.2](./architecture.md),
   [cross-cutting/inference-engines.md §3.2, §6.3](../../cross-cutting/inference-engines.md)).
   Engine versions that *do* serve it elsewhere: vLLM ≥ 0.27.0, SGLang ≥ 0.5.17.
2. **The hardware fit is real but marginal:** min **24 GPUs** (3 HGX A100 nodes,
   1.96 GB/GPU of KV budget — 9 concurrent requests at 8 K, useless);
   **recommended 32 GPUs** (4 nodes, **TP32**, attn-TP 32), which is exactly the
   topology vLLM and SGLang publish for **H100** — A100 would be that shape on a
   slower card and a slower fabric.
3. **Weight format actually executed: MXFP4 stays packed and is dequantised
   in-kernel by Marlin (W4A16), BF16 everywhere else** — a memory win with **zero
   compute win**, because sm_80 has no FP8 and no FP4 tensor core. ⚠️ the MXFP4
   *MoE* Marlin path on sm_80 is claimed by the code and contradicted by a bug
   report (§2, §6).
4. **Interactive (S1, TPOT ≤ 50 ms) cost per 1M output tokens: $35.21 – $75.98**
   `est.` at concurrency 20 on 32 GPUs. **Max-throughput (S4): $14.72 – $31.75**
   `est.` at concurrency 143. Blended (75 % in / 50 % cached / 25 % out)
   **$10.51 – $22.67** against Moonshot's own **$4.99** blended API price.
5. **Confidence: not-runnable.** Fit is arithmetic and solid; throughput and cost
   are a roofline for a configuration nobody has run. Nearest runnable
   alternative: **H100 4×8 = TP32**, which has published launch commands (§6).

## 1. Fit

Fit is hardware, so this section is filled even though §0 says the pair does not
serve. METHODOLOGY §3:

```
usable_hbm      = hbm_capacity × 0.90
per_gpu_weights = 1,560,936,091,448 B / n_gpus          (TP; experts stay MXFP4-packed)
activation_ws   = 5 GB  est.   (93 layers, Marlin dequant workspace, CUDA-graph pools)
kv_budget       = usable_hbm − per_gpu_weights − activation_ws
max_concurrency(ctx) = floor( kv_budget / (S × state_slot(attn_tp) + ctx × kv_bytes_per_token) )
```

### 1.0 Two pinned capacities disagree — stated, not silently resolved

| Source | A100 80GB SXM4 capacity | usable at ×0.90 |
|---|---:|---:|
| [METHODOLOGY §8](../../METHODOLOGY.md) GPU table | **80 GB** (decimal) | **72.00 GB** |
| [gpus/a100.md §2](../../gpus/a100.md) | `nvidia-smi` 81,920 MiB = **80 GiB ≈ 85.9 GB** — itself marked ⚠️ TO BE VERIFIED ("no primary NVIDIA doc found stating the MiB figure") | **77.31 GB** |

**This document plans with METHODOLOGY §8's 80 GB**, the conservative reading.
The a100.md reading adds 5.31 GB/GPU, i.e. +170 GB across 32 GPUs — enough to
move `max_concurrency(8K, FP8 KV)` at 32 GPUs from 99 to roughly 128, and nothing
else in the document. ⚠️ **TO BE VERIFIED (1)** — which figure the fleet actually
reports.

### 1.1 Per-GPU budget by GPU count

Only counts the HGX A100 topology allows: 1/2/4/8 inside one NVSwitch baseboard
(4- and 8-GPU boards; a 16-GPU board exists), then multiples of 8 over
InfiniBand. There is **no NVL72-style rack domain on A100 at all**
([gpus/a100.md §4](../../gpus/a100.md)).

recurrent state per slot at that attention-TP width,
`69 × (96/attn_tp × 128 × 128 × 4 + 9 × 96/attn_tp × 128 × 2)`
([architecture.md §5.3](./architecture.md), SGLang's own calculator).

**Minimum that fits: 24 GPUs = 3 HGX A100 nodes.** It is a fit in name only —
1.96 GB/GPU of KV budget admits 9 requests at 8 K FP8 KV and **1** at 128 K.

### 1.2 Max concurrency by context and KV dtype

FP8 KV is **storage-only** on A100 — K/V are stored FP8 and dequantised to FP16
before the MMA, because per-head FP8 attention needs FA3
([gpus/a100.md §5, §6](../../gpus/a100.md)). The capacity win is real; there is no
compute win.

```
 GPUs      4K BF16       4K FP8      8K BF16       8K FP8     32K BF16      32K FP8    128K BF16     128K FP8      1M BF16       1M FP8
    8          n/a          n/a          n/a          n/a          n/a          n/a          n/a          n/a          n/a          n/a
   16          n/a          n/a          n/a          n/a          n/a          n/a          n/a          n/a          n/a          n/a
   24            9           13            6            9            1            3            0            1            0            0
   32           99          143           61           99           18           34            4            9            0            1
   40          165          248           98          165           29           54            7           14            0            1
   48          215          333          126          215           36           68            9           18            1            2
   64          287          464          162          287           45           87           11           23            1            2
   96          371          634          203          371           54          106           13           27            1            3
```

`n/a` = the weights do not fit; per METHODOLOGY §3 no concurrency row may be
printed for a configuration that cannot hold the model.

Per-request bytes at the recommended 32 GPUs (attn-TP 32, so `state_slot` = 13.39 MiB,
`S = 5` → 66.96 MiB):

| ctx | KDA state (S=5) | MLA KV BF16 | total BF16 | MLA KV FP8 | total FP8 |
|---:|---:|---:|---:|---:|---:|
| 4,096 | 66.96 MiB | 108.00 MiB | 174.96 MiB | 54.00 MiB | 120.96 MiB |
| 8,192 | 66.96 MiB | 216.00 MiB | 282.96 MiB | 108.00 MiB | 174.96 MiB |
| 32,768 | 66.96 MiB | 864.00 MiB | 930.96 MiB | 432.00 MiB | 498.96 MiB |
| 131,072 | 66.96 MiB | 3,456.00 MiB | 3,522.96 MiB | 1,728.00 MiB | 1,794.96 MiB |
| 1,048,576 | 66.96 MiB | 27,648.00 MiB | 27,714.96 MiB | 13,824.00 MiB | 13,890.96 MiB |

`kv_bytes_per_token` = `24 layers × (512 + 64) × B` = **27,648 B BF16 / 13,824 B
FP8** ([architecture.md §5.2](./architecture.md); METHODOLOGY §8 pins the FP8
figure at 13.5 KiB/token). NVFP4/INT4 KV does not exist for this model on any
GPU, and would not run on sm_80 anyway.

Note the inversion relative to Blackwell: because `attn_tp = 32` shrinks the KDA
state to 13.39 MiB/slot, the **state stops being the binding constraint** here —
at 8 K, KV is 62 % of the per-request bill at FP8, where on an 8×B300 node with
attn-TP 8 the state is the ceiling ([architecture.md §5.6](./architecture.md),
SGLang's measured 101-request cap). Wide TP is the one thing A100 does to this
model that helps.

### 1.3 What cannot be sharded — stated explicitly

| Tensor group | Shardable? | Consequence on A100 |
|---|---|---|
| **MLA KV cache** (24 layers, 512+64 latent) | **No.** MLA KV is TP-**replicated**: every rank holds the whole cache. DCP (`--dcp-size`) is the only lever that shards it, and vLLM's DCP path requires `TOKENSPEED_MLA`, which is **10.x-only and FP8-KV-required** ([cross-cutting/flash-attention.md §14.4](../../cross-cutting/flash-attention.md)). | **No DCP on sm_80.** Every concurrency figure in §1.2 is the replicated-KV figure. The +72 % ceiling DCP8 buys on B300 ([architecture.md §5.7](./architecture.md)) is unavailable. |
| **KDA recurrent state** (69 layers) | **Only by attention-TP.** "DP, EP and DCP do not shard it; only attention-TP width, SSM dtype and cache strategy change the per-GPU bill" (SGLang, quoted in [architecture.md §5.3](./architecture.md)). | TP32 divides it by 32 — the one place A100's forced wide TP pays. |
| **F32 KDA conv / `A_log` / `dt_bias` / `o_norm`** (506 tensors, 44.5 MB) | Replicated; must not be downcast ([architecture.md §3.5](./architecture.md)). | ~0.045 GB/GPU. |
| **Router `gate.weight` + F32 `e_score_correction_bias`** (92 × 896 × 7168 + 92 × 896) | Replicated per rank in every published shape. | ~1.18 GB/GPU at BF16 if fully replicated; vLLM shards `gate` with the MoE in TP, so treat as ≤ 1.2 GB ⚠️ **TO BE VERIFIED (2)**. |
| **`routed_expert_up_proj`** (7168 × 3584/layer) | vLLM's `LatentMoERunner` docstring: *"the replicated up-proj produces the full hidden dim on every rank"* ([vllm/models/kimi_k3/nvidia/latent_moe_runner.py](https://github.com/vllm-project/vllm/blob/main/vllm/models/kimi_k3/nvidia/latent_moe_runner.py)). | 92 × 7168 × 3584 × 2 B = **4.73 GB replicated on every GPU**, at any TP. This is the largest non-shardable weight and it is counted in the `~0.2 GB` column only for the *other* replicated tensors — see the correction below. |
| **`embed_tokens` / `lm_head`** | Shardable (vocab-parallel) in both engines. | 2.35 GB total. |
| AttnRes rank-1 projections, norms | Replicated, 4.02 M params. | negligible. |

**Correction to the `repl GB` column above.** The fit table's `~0.2` counts only
norms, router bias and AttnRes. The replicated **latent up-projection is 4.73 GB
per GPU**, which is already inside the `CKPT/n` term at low TP but is *not*
divided at high TP. At 32 GPUs the honest per-GPU weight figure is therefore
`(1,560.9 − 4.73×2)/32 + 4.73 ≈ 53.2 GB`, not 48.8 GB, which reduces
`kv_budget/GPU` from 18.22 to **13.8 GB** and `max_concurrency(8K, FP8)` from 99
to roughly **75**. ⚠️ **TO BE VERIFIED (3)** — whether vLLM's A100 path would
replicate it at all, since the fused tail that motivates the replication is
`is_device_capability_family(100)`-gated in the same file (so sm_80 takes the
"native path", which may column-parallel it instead). The §1.2 table keeps the
uncorrected numbers so it stays comparable with the sibling GPU docs; treat them
as an **upper bound** and the −24 % figure as the downside.

### 1.4 Multi-node fabric

**Required from 24 GPUs up.** A100 has no NVLink domain larger than one
8-GPU (or 16-GPU) baseboard; every cross-node hop is InfiniBand at **200 Gb/s =
25 GB/s per GPU on a DGX A100**, or 4×100 Gb/s EFA on AWS `p4de` — i.e. **24×
less than intra-node NVLink** ([gpus/a100.md §4](../../gpus/a100.md)). That file's
own guidance is *"Multi-node TP is therefore almost always wrong on A100; use PP
or replicate."* Kimi-K3 offers neither escape: it cannot be replicated (it does
not fit in one node) and PP does not reduce the weight footprint per node below
the 195 GB/GPU that an 8-GPU node cannot hold.

DP-attention — is architecturally unavailable.

   9–10× better. Moonshot report ">90 % cache hit rate in coding workloads"

   traffic ([serving-optimizations.md §1.5](../../cross-cutting/serving-optimizations.md)),

### 3.6 Estimated vs. measured — where the gap comes from

```
batch1 bytes 138.4 GB; est. A100 TP32 TPOT 13.61 ms vs MEASURED B300 1x8 8.51 ms -> 1.60x with 4x the GPUs
est. per-GPU output tok/s at S4: A100 30.01 vs MEASURED B300 Balanced conc64 155.1 -> 5.2x
```

Read those two lines together, because they say different things:

- **At batch 1 the estimate flatters A100.** 32 A100s at MBU 0.20 deliver 13.1 TB/s
  aggregate against an 8×B300 node's *measured-effective* 16 TB/s (8 TB/s × 25 %
  MBU) — the same order. This is the roofline being generous: it assumes 32-way
  TP streams weights at the same efficiency as 8-way, which the collective term
  partly corrects but the kernel-quality gap does not. Treat the batch-1 row as
  an **optimistic bound**.
- **Per GPU at max throughput, A100 is 5.2× worse**, and that is the number that
  decides procurement: you need **4× the GPUs to get 0.77× the aggregate
  throughput** (960 vs 1,241 tok/s), before DSPARK, which B300 has and A100
  probably cannot run (§2).
- **Where the remaining gap would show up in a real run and does not show up
  here:** (i) Triton MLA and Triton KDA versus hand-written FlashMLA/FlashInfer —
  unquantified anywhere, ⚠️; (ii) Marlin's dequant overhead on MXFP4 g32
  specifically, which [architecture.md §12 Q12](./architecture.md) lists as an open
  question even for Hopper; (iii) NCCL behaviour at TP32 over 4 nodes with 93
  sequential layers; (iv) power. [gpus/a100.md §11](../../gpus/a100.md) records a
  **1.56× MLPerf spread between 400 W and 500 W CTS A100s** on identical software
  — larger than most of the optimisations in §2.

**Direct corroboration that the Hopper envelope collapses, as a sanity anchor on
the direction of travel:** vLLM's published H100 4×8 = TP32 override for this
exact model is `--gpu-memory-utilization 0.97 --max-num-seqs 5 --max-model-len
32768 --moe-backend marlin` ([architecture.md §8.3, §8.6](./architecture.md)).
**Five concurrent sequences at 32 K on 32 H100s.** A100 at the same GPU count has
less bandwidth (2.039 vs 3.35 TB/s), no FlashMLA, no fused KDA and a slower
fabric. §1.2's 34 concurrent at 32 K is a *capacity* figure; vLLM's `5` is what
the engine authors were willing to promise on strictly better hardware. ⚠️ The
two are not directly comparable (vLLM's 5 is a conservative default at
`gpu-memory-utilization 0.97` with Marlin workspace pressure, not a measured
ceiling), but the direction is unambiguous.

### 4.3 Effect of prefix caching and speculative decoding

**Prefix caching** is already inside the blended figure (50 % cached at 10 %),
and it is the largest lever available on this GPU because A100's weakness is
prefill, not decode. Moving from 0 % to 90 % cache hit raises the effective
node-wide input rate ~9.7× (3,421 → 33,353 tok/s, recomputing the input term
at 19 % of uncached attention FLOPs + 10 % of GEMM, comm term scaled to the
10 % of tokens actually computed) and would pull the blended figures to
**$9.12 / $19.68 / $7.80** per 1M `est.` — about a 13 % reduction from the
50 %-cached blended figures in §4.2, because the 25 % output term (unaffected
by prefix caching) still dominates the blend at the S1 operating point.
*(Corrected 2026-09-19: this said "cuts the input term by ~4.3×" and
"$6.1 / $13.1 / $5.2" — recomputed in `python3` from the same TTFT90 model
validated against §3.2; the old figures did not reconcile with any formula in
this document, including the one stated alongside them.)*
`--prefix-match-unit 128` is the flag
that makes this real on a hybrid model; without it vLLM's hit boundary is "very

**Speculative decoding** would be worth 1.6–3.0× on TPOT if it ran — that is the

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

**Single node is impossible.** 1,560.9 GB against 8 × 72 GB usable = 576 GB. The
smallest working shape is **3 nodes (24 GPUs)** and the smallest *useful* one is
**4 nodes (32 GPUs, TP32)**. §3.4 says 5–6 nodes is where per-GPU throughput
stops improving.

### 5.2 When PD disaggregation or wide-EP pays for this pair

- **Wide-EP: never on A100.** There is no NVLink domain past 8 GPUs, no
  NVLink-C2C, no NVL72; DeepEP/EPLB/MegaMoE are rack-scale designs with no A100
  analogue, and vLLM states "DeepGEMM MegaMoE is not compatible with cross-node
  RDMA" ([gpus/a100.md §4](../../gpus/a100.md), [architecture.md §8.9](./architecture.md)).
- **PD disaggregation: it is the only structural fix for §3.2's TTFT, and it is
  unvalidated here.** §3.2 shows TTFT 38 s at S1/conc 32 and 355 s at S3/conc 8,
  against TPOT in the tens of ms — a textbook prefill-saturated system, the same
  diagnosis SGLang draws from its own B300 data ("At 8 K ISL the node is
  prefill-saturated well before decode is. This is the argument for PD
  disaggregation", [architecture.md §10.1](./architecture.md)). On A100 you would
  split 4 prefill nodes from N decode nodes, which **doubles** the weight
  footprint (both pools hold all 1,560.9 GB) — 8 nodes minimum, 64 GPUs. At
  §3.4's $10.29/1M that is still 14× the measured B300 PD figure. ⚠️ **TO BE
  VERIFIED (10)**: no A100 PD profile exists for any engine.

| `--attention-backend FLASHMLA` → **`TRITON_MLA`** | FlashMLA builds for **SM90/SM100 only** ([FlashMLA README](https://github.com/deepseek-ai/FlashMLA)). `TRITON_MLA` is the only `Any`-capability MLA backend. **This is a substitution nobody has tested for K3.** |
| `--moe-backend marlin` | **kept** — it is already the Hopper choice and the sm_80 landing spot per the oracle, but see §2's ⚠️. |
| add `--kv-cache-dtype fp8` | +45–71 % concurrency (§1.2). Omitted from the Hopper command; the Blackwell one has it. |
| add `--enable-prefix-caching --prefix-match-unit 128` | Off by default for K3; the single biggest cost lever (§4.3). |
| `--gpu-memory-utilization 0.97` | Hopper's value. On A100 with Marlin dequant workspace this is aggressive; §1 plans at 0.90 per METHODOLOGY §3. |
| host driver | **r580+** required by vLLM for this model; CUDA 13.x needs ≥ R580 for minor-version compatibility, and sm_80 was *not* removed in CUDA 13.0 ([gpus/a100.md §1, §11](../../gpus/a100.md)). An old A100 fleet on R535 cannot run the container. |

SGLang's equivalent H100 cell, also verbatim

### 5.4 Warm-up and loading

1,560.9 GB from NVMe, **390 GB per node** across 4 nodes (`est.`, assuming each
node loads only its TP shard — true with `--load-format fastsafetensors`, false
with naive loaders that read the whole checkpoint per rank):

| NVMe read rate | per node | whole checkpoint |
|---|---:|---:|
| 5 GB/s | **1.3 min** | 5.2 min |
| 10 GB/s | **0.7 min** | 2.6 min |
| 20 GB/s | **0.3 min** | 1.3 min |

Real-world warm-up is dominated by everything else: vLLM raises
`VLLM_ENGINE_READY_TIMEOUT_S=3600` for this model and pins
`--load-format fastsafetensors` ([architecture.md §1.2](./architecture.md)), and
first download is 1.56 TB (≈ 21 min of pure wire time at 10 Gbit/s). Add Triton
JIT compilation for the KDA and MLA kernels on first run — on sm_80 these are
cold caches with no shipped cubins — plus CUDA-graph capture across 93 layers.
**Budget an hour for a cold node, not five minutes.** ⚠️ **TO BE VERIFIED (15)**.

## 6. Risks and open questions

### 6.1 The blocking question

**Does the MXFP4 MoE Marlin path actually execute on sm_80?** Two primary sources
disagree:

- **For:** vLLM's `MarlinExpertsBase._supports_current_device()` returns
  `p.is_cuda() and p.has_device_capability((7, 5))` and lists `kMxfp4Static` in
  `SUPPORTED_W`; the CUDA MXFP4 MoE priority list ends in `MARLIN, BATCHED_MARLIN`
  ([marlin_moe.py](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/fused_moe/experts/marlin_moe.py),
  [oracle/mxfp4.py](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/fused_moe/oracle/mxfp4.py)).
  `Mxfp4Config.get_min_capability()` returns **80**. And gpt-oss-120b, an MXFP4
  MoE checkpoint, demonstrably serves on 2× A100 through vLLM (§3.5).
- **Against:** [vLLM #35922](https://github.com/vllm-project/vllm/issues/35922) —
  compressed-tensors MXFP4A16/NVFP4A16 on A100 fail with
  `no kernel image is available for execution on the device`, and INT4 W4A16 MoE
  fails with `illegal memory access` in `fused_marlin_moe` during `profile_run()`.
  Filed 2026-03-03, **closed "not planned"/stale, no fix**. Kimi-K3 is a
  compressed-tensors checkpoint, so it is in the failing family, not the gpt-oss
  family (which has its own `gpt_oss_mxfp4` method and its own backend priority
  list, `_get_priority_backends_for_gpt_oss`, that the generic path does not use).

**That distinction is the crux and it is unresolved.** Test the exact checkpoint
before committing capacity. ⚠️ **(6)**

### 6.2 Disagreement with a sibling document, stated per the inputs rule

[gpus/a100.md §9 "The repo's models on A100"](../../gpus/a100.md) records Kimi-K3
as: *"**No** — MXFP4; a BF16 conversion is 2,779.9 B × 2 B = **5.56 TB** ≈ **72
GPUs** (9 nodes) of weights alone `est.`"*.

- The **"No"** verdict: **agreed**, for software reasons (§0).
- The **5.56 TB / 72-GPU sizing: this document disagrees.** Marlin W4A16 keeps
  MXFP4 packed in HBM and dequantises *in-register*; it does not write a BF16
  checkpoint. METHODOLOGY §8 pins the checkpoint at **1,560.9 GB**, which is what
  §1 uses. The BF16-on-disk path is a real alternative (it is what DeepSeek
  FP8→BF16 conversion forces, [gpus/a100.md §11 gotcha 5](../../gpus/a100.md)) but
  it is not what the MXFP4 path does, and no such Kimi-K3 checkpoint exists —
  the model was **QAT'd at MXFP4 from the SFT stage onward, so there is no BF16
  original** ([architecture.md §1.3](./architecture.md)). For completeness: 5,560 GB
  ÷ 67 GB/GPU = **83 GPUs** of weights alone, not 72 — a100.md's figure divides
  by raw 80 GB without the 0.90 usable factor or workspace.
- Both figures are cited here so a reader can reconcile the two documents.

Also noted: METHODOLOGY §8 and gpus/a100.md §2 disagree on A100 capacity
(80 GB vs 80 GiB), §1.0. Neither is silently adopted.

### 6.5 Accuracy caveats of the executed precision

- **There is no BF16 Kimi-K3 to compare against.** QAT was applied "from the SFT
  stage onward", so the MXFP4 weights *are* the model
  ([architecture.md §1.3](./architecture.md)). Running them through Marlin W4A16
  is numerically the *gentlest* path available — dequant to FP16 and a BF16/FP16
  MMA is strictly higher precision than Blackwell's W4A8, so **A100 should be at
  least as accurate as B300 on this checkpoint**, not less. The cost is entirely
  in speed.
- The only published quantisation-accuracy datapoint for any K3 variant is
  **RedHatAI NVFP4: GPQA Diamond 93.5 → 91.0 (97.33 % recovery)** — and 93.5 is
  itself the MXFP4 model ([architecture.md §9](./architecture.md)).
- **FP8 KV on A100 is the accuracy risk to watch**, not the weights: the
  checkpoint ships `kv_cache_scheme: null`, per-head scales are unavailable
  without FA3, and the default (all scales = 1.0) is "the accuracy-risky option"
  ([gpus/a100.md §6](../../gpus/a100.md)). Calibrate per-tensor scales with
  llm-compressor before using `--kv-cache-dtype fp8`, which §1.2 and §4 both
  assume you do.
- The F32 tensors (`{q,k,v}_conv1d`, `dt_bias`, `A_log`, `o_norm`,
  `e_score_correction_bias`; 506 tensors, 44.5 MB) **must not be silently
  downcast** — the conv kernels and decay parameterisation are numerically
  sensitive ([architecture.md §3.5](./architecture.md)). A Triton KDA fallback path
  that is not exercised on sm_80 is exactly where such a downcast would hide.

### 6.6 Nearest runnable alternatives, in order

1. **H100 4×8 = TP32 (32 GPUs).** The same GPU count, published launch commands
   for both vLLM and SGLang, `--moe-backend marlin` (same dequant story), plus
   FlashMLA and native fused CUDA KDA decode that A100 lacks. 1.64× the
   bandwidth. This is the A100 plan with the kernels present. Cost anchor:
   `h100` planning prices $3.20 low / $6.880 high
   ([cloud-pricing.md §5.14](../../cross-cutting/cloud-pricing.md)). **Caveat:**
   vLLM still only promises `--max-num-seqs 5` at 32 K there, and no H100
   throughput for this model has ever been published
   ([architecture.md §12 Q10](./architecture.md)).
2. **8× B300 = TP8, one node.** The only *verified* cells that exist for this
   model, at 155 output tok/s/GPU measured. One node instead of four.
3. **A different model on A100.** [gpus/a100.md §9](../../gpus/a100.md) shows
   Qwen3.8-27B (FP8 W8A16, 800–1,309 concurrent at 8 K on 8 GPUs) and Marlin-2B
   both run natively. If the requirement is "serve something good on the A100s we
   own", it is not Kimi-K3.
4. **`unsloth/Kimi-K3-GGUF` on llama.cpp, CPU+GPU offload.** Unsloth publish
   Dynamic 1-bit S at 610 GB and 2-bit XXS at 726 GB total RAM+VRAM, with the
   rule "RAM+VRAM ≈ the quant size; otherwise it'll still work, just much slower
   due to disk offloading", and report "~20 tokens/s generation when using B200s"
   ([Unsloth Kimi K3 docs](https://unsloth.ai/docs/models/kimi-k3)). This is a
   *capability* path, not a serving path — 1–2 bit REAP-pruned quants are a
   different model quality-wise, and whether llama.cpp's MXFP4 CUDA kernels build
   for sm_80 is contradicted by its own secondary sources. ⚠️ **(16)**.
