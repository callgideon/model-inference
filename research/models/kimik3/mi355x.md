# moonshotai/Kimi-K3 on AMD Instinct MI355X 288GB (8-GPU platform, ROCm 7; MXFP4/FP8 native, NVFP4 not native)

> Research date **2026-09-19**. Formulas, legend and pinned inputs per
> [`research/METHODOLOGY.md`](../../METHODOLOGY.md). Model facts from
> [`models/kimik3/architecture.md`](./architecture.md); hardware facts from
> [`gpus/mi355x.md`](../../gpus/mi355x.md). Every non-derived number carries a
> source link; every derived number is labelled `est.` with its formula.
> All arithmetic was run in `python3`; the script's output tables are pasted
> verbatim below.
>
> **Standing disagreement with the GPU doc, declared up front.** AMD's own
> Day-0 deployment note sizes this pair against **288 GiB** of HBM
> ([AMD, 2026-07-27](https://www.amd.com/en/developer/resources/technical-articles/2026/kimi-k3-on-amd-instinct-gpus.html)),
> which is the ROCm GPU-specification-table unit error that
> [`gpus/mi355x.md` §2](../../gpus/mi355x.md) documents and
> [METHODOLOGY §8](../../METHODOLOGY.md) resolves to **288 GB**
> (= 268.22 GiB). This document plans with **288 GB**. Consequence: AMD's
> "71.3 % HBM utilisation, 82.6 GiB remaining" becomes **76.6 % utilisation,
> 62.8 GiB remaining** at the physical capacity, and **36.0 GiB remaining**
> after METHODOLOGY's 0.90 usable factor. Both figures are cited where used.

## 0. Verdict

1. **Runnable today, and measured.** vLLM ≥ 0.27.1 (`"mi355x": "verified"`,
   image `vllm/vllm-openai_rocm:kimi-k3`) and SGLang v0.5.17+ (`mi355x` cell,
   `verified: false`) both ship an MI355X TP8 recipe; AMD's own **ATOM** engine
   shipped a Day-0 recipe on 2026-07-27, and **SemiAnalysis InferenceX has been
   sweeping this exact pair nightly since 2026-08-12** — 20 published rows on
   `mi355x` across ATOM and vLLM.
2. **Min 8 GPUs, recommended 8 GPUs, TP8 on one UBB 2.0 node.** 7 GPUs would
   hold the weights arithmetically but the node is 8 and 96 attention heads do
   not divide by 7. Above 8 GPUs you leave the XGMI mesh; run **replicas**, not
   TP16.
3. **Weight format actually executed: native MXFP4** (E2M1 + E8M0/32) on the
   routed experts through AITER SiTU v2 — `A8W4` (SGLang default) or `A4W4`
   (vLLM default) — with **BF16 non-expert tensors**. No dequantisation, no
   requantisation. Nothing about NVFP4 applies: there is no NVFP4 Kimi-K3 path
   on CDNA 4 and no reason to want one.
4. **Interactive (S1, TPOT ≤ 50 ms): $32.28 per 1M output tokens** at the only
   published MI355X rate (OCI $8.60/GPU-h) — $11.07 at TensorWave's ⚠️ $2.95
   quote, $5.33 on owned hardware. **Max throughput (S4): $26.16 / 1M output**
   measured, **$10.01–$12.00 est.** at the S4 workload definition.
4a. **Two throughput bases, and item 4 quotes the sustained one.** InferenceX's
   `out tok/s/GPU` — **74.0 at S1 (conc 44), 91.3 at S4 (conc 70)**, giving
   **$32.28 / $26.16 per 1M output, $8.49 blended** — is a **sustained
   end-to-end** rate on a 119 K-input agentic trace, and §3 is explicit that
   those traces are prefill-dominated (99.3 % of the token work is input, "so
   decode never gets the node"). The **decode-only** rate
   [METHODOLOGY §4](../../METHODOLOGY.md) defines (`batch / decode_step_time` =
   44 / 49.2 ms and 70 / 78.9 ms over 8 GPUs) is **111.8 / 110.9 out tok/s/GPU
   → $21.37 / $21.54 per 1M output, $5.76 blended**. `pairs.json` and
   [matrix/cost-matrix.md](../../matrix/cost-matrix.md) carry the
   **decode-only** pair for cross-pair comparability; 74.0 / 91.33 survive as
   `sustained_output_tokens_per_s_per_gpu`. This is not a speculative-decoding
   artefact — DSpark is off in both InferenceX rows — and even on the
   decode-only basis self-hosting still loses to Moonshot's API (§4.5).
5. **Confidence: measured.** End-to-end serving numbers for this exact
   (model, GPU) pair exist from three independent parties (SemiAnalysis
   InferenceX, Wafer, AMD/ATOM). The weight-placement model in §1 reproduces
   AMD's published per-GPU figure to **0.5 MB in 205 GB**, and the KV-budget
   model reproduces InferenceX's measured `kv_cache_pool_tokens` to within 10 %.

## 1. Fit

### 1.1 The tensors that cannot be sharded

TP on this model does **not** reduce to `checkpoint / n`. AMD's ATOM loader
publishes its tensor-by-tensor placement rules
([AMD Day-0 blog](https://www.amd.com/en/developer/resources/technical-articles/2026/kimi-k3-on-amd-instinct-gpus.html)):

> "MLA `q_a`/`kv_a`, KDA `f_a`, LatentMoE down/up, Norm, router, and AttnRes
> score projections are **replicated across ranks**."
> "Every rank retains all 896 expert IDs; TP shards each expert's matrices
> rather than partitioning the expert IDs."

Resolved against the checkpoint tensor inventory
([architecture.md §3.2](./architecture.md)), the replicated set is:

```
TABLE 0 — replicated-tensor model, validated against AMD ATOM's loader-aware TP8 figure
  MLA q_a_proj + kv_a_proj_with_mqa (24 layers)          0.7267 GB
  KDA f_a_proj (69 layers)                               0.1266 GB
  LatentMoE routed_expert_up/down_proj (92 l.)           9.4540 GB
  MoE router gate (92 layers)                            1.1821 GB
  norms + AttnRes rank-1 projections                     0.0080 GB
  routed_expert_norm (92 layers)                         0.0007 GB
  TOTAL replicated per GPU (any TP)                     11.4980 GB
  vision tower + projector (skipped by ATOM text-only)   0.8947 GB

  model:  (1560.860 - 11.498 - 0.895)/8 + 11.498 = 205.056 GB/GPU
  AMD ATOM published loader-aware TP8 per GPU        =  205.057 GB   (delta -0.0005 GB)
  naive checkpoint/8                                 =  195.108 GB  (understates by 9.95 GB/GPU = 5.1 %)
```

**The `routed_expert_up/down_proj` pair is 82 % of the replication bill.** It is
the Stable-LatentMoE 7168↔3584 bridge — 4.727 B BF16 parameters that every rank
needs because every rank runs every expert's inputs and outputs through it
([architecture.md §2.4](./architecture.md)). It is the price of the architecture
that made 896 experts affordable, and it does not go away with more GPUs.

**Formula used everywhere below** (`est.`, text-only; ATOM does not load the
vision tower in its text service, and vLLM's `--language-model-only` does the
same):

```
per_gpu_weights(tp) = (1,560.860 − 11.498 − 0.895) / tp  +  11.498      [GB]
```

Validation: at tp = 8 this gives **205.056 GB** against AMD's published
**205.057 GB** — a 0.0005 GB delta on a 205 GB number. The model is exact.
Serving images as well as text adds the 0.895 GB tower back, replicated or
data-parallel-sharded (`--mm-encoder-tp-mode data`).

### 1.2 Fit over the GPU counts this topology allows

MI355X's scale-up domain is **8 GPUs on a fully-meshed UBB 2.0 baseboard**;
there is no NVL72 equivalent ([gpus/mi355x.md §4](../../gpus/mi355x.md)). The
allowed set is therefore {1, 2, 4, 8} inside a node and {16, 32, …} only by
crossing 8 × 400G RoCE/IB.

Usable HBM = `0.90 × 288 GB = 259.2 GB` (METHODOLOGY §3).
Activation workspace = **6.47 GB** = 6.0 GB (METHODOLOGY's 2–6 GB band, top of
band for ROCm: HIP-graph pools, AITER grouped-GEMM workspaces, RCCL buffers)
+ **0.470 GB AttnRes prefill-chunk state** at `--max-num-batched-tokens 4096`,
using AMD's own formula `chunk × ⌈93/12⌉ × 7168 × 2 B` (0.940 GB at chunk 8192).
The AttnRes term is a Kimi-K3-specific memory line that appears in no other
model in this repo.

```
TABLE 1a — FIT over GPU counts (text-only; MXFP4 native; usable = 0.90 x 288 GB = 259.2 GB)
 GPUs nodes    parallel  wt/GPU GB  repl GB  act GB KV budget GB  fits?
    1     1         TP1     1560.0    11.50    6.47      -1307.2     NO
    2     1         TP2      785.7    11.50    6.47       -533.0     NO
    4     1         TP4      398.6    11.50    6.47       -145.9     NO
    8     1         TP8      205.1    11.50    6.47         47.7    yes
   16     2     TP16         108.3    11.50    6.47        144.5    yes   (2x400G RoCE/IB)
   32     4     TP32          59.9    11.50    6.47        192.8    yes   (4x400G RoCE/IB)
```

**Minimum = 8 GPUs = one node.** This matches every engine: vLLM's
`single_node_tp` `--tensor-parallel-size 8`
([recipe](https://recipes.vllm.ai/moonshotai/Kimi-K3/hw/mi355x.json)), SGLang's
`mi355x` cell `--tp-size 8`
([cookbook](https://docs.sglang.io/cookbook/autoregressive/Moonshotai/Kimi-K3)),
TokenSpeed's "AMD 8x gfx950" recipe, and AMD's own ATOM `-tp 8`. The
independent derivation in
[cross-cutting/inference-engines.md §6.3](../../cross-cutting/inference-engines.md)
(`⌈1680 / (288 × 0.9)⌉ = 7 → next power of two = 8`) lands on the same answer.

**Multi-node TP16/TP32 is published but is a trap here.** vLLM offers
`multi_node_tp`, `multi_node_tep`, `multi_node_tp_pp`, `multi_node_dep` and
`pd_cluster` strategies for `mi355x`
([alternatives in the recipe JSON](https://recipes.vllm.ai/moonshotai/Kimi-K3/hw/mi355x.json)),
but every TP all-reduce then crosses a 400G NIC (50 GB/s) instead of the
1,075 GB/s XGMI mesh, and METHODOLOGY's 20–40 % multi-node-TP comm overhead
applies to **93 sequential layers**. Use 16 or 32 GPUs as **2 or 4 independent
TP8 replicas** behind a router, not as one TP16/TP32 group, unless you
specifically need >1 concurrent 1M-token session (§5).

### 1.3 KV budget and maximum concurrency

Per METHODOLOGY §2, Kimi-K3 has two pools:

| Pool | Per-token | Per-sequence fixed | Shardable by |
|---|---|---|---|
| MLA latent KV (24 of 93 layers) | 27,648 B BF16 / **13,824 B FP8** | — | DCP only (TP replicates it) |
| KDA recurrent + conv state (69 layers) | **0** | `69 × ((96/tp)·128·128·B_ssm + 9·(96/tp)·128·2)` × S | attention-TP width only |

At tp = 8, fp32 SSM state: **53.57 MiB per slot**, and SGLang's default
`--mamba-radix-cache-strategy extra_buffer` allocates **S = 5 slots per
request** → **267.8 MiB per request per GPU** before one KV token is stored
([architecture.md §5.3](./architecture.md)). AMD's ATOM table independently
publishes **0.054 GB** for the same quantity at TP8 — identical.

⚠️ **AMD's own runtime-state table is internally inconsistent about the KV
dtype.** It heads the table "an FP8 latent KV cache", writes the formula as
`1,048,576 × (512+64) × 2 bytes/layer`, prints **14.496 GB**, and labels the
scaling behaviour "BF16". 14.496 GB is the **1-byte (FP8)** answer;
`× 2 bytes` would give 28.99 GB. The value is right and the formula and the
label are wrong. Same table: the KDA SSM row says `× 2 bytes` but prints
0.054 GB, which is the **4-byte (FP32)** answer, matching its own prose.

**DCP is measured to work on MI355X, contradicting both engines' published
recipes.** SemiAnalysis InferenceX reports `dcp_size: 8` on the vLLM and ATOM
MI355X rows at concurrency ≥ 8 (and `dcp_size: 1` below that), with
`kv_cache_pool_tokens` jumping from **2.95 M → 30.26 M tokens** at the
transition — a 10.3× step that only decode-context parallelism explains
([InferenceX `/api/v1/benchmarks?model=Kimi-K3`](https://inferencex.semianalysis.com/api/v1/benchmarks?model=Kimi-K3),
runs dated 2026-09-17). Meanwhile vLLM's recipes site returns **404** for
`hw/mi355x/variants/decode_context_parallelism.json`, and its DCP feature
definition pairs DCP with `--attention-backend TOKENSPEED_MLA`, which is
CUDA-10.x-only; SGLang's `mi355x` cell carries no `--dcp-size`. ⚠️ **TO BE
VERIFIED** — what exactly InferenceX launches. Both columns are given below.

```
TABLE 1b — max concurrency, 8x MI355X TP8, S=5 fp32 state   [est., METHODOLOGY §3]
     ctx    KV  DCP1 @0.90  DCP8 @0.90  DCP1 @0.95  DCP8 @0.95
    8192  bf16          93         154         122         200
    8192   fp8         120         161         157         210
   32768  bf16          40         120          52         157
   32768   fp8          64         141          84         183
  131072  bf16          12          64          15          84
  131072   fp8          22          93          29         122
 1048576  bf16           1          12           2          15
 1048576   fp8           3          22           4          29
```

**Validation against measurement** — this is the strongest check in the
document:

```
mem-util 0.90: KV budget 47.67 GB/GPU -> pool 27.59 M tok (DCP8) / 3.45 M tok (DCP1)
mem-util 0.95: KV budget 62.07 GB/GPU -> pool 35.92 M tok (DCP8) / 4.49 M tok (DCP1)
InferenceX measured (vLLM, mi355x, 2026-09-17): 30.26 M tok at dcp=8; 2.95 M tok at dcp=1
```

vLLM's shipped MI355X recipe sets `--gpu-memory-utilization 0.95`, and the
measured 30.26 M sits between the 0.90 and 0.95 predictions — i.e. the model is
right and the real allocator keeps ~13 % more overhead than `0.95` implies.
The DCP1 prediction (3.45 M) versus measured (2.95 M) agrees to 17 %.

**The state levers, quantified** (8 GPUs, FP8 KV, `est.`):

```
   S=5 fp32 (SGLang default)                8K= 120 32K=  64 128K=  22 1M=  3
   S=4 fp32 (extra_buffer_lazy)             8K= 141 32K=  70 128K=  23 1M=  3
   S=5 bf16 (--mamba-ssm-dtype bfloat16)    8K= 184 32K=  79 128K=  24 1M=  3
   S=4 bf16 (both levers)                   8K= 207 32K=  83 128K=  24 1M=  3
   S=1 (PD decode role / radix off)         8K= 281 32K=  93 128K=  25 1M=  3
   S=13 (DSPARK block 7 + 1, fp32)          8K=  56 32K=  40 128K=  18 1M=  3
```

Read the shape: at 8 K the state levers are worth **2.3×** admitted requests and
FP8 KV is worth almost nothing; at 128 K and 1 M they are worth nothing and only
FP8 KV and DCP matter. The crossover — where five fp32 state slots cost more
than the entire KV cache — is at **20,317 tokens (FP8 KV)** / **10,158 tokens
(BF16 KV)** at tp = 8. SGLang's one-line summary holds exactly:
*"`bfloat16` state buys admission, `fp8` KV buys context."*

**Per-GPU bill at 8 K, FP8 KV, S = 5 fp32, DCP1: 375.8 MiB per request, of
which 267.8 MiB (71 %) is KDA state.** Any concurrency estimate for this model
that counts one state slot instead of S is wrong by 5×.

### 1.4 Multi-TP-group shapes

```
  TP16: 108.3 GB/GPU weights, 144.5 GB/GPU KV budget, state/slot 26.78 MiB
       FP8 KV, DCP1:  8K=569  32K=243  128K=73   1M=9
       FP8 KV, DCP16: 8K=979  32K=856  128K=569  1M=138
  TP32:  59.9 GB/GPU weights, 192.8 GB/GPU KV budget, state/slot 13.39 MiB
       FP8 KV, DCP1:  8K=1051 32K=368  128K=102  1M=13
       FP8 KV, DCP32: 8K=2614 32K=2285 128K=1520 1M=368
```

These are the only shapes that make **1 M context at useful concurrency**
possible on MI355X: 3 concurrent 1M sessions on one node, 9 on two, 13 on four
without DCP. They cost a cross-node all-reduce on every one of 93 layers.
Two independent TP8 replicas would give 2 × 3 = 6 sessions at 1 M with no
fabric penalty — **prefer replicas unless a single session must exceed what one
node admits.**

## 3. Throughput and latency

### 3.1 Assumptions, and why they are not METHODOLOGY's defaults

METHODOLOGY §4 offers **MBU 0.4–0.6 for MI355X/ROCm**. For this model that band
is wrong, and the measurements say so. Two directly-published TPOT numbers pin
the curve:

```
  MBU calibration against published measurements:
    b=1  Wafer 118 tok/s/stream / 2.2x spec = 53.6 tok/s -> TPOT 18.6 ms; 137.6 GB/step -> MBU 0.115
    b=64 SGLang MI350X NOSPEC TPOT 70.39 ms; 1191.4 GB/step -> MBU 0.264   (MI350X = same 288 GB / 8 TB/s, 8.3 % lower clocks)
    b=24 Wafer no-spec peak 952/1.18=807 tok/s at c24 -> TPOT 29.7 ms; 633.0 GB/step -> MBU 0.332

  ADOPTED  MBU(b) = min(0.34, 0.12 + 0.164*(1-exp(-(b-1)/30)))   [est.]
   b=1:0.120  b=8:0.154  b=32:0.226  b=64:0.264  b=128:0.282  b=256:0.284
```

The two anchors used are directly published TPOT values (Wafer's 118 tok/s
single-stream ÷ its own measured 2.2× DSpark gain; SGLang's MI350X `Balanced`
NOSPEC cell at ISL 8192 / OSL 1024). The third, Wafer's back-derived c24 point,
implies ~1.4× higher MBU, so **read the decode tables below as a floor.**

**Why MBU is this low: 93 sequential layers of small per-GPU GEMMs.** At batch 1,
**81 % of the bytes are the BF16 non-expert weights** (111.2 of 137.6 GB) —
MXFP4 buys capacity, not batch-1 latency. B300 on the same model reaches
2.03 TB/s/GPU at conc 1 ([architecture.md §6.4](./architecture.md)) against
MI355X's 0.92 TB/s/GPU from the Wafer anchor, on **identical 8.0 TB/s** HBM.
That 2.2× gap is entirely software.

**MFU / the Amdahl ceiling.** MI355X's headline 10,100 dense MXFP4 TFLOPS is not
available to this checkpoint:

```
  46.66 % of active params MXFP4 @10 100 TF, 53.34 % BF16 @2 500 TF
    -> effective dense peak 3,853 TFLOPS/GPU (NOT 10 100)
    -> with FP8 non-expert (amd/Kimi-K3-Quark-MXFP4-AttnFP8): 6,541 TFLOPS/GPU
    -> FP4 speedup capped at 1.54x over an all-BF16 run
```

(That 1.54× is [architecture.md §6.1](./architecture.md)'s formula
`1/(0.533 + 0.467/k)` evaluated at MI355X's actual k = 10,100/2,500 = 4.04;
the doc's 1.89× is the k → ∞ limit.)

The spread between the measured and the est. S4 column — **$26.16 vs $10.01 at
the same price** — is the whole prefill-vs-decode argument of §3.4 expressed in
dollars. Which one applies to you is decided entirely by your input:output ratio.

### 4.3 What the two big levers are worth

**Speculative decoding (DSpark), measured on this pair** (Wafer: 1.7× per-stream
at moderate load, +18 % peak aggregate):

| | before | after | $/1M out at $8.60 |
|---|---:|---:|---|
| S1 (est. b = 26) | 65.4 tok/s/GPU | 111.2 | $36.52 → **$21.48** (−41 %) |
| S4 (est. b = 138) | 199.0 tok/s/GPU | 234.9 | $12.00 → **$10.17** (−15 %) |

It costs S = 5 → 13 state slots, which drops the 8 K admission cap 120 → 56
(§1.3) — so on MI355X, DSpark trades away **more than half** your concurrency
ceiling for a 15 % throughput gain at the top end. At low-to-moderate
concurrency, where it is worth 1.7–2.2×, it is unambiguously right; at the
throughput ceiling it is marginal. Note this is the opposite of B300, where
DSPARK is worth a simulated 1.64× even at conc 64.

**Prefix caching.** At a 90 % hit rate with the METHODOLOGY 10 % own-serving
rule, input cost falls $1.010 → **$0.192 per 1M**, and the blended figure at the
est.-S4 point falls $2.92 → **$2.65**. But the measured evidence says caching's
real effect here is on **TTFT, not on $/token**: InferenceX's two catastrophic
TTFT rows (137.9 s and 5.15 s) are exactly its two low-hit-rate rows (7.5 % and
41.6 %), while every 82–96 % row lands at 1.0–3.0 s. ⚠️ And vLLM's AMD override
omits `--prefix-match-unit 128`, which the Blackwell override sets specifically
because the hybrid KV manager's default hit boundary is very coarse
([architecture.md §8.8](./architecture.md)) — so there may be headroom above the
already-measured 82–96 %.

### 4.4 Versus the vendor API

Moonshot's list price for `kimi-k3`
([architecture.md §11](./architecture.md), re-verified against
[platform.kimi.ai/docs/pricing](https://platform.kimi.ai/docs/pricing)):
**$3.00 / 1M input (cache miss), $0.30 (cache hit), $15.00 / 1M output.**
Blended on the same 75/25, 50 %-cached definition, using Moonshot's **own
published** 10.0 % cached ratio as METHODOLOGY §6 requires for vendor
comparisons: **$4.99 / 1M**.

Break-even utilisation — self-hosting at utilisation *u* costs `c/u` per token,
so it beats the API when `u > c / API_price`:

| Operating point | $/GPU-h | self-host $/1M out | vs $15.00 API | blended vs $4.99 |
|---|---:|---:|---:|---:|
| **S1, measured (conc 44)** | 8.60 | $32.28 | **215 % — never breaks even** | 170 % — never |
| S4, measured (conc 70) | 8.60 | $26.16 | **174 % — never** | 139 % — never |
| S4, est. DCP8 (4K/512) | 8.60 | $10.01 | **67 % utilisation** | 59 % |
| S4, est. DCP8 + DSpark | 8.60 | $8.48 | **57 %** | 51 % |
| S4, est. DCP8 | 2.95 ⚠️ | $3.43 | **23 %** | 20 % |
| S4, est. DCP8 | 1.42 `est.` | $1.65 | **11 %** | 10 % |

**The conclusion is uncomfortable and should be stated plainly: at the only
published MI355X price, and on the only measured agentic-trace operating point,
self-hosting Kimi-K3 on MI355X costs 1.7–2.2× Moonshot's list price and never
breaks even at any utilisation.** It becomes rational only if (a) your traffic
is output-heavier than 118 k-input agentic traces — the synthetic 4 K/512 mix
needs 57–67 % utilisation to win — or (b) you get MI355X below ~$5/GPU-hour,
which the ⚠️ quote band and the colo estimate both suggest is achievable but
which no public rate card confirms. Wafer's 48 tok/s/$ headline is true *and*
rests on a $2.50 assumption that is 3.4× below the only published rate.

The non-cost reasons to self-host this pair are unchanged and may dominate:
data residency, the Kimi K3 License §2 MaaS threshold
([architecture.md §1.1](./architecture.md)), latency floors, and the fact that
1.56 TB of MXFP4 weights fit on **one** AMD node.

## 5. Scaling and deployment shape

### 5.1 Single node is the shape

Eight MI355X is not "the minimum", it is **the design point**: 205.06 GB of
weights per GPU against 259.2 GB usable leaves 47.7 GB of KV budget, which is
enough for ~120–161 concurrent 8 K requests. One node is also the entire
scale-up domain — TP9+ does not exist on this platform. Scale by replicas.

### 5.3 When PD disaggregation pays — and it pays for a different reason here

On B300, PD disaggregation is argued from TTFT growth
([architecture.md §10.1](./architecture.md)). On MI355X the argument is
**stronger and structural**:

1. **Prefill is this pair's weak axis.** A 172 k cold prefill takes ~51 s on
   MI355X against ~23 s on B300 (2.2×), improving to ~17–25 s after the AITER
   MLA head-padding fix. The Amdahl ceiling (§3.1) caps prefill at 3,853
   effective TFLOPS/GPU and the measured MFU is 10–14 %.
2. **Decode is nearly a tie with Blackwell.** Identical 8.0 TB/s HBM; the gap is
   kernel maturity, which is closing.
3. **The KDA state pool collapses in the decode role.** SGLang's PD decode role
   allocates **S = 1** instead of 5, taking the 8 K admission cap from
   **120 → 281** (§1.3) — a 2.3× capacity gain that exists on **no other axis**.

So: put prefill on a separate, smaller pool sized for its own latency SLO, and
run decode at S = 1 with DCP. SGLang ships an `mi355x` decode-role cell already
(`--disaggregation-mode decode --disaggregation-transfer-backend nixl`), and
vLLM ships an `mi355x` `pd_cluster` strategy. ⚠️ Neither has a published
measurement on this GPU, and the SGLang PD gotchas apply verbatim (the
positional `8998` after `--prefill` must match
`--disaggregation-bootstrap-port`; keep `--disaggregation-decode-extra-slots`
pinned).

**Wide-EP does not pay here, and cannot.** DeepEP/EPLB economics need a 32–72
GPU coherent domain; MI355X's is 8 ([gpus/mi355x.md §4](../../gpus/mi355x.md)).
EP beyond one node rides 400G RoCE. Design for TP ≤ 8 + data-parallel replicas.

### 5.4 Warm-up and load time

1,560.9 GB of safetensors:

```
   5 GB/s aggregate:    312 s ( 5.2 min)
  10 GB/s aggregate:    156 s ( 2.6 min)
  20 GB/s aggregate:     78 s ( 1.3 min)
```

Plus, and ⚠️ **not timed by any published source**: the MXFP4 **A8W4
GU-interleaved preshuffle** that AITER's SiTU v2 path performs at load. Budget
generously — ATOM sets `ATOM_DIST_TIMEOUT_SECONDS=3600` and vLLM's Blackwell
profile sets `VLLM_ENGINE_READY_TIMEOUT_S=3600` for exactly this reason (the AMD
override does not set it; ⚠️ consider adding it). vLLM's AMD profile uses
`--load-format auto` with `SAFETENSORS_FAST_GPU=1`, **not** the
`fastsafetensors` loader the Blackwell profile pins; ATOM instead uses a
16-worker loader thread pool. First boot also pays the HF download: 1.56 TB at
10 Gbit/s ≈ 21 minutes of pure wire time.

## 6. Risks and open questions

**⚠️ 1 — Does DCP actually run on MI355X?** InferenceX reports `dcp_size: 8`
with a 10.3× `kv_cache_pool_tokens` step, on both vLLM and ATOM. vLLM's recipe
site 404s for the `mi355x` DCP variant and pairs DCP with `TOKENSPEED_MLA`,
which is CUDA-10.x-only and FP8-KV-required; SGLang's `mi355x` cell has no
`--dcp-size`. This is worth **4–7× concurrency at 32 K–1 M** and is the single
highest-value unresolved item here. *Method to close: launch vLLM ROCm with
`--decode-context-parallel-size 8 --dcp-comm-backend a2a` on `ROCM_AITER_MLA`
and read back `max_total_num_tokens`.*

**⚠️ 2 — vLLM's shipped AMD profile is materially weaker than its Blackwell
profile.** No `--kv-cache-dtype fp8`, no `--enable-prefix-caching`, no
`--prefix-match-unit 128`, no `--max-model-len`, no
`VLLM_ENGINE_READY_TIMEOUT_S`. Every one of those is set on Blackwell. Whether
this is deliberate (unsupported on ROCm) or simply un-ported is unstated.

**⚠️ 3 — The two engines give opposite advice on the MoE activation path.**
vLLM: "Do not set `AITER_SITUV2_A8W4=1`; AITER checks that flag first and it
would override a4w4." SGLang ships A8W4 as its default and measures it faster
(537.3 vs 530.8 tok/s). 1.2 % apart; benchmark both on your build.

**⚠️ 4 — SGLang pins `--attention-backend triton` on MI35x**, forgoing the
1.2–1.5× AITER MLA win that vLLM's own blog measures (1.52× at conc 64 on
MI355X). No explanation is given.

**⚠️ 5 — 69 of 93 layers run unfused Triton KDA.** Both fused KDA decode
kernels are hard-gated on CUDA compute capability. SGLang's
`SGLANG_K3_KDA_FUSED_BACKEND=aiter` recovers 8.9 % of the KDA layer time on
gfx950; how far that is from what B300's FlashInfer fused kernel achieves is
unpublished on both sides.

**⚠️ 6 — SGLang has no MI355X speed cell at all.** The `mi355x` cell is
`verified: false` / "in-progress" with zero benchmark rows; all published AMD
numbers are **MI350X**. SGLang's own banner applies: "Accuracy has not been
re-measured on any cell."

**⚠️ 7 — DSpark on ROCm crashes out of the box in SGLang.**
`NameError: name 'top_k_renorm_prob' is not defined` — the ROCm build aliases
only a Triton top-p kernel. Wafer patched it in PyTorch; upstream status
unknown. Spec decoding is worth 1.7–2.2× here, so this is a blocker, not a
nuisance.

**⚠️ 8 — InferenceX labels the MI355X spec method `"mtp"`,** but
`num_nextn_predict_layers: 0` — this checkpoint ships no MTP head. The label
cannot be literal. Assume it means DSpark, and note that **no `spec_method:
"none"` MI355X row exists**, so there is no measured no-spec baseline from
InferenceX on this GPU (B200, GB200 and GB300 all have one).

**⚠️ 9 — Acceptance rate is unmeasured on real traffic.** SGLang's MI350X
DSPARK rows pin `SGLANG_SIMULATE_ACC_LEN=4.5` — a synthetic constant, not a
measurement. RadixArk's acc_len table (5.51 HumanEval → 2.99 AIME26) is offline
evaluation. Wafer's 2.2×/1.7×/+18 % *are* real end-to-end gains but no
acceptance length is published with them. Measure NOSPEC vs DSPARK on your own
traffic.

**⚠️ 10 — Two InferenceX rows are outliers driven by cache misses, not by the
engine.** ATOM conc 40: TTFT 137.9 s at a 7.5 % hit rate. ATOM conc 16: 5.15 s
at 41.6 %. ATOM conc 4: TPOT 169.7 ms against 7.5 ms at conc 2. Do not average
these into a curve; they are cold-cache and (for conc 4) unexplained.

**⚠️ 11 — AMD's own runtime-state table has two formula/label errors** (§1.3):
the MLA KV row prints the FP8 value under a `× 2 bytes` formula labelled
"BF16"; the KDA SSM row prints the FP32 value under a `× 2 bytes` formula. The
*values* are correct and match this document's independent derivation; the
formulas and labels are not.

**⚠️ 12 — AMD sizes this deployment against 288 GiB, not 288 GB.** Their
"71.3 % HBM utilisation / 82.6 GiB remaining" becomes 76.6 % / 62.8 GiB at the
physical 288 GB, and 36.0 GiB after METHODOLOGY's 0.90 factor. The conclusion
(it fits, comfortably) survives; the headroom number does not.

**⚠️ 13 — MI355X per-GPU achieved bandwidth is unmeasured.** No BabelStream or
`rocm-bandwidth-test` figure for gfx950 exists in a primary AMD document
([gpus/mi355x.md §2](../../gpus/mi355x.md)). The 8.0 TB/s peak used throughout
§3 is the datasheet number; the MBU curve absorbs whatever the real STREAM
efficiency is.

**⚠️ 14 — Accuracy of MXFP4 Kimi-K3 has no unquantised reference.** The model
is QAT-MXFP4 from the SFT stage onward, so no BF16 checkpoint exists to compare
against ([architecture.md §12 Q17](./architecture.md)). What *is* measured on
this GPU is that the MXFP4 path holds GSM8K at **0.941–0.975** across 32
InferenceX configurations, 0.950 in SGLang's fused-KDA run, and a full
1,319-sample pass in AMD's Day-0 validation. That is reassurance, not a
quantisation-error bound. The vLLM conc-52 dip to 0.941 is ⚠️ unexplained.

**⚠️ 15 — MXFP6, MI355X's one exclusive, is unexploited.** 10,100 TFLOPS at
6-bit — 2.24× B200's FP6 rate — and no engine emits MXFP6 MFMA for any model
([quantization-formats.md §6.4](../../cross-cutting/quantization-formats.md)).
For a QAT-MXFP4 model the accuracy motive is weak, but a **W4A6** variant would
lift the Amdahl ceiling if the non-expert tensors moved to MXFP6.

**⚠️ 16 — The `amd/Kimi-K3-Quark-MXFP4-AttnFP8` build is untested here.** It
would cut per-GPU weights by ~7 GB and lift the effective compute ceiling from
3,853 to 6,541 TFLOPS/GPU by moving the 53 % BF16 remainder to FP8. AMD
published it and published no evals or throughput for it.

**⚠️ 17 — Every MI355X price in this document rests on one row.** OCI's $8.60
is the only published on-demand rate anywhere; `low`, `high` and `res1y` are all
the same number. The $2.59–$2.95 band is quote-based and secondary, and Wafer's
headline uses $2.50. If the real clearing price is near $2.95, every conclusion
in §4.4 flips.

**⚠️ 18 — MI355X needs more per-model hand-tuning than a Blackwell node does.**
SemiAnalysis's operational findings on this silicon: AITER arch-string
mis-detection on gfx950, chunked-prefill crash dumps at the default 196,608
(fixed by dropping to 32,768), and an explicit recommendation to AMD to "reduce
ROCm-specific manual flag requirements"
([gpus/mi355x.md §11](../../gpus/mi355x.md)). Wafer's experience on this exact
model — one missing PyTorch function, one head-count pad — is the same story
with a happier ending.

**⚠️ 19 — Multi-node behaviour is entirely unmeasured for this pair.** vLLM
publishes `multi_node_tp/tep/tp_pp/dep` and `pd_cluster` strategies for
`mi355x`; not one has a number attached, on any GPU, for Kimi-K3.

**Nearest runnable alternatives, for completeness.** None is needed — this pair
runs natively — but for the record: the `amd/Kimi-K3-Quark-MXFP4-AttnFP8` build
(⚠️ 16) is the obvious upgrade path, and `Kimi Linear 48B-A3B` is the
already-validated small sibling on this exact hardware if 1.56 TB is too much
machine for the job (§3.3f).

**Deliberate deviation from METHODOLOGY §3's literal `max_concurrency = floor(kv_budget ×
n_gpus / …)` formula, confirmed correct, not a bug:** this document computes
`max_concurrency = floor(kv_budget_per_gpu / per_request_bytes_per_gpu)` — i.e. it does
**not** multiply by `n_gpus`. This is correct for Kimi-K3 under plain TP8 (no DCP) because
MLA KV is *replicated*, not sharded, across TP ranks (`architecture.md` §5.3, this
document's §1.2/§3.1) — unlike ordinary GQA/MHA, where TP naturally shards KV heads and
METHODOLOGY's `× n_gpus` scaling applies. Multiplying by `n_gpus` here would overstate
concurrency 8× and contradict the InferenceX/AMD measurements this document validates
against.
