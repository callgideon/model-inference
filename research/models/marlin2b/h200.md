## 0. Verdict

1. **Runnable today, with one flag, on one GPU.** vLLM **0.29.0** ([gpus/h200.md §7](../../gpus/h200.md)) plus `--hf-overrides '{"architectures": ["Qwen3_5ForConditionalGeneration"]}'` — the checkpoint's own class is an unmodified subclass ([architecture.md §8.1](architecture.md)); HF `transformers >= 5.7.0` is the only *first-class* path. ⚠️ the remap is not verified end-to-end.
2. **min 1 GPU, recommended 1 GPU per replica, TP=1** — 4.426 GB of weights against 126.9 GB usable. An 8-GPU HGX node is **8 independent replicas**, never a TP/PP/EP shard; no fabric is involved.
3. **Weight format actually executed: BF16.** No FP8/NVFP4/MXFP4 Marlin checkpoint exists ([architecture.md §9](architecture.md)); H200 has FP8 tensor cores it cannot use here, and no FP4 tensor core at all ([gpus/h200.md §3](../../gpus/h200.md)).
4. **Interactive (S1, TPOT ≤ 50 ms): $0.023–$0.066 per 1M output tokens** (`res1y` $2.79 → `high` $7.912); **max-throughput (S4) $0.020–$0.058**. The SLO never binds — KV capacity does — so S1 and S4 land on the same operating point. As video: **$0.38–$1.07 per 1,000 two-minute clips**, i.e. **$0.00019–$0.00054 per video-minute**.
5. **Confidence: `estimate`.** Every throughput number here is roofline `est.`; **no measurement of Marlin-2B on any GPU exists** ([architecture.md §10.2](architecture.md)), and the closest published H200 proxies are a 397B MoE sibling and an 8B dense model, not this shape.

### 1.2 Fit over the GPU counts this topology allows

HGX H200 exposes **1, 2, 4 and 8 GPUs in one NVLink/NVSwitch domain**; 16 and beyond cross a node
boundary over 400G-class fabric ([gpus/h200.md §4](../../gpus/h200.md)). There is **no NVL72-style
rack domain on Hopper** — the largest single NVLink domain is 8 GPUs / 1,128 GB.

For this model none of that matters, because **every row below is TP=1 with a full weight copy per
GPU**. Concurrency is exactly linear in GPU count; the fabric is never in the critical path.

`kv_budget/GPU = 126.9 GB − 4.426 GB − 4 GiB = 118.18 GB (110.06 GiB)` — identical at every
GPU count.

`est.`, METHODOLOGY §3. Notes that must travel with the table:

- **The 1M column is out of spec and is arithmetic only.** `max_position_embeddings` is **262,144**
  and `rope_parameters.rope_type` is `default` with no YaRN/NTK entry
  ([architecture.md §5.3](architecture.md)). Do not plan there. At the native 262,144 maximum the
  per-GPU figure is **36** (BF16 KV) / **72** (FP8 KV).
- **FP8 KV buys 1.72× at 8K, 1.88× at video context (23.5K), and 1.99× at 128K** — approaching but
  never reaching 2×, because the 18.63 MiB GDN state is dtype-invariant at these settings (recomputed
  `python3`: 720/383 = 1.880 at 23.5K, 143/72 = 1.986 at 128K). Below ~1,590 tokens of context the
  fixed state costs *more* than the KV cache ([architecture.md §5.2](architecture.md)).
- **With untied (5.444 GB) weights** the per-GPU BF16 figures become **974 / 379 / 277 / 71** — a
  0.9 % haircut, reconciling with [gpus/h200.md §2](../../gpus/h200.md)'s 7,797 / 2,220 / 574.
- **The video fleet only ever operates in the 23.5K column.** The 240-frame cap bounds every video
  request at ~23,560 prefill tokens regardless of clip length
  ([architecture.md §6.3](architecture.md)), so `max_concurrency` is a constant (383/GPU), not a
  distribution. 128K and 1M are reachable only with text or multi-image prompts.

### 1.3 What cannot be sharded — explicitly

The question is moot at the recommended TP=1, but it decides whether TP>1 is *available* as a lever
at all (it is not):

| Tensor group | Shardable under TP? | Why |
|---|---|---|
| `self_attn.{q,k,v,o}_proj` (6 layers) | **TP ≤ 2 only** | `num_key_value_heads = 2`. TP=4 or 8 would have to replicate the KV heads, which multiplies KV bytes by TP/2 — the opposite of the goal |
| `self_attn.{q,k}_norm` `[256]` | ❌ replicated | per-head RMSNorm |
| `linear_attn.conv1d.weight` `[6144,1,4]` (18 layers) | ❌ **depthwise conv** | not a 2-D linear; vLLM's GDN state-shape calculator shards the *heads*, and the conv follows them, but the tensor itself carries no reduction dimension |
| `linear_attn.A_log`, `dt_bias` `[16]` each | ❌ replicated | per-head SSM scalars; 16 v-heads caps GDN TP at 16 and any TP that does not divide 16 is illegal |
| `linear_attn.norm` `[128]` | ❌ replicated | RMSNormGated over `value_head_dim` |
| `input_layernorm`, `post_attention_layernorm`, `model.norm` | ❌ replicated | 98,304 + 2,048 params |
| `embed_tokens` / `lm_head` `[248320, 2048]` | ✅ vocab-parallel | but it is 508.6 M params = 23 % of the model, and with `tie_word_embeddings: true` the gather side is replicated anyway |
| **Vision tower (331.4 M params, 24 ViT blocks)** | data-parallel, not tensor-parallel | the repo-wide recommendation for small encoders: `--mm-encoder-tp-mode data` ([serving-optimizations.md §6.2](../../cross-cutting/serving-optimizations.md), [vLLM Qwen3-VL recipe](https://docs.vllm.ai/projects/recipes/en/stable/Qwen/Qwen3-VL.html)) |

Non-shardable total is small — `548,672` language params plus the whole vision tower
([architecture.md §3.6](architecture.md)) — but the `num_key_value_heads = 2` and
`linear_num_value_heads = 16` constraints mean **TP is capped at 2 before KV replication starts**.
At 4.43 GB there is no reason to pay that. **TP=1, scale by replicas.**

## 3. Throughput and latency

### 3.1 Assumptions, stated per METHODOLOGY §4

| Parameter | Value | Justification |
|---|---:|---|
| MBU (decode) | **0.75** | [architecture.md §10.3](architecture.md) uses 0.75 for `h200`; [gpus/h200.md §9](../../gpus/h200.md) recommends **0.65–0.75** for dense decode with FA3 + CUDA graphs. 0.75 is the **top** of that band — sensitivity below |
| MFU (BF16 prefill GEMM) | **0.40** | METHODOLOGY §4 band 0.35–0.50; [architecture.md §10.3](architecture.md) uses 0.40 |
| MFU (attention) | **0.60** | the value [gpus/h200.md §9](../../gpus/h200.md)'s worked table uses; FA3 *measures* 0.75 on BF16 [src](https://tridao.me/blog/2024/flash3/), so this is conservative |
| Weights read per decode step | **3.764 GB** | `1,881,825,088 × 2` — language layers + `lm_head` only; **the 331.4 M-param vision tower is idle during decode** ([architecture.md §6.2](architecture.md)) |
| Comm overhead | **0 %** | TP=1. No all-reduce exists |

**Decode-byte model (this document corrects [architecture.md §6.2](architecture.md)):**

```
bytes_per_decode_step(batch, ctx)
    = weights_read                                       3,763,650,176 B
    + batch × ctx × 12,288                               KV read,  scales with batch × ctx
    + batch × 2 × 19,537,920                             GDN recurrent + conv state, READ AND WRITTEN every step
decode_step_time = max( bytes / (4.8e12 × 0.75),  2 × 1,881,825,088 × batch / (989.5e12 × 0.40) )
```

[architecture.md §6.2](architecture.md) prints `3.764 GB + batch × ctx × 12,288` and **omits the GDN
state traffic entirely**. The 18 GDN layers hold a per-sequence recurrent state that the decode
kernel must load, update and store on every step — METHODOLOGY §2 counts it as capacity, but it is
also *bandwidth*. The omission is material at short context and mild at video context:

| context | batch 32 | batch 128 | batch 256 |
|---|---:|---:|---:|
| S1 avg 4,352 | 1.87 vs 1.52 ms (**+22.8 %**) | 4.34 vs 2.95 ms (**+47.1 %**) | 7.63 vs 4.85 ms (**+57.3 %**) |
| video 23,520 | 3.96 vs 3.61 ms (+9.6 %) | 12.71 vs 11.32 ms (+12.3 %) | 24.38 vs 21.60 ms (+12.9 %) |
| 128K | 15.71 vs 15.36 ms (+2.3 %) | *infeasible (KV)* | *infeasible (KV)* |

(left = with state read+write, right = architecture.md's model). ⚠️ **TO BE VERIFIED:** whether the
fused CUDA GDN decode kernel reads and writes the full state or updates in place — the 1× variant
halves the penalty. The read+write assumption is the conservative one and is used throughout below.

**Explaining the gap between `est.` and `meas.`** The table above has no like-for-like row, so the
honest calibration is to run *this document's own roofline* against a model that **is** measured on
1×H200 and see how far the roofline overshoots. Llama-3.1-8B FP8 is the right subject: same GPU,
same engine class, single GPU, published number.

```
Llama-3.1-8B FP8, 1×H200, ISL 1,024 / OSL 294:
  decode asymptote  = 1,171 × 65,536 B / (4.8e12 × 0.75)       = 21.3 µs / token
  prefill amortised = 2 × 8.03e9 × 1,024 / (1979e12 × 0.50) / 294 = 56.5 µs / token
  roofline          = 1 / 77.8 µs                              = 12,846 tok/s/GPU
  measured (MLPerf v6.1 Offline)                               =  7,796.6 tok/s/GPU
  realisation                                                  = 61 %
  (at MBU 0.70 / MFU 0.45 the roofline is 11,675 and realisation is 67 %)
```

⚠️ The ISL/OSL statistics are the commonly quoted OpenOrca figures, which
[gpus/h200.md §9](../../gpus/h200.md) explicitly flags as **⚠️ TO BE VERIFIED** — so treat the
realisation factor as a band, not a constant.

**Apply a 0.60–0.67 haircut and this document's headline numbers become:**

| Roofline `est.` | With engine realisation |
|---|---|
| S1 batch 256: 33,565 tok/s/GPU | **20,100–22,500 tok/s/GPU** |
| Video ctx, batch 128: 10,056 tok/s/GPU | **6,000–6,700 tok/s/GPU** |
| Sustained 7,372 videos/h/GPU (768-tok captions) | **4,400–4,900 videos/h/GPU** |

Four further reasons the roofline is optimistic, none of them quantified:

1. **The GDN prefill kernel is not free.** The roofline charges GDN
   `≈ 18.9 MFLOP/token` — 0.5 % of the linear term — but GDN is a chunked scan with a state
   read-modify-write, i.e. **bandwidth- and occupancy-bound, not FLOP-bound**
   ([architecture.md §6.1](architecture.md)). FlashQLA's own framing makes the point: at TP8 *"only
   8 blocks occupy a 132-SM H200, leaving 94 % of the GPU idle"* ⚠️ secondary
   [src](https://netraruntime.com/blog/how-to-speed-up-gdn-kernels-for-qwen-models). Marlin at TP1
   has 16 v-heads — better than 8, far short of saturating 132 SMs at small batch.
2. **FlashInfer GDN prefill carries a JIT warm-up** ([flash-attention.md §14.3](../../cross-cutting/flash-attention.md)) — a cold-start cost the steady-state roofline never sees.
3. **Video decode is plausibly the real bottleneck.** vLLM's own measurement says CPU video decode
   saturates before 4 GPUs on a *16-frame* workload [src](https://vllm.ai/blog/2026-09-18-pynvvideocodec);
   Marlin's canonical path is **240 frames at 448×448**, 15× more. torchcodec throughput at that
   rate is unmeasured everywhere ([architecture.md §12 #6](architecture.md)).
4. **`.multi_find` is invisible to every table here.** It re-encodes the video tail with
   `ffmpeg -c:v libx264` (frame-accurate, not stream-copy) and runs a **full prefill per hit** —
   budget `N × (re-encode + prefill + decode)` of CPU and GPU work
   ([architecture.md §1.4](architecture.md)).

### 4.4 Effect of the two levers METHODOLOGY asks about

| Lever | Effect on cost here |
|---|---|
| **Speculative decoding** | **$0 — unavailable.** MTP weights are not shipped ([architecture.md §7.1](architecture.md)); no EAGLE head exists; DSpark is not applicable. ### 4.5 Comparison to the vendor API, and break-even

**There is no hosted Marlin-2B API.** `inferenceProviderMapping` for `NemoStation/Marlin-2B` is
**`{}` — empty**; the base `Qwen/Qwen3.5-2B` has one provider (`featherless-ai`, task
`conversational` — **text only, not video**); the author runs a Gradio demo and monetises through
custom fine-tuning by email ([architecture.md §11.1](architecture.md)).

**Consequence: METHODOLOGY §6's vendor sanity check cannot be performed, and break-even utilisation
versus an API is undefined — there is no API to break even against.** The relevant break-even is
therefore against the *alternative* of a hosted frontier video model:

```
break-even utilisation u solves:  price_per_gpu_hour / (u × sustained_videos_per_hour) = API_price_per_video
```

At `low` $3.99 and 7,372 videos/h (768-token captions), any API charging more than
**$0.000541 per 2-minute video at 100 % utilisation** — equivalently **$0.0054 at 10 % utilisation**,
**$0.054 at 1 %** — is beaten by self-hosting. Since the card positions Marlin against
Gemini-2.5-class video understanding, whose per-video price was **not retrieved in this pass**
⚠️ ([architecture.md §12 #23](architecture.md)), the multiple is left uncomputed. What the arithmetic
does say is that **a single H200 at 1 % duty cycle still undercuts any per-request price above
5.4 cents**, so the decision is about latency, quality and operational burden, not about token cost.

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

**Single GPU, replicated.** Weights 4.426 GB; 0.287 GiB per concurrent 2-minute video
([architecture.md §5.3](architecture.md)). The base model's own recipes use `--tp-size 1` for the
2B. An 8-GPU HGX H200 node is **eight independent servers behind one load balancer** — the NVSwitch
fabric, the 900 GB/s NVLink and the 8 × 400G NICs are all **unused**. Two nodes is sixteen replicas
and still needs no fabric, because replicas share nothing.

That makes H200 a slightly awkward *purchase* for this model: you are buying
[gpus/h200.md §12(c)](../../gpus/h200.md)'s memory-per-dollar champion (31.3–35.3 GB per $/GPU-hour)
for a model that uses **3.5 % of the memory**. The thing H200 actually delivers here is
**4.8 TB/s of decode bandwidth — 1.43× H100 for a +17 %/+2 % price premium at Nebius/CoreWeave**
([gpus/h200.md §8, §12(a)](../../gpus/h200.md)) — and decode is 68–85 % of a batch-1 request (§3.2).

### 5.2 When PD disaggregation or wide-EP pays — it does not

| Technique | Verdict for this pair |
|---|---|
| **Wide-EP / DeepEP / EPLB** | **n/a.** No MoE ([architecture.md §2.2](architecture.md)) |
| **PD disaggregation** | **No.** Prefill 412 ms vs decode 0.87–2.31 s for one 2-min video; both fit one GPU comfortably, and a PD split would ship a 287 MiB KV cache per sequence across the fabric to save a phase that is already 15–32 % of the request. The general threshold in [serving-optimizations.md §3.5](../../cross-cutting/serving-optimizations.md) is a large prefill-heavy MoE, which this is the opposite of |
| **EPD (encode / prefill / decode) disaggregation** | ⚠️ **the one that is arguably interesting** — the ViT is 39 % of prefill compute and the video *decode* (NVDEC/ffmpeg) is CPU/hardware work the GPU roofline never sees. SGLang separates encode from prefill with Mooncake ([serving-optimizations.md §6.3](../../cross-cutting/serving-optimizations.md)). Unmeasured for this model |
| **Attention-DP** | **n/a.** A sharding technique for models that are sharded |

⚠️ Marlin's Path A budget is `min_frames 4 / max_frames 240` at 2 fps
([architecture.md §6.3](architecture.md)), so the `16/16` values above are the blog's workload, not
Marlin's. H200 has **7 NVDEC engines** ([gpus/h200.md §1](../../gpus/h200.md)), so `hw_decoders`
can go above 2 — untested.

**`transformers`** — the only first-class path, verbatim from the model card
([architecture.md §8.6](architecture.md)):

```shell
pip install "transformers>=5.7.0" "torch>=2.11.0" torchcodec "qwen-vl-utils>=0.0.14" av pillow
```
```python
marlin = AutoModelForCausalLM.from_pretrained("NemoStation/Marlin-2B", trust_remote_code=True,
                                              dtype=torch.bfloat16, device_map={"": "cuda"})
marlin.compile()
result = marlin.caption("video.mp4")                                  # max_new_tokens=2048
```

**What you must re-supply under the vLLM remap** ([architecture.md §8.1](architecture.md)): both EOS
ids `[248044, 248046]`, the Path A frame/pixel budget, the `<think>`-prefix strip, and the canonical
prompts — `.caption()` / `.find()` / `.multi_find()` and the output parsers are client-side wrappers
you lose.

**Container/driver floor for H200 in 2026:** driver **580.xx+** and CUDA **13.0**, because that is
what Dynamo 1.4.2 and current vLLM wheels are built against; `vllm/vllm-openai:v0.29.0` ships CUDA
13.0 by default with CUDA 12.9 wheels also published ([gpus/h200.md §1, §7](../../gpus/h200.md)).
FlashQLA additionally needs CUDA ≥ 12.8 and PyTorch ≥ 2.8 [src](https://github.com/QwenLM/FlashQLA).

### 5.4 Warm-up and loading

| Stage | Time | Basis |
|---|---:|---|
| Read 5.444 GB from NVMe @ 5 GB/s | **1.09 s** | on-disk size ([architecture.md §1.2](architecture.md)) |
| @ 10 GB/s | **0.54 s** | |
| @ 20 GB/s | **0.27 s** | |
| Host → HBM over PCIe Gen5 (128 GB/s bidirectional) | ~0.09 s | [gpus/h200.md §4](../../gpus/h200.md) |
| CUDA-graph capture | ⚠️ unmeasured | vLLM V1 capture *"uses more memory than V0"* ([gpus/h200.md §11](../../gpus/h200.md)) |
| **FlashInfer GDN prefill JIT warm-up** | ⚠️ unmeasured, **first request only** | vLLM warns about it explicitly ([flash-attention.md §14.3](../../cross-cutting/flash-attention.md)) |

**Weight loading is ~1 second and is never the problem.** Cold start on this model is dominated by
kernel JIT and graph capture, neither of which is published. Note also that a loader honouring
`tie_word_embeddings` reads all 5.444 GB from disk and keeps 4.426 GB resident — you pay the disk
cost for the duplicate either way.

## 6. Risks and open questions

### Blocking — resolve before committing

1. ⚠️ **Does the checkpoint actually load under `--hf-overrides` on vLLM 0.29.0?**
   ([architecture.md §12 #2](architecture.md)) Strong evidence — pure subclass with unmodified
   forward, third party already ships the remap, documented API — but **not verified end to end**.
   Sub-question: how vLLM reconciles the materialised `lm_head.weight` with
   `tie_word_embeddings: true`, which is also the 4.426-vs-5.444 GB fork in §1.1.
2. ⚠️ **Path A vs Path B video token budget: 23,520 vs 12,288 tokens, a 1.914× gap**
   ([architecture.md §6.3, §12 #1](architecture.md)). `qwen-vl-utils` bypasses the HF processor's
   `size`, so **serving through vLLM/SGLang likely silently halves frames or resolution**. Every
   number in §3 and §4 is built on Path A. If Path B is what the engine does, prefill halves and
   quality drops by an unmeasured amount.
3. ⚠️ **No measurement of this pair exists** (§3.3). The 0.60–0.67 realisation haircut derived from
   Llama-3.1-8B is a calibration borrowed from a different architecture, and its ISL/OSL inputs are
   themselves flagged ⚠️ in [gpus/h200.md §9](../../gpus/h200.md).
4. ⚠️ **torchcodec / video-decode throughput at 240 frames @ 448×448 is unmeasured.** vLLM's own
   data says CPU decode bottlenecks before 4 GPUs on a **16-frame** workload
   [src](https://vllm.ai/blog/2026-09-18-pynvvideocodec); Marlin's path is 15× heavier. This is the
   single most likely reason a real H200 deployment misses §3's numbers by more than the haircut.

### High-impact, non-blocking

5. ⚠️ **GDN state read+write in the decode byte model** (§3.1). This document adds
   `batch × 2 × 18.63 MiB` to every decode step and [architecture.md §6.2](architecture.md) does
   not. If the fused kernel updates in place (1× rather than 2×), S1 TPOT at batch 256 drops from
   7.63 to ~6.2 ms. Nobody has published which it is.
6. ⚠️ **Does vLLM/SGLang dispatch to FlashQLA at all for this head config?**
   ([architecture.md §8.3](architecture.md), [flash-attention.md §14.3](../../cross-cutting/flash-attention.md))
   vLLM's `_resolve_gdn_prefill_backend` selects **FlashInfer** on SM90; SGLang has its own
   `triton_gdn_fused_proj`. The 2.2–2.9× FlashQLA speedup on H200 may be entirely off the table
   for a stock deployment — and its H200 benchmark file was reachable only through a **third-party
   restatement** in this pass ⚠️ secondary.
7. ⚠️ **FP8 KV cache at `head_dim 256` on a hybrid Mamba-cache model.** Nothing in
   [flash-attention.md §9.2](../../cross-cutting/flash-attention.md) or
   [quantization-formats.md §8.1](../../cross-cutting/quantization-formats.md) forbids it, and
   nothing confirms it. §1.2's FP8 column and §4.4's lever both depend on it.
8. ⚠️ **`--mamba-cache-mode=align` prefix caching is "currently experimental"**
   ([architecture.md §8.7](architecture.md)) and `mamba_cache_mode == "all"` is a **hard error**.
   The one workload that could use caching (many questions about one video) rides on the
   experimental path.
9. ⚠️ **`causal_conv1d_update` assertion** when *"cuda graph capture size is larger than mamba cache
   size"* ([architecture.md §8.7](architecture.md)). A concurrency-dependent crash, not a slowdown.
10. ⚠️ **`--max-num-seqs` default.** §3.2's operating points assume the engine will schedule batch
    256–1,551. vLLM's default was not re-read for this document; verify before quoting the KV
    ceiling as reachable.
11. ⚠️ **SGLang video ingestion for `qwen3_5` is unconfirmed**
    ([architecture.md §8.4](architecture.md)) — the class is exported and subclasses
    `Qwen3VLForConditionalGeneration`, but the multimodal docs page 404'd. The measured H200 proxies
    in §3.3 are all SGLang runs, which makes this more than academic.
12. ⚠️ **TensorRT-LLM support for the Qwen3.5 hybrid/GDN path: no evidence either way**
    ([architecture.md §8.4](architecture.md)). Every clean single-GPU H200 MLPerf number in §3.3 is
    a TRT-LLM number, so the fastest measured Hopper stack is the one whose support is unknown.
13. ⚠️ **`.multi_find` production cost** ([architecture.md §12 #11](architecture.md)): N sequential
    `ffmpeg -c:v libx264` re-encodes plus N full prefills, all invisible to §3 and §4.

### Accuracy caveats of the executed precision

14. **BF16 is the executed format, so there is no quantisation accuracy risk at all** on the
    recommended path — which is the strongest thing this pair has going for it. The risk appears
    only if you take one of the levers:
    - **INT4 GPTQ / INT8 SDNQ / MLX-8bit / GGUF: ⚠️ zero published evaluations.** Not one repo
      reports a CaReBench, DREAM-1K or TimeLens score, a perplexity delta or any accuracy
      measurement ([architecture.md §9](architecture.md)). For a model whose value proposition is
      **second-precise timestamps**, 4-bit numeric error landing on the timestamp digits is a
      specific, plausible and entirely unmeasured failure mode.
    - **FP8 KV cache: "at most 1–2 points of accuracy degradation" on reasoning tasks and 97–98 % of
      baseline long-context AUC** for other models, uncalibrated
      ([quantization-formats.md §8.2](../../cross-cutting/quantization-formats.md),
      [gpus/h200.md §6](../../gpus/h200.md)). What that does to temporal grounding on a video model
      is unknown; calibrate with llm-compressor before trusting it.
15. ⚠️ **Engine-vs-`transformers` quality is unmeasured** ([architecture.md §12 #3](architecture.md)).
    The model was trained with a fixed prompt, a `<think>` prefix artefact, a two-element EOS list
    and a specific preprocessing path. Each is a place vLLM can silently diverge.
16. ⚠️ **The 240-frame cap is a quality cliff, not a cost one** — a 10-minute clip is sampled at
    0.40 fps and an hour at 0.067 fps for identical cost. "Second-precise timestamps" interpolated
    from frames 2.5 s apart are unvalidated ([architecture.md §6.3, §12 #4](architecture.md)).
17. ⚠️ **Benchmark contamination.** ActivityNet, Charades and TimeLens appear in **both** the
    training-source list and the evaluation list, and the card does not state how it was controlled
    ([architecture.md §10.1](architecture.md)). Every quality claim is vendor marketing with a
    three-panel PNG and `"model-index": null`.

### H200-specific engine issues inherited from the GPU doc

18. **FA4 is beta on sm_90** and is not a safe production default; FA3 is
    ([gpus/h200.md §7, §11](../../gpus/h200.md)).
19. **Dynamo 1.4.2 pins vLLM 0.26.0** while head is 0.29.0 — three minor versions of Hopper kernel
    work are not in the Dynamo container ([gpus/h200.md §7](../../gpus/h200.md)). If you orchestrate
    with Dynamo you are not running the vLLM this document assumes.
20. **vLLM MRV2 fallbacks** (sequence parallelism, dual-batch overlap, custom logits processors,
    some spec-dec) silently drop to MRV1 ([gpus/h200.md §7](../../gpus/h200.md)).
21. **CUDA 13 / driver 580 is the most common practical blocker on older H200 fleets**
    ([gpus/h200.md §11](../../gpus/h200.md)).
22. ⚠️ **Price risk:** AWS reportedly raised H200 instance prices ~15 % in 2026 (primary source
    returned HTTP 403); Hopper capacity is being repriced as Blackwell absorbs new build-out
    ([gpus/h200.md §11](../../gpus/h200.md)). §4's `high` tier is the one to stress-test.
23. ⚠️ **No hosted Marlin API exists**, so §4.5's break-even has no counterparty and
    METHODOLOGY §6's vendor sanity check cannot be run
    ([architecture.md §11.1, §12 #22](architecture.md)).
