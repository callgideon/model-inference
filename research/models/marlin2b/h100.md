Research date: **2026-09-19**. Formulas, legend (`[src]` / `est.` / `meas.` / **⚠️ TO BE VERIFIED**)
and the S1–S4 scenario definitions per [`research/METHODOLOGY.md`](../../METHODOLOGY.md).
Model facts from [`architecture.md`](architecture.md); GPU facts from

[`research/cross-cutting/cloud-pricing.md`](../../cross-cutting/cloud-pricing.md) §5.14 by row name.

## 0. Verdict

1. **Runnable today: yes, two ways.** `transformers >= 5.7.0` + `trust_remote_code=True` is the only
   first-class path ([architecture.md §8.4](architecture.md)); **vLLM v0.29.0** runs it after a
   one-flag architecture remap, `--hf-overrides '{"architectures":["Qwen3_5ForConditionalGeneration"]}'`
   — the class is a pure subclass whose forward pass is unmodified ([architecture.md §8.1](architecture.md)).
   ⚠️ the remap is verified by reading, not by running.
2. **Min and recommended GPUs: 1 and 1.** `--tensor-parallel-size 1`, weights 4.426 GB resident.
   TP > 2 is actively harmful (`num_key_value_heads: 2`). Scale a fleet with **8 independent TP1
   replicas per HGX node**, ViT data-parallel; no NVLink and no fabric requirement at all.
3. **Weight format executed: BF16 native.** The checkpoint is BF16 for all 618 tensors; H100 has no
   FP4 path and the model is too small for quantisation to matter above batch ≈ 14 at video context.
4. **Interactive (S1, 4K/512, TPOT ≤ 50 ms): $0.0237–$0.0509 per 1M output tokens**
   (`low` $3.20 → `high` $6.880/GPU-hr), at 834 concurrent seats and 22.2 ms TPOT — the 50 ms SLO is
   **never binding**, so **S4 max-throughput is the same operating point and the same cost**.
5. **Confidence: `estimate`.** Every throughput number here is roofline `est.`; **no measured
   Marlin-2B number exists on any hardware** ([architecture.md §10.2](architecture.md)), and the
   nearest measured proxies are family-level, not size-matched.

**Net effect of the disagreement**: KV budget on one H100 is **59.21 GiB** (this document, 4.426 GB
weights + 4 GB workspace), **58.93 GiB** (architecture.md §8.5), or **58.26 GiB**
(gpus/h100.md §2 "the repo's own models" row, 5.444 GB weights + 4 GB workspace). The three give
528 / 520 / 520 seats at 8 K and 206 / 205 / 202 at video context — a ≤ 2 % spread that changes no
decision. **We plan on 59.21 GiB and print the others.**

### 1.2 Fit over the GPU counts this topology allows

HGX/DGX H100 is an 8-GPU NVSwitch domain ([gpus/h100.md §4](../../gpus/h100.md)); 16 means two nodes
over InfiniBand/RoCE. Two tables, because for a 2 B model the two readings of "N GPUs" are completely
different deployments.

**(a) One replica sharded across N GPUs (TP).** `est.`, METHODOLOGY §3.

```
replicated bytes/GPU (norms+SSM 548,672 p + data-parallel ViT 331.42 M p) = 0.6639 GB
shardable bytes total = 3.7626 GB

  N parall.                 W/GPU GB  act GB  KVbud GiB  KV/tok/GPU      8K     32K     128K     1M | FP8 KV:      8K     32K     128K     1M
  1 TP1 (1 GPU)                4.426     4.0      59.21       12288     528     150       38      4 |             909     287       77      9
  2 TP2                        2.545     4.0      60.96        6144    1872     592      158     20 |            2928    1088      310     40
  4 TP4                        1.605     4.0      61.84        6144    3800    1200      320     40 |            5940    2208      628     80
  8 TP8                        1.134     4.0      62.27        6144    7656    2416      648     80 |           11960    4448     1264    160
 16 TP16 (multi-node IB)       0.899     4.0      62.49        6144   15360    4848     1296    160 |           24016    8928     2528    320
```

The `KV/tok/GPU` column stops falling at TP2 and that is the whole story of this row set: the model
has **`num_key_value_heads: 2`** ([architecture.md §2.2](architecture.md)). Standard tensor
parallelism cannot slice a single KV head, so beyond TP2 the KV heads are **replicated**
`tp_size // 2` times and node-aggregate KV capacity grows only linearly with the replication waste.
vLLM's own TP design doc states only the divisibility requirement (`num_kv_heads % tp == 0`)
[src](https://docs.vllm.ai/projects/vllm-omni/en/latest/design/feature/tensor_parallel/); the
replication behaviour above is ⚠️ **TO BE VERIFIED** against a run — it is standard GQA-TP behaviour
and is described in secondary write-ups, but no first-party vLLM page fetched this session states it
for `tp_size > num_kv_heads`.

**(b) N independent TP1 replicas — the recommendation.** `est.`

```
weights/GPU 4.426 GB   KV budget/GPU 59.21 GiB (63.57 GB)
  N       8K      32K     128K      1M  23.5K(video) | FP8 KV       8K      32K     128K      1M    23.5K
  1      528      150       38       4           206 |            909      287       77       9      387
  2     1056      300       76       8           412 |           1818      574      154      18      774
  4     2112      600      152      16           824 |           3636     1148      308      36     1548
  8     4224     1200      304      32          1648 |           7272     2296      616      72     3096
 16     8448     2400      608      64          3296 |          14544     4592     1232     144     6192
```

**8 replicas beat TP8 on every column** (4,224 vs 3,828 effective 8 K seats once KV replication is
counted, and with zero collective traffic). **Minimum GPUs = 1. Recommended = 1 per replica.**
**No multi-node fabric is needed at any scale** — this model never crosses a GPU boundary, so the
METHODOLOGY §4 20–40 % multi-node TP penalty and the whole NVLink-domain argument in
[gpus/h100.md §4](../../gpus/h100.md) are irrelevant here. Scale-out is a load balancer, not a fabric.

| `model.norm` | 2,048 | ❌ | — |
| `self_attn.q_norm` / `k_norm` (12 × 256) | 3,072 | ❌ (per-head RMSNorm) | — |
| `linear_attn.norm` (18 × 128) | 2,304 | ❌ | — |

## 3. Throughput and latency

Model constants: weights read per decode step = `2 × 1,881,825,088 = 3.7637 GB` (the 331 M-param
vision tower is **not** read during decode); KV read = `batch × ctx × 12,288`;
`prefill_linear(T) = 2 × 1,881,825,088 × T`; `attention_flops(T) = 24,576 · T²`;
ViT = 272.2 GFLOP/frame.

### 3.6 Why estimate and measurement would differ, concretely

The estimates above are a roofline. Five named reasons they will read high on a real H100:

1. **No GDN-kernel term.** 18 of 24 layers run a chunked-scan recurrence whose cost is kernel
   efficiency, not FLOPs. FlashQLA's own numbers show a **2.2–2.9× spread between two real kernels**
   for the same math — an uncertainty band wider than anything else in this document, and vLLM on
   sm_90 lands on FlashInfer, whose position in that spread is unpublished ⚠️.
2. **No sampling term.** At batch 834 the sampler handles `834 × 248,320` logits per step; the lm_head
   GEMM is counted (it is inside the 1.8818 B), the softmax/top-p passes over ~830 MB of logits are
   not. Expect a low-single-digit-ms addition per step at the ceiling.
3. **Scheduler and Python overhead dominate at 2 B.** The weight read is only 3.76 GB; a step at
   batch 1 is 1.75 ms, which is the regime where vLLM's per-step host work is a visible fraction.
   CUDA graphs are essential, and their capture has a known assertion failure against the mamba cache
   (§2).
4. **Video I/O is probably the real bottleneck.** The PyNvVideoCodec result exists precisely because
   CPU video decode saturates before 4 H100s. [architecture.md §10.3](architecture.md) flags the same
   thing from the author's demo Space: 75–180 s reservations against a few seconds of predicted GPU
   work. **`torchcodec` throughput for 240 frames at 448×448 is unmeasured everywhere** ⚠️.
5. **`multi_find` is N sequential requests plus ffmpeg re-encoding** that the GPU roofline cannot see
   ([architecture.md §1.4](architecture.md)).

### 4.5 Effect of prefix caching and speculative decoding on cost

**Prefix caching — worth $0 on this workload.** The arithmetic if you could get hits:

```
  S1 4K        hit    0%: TTFT     39.5 ms (100.0% of miss), input $/1M at low = 0.00857
  S1 4K        hit   50%: TTFT     19.6 ms ( 49.6% of miss), input $/1M at low = 0.00426
  S1 4K        hit   90%: TTFT      3.9 ms (  9.9% of miss), input $/1M at low = 0.00085
  S2 32K       hit   90%: TTFT     31.5 ms (  9.1% of miss), input $/1M at low = 0.00085
  S3 128K      hit   90%: TTFT    130.3 ms (  7.2% of miss), input $/1M at low = 0.00088
  video 23.5K  hit   90%: TTFT    187.6 ms ( 46.0% of miss), input $/1M at low = 0.00708
```

The video row saturates at 46 % of the miss cost even at a hypothetical 90 % hit, because **the ViT
must re-run on every new video regardless** (165 ms of the 408 ms). And the achievable hit rate is
**~0 %** for three independent reasons, any one sufficient: (i) every request carries a different
video, and the cacheable scaffold is < 0.2 % of the prompt
([architecture.md §5.5](architecture.md)); (ii) vLLM sets the hybrid block size to the mamba page
size, **528 tokens**, and a 40-token scaffold fills no block at all — measured QPS in that issue fell
from 200 to < 100 simply by crossing below the block boundary
[src](https://github.com/vllm-project/vllm/issues/40696); (iii) `--mamba-cache-mode=align` prefix
caching is "currently experimental" for this architecture and `"all"` is a hard error
([architecture.md §5.5](architecture.md)). Leaving APC on with zero overlap has a measured cost of
its own — **−36.7 % throughput** on 2024-era vLLM ([serving-optimizations.md §1.2](../../cross-cutting/serving-optimizations.md)),
⚠️ unremeasured on 2026 software. **Recommendation: leave `--enable-prefix-caching` off and measure
before turning it on.**

**Speculative decoding — unavailable, and the gain would be smaller than it looks.** No drafter
exists: zero `mtp` tensors in the checkpoint. If one did, with the verification compute counted:

```

```

**The 0.7 and 0.6 acceptance rates above are illustrative constants, not measurements** — no
acceptance rate for any Qwen3.5 MTP head is published ([architecture.md §7.3](architecture.md)), and
this repo's one nearby number, DSpark 3.51 in the MI355X recipe, is a **synthetic benchmark
constant** for a different model family (METHODOLOGY §8). The roofline above also overstates the
high-batch case: [serving-optimizations.md §4.3](../../cross-cutting/serving-optimizations.md)
records real large-γ speculation moving the frontier **inward** at high concurrency, and the
InferenceX Qwen3.5 H100 rows in §3.5 show MTP giving +41 % at conc 32 but being dropped entirely from
the conc-64+ configurations. And for `.find()` — 167.6 TFLOP of prefill against 64 decode steps —
speculation cannot touch the dominant cost at all.

API and monetises via custom fine-tuning by email. ⚠️ **TO BE VERIFIED**: whether Fireworks, Together,
Replicate, Baseten, DeepInfra or SiliconFlow host it — none was found in this pass either.

So METHODOLOGY §6's "compare to the model vendor's public API price" **cannot be executed for this
pair**, and this document does not invent a comparator. What can be stated is the break-even, as a
function of whatever price a hosted alternative would charge:

```
break-even utilisation U vs an API price A ($/1M output tokens): U = (self-host $/1M out) / A
   API $ 0.10/1M out, low  : break-even U =  23.67%      high : 50.90%
   API $ 0.30/1M out, low  : break-even U =   7.89%      high : 16.97%
   API $ 1.00/1M out, low  : break-even U =   2.37%      high :  5.09%
   API $ 3.00/1M out, low  : break-even U =   0.79%      high :  1.70%
```

Read it as: **a single rented H100 at $3.20/hr beats a $0.30/1M-output API as soon as you keep the
card busy 7.9 % of the time.** For any plausible hosted price, self-hosting wins at trivial
utilisation — which is the expected answer for a 2 B model, and is why the real decision for this
pair is engineering effort and video-pipeline throughput, not $/token.

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

**Single GPU per replica; 8 replicas per HGX H100 node; never multi-node for one replica.** The model
is 4.426 GB. There is no weight-sharding reason, no KV-capacity reason (§1.2), and no MoE to
expert-parallelise. Concretely:

- **TP > 2 is a downgrade**: `num_key_value_heads = 2` caps clean KV sharding at 2, and H100's
  measured KV-inclusive MBU falls from 66.7 % at TP2 to 37.4 % at TP8
  ([gpus/h100.md §9.3](../../gpus/h100.md)).
- **PD disaggregation does not pay here.** It is a "thousand-GPU problem"; below that it costs
  −20–30 % ([serving-optimizations.md §4.3](../../cross-cutting/serving-optimizations.md)). A
  disaggregated 2 B model would spend more time moving a 0.287 GiB KV blob than saving.
- **Wide-EP / DeepEP / EPLB: not applicable.** No experts.
- **The one disaggregation worth evaluating is EPD** (encode / prefill / decode) — because the ViT is
  39 % of prefill FLOPs and the video decode is a separate resource entirely. ⚠️ no H100 video
  measurement exists; the only published EPD number is +25 % throughput on GB200 images
  ([serving-optimizations.md §6.2](../../cross-cutting/serving-optimizations.md)).
- **What *does* scale is replicas.** NVIDIA's own H100 video-captioning deployment is *"one container
  per vLLM server replica … exposing a single GPU to each container … a reverse proxy to distribute
  requests among the vLLM replicas"* [src](https://vllm.ai/blog/2026-09-18-pynvvideocodec).

### 5.2 Launch commands

**(a) vLLM — architecture remap + hybrid flags.** From [architecture.md §8.1](architecture.md); the
`--hf-overrides` form is documented vLLM API for exactly this remapping, the supported-models page
giving the same shape for other models
[src](https://docs.vllm.ai/en/latest/models/supported_models.html):

```shell
vllm serve NemoStation/Marlin-2B --port 8000 --tensor-parallel-size 1 \
  --hf-overrides '{"architectures": ["Qwen3_5ForConditionalGeneration"]}' \
  --max-model-len 32768 --mamba-cache-mode=align \
  --media-io-kwargs '{"video": {"num_frames": -1}}'
```

`--mamba-cache-mode=align` is **not optional** — *"Qwen3.5 currently does not support 'all' prefix
caching, please use '--mamba-cache-mode=align' instead"* is a raised `NotImplementedError` in vLLM's
`qwen3_5.py` ([architecture.md §5.5](architecture.md)); the Qwen3.5 recipe repeats it: *"The
`--mamba-cache-mode align` flag is required (GDN does not support the all mode)"*
[src](https://docs.vllm.ai/projects/recipes/en/stable/Qwen/Qwen3.5.html).

**(b) The H100 video-captioning shape, verbatim from NVIDIA/vLLM** — this is the command whose
scaling was measured on 8 × H100, and the one to adapt (substituting the Marlin model id and the
remap above) [src](https://vllm.ai/blog/2026-09-18-pynvvideocodec):

```bash
# First launch CUDA MPS Daemon
nvidia-cuda-mps-control -d

# Launch vLLM with pynvvideocodec video backend
vllm serve Qwen/Qwen3-VL-8B-Instruct \
  --dtype bfloat16 \
  --max-model-len 32768 \
  --max-num-seqs 1024 \
  --max-num-batched-tokens 32768 \
  --api-server-count 4 \
  --renderer-num-workers 4 \
  --async-scheduling \
  --mm-ipc-gpu-memory-gb 2 \
  --media-io-kwargs \
    '{"video":{"backend":"pynvvideocodec","min_frames":16,"max_frames":16,"hw_decoders":2}}' \
  --mm-processor-kwargs \
    '{"size":{"shortest_edge":65536,"longest_edge":9437184}}'
```

Notes when adapting it to Marlin: set `min_frames: 4, max_frames: 240` and the Path-A pixel budget
(`VIDEO_MAX_PIXELS=200704`, `FPS=2.0`) or the HF video processor silently gives the model **half the
frames or half the resolution** the training-time path used — a 1.914× budget mismatch
([architecture.md §6.3](architecture.md)). `--max-num-seqs 1024` matters: the S1 ceiling is 834 seats
and vLLM's older default of 256 would leave two-thirds of the KV pool idle. *"CUDA MPS is essential
for good performance with multi-process high concurrency work such as bulk VLM inference"* — same
source.

**(c) transformers — the first-class path**, from the model card
([architecture.md §8.6](architecture.md)):

```bash
pip install "transformers>=5.7.0" "torch>=2.11.0" torchcodec "qwen-vl-utils>=0.0.14" av pillow
```

```python
marlin = AutoModelForCausalLM.from_pretrained(
    "NemoStation/Marlin-2B", trust_remote_code=True,
    dtype=torch.bfloat16, device_map={"": "cuda"})
marlin.compile()
result = marlin.caption("video.mp4")                                 # max_new_tokens=2048
```

**(d) SGLang** — same remap; and on H100 set the GDN prefill backend explicitly, because SGLang's
FlashInfer auto-selection for GDN is documented for **SM100/SM103**, not SM90
([flash-attention.md §14.3](../../cross-cutting/flash-attention.md)):

```shell
python -m sglang.launch_server --model-path <marlin-with-remapped-architectures> --port 8000 \
  --tp-size 1 --mem-fraction-static 0.8 --context-length 32768 \
  --linear-attn-prefill-backend flashinfer
```

⚠️ SGLang video ingestion for this class is unconfirmed ([architecture.md §8.4](architecture.md)).

**Flags to also set, from the sources:** both EOS ids `[248044, 248046]` (the config's top-level
`eos_token_id` misses one — [architecture.md §1.3](architecture.md)); `--mm-encoder-tp-mode data` and
`--mm-processor-cache-type shm` if TP is ever raised; a reduced `--max-cudagraph-capture-size` if the
`causal_conv1d_update` assertion fires
[src](https://docs.vllm.ai/projects/recipes/en/stable/Qwen/Qwen3.5.html); and a client-side
`<think>`-prefix strip, since the remap loses `modeling_marlin.py`'s regexes.

### 5.3 Warm-up and loading

`est.` — checkpoint 5,443,602,048 B on disk, 4.426 GB resident:

```
   5 GB/s: checkpoint 5.444 GB ->  1.09 s read; resident 4.426 GB ->  0.89 s
  10 GB/s: checkpoint 5.444 GB ->  0.54 s read; resident 4.426 GB ->  0.44 s
  20 GB/s: checkpoint 5.444 GB ->  0.27 s read; resident 4.426 GB ->  0.22 s
  8 replicas from one NVMe at 10 GB/s, cold page cache: 4.4 s if serialised
```

**Weight load is under 1.1 s in every case and is not the warm-up cost.** What dominates a cold start
is: CUDA context creation, **CUDA-graph capture** (which allocates *outside* `--gpu-memory-utilization`
— [serving-optimizations.md §4.2](../../cross-cutting/serving-optimizations.md)), and the
**FlashInfer GDN prefill JIT warm-up**, which vLLM explicitly warns about on the Hopper branch
([flash-attention.md §14.3](../../cross-cutting/flash-attention.md)). ⚠️ none of those three is
measured for this model; budget tens of seconds, not the 0.5 s of I/O. Firing 8 replicas from one
NVMe simultaneously will also contend — stagger them or pre-warm the page cache (5.4 GB fits in host
RAM trivially).

## 6. Risks and open questions

**⚠️ TO BE VERIFIED — carried forward from the source documents**

1. **The vLLM remap has never been run.** That all 618 tensor names map 1:1 onto
   `Qwen3_5ForConditionalGeneration`'s loader, and how vLLM handles the materialised `lm_head.weight`
   against `tie_word_embeddings: true`, are both read-verified and run-unverified
   ([architecture.md §8.1](architecture.md)). Most likely benign. Budget an afternoon of validation.
2. **Which GDN kernel vLLM actually dispatches on sm_90, and where it sits in the 2.2–2.9× FlashQLA
   spread.** vLLM's resolver says FlashInfer on Hopper; FlashQLA lists SM90 but is a separate library
   nothing in the engine calls. This is the **largest single uncertainty in §3** — it applies to 18
   of 24 layers.
3. **SGLang on H100 probably runs Triton GDN** (the FLA baseline), i.e. the slow end of that spread,
   because its FlashInfer auto-selection is documented for SM100/SM103 only. Unmeasured.
4. **`torchcodec` / video-decode throughput for 240 frames at 448×448 is unmeasured everywhere**, and
   the one published H100 datum says CPU decode saturates before 4 GPUs. The GPU roofline in §3 may
   be describing a resource that is never the bottleneck.
5. **Path A vs Path B video-token budget disagree by 1.914×** — `qwen-vl-utils` env vars give 23,520
   tokens, the HF `Qwen3VLVideoProcessor` config gives 12,288. An engine ingesting through the HF
   processor silently halves the model's input. Resolving it requires running both and comparing
   output ([architecture.md §6.3](architecture.md)). **Every number in this document assumes Path A.**
6. **`--mamba-ssm-cache-dtype bfloat16`**: unverified whether it is honoured for this model; would
   halve the GDN state (immaterial to capacity, §1.3).
7. **Conv-state width**: vLLM may store `kernel` rather than `kernel − 1` (+1.1 % state, immaterial).
8. **KV-head replication above TP2** is standard GQA-TP behaviour but no first-party vLLM page
   fetched this session states it for `tp_size > num_kv_heads`.
9. **FA4 on sm_90** has no published TFLOPS; FA3 is the shipped default and what §3 assumes.
10. **EPD disaggregation for video on H100** — no measurement.
11. **No hosted Marlin API anywhere** — so METHODOLOGY §6's vendor sanity check cannot be run, and the
    break-even in §4.6 is parametric rather than concrete.
12. **Whether the fused CUDA GDN decode kernel is actually built** in the wheel you install — vLLM
    falls back to Triton *silently* if `torch.ops._C.fused_gdn_decode_post_conv_mtp` is missing.

**Accuracy caveats of the executed precision**

- **BF16 native: none.** The checkpoint is unquantised and H100 executes BF16 natively at
  989.5 dense TFLOPS. There is no dequantisation path, no block-scale approximation, no emulation.
  This is the cleanest precision story of any pair in this repo.
- If you quantise anyway: the two published quantisations (`SDNQ-int8`, `GPTQ-4BITS`) both touch only
  the **1,372,717,056 language linear weights** and keep embeddings, `lm_head`, norms, conv1d, SSM
  parameters and the whole vision tower in BF16 ([architecture.md §3.6, §9](architecture.md)).
  **No accuracy evaluation of either has been published** ⚠️ — and a temporal-grounding model whose
  headline metric is mIoU against second-precise timestamps is exactly the kind of model where a
  4-bit language tower could degrade silently. The model's own benchmark claims are vendor marketing
  with no numeric table ([architecture.md §10.1](architecture.md)), so you would have no baseline to
  regress against.
- **If FP8 KV is enabled**: 1–2 points on reasoning benchmarks is the general finding, but the
  `head_dim = 256` prefill regression and the open FA3 logprob-mismatch bug above are the
  shape-specific risks, and neither has been evaluated on a timestamp-grounding task ⚠️.

**The biggest non-GPU risk**: `.find()`'s docstring warns it *"always emits some span"*
([architecture.md §1.4](architecture.md)) — so a `multi_find` sweep spends real GPU money producing
low-confidence later spans. That is a cost driver no roofline captures.
