## 0. Verdict

1. **Runnable today, and this is the one GPU where that is not in doubt**: NVIDIA validated *this exact checkpoint* on **GB300**, on **vLLM** (`vllm/vllm-openai:deepseekv41-flash-0909`) and **SGLang** (`lmsysorg/sglang:dev-cu13-dsv41`, commit `da64c5cbb8cf6bfd39be19da43573fdfd484c43a`), both at **TP4** on **4 GB300 GPUs** [src](https://huggingface.co/nvidia/DeepSeek-V4.1-Flash-NVFP4/raw/main/README.md); neither engine has a numbered release carrying `DeepseekV41ForCausalLM` — both are main/preview builds ([inference-engines.md §6.1](../../cross-cutting/inference-engines.md), [§6.2](../../cross-cutting/inference-engines.md)).
2. **Min 4 GPUs** (TP2 = 264.9 GB/GPU of weights against a 251.1 GB usable budget → negative KV budget, `infeasible (KV)`); **recommended 4 GPUs TP4** (the only validated shape) or **8 GPUs TP8/TP4+DP2** when you want KV headroom, with the full 72-GPU rack useful only as *many replicas + wide-EP*, never as one TP domain.
3. **Weight format actually executed: native NVFP4 W4A4 on the routed experts (58.0 % of bytes) via `flashinfer_trtllm_routed`, FP8/MXFP8 for the other 42 %** — no dequant, no Marlin fallback, no emulation. GB300 `sm_103` is the format's home silicon ([quantization-formats.md §5, §9.2](../../cross-cutting/quantization-formats.md)).
4. **Interactive (S1, 4K in / 512 out, TPOT ≤ 50 ms, conc 256 on 4 GPUs): $1.24 per 1M output tokens** at the only published GB300 on-demand rate (OCI $18.00/GPU-h), **$0.159–$0.344** at the SemiAnalysis volume/retail anchors; **max-throughput (S4, conc 1,024): $0.356 → $0.046–$0.099**. Blended (75 % in @ 50 % cached / 25 % out): **$0.331 (OCI) → $0.042–$0.092 (anchors)**. All `est.`
5. **Confidence: `estimate`.** Capacity, format support and engine support are `meas.`; every throughput and cost figure is roofline `est.` calibrated against the one published proxy (InferenceX GB300 NVL72, vLLM TP4, 8 concurrency points, `precision: fp4` but **checkpoint not identified by the API**). **NVIDIA publishes no tok/s, TTFT or TPOT for this checkpoint, and nobody has published a paired NVFP4-vs-base benchmark on any GPU** — so the central question, *does the NVFP4 build beat the 510.29 GB MXFP4 base on GB300*, is answered here **only by arithmetic**, and the arithmetic says **no**: §3.4 shows it is **2–5.7 % slower per decode step** and costs 4.25 GB/GPU more at TP4, because the extra scale byte per 32 weights is extra HBM traffic on a memory-bound decode. The only defensible reason to pick it is NVIDIA's group-16 accuracy audit (§6).

### 1.2 Which tensors cannot be sharded — stated explicitly

Per [architecture.md §3.3](architecture.md) and the reference
[`inference/model.py`](https://huggingface.co/nvidia/DeepSeek-V4.1-Flash-NVFP4/raw/main/inference/model.py):

| Tensor group | Bytes | Shardable? | Why |
|---|---|---|---|
| Routed experts (NVFP4) | 305,765,130,240 (284.77 GiB) | ✅ TP (per-column/row) **and** EP (per-expert) | the whole reason wide-EP exists |
| Engram lookup tables (FP8/MXFP8) | 202,758,032,400 (188.83 GiB) | ✅ by **row** — `ParallelEngramEmbedding` | a random-gather table, not a GEMM; also CPU-offloadable (`--engram-config '{"cpu_offload":true}'`, the vLLM H100/B300 profiles) ([inference-engines.md §3.6, §6.1](../../cross-cutting/inference-engines.md)) |
| Attention projections (FP8) | 5,070,131,200 | ✅ TP by head / by low-rank group (`o_groups: 8`, so TP > 8 splits a group) | `o_groups = 8` is a hard ceiling on clean output-projection sharding ⚠️ |
| Shared experts (FP8) | 1,416,960,000 | ✅ TP | always-on, one per layer |
| **`embed.weight` (BF16)** | **1,323,827,200** | ❌ **replicated in practice** | vocab-parallel embedding is possible but is not what the recipes do |
| **LM head (BF16)** | 1,323,827,200 | ✅ vocab-parallel | counted as shardable here |
| **Vision encoder + aligner (BF16)** | **970,536,960** | ❌ **replicated** — the recipes pass `--mm-encoder-tp-mode data`, i.e. **data**-parallel ViT, one full copy per rank ([inference-engines.md §6.1](../../cross-cutting/inference-engines.md)) | vLLM's NVFP4 recipe passes `--language-model-only` and does not load it at all |
| **MoE routers (`gate.weight`, FP32 `bias`, `bias_vl`)** | **157,409,280** | ❌ **replicated** | the router must score all 384 experts from every rank |
| **mHC (`hc_attn_fn`, `hc_ffn_fn`, FP32)** | **157,295,040** | ❌ **replicated** | the Sinkhorn-normalised 24×20480 mixing matrix acts across the 4-copy residual stream; it is a per-sublayer global mix |
| Norms, attention sinks, image tokens | 419,840 | ❌ replicated | trivial |
| **The compressed KV cache itself** | 890 B/token | ❌ **under TP** — `num_key_value_heads: 1`, so *every* TP rank holds a full copy | *"KV sharded by head — **but not for MLA**, which has one KV head, so every rank holds a full copy"* ([serving-optimizations.md §3.1](../../cross-cutting/serving-optimizations.md), [src](https://www.lmsys.org/blog/2026-07-27-kimi-k3-day0-support/)). Sharding it requires **DCP** (shard by token position, exact merge by log-sum-exp) or **DP-attention** (shard the batch). This is the single biggest lever in the fit table. |

**Replicated total = 2.609 GB = 2.430 GiB per GPU** (embed + ViT + routers + mHC
+ norms), which is small enough that it never changes a verdict — but the
**replicated KV cache does**, by a factor of `n_gpus`.

### 1.3 Fit over the GPU counts this topology allows

GB300 NVL72 = 18 compute trays × (2 Grace + 4 B300), one 72-GPU flat NVLink-5
all-to-all at 130 TB/s ([gb300.md §4.1, §4.3](../../gpus/gb300.md)). So the
allowed set is **{1, 2, 4, 8, 16, 18, 36, 72}** — 4 is one tray, 18 is one GPU
per tray (a valid but unusual EP shape), 72 is the rack.

* `est.`, `per_gpu_weights = (W − replicated)/n + replicated`,
  `kv_budget = 251.10 GB − per_gpu_weights − 4 GB`, all in bytes.
* **n = 1 and n = 2 are `infeasible (KV)`.** TP2 leaves −17.8 GB. This is the
  same verdict [architecture.md §5.6](architecture.md) reaches for HGX B300 at
  268 GB, and it holds here at 279 GB too — but note it **does** close against

  and why [architecture.md §12.7](architecture.md) keeps that as an open
  question. **Do not plan TP2.**
* **Engram CPU-offload makes TP2 fit** (83.5 GB of KV budget), because 202.76 GB
  of the checkpoint is a lookup table that is gathered, not GEMM'd. On GB300 the
  offload target is **Grace LPDDR5X at 900 GB/s NVLink-C2C** — ~9× a PCIe Gen5
  x16 link ([gb300.md §10.7](../../gpus/gb300.md)) — which makes this far more
  attractive here than on an x86 HGX node. **⚠️ TO BE VERIFIED:** no published
  GB300 run uses `--engram-config '{"cpu_offload":true}'`; the flag appears in
  vLLM's **H100 and B300** profiles ([inference-engines.md §3.6, §6.1](../../cross-cutting/inference-engines.md)), and the 12,672 B/token of
  scattered Engram gather ([architecture.md §6.3](architecture.md)) would then
  cross C2C on every token.

differs by `n_gpus`:

* **TP(repl)** — the binding reading for the validated TP4 recipe. MLA's single
  KV head means every rank carries a full copy, so the *per-GPU* budget caps
  concurrency no matter how many GPUs you add.
* **DP/DCP** — DP-attention or decode context parallelism shard the KV (by
  request or by token position), so the rack-aggregate budget applies.

**Reading this honestly.** The FP4 row is the *real* one — the FP8 and BF16
columns are printed because METHODOLOGY asks for them, but on GB300 there is
nothing to choose: the FP4 main-KV layout is baked into the architecture
(`kv_cache_quant_algo: null`), realised by `nvfp4_ds_mla` →
`FLASHMLA_MEGA_ATTN_DSV41` → `major == 10` only
([flash-attention.md §11](../../cross-cutting/flash-attention.md)), and `sm_103`
satisfies that gate. Running this model at FP8 KV on GB300 would be a
*downgrade* you would have to go out of your way to configure.

**The striking property, same as the base checkpoint: KV is not the binding
constraint.** At 4 GPUs and 128K context, 947 concurrent sequences fit even
under the pessimistic replicated reading — and NVIDIA's own recipes cap at
`--max-running-requests 16` (SGLang) and `--max-num-seqs 32` (vLLM). The gap
between 16 and 947 is not a memory fact; it is an untuned configuration, and
nobody has published the tuned number ([architecture.md §8.6](architecture.md)).
The measured InferenceX GB300 run sits at a **68.4 M-token KV pool ≈ 60.9 GB**
against a 453.3 GB rack-slice budget — evidently capped by engine configuration,
not capacity (an open question in [architecture.md §12.16](architecture.md)).

**Multi-node fabric needed?** No, at any shape in this table. 4/8/16/18/36/72 all
live inside one NVL72 domain at NVLink-5 speed. Crossing racks drops you to
800 Gb/s/GPU over ConnectX-8 IB — an ~18× cliff that is fatal for MoE
all-to-all ([gb300.md §4.4](../../gpus/gb300.md)). Multi-rack only matters if
you want more than 72 GPUs of *replicas*, and then each replica still lives in
one rack.

`est.`, `prefill_time(T) = T × [2·p_fp4/(15e15·MFU) + 2·p_fp8/(5e15·MFU) +
2·p_bf16/(2.5e15·MFU) + (attn_flop + indexer_flop(ctx))/(5e15·MFU)] × 1.10`,
with the encoder-only active split (CED: prefill runs 20 layers, decode 40) and

**Two things worth extracting from this table.**

1. **Prefill is context-independent until ~128K, then the indexer bites.**
   Attention costs a flat 3.221 GFLOP/token regardless of context
   ([architecture.md §6.2](architecture.md)); what grows is the four *full-pool*
   indexers, which reach **21.47 GFLOP/token at 1M** — more than the entire
   encoder forward pass. That is why the 1M row is 2.5× slower per token than
   the 4K row. **⚠️ TO BE VERIFIED** whether production kernels bound those four
   the way the reference implementation does not.
2. **The commonly-quoted prefill figure for this model is ~2.4× too high for
   *this* checkpoint.** [gb300.md §9.3](../../gpus/gb300.md) lists
   *"DeepSeek-V4.1-Flash, prefill (8 B active): 234,375 tok/s/GPU at NVFP4,
   MFU 0.25"* — that assumes **all** 8 B of active params execute at the 15,000
   TFLOPS NVFP4 rate. In this checkpoint only **52 %** of decode-active and a
   similar share of prefill-active params are NVFP4; attention, shared experts
   and the Engram projection are FP8 at 5,000 TFLOPS. Recomputing with the
   mixed split gives **97,246 tok/s/GPU at 4K** — 2.4× lower. The gb300.md
   figure is a correct *format* roofline and a wrong *checkpoint* roofline.

```

     1       6.0          12.25           12.49               2.02%                      2.00%
     8      45.5          39.88           41.75               4.70%                      4.58%
    32     152.0         114.51          120.77               5.47%                      5.28%
    64     243.8         178.83          188.87               5.62%                      5.37%
   128     332.8         241.16          254.87               5.69%                      5.31%
   256     377.2         272.22          287.76               5.71%                      5.08%
```

Read that carefully, because it is the finding this document exists to produce.

* GB300 executes **both** formats natively on the same `tcgen05` block-scaled
  datapath — FlashInfer implements *"FP4 GEMM: NVFP4 **and MXFP4**"*
  [src](https://github.com/flashinfer-ai/flashinfer), and NVIDIA publishes no
  table separating their rates ⚠️ ([gb300.md §11.13](../../gpus/gb300.md)). So
  the compute side is, to the best available evidence, **a wash**.
* The decode step on this model is **memory-bound at every concurrency in the
  table** (the `bound` column in §3.2 reads `mem` throughout). NVFP4's finer
  scale layout is **+5.88 % bytes per routed expert** — one extra scale byte per
  32 weights. On a memory-bound step, extra bytes are extra time, **full stop**.
* Net: the NVFP4 build is `est.` **2.0 % slower at batch 1 and ~5.1–5.4 % slower
  from batch 32 up**, and costs **4.25 GB/GPU more at TP4** (3.6 % of the KV
  budget, 36 seats at 128K).
* **What it buys**: NVIDIA's group-16 accuracy audit — all 16,986,931,200 blocks
  losslessly converted, 1,024 calibration samples, and a six-benchmark eval that
  is a **wash** (+0.40 points mean, NVFP4 winning 4 of 6 within ±1.5 points)
  ([architecture.md §10.1](architecture.md),
  [quantization-formats.md §9.2](../../cross-cutting/quantization-formats.md)).
  It also buys **W4A4** — the activations are quantised too, where the base's
  DeepGEMM MegaMoE path was W4A8 until SGLang PR #25052 added a **MXFP4 W4A4**
  option to the *base* path too [src](https://pytorch.org/blog/serving-deepseek-v4-on-gb300-with-sglang-5x-higher-throughput-at-the-same-interactivity-since-day-0/),
  narrowing even that differentiator.

**Verdict: on GB300 the NVFP4 build is a slightly worse-performing artifact with
a better-documented accuracy story.** Pick it if you are running a
Blackwell-only fleet and want NVIDIA's audit behind the numbers; pick the base
`deepseek-ai/DeepSeek-V4.1-Flash` for everything else, including every mixed
fleet, because it is smaller, marginally faster here, and the only artifact with
first-class Hopper, sm_120 and MI355X recipes
([quantization-formats.md §9.2](../../cross-cutting/quantization-formats.md)).
⚠️ This conclusion is **arithmetic, not measurement** — a paired benchmark would
settle it in an afternoon and nobody has run one.

### 3.6 Estimated vs measured — where the gap is, and why

```
measured InferenceX GB300 TP4 vLLM rows vs this roofline at S3 (128K):
 conc  meas TPOT ms  est TPOT ms  meas/est  meas out tok/s/GPU  est out tok/s/GPU  meas mean input

    4          2.22         1.37      1.62                63.8              730.7          188,073
    8          2.46         2.26      1.09               112.0              886.1          159,245
   16          3.27         3.88      0.84               178.6             1031.0          154,107
   32          4.76         6.59      0.72               333.5             1213.9          177,581
   64         12.39        10.40      1.19               636.3             1538.0          134,713
  128         25.10        14.33      1.75               887.1             2233.4          114,166
```

Four distinct effects, and they pull in opposite directions:

1. **Batch 1–4: the roofline is 1.6–3.2× optimistic.** At 3.37 GB/step/GPU the
   step is dominated by kernel launch and scheduling, not bandwidth. Effective
   MBU is ≈ **0.22** at batch 1, not 0.70. This is the standard small-batch
   collapse and [architecture.md §6.3](architecture.md) flags the same ~3.5×
   gap. **Do not plan batch-1 latency from a roofline on this model.**
2. **Batch 16–32: the roofline is 20–28 % *pessimistic*.** The measured rows run
   with speculation on (`spec_method: "mtp"`, i.e. the in-checkpoint DSpark
   drafter), so each wall-clock step emits more than one accepted token — the
   published TPOT is per *accepted output token*, not per forward pass. That is
   exactly the regime where draft tokens are nearly free
   ([serving-optimizations.md §2.5](../../cross-cutting/serving-optimizations.md)).
3. **Batch 64–128: the roofline is 1.2–1.75× optimistic again.** Two causes.
   (a) The verify pass stops being free — *"at concurrency 256, draft tokens
   compete with real tokens for the same compute"*
   [src](https://vllm.ai/blog/2026-08-14-dspark-adaptive-verification). (b) The
   measured mean input is **114K–307K tokens**, not my 128K — and crucially the
   indexer scan term `ctx × 170 B` per sequence per step is the one part of KV
   read that grows, so a 307K-token trace at batch 1 reads 2.4× the indexer
   bytes my 128K assumption gives.
4. **Output tok/s/GPU is 5–9× below the roofline at every concurrency, and that
   is the workload, not the hardware.** The InferenceX trace generates ~1,000
   output tokens against 114K–307K input at 96–98 % prefix-cache hit. The GPU is
   overwhelmingly doing cache lookup and indexer work, not decode. Read the
   `all tok/s/GPU` column instead: **102,318 tok/s/GPU at concurrency 128** is a
   genuinely large number and is what that workload actually produces.

**Net calibration guidance:** for a 4K–32K interactive workload on 4 GB300 GPUs,
treat the §3.2 roofline as an upper bound and apply **×0.5–0.7** above batch 64;
below batch 8, ignore it entirely and use ~400–500 tok/s/user as the
single-stream figure implied by the measured 2.1–2.5 ms TPOT.

**Prefix caching** (self-hosted, ~10 % of uncached prefill cost per

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

Everything in §1 fits inside **one GB300 NVL72 rack**, and the interesting
shapes fit inside **one or two 4-GPU compute trays**. There is no multi-node
question for this model on this rack — only a *replica* question.

| Shape | When | Why |
|---|---|---|
| **4 GPUs, TP4, one tray** | default; the only validated configuration | 133.8 GB/GPU of weights, 113.3 GB/GPU of KV budget, 947 seats at 128K even with replicated KV. Both NVIDIA recipes are exactly this. |
| **8 GPUs, TP8** | when you want KV headroom or lower single-stream latency | 178.9 GB/GPU KV budget, 1,496 seats at 128K; TPOT halves. **⚠️ `o_groups: 8` means TP8 puts exactly one output-projection group per rank — TP16 splits a group and is unexplored.** |
| **4 GPUs TP4 + DP2 across 2 trays** | better than TP8 for throughput | DP-attention shards the batch, so aggregate KV scales ×2 and you avoid TP8's wider AllReduce. Unvalidated for V4.1 ⚠️ |
| **18 replicas of 4 GPUs** (or 9 of 8) | **the rack shape I would actually deploy** | 18 independent TP4 servers behind one router, 18 × 16,136 = ~290K aggregate output tok/s at S1 `est.`, no all-to-all, no cross-tray failure domain. KV pooling across the rack is the *only* thing you give up, and §1.4 says you have KV to spare. |
| **1P1D disaggregation, TP4 + TP4** | long-context agentic traffic | **TokenSpeed runs exactly this as a per-commit GB300 Slurm CI job** [src](https://lightseek.org/tokenspeed/recipes/models) — for the **base** repo, not the NVFP4 one ⚠️ |
| **Wide-EP across 32–72 GPUs** | ⚠️ not for this model, not yet | See below. |

### 5.2 When PD disaggregation pays here — and it should

The CED architecture makes this pair an unusually good disaggregation candidate:
**prefill activates 7.89 B params over 20 encoder layers; decode activates
15.75 B over all 40 plus the LM head** ([architecture.md §3.2](architecture.md)).
The two phases have genuinely different arithmetic intensity and different
optimal parallelism (PP for prefill, EP/DP for decode —
[serving-optimizations.md §3.2](../../cross-cutting/serving-optimizations.md)),
and the NVL72 domain makes the KV hand-off nearly free at 1.8 TB/s/GPU rather
than 800 Gb/s.

Measured support on this GPU: DeepSeek-V3.2 on GB300 kept **TPOT under 60 ms at
batch 256 disaggregated vs > 80 ms integrated**
[src](https://vllm.ai/blog/2026-02-13-gb300-deepseek); the SGLang GB300 disagg
lane for DeepSeek-V4-Pro reached ~11,200 tok/s/GPU at ~50 tok/s/user
[src](https://pytorch.org/blog/serving-deepseek-v4-on-gb300-with-sglang-5x-higher-throughput-at-the-same-interactivity-since-day-0/).

Against that: *"disaggregation is a thousand-GPU problem"* — at small GPU counts
rounding losses dominate and Modular reports a **20–30 % performance drop** on
small or untuned workloads
([serving-optimizations.md §3.5](../../cross-cutting/serving-optimizations.md)).
A 1P1D pair here is 8 GPUs. **Rule for this pair: aggregate below ~16 GPUs,
disaggregate above it, and only for the 128K+ agentic traffic.** Also note the
SGLang constraint: **PD and speculative decoding cannot be combined**, and with
vLLM, *"DSpark must run in both pools so the transferred KV stays compatible"*.

### 5.3 When wide-EP pays — currently, it does not

384 routed experts across 72 GPUs is 5.3 experts/GPU, squarely inside NVIDIA's
4–32 wide-EP band, and the routed experts (284.77 GiB) are 58 % of the
checkpoint — so on paper this is a textbook wide-EP model. Three facts say wait:

1. **The only published EP run on this model family is a disaster.** B200
   SGLang TP4/EP4 peaks at 11,003 tok/s/GPU against vLLM EP1's 92,073 on the
   same traces, and collapses past concurrency 32 (TTFT 713 s at 128)
   ([architecture.md §10.2](architecture.md)). ⚠️ Very likely an untuned
   configuration rather than an engine property — but it is what is published.
2. **DeepEP publishes no SM103 row.** Its numbers cover SM90 and SM100
   ([gb300.md §10.6](../../gpus/gb300.md)).
3. **The model does not need the rack to hold its experts.** DeepSeek-R1's
   256 experts need 64 GPUs to sit once — that is the classic NVL72 argument.
   This model's entire 527 GB fits in **4** GPUs. Wide-EP here buys smaller
   per-GPU expert reads, which is a throughput optimisation on a model that is
   already cheap to read, not a feasibility requirement.

**Revisit when** a tuned SGLang EP result for V4.1 is published, or when DeepEP
ships an SM103 perf table.

```bash
  --tp 4 --ep-size 4 --mem-fraction-static 0.8 \
  --speculative-algorithm DSPARK --speculative-dspark-block-size 5 \
  --cuda-graph-max-bs-decode 64 \
  --reasoning-parser auto --tool-call-parser auto \
  --host 0.0.0.0 --port 30000
```

GB300/GB200 NCCL env that vLLM's recipes call out and NVIDIA's NVFP4 command
omits: `NCCL_MNNVL_ENABLE=1`, `NCCL_CUMEM_ENABLE=1`, `NCCL_NVLS_ENABLE=1`
([flash-attention.md §9.4](../../cross-cutting/flash-attention.md)).

**Three flags in NVIDIA's own vLLM command deserve a second look** before you
copy it into production, all flagged in [architecture.md §8.2](architecture.md):
`--language-model-only` disables the vision tower (the model's headline
multimodal capability); `--no-enable-prefix-caching` forfeits the biggest win
available on the target workload; and `--max-num-seqs 32` against a 947-seat KV
budget at 128K is a factor of 30 of unused capacity.

### 5.5 Warm-up and loading

```
NVMe load times (527.27 GB):
  @   5 GB/s:  105.5 s (1.8 min); two 101.54 GB Engram shards alone  40.6 s
  @  10 GB/s:   52.7 s (0.9 min); two 101.54 GB Engram shards alone  20.3 s
  @  20 GB/s:   26.4 s (0.4 min); two 101.54 GB Engram shards alone  10.2 s
```

`est.` — 527,273,322,840 B ÷ sustained NVMe read, single stream, ignoring
page-cache and decompression.

Three operational facts on top of that number:

1. **Shard shape is a hazard.** 46 of the 48 shards are ≤ 7.81 GB; shards 47 and
   48 are **101.54 GB each** (the two Engram tables). A naive single-threaded
   `safetensors` load stalls on them — which is exactly why the card passes
   `--model-loader-extra-config '{"enable_multithread_load": true,
   "num_threads": 128}'` ([architecture.md §1.1](architecture.md)).
2. **The index file lies about the size.** `model.safetensors.index.json` carries
   the base checkpoint's `metadata.total_size = 510,286,023,000`; any loader
   sizing an allocation from it under-allocates by **17 GB**.
3. **Budget far more than the file-read time.** vLLM's own base env sets
   `VLLM_ENGINE_READY_TIMEOUT_S=3600` — an hour — because CUDA-graph capture
   (a 26-size ladder in the B300 profile), FlashInfer autotune, JIT and CuTeDSL
   warm-up dominate. The GB200 disagg profile disables several of these
   explicitly (`--kernel-config`, `VLLM_DEEP_GEMM_WARMUP=skip`)
   ([serving-optimizations.md §3.5](../../cross-cutting/serving-optimizations.md)).
   SGLang additionally prewarms MHC token-count buckets so first requests do not
   pay lazy compile costs [src](https://github.com/sgl-project/sglang/pull/25810).
   **Plan 5–15 minutes to a warm server, not 2.**

## 6. Risks and open questions

### 6.1 The one that decides whether to use this checkpoint at all

**R1. No paired NVFP4-vs-base benchmark exists, on GB300 or anywhere.** ⚠️
NVIDIA publishes zero throughput/latency numbers for this build; InferenceX does
not identify checkpoints; MLPerf does not carry the model. §3.4's conclusion
(NVFP4 is 2–5.4 % *slower* on a memory-bound decode, for 4.25 GB/GPU more) is
arithmetic on the byte counts and the `mem`-bound classification, both of which
are solid — but it is not a measurement. **This is the single highest-value
experiment in this document**: two containers, one tray, one afternoon.

### 6.2 Format and kernel

**R2. MXFP4-vs-NVFP4 rate parity on `sm_103` is undocumented.** ⚠️ Both use the
block-scaled `tcgen05` datapath and FlashInfer implements both, but NVIDIA
publishes no separate MXFP4 line ([gb300.md §11.13](../../gpus/gb300.md)). §3.4
assumes parity; if NVFP4 is actually *faster* per FLOP on sm_103, the verdict
flips.

**R3. NVFP4 backbone experts + MXFP4 MTP/DSpark experts in one process is
validated by nobody.** ⚠️ `ignore: ["mtp.*"]` leaves the 3 × 128 draft experts
MXFP4-packed while the 40 × 384 backbone experts are NVFP4. An engine must
instantiate two MoE quantisation methods in one model
([architecture.md §7.3](architecture.md)). Both run on Blackwell in principle;
nobody has exercised the combination — and NVIDIA explicitly *did not* run
speculation. **This is the most likely place for this checkpoint to break.**

**R4. The activation-scale contradiction inside the shipped config.** ⚠️
`config_groups.group_0.input_activations.dynamic = false` (static/calibrated)
versus the sibling top-level `activation_scheme: "dynamic"`. Both are in the
same `config.json`. Which one an engine honours — and therefore whether
activation scales are recomputed per batch — is unresolved
([architecture.md §1.2](architecture.md)). It is a W4A4 checkpoint, so this is
not cosmetic.

**R5. Accuracy caveats of the executed precision.** The eval is a **wash**, not
a win: NVFP4 takes 4 of 6 benchmarks by margins inside ±1.5 points on runs with
5–16 repeats ([architecture.md §10.1](architecture.md)). NVIDIA is careful about
this itself — *"Lossless weight conversion does not imply identical inference
outputs."* And **18 of 46,080 projection entries used fallback activation
scales** (0.04 %); which layers they sit on is ⚠️ unknown. Supporting evidence
that the recipe class is safe at long context: SGLang measured LongBench-v2
**57.2 %** on DeepSeek-R1-NVFP4 at 128K with NVFP4 weights + FP8 KV
[src](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/) — a different model,
but the same precision recipe on the same GPU.

**R6. flash-attn-4 rejects `sm_103` in some builds.** SGLang v0.5.12-cu130 +
`flash-attn-4>=4.0.0b9` crashes at warmup with
`AssertionError: Only SM 10.x and 11.x are supported`
[src](https://github.com/sgl-project/sglang/issues/25564); root-cause fix is
[Dao-AILab/flash-attention#2572](https://github.com/Dao-AILab/flash-attention/pull/2572).
This model's **language** attention never touches FA4, but the **ViT** does —
so it bites only if you serve images. Pin v0.5.11-cu130 or verify the
flash-attn-4 pin before standing up a fleet.

**R7. Sparse attention is not free on this GPU.** DeepSeek-V3.2's
Indexer/sparse-MLA path costs **2.7× the dense-MLA kernel time on GB300**
[src](https://vllm.ai/blog/2026-02-13-gb300-deepseek). §3.3's prefill roofline
charges the indexer its FLOPs but assumes it achieves the same MFU as a GEMM,
which that measurement suggests it does not. ⚠️ No published per-GPU top-k
kernel latency table exists
([flash-attention.md §6.3](../../cross-cutting/flash-attention.md)).

**R8. Do the production kernels bound the four full-pool indexers?** ⚠️ At 1M
context they cost 21.47 GFLOP/token — more than the entire encoder forward pass
— and the reference implementation does not bound them
([architecture.md §6.2](architecture.md)). The §3.3 1M row assumes they are not
bounded; if a kernel fixes this, 1M-context prefill gets ~2× faster.

### 6.3 Loading and memory

**R9. A community report of 14 consecutive failed boots of this exact
checkpoint.** On four **DGX Spark** (`sm_121`, not GB300), vLLM pinned to commit
`e47aa780b`: *"fourteen boots of `nvidia/DeepSeek-V4.1-Flash-NVFP4` that never
served"*, root-caused to *"COW-broken private mappings of the shards during the
fused-MoE expert copy"*; the partial mitigation
`--enable-expert-parallel --enable-ep-weight-filter` skipped 194.6 of 302 GiB
per rank and still did not serve
[src](https://github.com/tonyd2wild/DeepSeek-V4.1-Flash-vLLM-DGX-Spark).
**This is a different GPU, a different vLLM commit and a different memory
architecture from GB300**, where NVIDIA validated loading — but it is the only
independent attempt to boot this checkpoint that anyone has written up, and it
failed in the loader, not the kernel. Treat it as a reason to test the load path
with your own pin before committing, not as evidence against GB300.

**R10. `model.safetensors.index.json` still reports the base model's
`total_size`.** 510,286,023,000 against a true 527,273,322,840. ⚠️ Whether any
loader sizes an allocation from that field is unknown
([architecture.md §12.2](architecture.md)).

**R11. The capacity basis disagreement (279 vs 288 GB).** Declared in §1.1 and
quantified in §1.4 (~7 % on every concurrency figure at 4 GPUs). This document
uses 279; [architecture.md §5.6](architecture.md)'s GB300 row used 288. Neither
is wrong — they are different conventions for the same silicon — but a matrix
built across both will not add up. Someone should reconcile the two documents.

**R12. Engram CPU-offload on GB300 is untested.** ⚠️ §1.3 shows it makes TP2
fit and doubles the TP4 KV budget, and Grace's 900 GB/s C2C is the best offload
target in the fleet — but the flag appears only in vLLM's H100 and B300
profiles, and the 12,672 B/token of scattered per-token Engram gather would then
cross C2C on every token. Nobody has measured what that costs.

### 6.4 Engine and configuration

**R13. Neither engine has a numbered release.** vLLM's `main` registers
`DeepseekV41ForCausalLM`; `v0.29.0` and `v0.28.0` 404. SGLang's `main` has
`configs/deepseek_v41.py`; `v0.5.20` and `v0.5.19` 404
([inference-engines.md §6.1](../../cross-cutting/inference-engines.md)). You are
pinning a nightly or a dev image. The vLLM tracking issue
[#57448](https://github.com/vllm-project/vllm/issues/57448) (opened 2026-09-17 by
WoosukKwon) lists 16 open items of kernel and performance work still landing —
MegaAttention integration, sparse logits indexer, Mega mHC, MegaMoE padding
removal, a **FlashInfer DSpark attention bug fix**, Engram DP sharding. The
performance picture on this pair will move substantially, and
[gb300.md §11.12](../../gpus/gb300.md)'s rule applies: *"benchmark half-life is
about two quarters."*

**R14. TensorRT-LLM has no V4.1 entry at all** — the supported-models matrix has
V3, V3.2 and V4, no V4.1 row
[src](https://nvidia.github.io/TensorRT-LLM/models/supported-models.html). Since
every MLPerf GB300 record is TRT-LLM, this model is absent from the stack that
produces GB300's best published numbers.

**R15. SGLang's NVFP4-checkpoint support is on the roadmap, not done.** The
SGLang/NVIDIA GB300 retrospective lists, under *Roadmap*: *"Expand DeepSeek-V4
support on SM120/SM121 hardware as well as **NVFP4 checkpoints**"*
[src](https://pytorch.org/blog/serving-deepseek-v4-on-gb300-with-sglang-5x-higher-throughput-at-the-same-interactivity-since-day-0/).
NVIDIA's card says SGLang was *"validated through loading, generation,
reasoning/tool-call parsing, and image-input smoke tests"* — smoke tests, not a
performance sweep. ⚠️ The two statements are consistent, and together they mean
**SGLang is validated to run this checkpoint and is not yet optimised for it.**

**R16. Why is prefix caching off in NVIDIA's reference command?** ⚠️ Unstated.
The likely interaction is SWA Bounded Replay, whose windowed state must be
replayed from the last 128 tokens rather than restored
([architecture.md §8.2](architecture.md)); SGLang's own flag
`--enable-decoder-swa-bounded-replay` is *"validated on the decode path only,
refuses prompt logprobs by design, is not numerically equivalent to full
prefill, and is excluded at launch with the prefill CUDA graph and with DP
attention"* ([inference-engines.md §6.1](../../cross-cutting/inference-engines.md)).
That last exclusion matters here: **the DP-attention shape that fixes TP's
replicated KV (§1.4) is the same shape that disables the mechanism the model
relies on to avoid persisting SWA state.**

**R17. Nobody has published tuned concurrency settings.** `--max-running-requests
16` / `--max-num-seqs 32` against 947–11,113 seats of KV budget. Every throughput
number in §3.2 above concurrency 32 is therefore extrapolating past the largest
configuration anyone has run on this checkpoint.

**R18. No measured DSpark acceptance rate for this model, on any GPU.** ⚠️ The
3.51 in circulation is a synthetic benchmark constant. §4.4's cost effect spans
0.58× to 3.51× on that one unknown.

**R19. Pricing rests on a single published number.** `low = high = $18.00`,
Oracle OCI `BM.GPU.GB300.4`, and OCI is a hyperscaler at 2.2–2.4× neocloud rates
([cloud-pricing.md §5.9, §5.14](../../cross-cutting/cloud-pricing.md)). No 1-year
reserved rate is published for GB300 anywhere. Every $/token figure in §4 should
be read as a band from $2.31 to $18.00, not a point.

**R20. Rack power is vendor-sourced, not NVIDIA-sourced.** NVIDIA publishes no
GB300 NVL72 rack-power figure; Lenovo's product guide does — **135 kW TDP, up to
155 kW peak** (EDPp) — and that is what cloud-pricing.md's on-prem model uses.
Per-GPU power is **1,100 W** in both foundation docs as of 2026-09-19
([gb300.md §1.1, resolved 1,100 W](../../gpus/gb300.md),
[cloud-pricing.md §8.1–§8.2](../../cross-cutting/cloud-pricing.md)); the earlier
1.4 kW figure in gb300.md, and the 72 × 1.4 kW = 100.8 kW GPU-only estimate derived
from it, are withdrawn — at 1,100 W the GPU-only draw is 79.2 kW. The $2.569/GPU-h
on-prem anchor is rack-level and unchanged, but it still rests on a single OEM's
rack figure ⚠️.
