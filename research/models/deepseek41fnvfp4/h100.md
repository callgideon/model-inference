## 0. Verdict

1. **Not runnable in any supported sense today.** The checkpoint *loads* on
   `sm_90` — vLLM/SGLang fall back to **Marlin W4A16** for NVFP4 MoE — but NVIDIA
   scopes it to *"NVIDIA Blackwell"* only, no engine recipe lists an H100 target for
   it, and the NVFP4-MoE-on-Hopper Marlin path has an **open** correctness bug
   (vLLM #49070: garbage at concurrency 1, illegal memory access at concurrency ≈ 8;
   fix PRs #48929 / #48624 both still open). Engines: vLLM `main` (post-0.29.0,
   `min_vllm_version 0.30.0`, nightly) / SGLang `main` (`dev-cu13-dsv41`) — neither
   in a numbered release, neither validated off Blackwell.
2. **Min 8 GPUs, recommended 8 (one HGX node), TP8 + `--engram-config '{"cpu_offload":true}'`.**
   4 GPUs cannot hold 527.27 GB; 8 GPUs hold it with **0.62 GB/GPU** of KV left,
   which is 5 seats at 128K — the Engram CPU offload is not optional on H100.
3. **Weight format actually executed: NVFP4 dequantised to BF16 in the Marlin
   epilogue (W4A16).** Hopper has no FP4 tensor core; the 4-bit storage is kept, the
   FP4 math is not. Against the base MXFP4 checkpoint on the *same* Marlin path this
   build is **+16.99 GB of weights (−77 % of the TP8 KV budget without Engram
   offload) and +2.0 – 5.7 % of decode bytes per step, for identical math** — so on
   H100 it is strictly worse than `deepseek-ai/DeepSeek-V4.1-Flash`, which is the
   nearest runnable alternative and is marked `"h100": "verified"` by vLLM's recipe.
4. **Interactive (S1, 4K/512, TPOT ≤ 50 ms): $0.78 – $1.98 per 1M output tokens**
   ($2.72 reserved → $6.880 AWS on-demand), blended $0.216 – $0.546 per 1M.
5. **Max throughput (S4): $0.18 – $0.45 per 1M output**, blended $0.064 – $0.162.
   **Confidence: `estimate` (not measured for this checkpoint on this GPU; anchored
   to 12 measured InferenceX rows for the base checkpoint on 8×H100, §3.2).**

### 1.1 Which tensors cannot be sharded

| Tensor group | Bytes | Shardable on H100? |
|---|---|---|
| Routed experts (40 × 384 × {w1,w2,w3}), NVFP4 | 305.77 GB | **yes** — TP (column/row split of `moe_intermediate_size 2304`) or EP. ⚠️ `2304 / 8 = 288`, **not a multiple of 64**, which is exactly the Marlin tile-alignment class that crashes in vLLM #47769 (§6) |
| Engram lookup tables ×2, FP8 | 202.76 GB | **yes**, by row (`ParallelEngramEmbedding`) — or moved off-GPU entirely with `--engram-config '{"cpu_offload":true}'` |
| Attention projections, FP8 | 5.07 GB | yes (head/rank split) |
| Shared experts, MTP/DSpark | 8.64 GB | yes |
| `embed.weight` (BF16) | 1.324 GB | **replicated** in practice |
| MoE routers (`gate.weight` + fp32 `bias`, `bias_vl`) | 0.157 GB | **replicated** — every rank must score all 384 experts |
| mHC (`hc_attn_fn`, `hc_ffn_fn`, bases, scales), FP32 | 0.157 GB | **replicated** — the Sinkhorn mix runs on the full 4-copy residual stream |
| KV compressor (`wkv` BF16, `wgate` FP32), norms, sinks, image tokens | 0.037 GB | **replicated** |
| **Replicated total** | **1.675 GB per GPU** | added to every `weights/GPU` figure below |
| **The compressed KV cache itself** | 890 B/token | **cannot be head-sharded**: `num_key_value_heads = 1` — a single latent stream. Under plain TP it is **replicated on every rank**; only DP-attention would partition it by *request*, and no DP-attention configuration is published for V4.1 on Hopper (⚠️) |
| The 128-slot SWA ring | 2.58 MiB/seq | same — one 512-dim stream per layer, replicated under TP |

This single fact — **KV replicated, not sharded** — is what makes H100 hard, and it
is confirmed by measurement in §3.2. METHODOLOGY §3's
`max_concurrency = floor(kv_budget × n_gpus / …)` assumes sharding; for this model
under TP the correct denominator is the **per-GPU** budget. Both readings are given.

892.6 MiB against a 0.62 GB budget), so a 1M-context deployment needs ≥ 16 GPUs
(two nodes) **or** the Engram offload below.

With the Engram tables moved to host memory — the configuration vLLM's own H100
recipe ships (`--engram-config '{"cpu_offload":true}'`,
[src](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash/hw/h100.json)) — the
GPU-resident checkpoint drops to 324.52 GB:

| GPUs | Weights/GPU (GB) | KV budget/GPU (GB) | max conc @8K / 32K / 128K / 1M (FP4 KV) |
|---|---|---|---|
| 4 | 82.39 | **−14.39** | does not fit |
| **8** | **42.03** | **25.97** | **2,598 / 814 / 217 / 27** |
| 16 | 21.85 | 46.15 | 4,617 / 1,448 / 386 / 49 |
| 32 | 11.76 | 56.24 | 5,626 / 1,764 / 471 / 60 |

**Engram CPU offload is the single highest-leverage flag on this GPU**: it multiplies
max concurrency at 128K by **43×** (5 → 217) at TP8. It does not shrink the
checkpoint, it moves 202.76 GB of it to host DRAM; the cost is 12,672 B/token of
scattered gather per token per step crossing PCIe Gen5 ×16 (§2, §6).

### 1.4 The central question: does the NVFP4 build beat the base on H100?

Both checkpoints execute through the **same** Marlin W4A16 path on `sm_90`. The only
differences are bytes.

| Config | | base MXFP4 (510.29 GB) | NVFP4 (527.27 GB) | Δ |
|---|---|---|---|---|
| TP8, no offload | weights/GPU | 65.25 GB | 67.38 GB | **+2.12 GB** |
| | KV budget/GPU | **2.75 GB** | **0.62 GB** | **−77.3 %** |
| | seats @128K | 23 | **5** | −78 % |
| TP8, Engram offload | weights/GPU | 39.91 GB | 42.03 GB | +2.12 GB |
| | KV budget/GPU | 28.09 GB | 25.97 GB | −7.6 % |
| | seats @128K | 235 | 217 | −7.7 % |
| TP16, no offload | KV budget/GPU | 34.54 GB | 33.47 GB | −3.1 % |
| TP16, Engram offload | KV budget/GPU | 47.21 GB | 46.15 GB | −2.2 % |

And per decode step, because the NVFP4 expert is 5.88 % larger
(`19,906,584 B` vs `3×(2304×5120/2) + 3×(2304×5120/32) = 18,800,640 B`):

| Batch | E[distinct experts / layer] | base GiB/step | NVFP4 GiB/step | **NVFP4 penalty** |
|---|---|---|---|---|
| 1 | 6.0 | 12.25 | 12.49 | **+2.02 %** |
| 8 | 45.5 | 39.88 | 41.75 | +4.70 % |
| 32 | 152.0 | 114.51 | 120.77 | +5.47 % |
| 64 | 243.8 | 178.83 | 188.87 | +5.62 % |
| 128 | 332.8 | 241.16 | 254.87 | +5.69 % |
| 256 | 377.2 | 272.22 | 287.76 | **+5.71 %** |

`distinct_experts(b) = 384 × (1 − (1 − 6/384)^b)` (METHODOLOGY §4).
Decode on H100 is memory-bound at every batch in the table (§3.1), so a
**+2 – 5.7 % byte penalty is a +2 – 5.7 % TPOT penalty**, with no compensating math.

> **Answer: no.** On H100 the NVFP4 build is slower, larger, and (without Engram
> offload) leaves a quarter of the base's KV budget, for exactly the same
> dequantise-to-BF16 arithmetic. The only H100 argument for it would be accuracy, and
> the accuracy delta against the base is a wash (±1.5 points, 4 wins / 2 losses,
> [architecture.md §10.1](architecture.md)) — and that wash was measured on
> **Blackwell W4A4**, which is not the arithmetic H100 performs. ⚠️ **TO BE
> VERIFIED**: nobody has published accuracy for NVFP4-dequantised-to-BF16 (W4A16) on
> Hopper; the W4A4 calibration (including the 18 of 46,080 fallback activation
> scales) is *irrelevant* when activations never go to FP4.

**(a) The KV cache is replicated per TP rank, and it is 890 B/token on Hopper.**
Reconciling the measured vLLM pool against the fit model for the *base* checkpoint

```

weights/GPU    = 510,286,023,000/8 + 1.675×7/8 = 65.25 GB
remaining                                      =  8.35 GB
measured pool  = 7,957,495 tok × 890 B         =  7.08 GB   <- REPLICATED reading
```

If the pool were *sharded* across 8 ranks it would be 0.89 GB/GPU and 8.9 GB of

### 4.1 Effect of prefix caching and speculative decoding on cost

**Prefix caching** is the dominant lever and it is already in the blended formula:
at 50 % hit / 10 % cost the input term is ×0.55; at the **97.6 % median hit rate the
InferenceX agentic traces actually see** ([architecture.md §10.2](architecture.md))
the input term is ×0.0316, and blended cost collapses to essentially the output
term alone. For this model the case is overwhelming — a 128K prefix is 0.117 GB and
reloads in **1.4 ms** against a 2.097 PFLOP recompute
([serving-optimizations.md §1.5](../../cross-cutting/serving-optimizations.md)).
⚠️ NVIDIA's own NVFP4 vLLM command nevertheless passes `--no-enable-prefix-caching`,
unexplained; and on `sm_90` FlashMLA's **page size 64** fragments reuse.

**Speculative decoding (DSpark γ=5)** — sensitivity only, because **no acceptance
rate is published for this checkpoint** and NVIDIA explicitly did not exercise it:

| Batch | a = 1.0 (off) | a = 2.0 | a = 3.51 (⚠️ *synthetic* constant, not a measurement) |
|---|---|---|---|
| 1 | 93.9 tok/s/GPU | 187.8 | 329.6 |
| 32 | 305.0 | 610.1 | 1,070.7 |
| 256 | 963.8 | 1,927.6 | 3,382.9 |

$/1M output scales as `1/a`, so at a = 2.0 the S1 band would be $0.39 – $0.99.
**Do not plan on it.** At batch ≥ 64 the distinct-expert count is already 244/384
([architecture.md §6.3](architecture.md)), so drafting adds a full verify pass over
nearly the whole expert set for little gain; and this checkpoint has to run the
**MXFP4** DSpark experts alongside **NVFP4** backbone experts through two different
Marlin paths in one process, which nobody has validated.

## 5. Scaling and deployment shape

**Single node vs multi-node.** TP8 in one HGX/DGX H100 node is the only shape worth
running. TP16 across two nodes buys 33.47 GB/GPU of KV instead of 0.62 GB (§1.2) —
but METHODOLOGY §4 charges **20–40 % comm overhead** for multi-node TP over
InfiniBand against 5–15 % for TP8 over NVSwitch, and 16 GPUs doubles the bill for at
most 1.5× the work. **The Engram CPU offload gets you the same KV headroom on one
node for free** (25.97 GB/GPU at TP8), which is precisely why vLLM's H100 profile
ships it. Use 16 GPUs only if you need 1M context *and* refuse the offload.

**When PD disaggregation or wide-EP pays: not here.** PD needs 8 GPUs per pool =
two nodes, and the only *verified* V4.1 1P1D layout is GB200 NVL4 (TP4+TP4,
text-only) — the H100 equivalent is TP8+TP8 across two nodes with KV over
InfiniBand, i.e. exactly the regime where *"disaggregation is a thousand-GPU
problem"* and Modular measures a **20–30 % drop**
([serving-optimizations.md §3.5](../../cross-cutting/serving-optimizations.md)).
Wide-EP is worse than useless: the H100 NVLink domain is 8 GPUs, and the measured
EP=8 SGLang rows run ~8× slower than EP=1 vLLM on the same hardware (§3.2), with an
**open** Marlin-MoE-under-EP illegal-memory-access bug on Hopper (vLLM #47769).
The architecture would love PD (prefill activates 8B, decode 16B —
[architecture.md §3.2](architecture.md)); the *fabric* will not pay for it on Hopper.

**Launch command.** There is **no published H100 recipe for the NVFP4 checkpoint**.
The two commands NVIDIA publishes are both **4 × GB300, TP4**, quoted verbatim from
the card [src](https://huggingface.co/nvidia/DeepSeek-V4.1-Flash-NVFP4/raw/main/README.md):

```bash
# NVIDIA's SGLang recipe — GB300, NOT H100
python -m sglang.launch_server \
    --model-path nvidia/DeepSeek-V4.1-Flash-NVFP4 \
    --served-model-name DeepSeek-V4.1-Flash-NVFP4 \
    --host 127.0.0.1 --port 30000 \
    --tp 4 \
    --context-length 1048576 \
    --reasoning-parser deepseek-v41 \
    --tool-call-parser deepseekv41 \
    --chunked-prefill-size 4096 \
    --max-running-requests 16 \
    --log-level info
```

> *"The tested build automatically selects `flashinfer_trtllm_routed` for the NVFP4
> experts."* — that selector is **Blackwell-only**; on `sm_90` it resolves to Marlin.

The command that actually runs this *architecture* on 8 × H100 is vLLM's H100
profile for the **base** checkpoint, quoted verbatim
[src](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash/hw/h100.json):

```bash
VLLM_ENGINE_READY_TIMEOUT_S=3600 VLLM_USE_V2_MODEL_RUNNER=1 \
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True VLLM_USE_RUST_FRONTEND=1 \
vllm serve deepseek-ai/DeepSeek-V4.1-Flash \
  --tokenizer-mode deepseek_v41 \
  --engram-config '{"cpu_offload":true}' \
  --max-num-batched-tokens 4096 \
  --gpu-memory-utilization 0.92 \
  --tensor-parallel-size 8 \
  --tool-call-parser deepseek_v41 --enable-auto-tool-choice \
  --reasoning-parser deepseek_v41 --mm-encoder-tp-mode data
```

To attempt the NVFP4 build on H100 you would substitute the model id, keep every
flag above, and add the Marlin selector — **untested by anyone, and expected to

## 6. Risks and open questions

**Blocking, with sources**

1. **vLLM #49070 — NVFP4 MoE on Hopper is broken, and the issue is OPEN.**
   H100/H200, MiniMax-M3-NVFP4: *"Using 'MARLIN' NvFp4 MoE backend out of potential
   backends: ['FLASHINFER_TRTLLM', 'FLASHINFER_CUTLASS', 'MARLIN']"*, then corrupted
   output (null bytes / repeated tokens) at concurrency 1 and
   *"CUDA error: an illegal memory access was encountered"* inside the Marlin MoE
   kernel at concurrency ≈ 8. Causes: the Marlin adapter substitutes plain-SiLU for
   the model's SwiGLU α/β/clamp, and unaligned `moe_intermediate_size` produces
   out-of-bounds padding. Fix PRs **#48929** and **#48624** are both still open
   (re-checked 2026-09-19) [src](https://github.com/vllm-project/vllm/issues/49070).
2. **vLLM #47769 — Marlin MXFP4 MoE + EP on Hopper, DeepSeek V4, OPEN.** Illegal
   memory access in `prepare_moe_mxfp4_layer_for_marlin` at the scale-permutation
   step; *"Marlin kernels require N/K dimensions to be tile-aligned (multiples of 64
   or 128)"* and `intermediate_size_per_partition` is not guaranteed to satisfy it.
   The reporter notes PR **#45295** added padding to *"dense NVFP4 and NVFP4 MoE
   paths"* but *"did not update `prepare_moe_mxfp4_layer_for_marlin`"*
   [src](https://github.com/vllm-project/vllm/issues/47769). **This checkpoint needs
   both paths at once** — NVFP4 backbone experts *and* MXFP4 DSpark experts — so it
   inherits the unpadded MXFP4 path for its drafter. ⚠️ Whether #45295's NVFP4
   padding is the same fix #49070's #48624 proposes is unresolved; the two issues
   describe it differently.
3. **Derived alignment hazard.** `moe_intermediate_size = 2304`; at **TP8,
   2304 / 8 = 288**, and `288 mod 64 = 32` — not tile-aligned. At TP16 it is 144
   (`144 mod 64 = 16`). This is the exact shape class in #47769/#49070.
   ⚠️ **TO BE VERIFIED** whether vLLM pads it for the NVFP4 MoE path on `sm_90`.
4. **NVFP4 backbone + MXFP4 MTP in one process is unvalidated anywhere**, on any GPU
   ([architecture.md §7.3](architecture.md)). On Hopper both halves take *different*
   Marlin fallbacks, which is strictly more surface than on Blackwell.
5. **vLLM #51326** — DeepSeek-V4-Flash-0731 on 8 × H100 TP8+EP produced *"semantically
   corrupted"* output on vLLM 0.26.0 but coherent output on 0.25.0, across both the
   Marlin backend and `--moe-backend=triton_unfused`. Closed, but it is the third
   H100-specific correctness incident in this family
   [src](https://github.com/vllm-project/vllm/issues/51326).
6. **Neither engine has shipped V4.1 in a numbered release.** `min_vllm_version
   0.30.0` with `nightly_required: true`; SGLang serves it from `main` only. The
   measured H100 rows used `vllm/vllm-openai:nightly-cd10ed6f…` and
   `lmsysorg/sglang:dev-dsv41`.
7. **Vendor scope.** *"Supported Hardware Microarchitecture Compatibility: NVIDIA
   Blackwell"*; *"Test Hardware: NVIDIA GB300 (Blackwell)."* Running this on H100 is
   outside every support statement that exists.

**⚠️ TO BE VERIFIED (unresolved)**

8. **Does V4.1 sparse *decode* have an SM90 kernel?** FlashMLA's README says
   *"Sparse Decoding for DeepSeek V4.1 is only available on SM100"*; vLLM's
   `FLASHMLA_SPARSE_DSV41` admits `capability.major in [9, 10]` with block size 64.
   The 12 measured H100 rows prove something decodes; which kernel, and at what
   KV precision, is unconfirmed.
9. **Is the KV really 890 B/token on `sm_90`, or 1,650 B?** §3.2's pool
   reconciliation says 890 B and closes to 1.27 GB; `flash-attention.md` §16.1 says
   budget 1,650 B off SM100. If 1,650 is right, every max-concurrency figure in §1
   drops ~1.85× and the S2/S3 tables lose rows. Both columns are printed.
10. **Is the latent KV replicated or sharded under TP8?** §1.1 argues replicated
    (`num_key_value_heads = 1`) and §3.2's measurement supports it; METHODOLOGY §3's
    formula and [serving-optimizations.md §7.1](../../cross-cutting/serving-optimizations.md)
    both flag the alternative. The gap between the two readings is **8×**.
11. **Accuracy of NVFP4 executed as W4A16 on Hopper.** NVIDIA's ±1.5-point wash was
    measured as **W4A4 on Blackwell**. Dequantising NVFP4 weights to BF16 and running
    BF16 activations is a *different* numerical path — plausibly *more* accurate
    (BF16 activations) but never evaluated. The 18 of 46,080 fallback activation
    scales become dead weight.
12. **Engram CPU offload cost on H100.** 12,672 B/token of scattered gather (2 layers
    × 24 rows × 264 B) crosses PCIe Gen5 ×16: 0.013 MB/step at batch 1, 3.24 MB at
    batch 256, 25.95 MB at batch 2,048 — i.e. 0.1 µs / 25.3 µs / 202.8 µs of pure
    bandwidth at 128 GB/s `est.` **Random-access latency is not modelled and is the
    real risk**; no published H100 profile of the offloaded path exists. Every
    Engram-offload row in §1 and §3 rests on this being cheap.
13. **DSpark acceptance rate** for this checkpoint: unpublished. The 3.51 in the tree
    is a *synthetic benchmark constant*. Also, the InferenceX rows label
    `spec_method: "mtp"` while both engines state V4.1 **dropped MTP** and ships
    DSpark only — one of the two is wrong.
14. **Why `--no-enable-prefix-caching` in NVIDIA's own command**, when the target
    workload runs at 97 % hit. Suspected interaction with SWA Bounded Replay; unstated.
15. **`model.safetensors.index.json` still carries the base checkpoint's
    `total_size = 510,286,023,000`** — 17 GB short. On an 80 GB card with 2.12 GB of
    slack, a loader that sizes an allocation from that field under-allocates by more
    than the entire KV budget ([architecture.md §1.1](architecture.md)).
16. **`activation_scheme: "dynamic"` contradicts `input_activations.dynamic: false`**
    in the shipped `config.json`. Moot on H100 (W4A16 never quantises activations),
    but it means the checkpoint's own config is self-inconsistent.
17. **`S` (engine state slots per request)** is unstated for V4.1 by any engine; every
    fixed-state figure here assumes `S = 1`. Moves max concurrency by < 1 % at 8K and
    not at all at 1M.
18. **MFU 0.15 for the decode compute ceiling** is an unsourced planning guess, and it
    is what places the FLOP crossover at batch ≈ 1,713 in §3.3. If real MFU is 0.25
    the crossover moves to ~2,850 and S4 throughput rises 1.67×.

**Accuracy caveats of the executed precision**

- On H100 the executed precision is **W4A16**: NVFP4-encoded weights, BF16
  activations, BF16 accumulate. Weight values are bit-identical to the Blackwell
  path (*"All 16,986,931,200 weight blocks passed lossless conversion"*), so
  weight-induced error should match or improve on the W4A4 numbers.
- The FP8 remainder (attention, shared experts, the 188.83 GiB Engram tables) uses
  **32×32 UE8M0 block scaling**, which Hopper applies *in software* with FP32
  promotion because its FP8 MMA has no hardware block scaling — a lower fraction of
  the 1,979 TFLOPS peak and a different rounding path than Blackwell. ⚠️ No measured
  Hopper DeepGEMM efficiency figure was captured.
- `rms_norm_eps = 1e-20` makes fp32 norm accumulation mandatory; any engine path that
  demotes it will produce garbage before it produces a warning.
- NVIDIA's own caution applies unchanged: *"Lossless weight conversion does not imply
  identical inference outputs."*
