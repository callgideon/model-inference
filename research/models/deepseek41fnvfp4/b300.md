## 0. Verdict

1. **Runnable today? Not as a supported configuration.** vLLM `main` and SGLang
   `main` both load this checkpoint and both run NVFP4 experts on any
   `is_blackwell` device, which includes `sm_103`
   ([architecture.md §8.4](architecture.md)) — but NVIDIA's card names **GB300 as
   the only test hardware and TP4 as the only tested shape**, `nvidia/DeepSeek-V4.1-Flash-NVFP4`
   is **absent from vLLM's recipe catalogue** (only `deepseek-ai/DeepSeek-V4.1-Flash`
   is listed) [src](https://recipes.vllm.ai/models.json), and three separate
   `sm_103`-specific kernel faults are on record for this model family (§6).
   Engine + version: **vLLM `vllm/vllm-openai:deepseekv41-flash-0909`** or
   **SGLang `lmsysorg/sglang:dev-cu13-dsv41` @ `da64c5cb`** — both GB300-validated, neither B300-validated.
2. **Min GPUs 4 (TP4/EP4), or 2 with the Engram tables off-GPU; recommended 4.**
   2 × 268 GB cannot hold 527.27 GB of weights at all — TP2 is
   `infeasible (KV)` unless the 188.83 GiB Engram tables move to host memory or
   are row-sharded, which is exactly what vLLM's own B300 profile does for the
   base checkpoint (`--engram-config '{"cpu_offload":true}'`) [src](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash/hw/b300.json).
3. **Weight format actually executed: NVFP4 W4A4 natively on `sm_103` tensor
   cores — for 58.0 % of the bytes.** The other 42 % (Engram MXFP8, attention
   FP8, MTP/DSpark **MXFP4**, embeddings/head BF16, mHC FP32) runs at its own
   precision, and 38.5 % of the checkpoint is an Engram table no FP4 kernel
   touches ([architecture.md §3.3](architecture.md)).
4. **Cost per 1M output tokens: $4.27 (cheapest reputable on-demand, Hyperstack
   $7.40/GPU-h) – $8.66 (cheapest hyperscaler, OCI $15.00/GPU-h)** at the
   interactive point (4 × B300, TPOT ≤ 50 ms, no speculation), `est.`;
   **$0.216 – $0.437** at max throughput. Blended (75 % in / 50 % of that cached
   / 25 % out): **$1.16 – $2.35 per 1M**.
5. **Confidence: estimate.** No measurement of *this checkpoint* on *this GPU*
   exists. The closest published proxy — 15 InferenceX rows on B300 running the
   exact container NVIDIA's card names — does not disclose which HF repo it
   served (§3), and its TP2 memory footprint only closes against 288 GB/GPU, not
   the pinned 268.

> **The question this pair exists to answer, answered.** The NVFP4 build has
> **no published speedup over the base MXFP4 checkpoint anywhere**
> ([architecture.md §0](architecture.md), [gpus/b300.md §6](../../gpus/b300.md),
> re-confirmed by search 2026-09-19). On B300 the arithmetic runs the other way:
> decode for this model is **bandwidth-bound at every batch anyone has measured**
> (measured MBU 0.054–0.215, §3), and at saturated batch the NVFP4 experts are
> **5.7 % more bytes to read per decode step** than the MXFP4 experts (§2).
> B300's one advantage over B200 — 1.5× dense FP4 — lands on a prefill whose
> **measured MFU is 1.3 % of FP4 peak** (§3), so it buys essentially nothing
> here. **The expected outcome on B300 is that this checkpoint is ~5 % slower in
> decode than the base and indistinguishable in prefill, at +16.99 GB of
> weights, for an accuracy wash.** That is a prediction from measured inputs, not
> a measurement — ⚠️ **TO BE VERIFIED**: nobody has published a paired
> iso-model MXFP4-vs-NVFP4 run on `sm_103`.

**Disagreements, stated rather than resolved silently:**

* METHODOLOGY §8 and gpus/b300.md **agree** on 268 GB / 2,144 GB. No conflict.
* [architecture.md §5.6](architecture.md) prints TP4 max-concurrency
  **41,338 / 13,144 / 3,525 / 450** where this document prints
  **40,801 / 12,973 / 3,479 / 444**. The remaining difference is that §5.6 charges
  no replicated tensors; the ring is no longer a difference — §5.6 was recut
  2026-09-19 onto the **43-ring** 2,906,112 B fixed state this document already
  used (2,703,360 B is the `--num-speculative-tokens 0` floor). This document
  uses the stricter pair.
* Fixed per-sequence state has **three** published readings:
  METHODOLOGY §8 says 2.77 MiB (FP8, engine-optimal) – 5.38 MiB (BF16 reference);
  [architecture.md §5.3](architecture.md) derives 2.77 MiB at `S = 1`; and the
  only engine that documents its allocation, **kern, allocates 43 rings of
  256 slots = 5.81 MB (5.54 MiB) per sequence slot** — i.e. `S = 2`
  [src](https://huggingface.co/Pegainfer/kern-deepseek-v41-flash-sm103). A
  `S = 2` row is given below. At 128K context the difference moves
  max-concurrency by 2.4 %; at 8K by 22 %.

### 1.2 Fit over the GPU counts this topology allows

An HGX B300 node is **8 GPUs in one NVLink-5 domain (1.8 TB/s per GPU,
14.4 TB/s total)**; there is no 18/36/72 option — that is GB300 NVL72, a
different part ([gpus/b300.md §4](../../gpus/b300.md)). Above 8 GPUs you leave
the NVLink domain and pay 20–40 % comm overhead over Quantum-X800 InfiniBand or
Spectrum-X ([METHODOLOGY §4](../../METHODOLOGY.md)).

```
nGPU parallelism       W/GPU GiB  repl GiB  KV/GPU GB  KV tot GB  multi-node?
   1 none                 491.06      1.27     -291.4     -291.4  NO - one HGX B300 node
   2 TP2 or EP2           245.53      1.27      -27.8      -55.6  NO - one HGX B300 node
   4 TP4 / EP4            122.77      1.27      104.0      416.1  NO - one HGX B300 node
   8 TP8 / EP8             61.38      1.27      169.9     1359.4  NO - one HGX B300 node
  16 EP16 (2 nodes)        30.69      1.27      202.9     3246.0  YES - 2 nodes, IB/Spectrum-X

  with Engram tables off-GPU (host-mapped or row-sharded); resident = 324.52 GB = 302.23 GiB
   1 TP1 + host Engram     302.23      1.27      -88.7      -88.7
   2 TP2 + host Engram     151.11      1.27       73.6      147.1
   4 TP4 + host Engram      75.56      1.27      154.7      618.8
   8 TP8 + host Engram      37.78      1.27      195.3     1562.1
```

* **1 GPU and 2 GPUs are `infeasible (KV)` with the full checkpoint resident.**
  2 × 268 GB = 536 GB against 527.27 GB of weights leaves 8.7 GB *before* the
  0.90 usable factor; after it the budget is **−27.8 GB per GPU**. This is the
  same conclusion [architecture.md §5.6](architecture.md) reaches, and it is why
  vLLM's B300 profile for the base checkpoint carries
  `--engram-config '{"cpu_offload":true}'` as a **load-bearing flag, not an
  optimisation** ([cross-cutting/inference-engines.md §3.6](../../cross-cutting/inference-engines.md)).
* **4 GPUs is the minimum for a plain TP/EP deployment** and is also the only
  shape NVIDIA tested (on GB300).
* **2 GPUs becomes feasible once the Engram tables leave HBM**, giving
  73.6 GB of KV per GPU. Whether `--engram-config '{"cpu_offload":true}'` works
  against the **NVFP4** repo is ⚠️ **TO BE VERIFIED** — the flag is
  architecture-level and the Engram tensors are byte-identical between the two
  builds, but the recipe that carries it names only `deepseek-ai/DeepSeek-V4.1-Flash`.
* An HGX B300 node is an x86 host with **PCIe 6.x at 128 GB/s** and no
  NVLink-C2C ([gpus/b300.md §1](../../gpus/b300.md)). Host-mapped Engram lookups
  are 24 random 264-byte rows per token per Engram layer
  ([architecture.md §6.3](architecture.md)) crossing that PCIe link — which is
  precisely why kern ships a **separate `-hbm` manifest for HGX B300** that
  row-shards the two tables into HBM across four ranks instead
  (+47 GiB/GPU), describing the target as *"a device that cannot read host
  memory at speed, an **HGX B300** (x86 host, no NVLink C2C)"*
  [src](https://huggingface.co/Pegainfer/kern-deepseek-v41-flash-sm103).

### 1.3 Tensors that cannot be sharded

`per_gpu_weights = 527.27 GB / n` is optimistic. These stay on **every** rank:

| Replicated tensor group | Bytes | Why |
|---|---|---|
| mHC `hc_attn_fn` / `hc_ffn_fn` / bases / scales (**FP32**) | 157.3 MB | Single-Pass mHC mixes 4 residual copies through a Sinkhorn-normalised 24×20480 matrix per sublayer; it is a whole-residual operator |
| MoE routers (`gate.weight` BF16 + FP32 `bias` + `bias_vl`) | 157.4 MB | every rank must score all 384 experts to route |
| KV compressor (`wkv` BF16, `wgate` FP32) | 36.7 MB | produces the single shared latent stream |
| CSA2 indexer `weights_proj` / `k_norm` / `wk` | 45.1 MB | 32 indexer heads are splittable, the norms and projections are not |
| all RMSNorms, attention sinks, image tokens | 0.4 MB | `rms_norm_eps 1e-20` forces fp32 accumulation everywhere |
| vision tower + aligner (BF16) | 970.5 MB | vLLM's recipe runs the encoder **data-parallel** (`--mm-encoder-tp-mode data`), i.e. one full copy per rank |
| **total replicated** | **1.367 GB = 1.27 GiB** | charged on every row of §1.2 |
| token embedding (BF16) | +1.324 GB | replicated unless the engine runs vocab-parallel embedding |

**The one that actually matters is not a weight — it is the KV cache.**
`num_key_value_heads = 1`: this model keeps **one shared latent KV stream**
([architecture.md §2](architecture.md)). There is no head dimension to split, so
under plain TP the compressed-KV and indexer-K caches are **replicated on every
rank**, and the node's KV budget is the *per-GPU* budget, not the sum. Sharding
them needs DP-attention or decode context parallel (SGLang `--dcp`), which
neither NVIDIA recipe enables. Both readings are given below; ⚠️ **TO BE
VERIFIED** which one a given engine build takes — this is the same open question
[cross-cutting/serving-optimizations.md §7.1](../../cross-cutting/serving-optimizations.md)
flags for the base checkpoint.

### 1.4 Max concurrency

`max_concurrency(ctx) = floor(kv_budget / (ctx × kv_bytes_per_token + fixed_state))`,
all arithmetic in bytes, `fixed_state = 2,906,112 B`.

**Conservative reading — KV replicated per rank (plain TP, `n_kv_heads = 1`):**

| Config | KV budget/GPU | 8K | 32K | 128K | 1M |
|---|---|---|---|---|---|
| TP2 + Engram off-GPU | 73.6 GB | 7,217 | 2,295 | 615 | 78 |
| **TP4** | **104.0 GB** | **10,199** | **3,242** | **869** | **111** |
| TP8 | 169.9 GB | 16,661 | 5,297 | 1,421 | 181 |

(The TP4/128K figure of **869** reproduces the ≈917 that
[serving-optimizations.md §7.1](../../cross-cutting/serving-optimizations.md)
derives for the base checkpoint — the 5 % gap is the 17 GB of extra NVFP4
weights plus the replicated tensors.)

**With kern's `S = 2` ring** (5.81 MB/seq), TP4 full checkpoint, sharded reading:
8K **31,752** / 32K **11,895** / 128K **3,397** / 1M **443**.

**BF16 KV is a hypothetical here.** The FP4 KV format is baked into the
architecture (`fp4_act_quant` in the reference `model.py`, `kv_cache_quant_algo:
null`), so the BF16 and FP8 columns describe what an engine *without* the
`nvfp4_ds_mla` kernel would have to spend — and on `sm_103` that kernel exists
([flash-attention.md §11](../../cross-cutting/flash-attention.md): `nvfp4_ds_mla`
requires `FLASHMLA_MEGA_ATTN_DSV41`, gated on `major == 10`, which `sm_103`
satisfies). They are the fallback columns, not a tuning knob.

**Engine-reported KV pools, measured.** The 15 InferenceX B300 rows report a
`kv_cache_pool_tokens` of **78,110,198 / 63,091,247 tokens at TP4** (69.5 / 56.2 GB
of 890-byte records) and **32,580,148 / 42,635,881 / 50,132,268 at TP2**
(29.0 / 37.9 / 44.6 GB), with `offload_mode: off` and
`allocated_cpu_dram_gb: 0` throughout
[src](https://inferencex.semianalysis.com/api/v1/benchmarks?model=DeepSeek-V4.1-Flash).
The TP4 pools sit **at 13–17 % of the 416 GB this section says is available** —
the harness is capped by configuration, not capacity. The TP2 pools **cannot
close against 268 GB/GPU at all** (2 × 268 − 527.27 = 8.7 GB before overheads,
against a 29–45 GB pool with no offload); they close only against 288 GB
physical, which is the GB300/die-nameplate figure. ⚠️ **TO BE VERIFIED** which
SKU those rows ran on; the API does not expose it. Do not plan a TP2 deployment
of this checkpoint on a 268 GB B300 without moving the Engram tables off HBM.

## 3. Throughput and latency

### 3.1 MBU / MFU assumptions — calibrated, not assumed

[METHODOLOGY §4](../../METHODOLOGY.md) offers MBU 0.5–0.7 and FP4 MFU 0.20–0.35
for first-gen Blackwell software. **For this model those bands are wrong by a
factor of 3–20**, and two primary measurements say so. Rather than deviate
silently, both anchors and the fit between them are printed:

```
0. MBU CALIBRATION (the only two clean saturated/idle decode measurements of this model)
  vLLM PR #56686, 8xB200 TP8, b~640, 22.2 ms step -> bytes  284.81 GiB  => MBU = 0.215
  kern 4xGB300, b=1, 7.6 ms plain step           -> bytes   12.26 GiB  => MBU = 0.054
  MBU(b) = 0.054 + (0.215-0.054) x ln(b)/ln(640), clamped [0.054, 0.215]   [est., two-point log fit]
  b=1:0.054  b=8:0.106  b=32:0.141  b=64:0.158  b=128:0.175  b=256:0.192  b=640:0.215
  METHODOLOGY SS4's Blackwell planning band is 0.5-0.7; this model measures 0.06-0.21.
```

* **Anchor A** — vLLM PR #56686, `deepseek-ai/DeepSeek-V4.1-Flash` on **8 × B200
  TP8**: *"decode steps at 257 to 1024 requests 23.1 ms median, from 25.6 ms"*,
  then *"the same decode bucket 22.2 ms median"*
  [src](https://github.com/vllm-project/vllm/pull/56686). `meas.`
* **Anchor B** — kern on **4 × GB300**, same base checkpoint, concurrency 1:
  *"plain decode step 7.6 ms, DSpark round 9.6 ms with 2.6 to 2.7 tokens accepted
  per step"* [src](https://huggingface.co/Pegainfer/kern-deepseek-v41-flash-sm103). `meas.`

Both anchors are the **base MXFP4** checkpoint; the byte model below uses the
NVFP4 expert size (19,906,584 B vs 18,800,640 B per expert,
[architecture.md §6.3](architecture.md)).

**Prefill MFU is the more surprising number.** The same PR reports
*"the 16,384-token prefill steps went from 221 to 231 ms to a flat 220 to 222 ms"*:

```
  saturated prefill anchor: 16,384-tok chunks at 220-222 ms on 8xB200 TP8 = 9,267 tok/s/GPU
    implied prefill MFU = 1.29% of B300 dense NVFP4 peak, 3.88% of FP8 peak
    roofline ceiling at MFU 0.25 would be 716,199 tok/s on 4 GPUs - 30x the measured rate.
```

Prefill for this model activates only **7.55 B parameters** (20 encoder layers,
the CED payoff) and 3.76 GFLOP/token of context-independent sparse attention, so
it is launch-, gather- and bandwidth-bound long before it is GEMM-bound. kern's
own nsys breakdown of a DSpark round agrees: *"MegaMoE 40 %, dense GEMMs 21 %
(about 4 TB/s on the large projections), mHC 11 %, attention 9 %, launch-bound
glue 9 %, lm_head 4 %, gate 4 %"* — and *"the remaining gap to the weight-stream
floor is inside MegaMoE at small M"*
[src](https://huggingface.co/Pegainfer/kern-deepseek-v41-flash-sm103).
**Consequence: B300's 1.5× dense-FP4 advantage over B200 is unreachable for this
model in prefill, and irrelevant in decode. What B300 brings is 268 GB vs 180 GB
of HBM** ([gpus/b300.md §12(a)](../../gpus/b300.md): *"B300 is not a faster
decode chip than B200 for a fixed working set"*).

Comm overhead: +8 % for TP4 over NVLink ([METHODOLOGY §4](../../METHODOLOGY.md)
band 5–15 %). Decode-step bytes per
[architecture.md §6.3](architecture.md):
`weights_read(b) + b × (ctx × 170 + 13,058,048) + b × 12,672`, with
`distinct_experts(b) = 384 × (1 − (1 − 6/384)^b)`.

Three things fall out of the table and are worth stating plainly:

1. **TPOT barely moves between concurrency 128 and 256** (53.1 → 54.8 ms) while
   throughput doubles. At batch 128 the routing already touches 332.8 of 384
   experts; by 256 it is 377.2. **Once the expert set saturates, extra batch is
   almost free.** Running at 32 or 64 — let alone NVIDIA's `--max-running-requests 16`
   or `--max-num-seqs 32` — leaves most of the machine idle.
2. **Context length is nearly free.** S1 → S3 costs 1.8 % of TPOT at batch 256,
   because the main KV read is bounded by `index_topk = 512` and only the
   full-pool indexer scan grows (`ctx × 170 B`). kern says the same from
   measurement: *"A single 200k-token prompt prefills at 9.4k tokens/s and then
   decodes at 7.9 ms per token (10k-token prompts: 7.3 ms), so the step is nearly
   flat in context length."*
3. **TTFT, not TPOT, is what long context costs.** 11.5 s for a cold 128K
   prompt; 1.2 s at a 90 % prefix-cache hit. This is the number NVIDIA's
   `--no-enable-prefix-caching` throws away.

### 4.4 Versus the vendor API, and break-even

DeepSeek first-party `deepseek-flash` ([architecture.md §11.1](architecture.md)):
**$0.15–0.30 /1M input (miss), $0.003–0.006 cached, $0.60–1.20 output** (lower
figure = off-peak). Third parties go lower still: DeepInfra **$0.42** output,
Relace **$0.13** input / **$0.52** output ([architecture.md §11.2](architecture.md)).

```
   off-peak $0.60/1M out:
     Hyperstack $7.40   need    13,704 out tok/s =  712.3% of S1 /  35.9% of S4
     Nebius $7.85       need    14,537 out tok/s =  755.6% of S1 /  38.1% of S4
     DigitalOcean $7.94 need    14,704 out tok/s =  764.3% of S1 /  38.6% of S4
     OCI $15.00         need    27,778 out tok/s = 1443.9% of S1 /  72.9% of S4
     AWS $17.802        need    32,967 out tok/s = 1713.6% of S1 /  86.5% of S4
     CoreWeave spot     need     8,296 out tok/s =  431.2% of S1 /  21.8% of S4

   peak $1.20/1M out:
     Hyperstack $7.40   need     6,852 out tok/s =  356.2% of S1 /  18.0% of S4
     OCI $15.00         need    13,889 out tok/s =  721.9% of S1 /  36.4% of S4
     CoreWeave spot     need     4,148 out tok/s =  215.6% of S1 /  10.9% of S4

   DeepSeek blended (same 75/25, 50%-cached shape), off-peak = $0.2074/1M
     Hyperstack $7.40   self-host $1.1600 -> DEARER by  459.4%
     OCI $15.00         self-host $2.3513 -> DEARER by 1033.8%
     CoreWeave spot     self-host $0.7023 -> DEARER by  238.6%
```

Read the "% of S1 / % of S4" columns as **required utilisation**: at Hyperstack's
$7.40 you must sustain **712 % of the interactive operating point** to match
DeepSeek's off-peak output price — impossible — but only **36 % of the
max-throughput point**, which is comfortable. **The break-even is not a price, it
is an operating point.** Self-hosting this checkpoint on rented B300 beats the
DeepSeek API only in batch-oriented service, never in low-latency service.
Adding DSpark at 2.65 accepted tokens moves the interactive requirement from
712 % to **269 %** — still short.

On blended cost the API wins everywhere by 2.4×–11×. That is not surprising:
DeepSeek's cached-input price is **2 % of its uncached price**, a 50× discount
that is only affordable *because* the architecture puts KV at 890 B/token
([serving-optimizations.md §1.5](../../cross-cutting/serving-optimizations.md):
*"The architecture sets the price"*). A self-hoster gets the same architectural
advantage but pays list prices for silicon; the gap is margin, utilisation and
scale, not efficiency. Compare
[architecture.md §11.3](architecture.md), which reaches the same conclusion from
the measured InferenceX rows at $/1M **all tokens**: $0.033 on B300 TP2 against a
blended API price of roughly $0.01–0.02.

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

**Stay on one node.** An 8 × B300 HGX node holds 2,144 GB; this checkpoint needs
527.27 GB. Even TP4 leaves 416 GB of KV headroom — enough for 3,479 concurrent
128K sequences, an order of magnitude past anything the engines will schedule.
There is no capacity reason to cross the NVLink boundary, and every reason not
to: beyond 8 GPUs you pay 20–40 % comm overhead
([METHODOLOGY §4](../../METHODOLOGY.md)) and lose the 1.8 TB/s per-GPU fabric.

The natural node shape is therefore **two independent TP4/EP4 replicas per
8-GPU node**, which is exactly how kern documents the HGX B300 case: two
`kern-serve` processes on GPUs 0–3 and 4–7, ports 8000 and 8001. Alternatives
worth measuring on the same node: one TP8 replica (169.9 GB KV/GPU, lower TPOT
at fixed batch, worse GPU efficiency) or four TP2 replicas with the Engram
tables off-GPU (73.6 GB KV/GPU, highest aggregate throughput per node, highest
risk — see §1.4 on the TP2 pool arithmetic).

### 5.2 When PD disaggregation and wide-EP pay

**Wide-EP: not on this node.** The 8-GPU NVLink domain caps EP at 8
([gpus/b300.md §11.11](../../gpus/b300.md)), and a 384-expert top-6 MoE whose
expert set already saturates at batch ~256 does not need EP32. Worse, DeepEP +
DP-attention on B300 is the exact configuration that produced
`CUDA_ERROR_ILLEGAL_ADDRESS` in SGLang #25574. ⚠️ Verify the fix (PR #25575) is
in your build before enabling it.

**PD disaggregation: the architecture argues for it, the scale argues against
it.** CED makes this the textbook case — prefill activates **7.55 B** parameters
over 20 encoder layers, decode activates **15.75 B** over 40 plus the LM head
([architecture.md §3.2, §6.1](architecture.md)) — so prefill and decode want
genuinely different machines. Against that: *"disaggregation is a thousand-GPU
problem"*, and Modular reports a **20–30 % performance drop** on small or untuned
workloads ([serving-optimizations.md §3.5](../../cross-cutting/serving-optimizations.md)).
On a single 8-GPU node a 1P1D split is 4+4, which is the smallest configuration
where the KV-transfer cost is paid on every request and the specialisation gain
is eaten by rounding. **Verdict: run aggregated on 4 or 8 GPUs; consider PD only
at ≥ 4 nodes**, and note that the only *verified* V4.1 PD layout is 1P1D on
GB200 NVL4 with TP4 per pool, text-only, and that with speculation on **DSpark
must run in both pools** or the transferred KV is incompatible
([serving-optimizations.md §3.5](../../cross-cutting/serving-optimizations.md)).
vLLM does publish a `pd_cluster` strategy for this model on B300
[src](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash/hw/b300/strategies/pd_cluster.json)
— it emits no command, only a topology.

```bash
kern-serve ... --gpus 4,5,6,7 --port 8001
```

> v0.2.1 or newer."* And the trap: *"a manifest whose Mega kernels ask for more
> SMs than the device has hangs on their first grid barrier, which the driver
> ends as a grid sync timeout"* — **a B300 SXM6 has 148 SMs where a GB300 has
> 152**, and the persistent `dsv41_mega_moe` / `dsv41_mhc` / `dsv41_gate`
> kernels bake the SM count into both the template and the launch grid. This is
> a `sm_103`-family hazard that has nothing to do with PTX target suffixes.

### 5.4 Warm-up and loading

```
  NVMe  5 GB/s: full 527.27 GB =  105.5 s | Engram off-GPU  64.9 s | the two 101.5 GB shards alone  40.6 s
  NVMe 10 GB/s: full 527.27 GB =   52.7 s | Engram off-GPU  32.5 s | the two 101.5 GB shards alone  20.3 s
  NVMe 20 GB/s: full 527.27 GB =   26.4 s | Engram off-GPU  16.2 s | the two 101.5 GB shards alone  10.2 s
```

Those are the **transfer** floors. The measured figure is far larger: vLLM engine
init for this model on 8 × B200 is **111–114 s with a warm DeepGEMM cache and
190 s cold**, of which **22.3 s is an o-projection kernel warm-up for 27 kernels**
[src](https://github.com/vllm-project/vllm/pull/56686). NVIDIA sets
`VLLM_ENGINE_READY_TIMEOUT_S=3600` for a reason.

Two loading hazards specific to this checkpoint
([architecture.md §1.1](architecture.md)):

* **Shards 47 and 48 are 101.54 GB each** — the two Engram tables. A
  single-threaded `safetensors` load stalls on them; this is why the card passes
  `--model-loader-extra-config '{"enable_multithread_load": true, "num_threads": 128}'`.
* **`model.safetensors.index.json` still carries the base checkpoint's
  `metadata.total_size = 510,286,023,000`.** Anything that sizes an allocation
  from that field under-allocates by 16.99 GB. The true payload is
  527,273,322,840 B.

An AWS `p6-b300.48xlarge` carries 8 × 3.84 TB = **30.72 TB** of local NVMe and
4 TB of host RAM ([gpus/b300.md §11.13](../../gpus/b300.md)) — enough to stage
the checkpoint locally and, if you take the offload route, to hold the 202.76 GB
of Engram tables in pinned host memory. kern requires that host memory be backed
by **512 MiB transparent huge pages**: *"the runtime refuses to start otherwise,
because 64 KiB pages make the random lookups about ten times slower."*

## 6. Risks and open questions

### 6.1 The central unanswered question

**⚠️ Nobody has published an iso-model MXFP4-vs-NVFP4 throughput comparison on
`sm_103`** (or on any Blackwell part). NVIDIA's card has no performance number at
all; the vLLM recipe catalogue does not list the NVFP4 repo; and a targeted
search on 2026-09-19 found nothing. §2's arithmetic predicts the NVFP4 build is
**~5.7 % slower in decode** at saturated batch on B300 and no faster in prefill,
but that is a derivation, not a measurement. If you are choosing between the two
checkpoints, **benchmark them back to back before deciding** — and if you cannot,
the base MXFP4 checkpoint is the one with B300 recipes, community kernels, an
Engram-offload profile, and portability to MI355X.

### 6.2 `sm_103`-specific kernel faults on record for this model family

| # | Fault | Status |
|---|---|---|
| 1 | **FlashMLA sparse prefill device-asserts on B300.** *"DeepSeek-V4-Flash `flash_mla_sparse_fwd` device-side assert on B300/sm_103"*, 4 × B300 SXM6, `--tp-size 4`: `TRAP_ONLY_DEVICE_ASSERT(plan.tmem_start_addr.data()[0] == 0)`. Native `sm_103a` SASS **is** in the wheel — the kernel runs and then asserts. Identical image is token-exact on B200 | **Closed as inactive**, no fix merged. Proposed mitigation was to gate `flash_mla_sparse_fwd` away from `sm_103` [src](https://github.com/sgl-project/sglang/issues/27384) |
| 2 | **DSv4 `topk_v2` cluster kernel illegal address on 8 × B300** with `SGLANG_OPT_USE_TOPK_V2=1` (now default) + `--enable-dp-attention --moe-a2a-backend deepep`, TP8/DP8 | **Fixed** in PR #25575, validated on B300 at 958.5 tok/s/GPU [src](https://github.com/sgl-project/sglang/issues/25574) |
| 3 | **NVFP4 + TRT-LLM-gen batched GEMM dispatches an `sm100f` kernel on `sm_103`** — `trtllm_batched_gemm_runner.cu:276`, crash at bs=128 draft-graph capture. Fails on `lmsysorg/sglang:v0.5.12-cu130`, works on v0.5.11 | Closed as a v0.5.12 regression, different model (GLM-5-NVFP4) but **the same NVFP4-on-`sm_103` dispatch path this checkpoint's `flashinfer_trtllm_routed` MoE uses** [src](https://github.com/sgl-project/sglang/issues/25563) |

Plus the structural hazard: **`sm_100a` binaries do not load on B300.** Projects
choosing arch-specific targets for SASS quality must also emit `sm_103a`.
FlashMLA does; others may not. Check with
`cuobjdump --list-elf lib*.so | grep -c sm_103` ([gpus/b300.md §11.2](../../gpus/b300.md)).

### 6.3 Everything else marked ⚠️ TO BE VERIFIED

**Checkpoint and format**
1. Whether `--engram-config '{"cpu_offload":true}'` works against the NVFP4 repo.
   It is what makes TP2 feasible at 268 GB/GPU, and no recipe names this repo.
2. `config.json` contradicts itself on activation scales:
   `input_activations.dynamic = false` versus top-level
   `activation_scheme: "dynamic"`. Which an engine honours — and therefore
   whether activation scales are recomputed per batch — is unresolved
   ([architecture.md §1.2](architecture.md)).
3. **NVFP4 backbone experts + MXFP4 MTP/DSpark experts in one process** has been
   validated by nobody. It is the highest-risk untested combination in this
   checkpoint, and DSpark is the largest available cost lever (§4.3).
4. `model.safetensors.index.json` still reports the base model's `total_size`.
5. Whether NVIDIA left the 188.83 GiB Engram tables at FP8 for a reason. NVFP4
   would save ≈ 92 GB and drop the checkpoint to ≈ 435 GB, which would make TP2
   feasible on 268 GB GPUs without any offload. Community repos have done it
   (LibertAIDAI 429.4 GB, msuiche 414.9 GB) with **no published accuracy data**
   ([architecture.md §4.1, §9.1](architecture.md)).

**Kernels and engines**
6. FlashMLA's support matrix says V4.1 sparse **decode** is *"only available on
   SM100"* while its `setup.py` emits `sm_103a`. Doc lag or real gap is unknown,
   and risk #1 above suggests it may be real
   ([gpus/b300.md §11.5](../../gpus/b300.md)).
7. FlashInfer's PrimTS backend is *"architecture-gated but **not yet
   signoff-qualified**"* on SM103a — and it is the **default** attention backend
   for both vLLM and SGLang on Blackwell
   [src](https://docs.flashinfer.ai/api/attention.html).
8. vLLM has **no Blackwell CI at all** (L4 and H100 only), and its own RFC says
   FA4 and full native NVFP4 paths are *"not yet qualified"*
   ([gpus/b300.md §11.7](../../gpus/b300.md)). Pin versions; test your exact
   model on your exact node.
9. The FlashInfer NVFP4 paged-KV sparse decode/prefill PR merged **2026-09-18** —
   one day before this research date. No production exposure.
10. Why NVIDIA's reference command sets `--no-enable-prefix-caching`. Likely an
    interaction with SWA Bounded Replay, but unstated, and it forfeits a 5.7×
    reduction in input cost (§4.3).
11. Whether the single latent KV stream is sharded or replicated across TP ranks
    in a given engine build (§1.3). The two readings differ by 4× in
    max-concurrency at TP4.
12. Neither TensorRT-LLM nor NVIDIA Dynamo has a V4.1 entry. TRT-LLM's
    supported-models matrix stops at `DeepseekV4ForCausalLM`
    ([architecture.md §8.1](architecture.md)).
13. Whether production kernels bound the four **full-pool indexers** the way the
    reference implementation does not. At 1M context they cost 21.5 GFLOP/token —
    more than the entire encoder forward pass
    ([architecture.md §6.2](architecture.md)).

**Measurement**
14. Which HF repo each InferenceX B300 row actually served. The image is the one
    NVIDIA's card names for the NVFP4 build, which is suggestive but not proof;
    the TP2 memory arithmetic points the other way (§1.4).
15. Which SKU the InferenceX B300 TP2 rows ran on. Their KV pool only closes
    against 288 GB/GPU physical, not the pinned 268.
16. DSpark acceptance for **this** checkpoint at production batch sizes. The only
    measured number (2.6–2.7) is the base checkpoint at concurrency 1 on GB300.
17. Whether B300's claimed **2× attention-layer (SFU) throughput** helps CSA2's
    softmax-heavy indexer. It is an unqualified vendor claim with **no caveat
    footnote and no published end-to-end measurement**, on a model whose
    attention is exactly the kind it should help
    ([gpus/b300.md §3, §5](../../gpus/b300.md),
    [quantization-formats.md §4.3](../../cross-cutting/quantization-formats.md)).
18. Sustained-clock behaviour of an **air-cooled** HGX B300 under long FP4
    prefill bursts. No public data; the 1,100 W air bin is itself a secondary
    source ([gpus/b300.md §1, §11.10](../../gpus/b300.md)).
19. `S`, the engine's per-request state-slot count, for this model. kern uses 2;
    no other engine documents one ([architecture.md §5.3](architecture.md)).
20. Engram `NgramHashState` per-sequence size — not stated anywhere.
21. Per-frame / video vision cost — no video pipeline is documented for this
    model, and the vLLM reference command disables the vision tower entirely.

### 6.4 Accuracy caveats of the executed precision

NVFP4 W4A4 at group 16 on this checkpoint is an **accuracy wash versus the source
MXFP4**, measured by NVIDIA on vLLM on GB300
([architecture.md §10.1](architecture.md)): GPQA Diamond +0.25, AA-LCR −0.13,
SciCode +1.44, IFBench +0.60, MMMU-Pro −0.35, Terminal-Bench 2.1 +0.56 — four
wins, two losses, all inside ±1.5 points on benchmarks with 5–16 repeats. The
defensible claim is *"group-16 NVFP4 does not cost accuracy versus group-32
MXFP4"*, not *"NVFP4 is more accurate"*.

Three caveats the card states itself:

* *"Lossless weight conversion does not imply identical inference outputs."*
* **18 of 46,080 projection entries used fallback activation scales** — 0.04 % of
  the calibrated scales failed and were defaulted. Which layers they sit on is
  not published (§6.3 item 2's sibling).
* Calibration was **1,024 samples at sequence length 512** (cnn_dailymail +
  Nemotron-Post-Training-v2). For a model whose headline is a 1,048,576-token
  context, the activation scales are calibrated on 512-token sequences. The card
  offers no long-context accuracy evaluation, and AA-LCR (the one long-context
  benchmark in the table) is the benchmark NVFP4 **loses** on.
* The accuracy evals were run on **vLLM on GB300**. SGLang was validated only by
  *"loading, generation, reasoning/tool-call parsing, and image-input smoke
  tests"*. Nothing was evaluated on B300.

One more precision caveat that is architectural rather than quantisation-related:
`rms_norm_eps` is **1e-20** ([architecture.md §2](architecture.md)). fp32 norm
accumulation is mandatory, and the mHC tensors are shipped FP32 for the same
reason. Any kernel that quietly drops a norm to BF16 on this model is a
correctness bug, not a speed/accuracy tradeoff — and SGLang has already shipped
one Blackwell numerical fix of exactly this shape for a sibling model
(*"DeepSeek-V4-Pro NaN on NVIDIA Blackwell … convert the fp8_einsum input scale
to ue8m0"*, [gpus/b300.md §7](../../gpus/b300.md)).

**Fixed:**

- §3.1: the printed MBU curve-fit formula read
  `MBU(b) = 0.055 + (0.210-0.055) × ln(b)/ln(640)`, which does not reproduce
  its own calibration table (at b=640 this gives 0.210, not the printed
  anchor 0.215; at b=1 it gives 0.055, not the printed 0.054). The actual
  constants used to produce every value in that table and in every
  downstream §3.2/§4 table are 0.054 and 0.215 (verified by exact
  reproduction of all six printed b-values and of every downstream table).
  Corrected the formula's displayed constants to match; no table values
  changed, since they were already computed with the correct constants.

**Not fixed — flagged as an internal modeling-assumption inconsistency,
not a >5% arithmetic error:**

- §3.2's decode-step formula divides the single shared latent KV-cache read
  (`kv_read`) by `n_gpus = 4`, i.e. it assumes the KV stream is **sharded**
  across TP4 ranks (DP-attention / decode context-parallel). But §5.3's
  launch commands — the only ones actually validated for this checkpoint —
  run plain `--tp 4` with no `--enable-dp-attention` or `--dcp`, which per
  §1.3's own analysis (`num_key_value_heads = 1`) means the KV cache is
  **replicated** on every rank instead. Under that (conservative) reading,
  §1.4's own table shows max-concurrency at 128K drops from 3,479 to 869 (4×
  lower), and per-GPU decode-step bytes at high context/batch would be
  correspondingly larger, materially changing every TPOT/TTFT/cost number in
  §3.2–§4 (not a small correction — the two readings differ by 4×, as §6.3
  open question 11 already states). This is the same ambiguity §6.3 item 11
  already flags as unresolved, but that item doesn't note that §3.2's own
  arithmetic silently picks the optimistic side of the ambiguity while its
  header says plain "TP4". Recomputing the whole of §3.2–§4.4 under the
  conservative assumption is a substantive re-derivation, not an in-place
  numeric fix, so it is left as noted here rather than silently resolved in
  either direction, per the audit brief.
