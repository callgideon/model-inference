# nvidia/DeepSeek-V4.1-Flash-NVFP4 on AMD Instinct MI355X 288GB (8-GPU platform, ROCm 7; MXFP4/FP8 native, NVFP4 not native)

Research date: **2026-09-19**. Formulas, markers, scenarios and planning constants follow
[`research/METHODOLOGY.md`](../../METHODOLOGY.md). Checkpoint facts come from
[`architecture.md`](./architecture.md); hardware facts from
[`research/gpus/mi355x.md`](../../gpus/mi355x.md); kernel, format, engine, serving and price
facts from the five `research/cross-cutting/` documents cited inline. Those documents are
fact-checked and are used as **inputs**, not re-derived. All arithmetic was run in `python3`
and the script's output tables are pasted verbatim.

The **base** checkpoint on this same GPU is analysed in
[`research/models/deepseek41f/mi355x.md`](../deepseek41f/mi355x.md). This document is about
the one question that matters for the NVFP4 build on AMD: **does it beat the base checkpoint
here, or even run?**

---

## 0. Verdict

1. **Not runnable today as a production configuration.** No engine serves *this* checkpoint on
   gfx950: SGLang's only fast path (`--quantization quark_mxfp4`, NVFP4→MXFP4 at load) has **no
   DeepSeek-V4.1 model support on gfx950 at all** — [PR #39186 is closed, unmerged, 2026-09-12](https://github.com/sgl-project/sglang/pull/39186)
   — and vLLM-ROCm, which *does* serve V4.1, routes a `MIXED_PRECISION` ModelOpt checkpoint to
   `modelopt_mixed`, whose NVFP4 MoE backends on gfx950 reduce to **`EMULATION`** (Triton,
   dequantise-to-BF16 **every forward step**). Engine + version if you try it anyway: **vLLM
   `main` / `vllm/vllm-openai-rocm:nightly`** with `--moe-backend emulation` — ⚠️ untested for
   this pair by anyone.
2. **Min 4 GPUs, recommended 4** — `--tensor-parallel-size 4` on half a UBB baseboard. TP2 is
   `infeasible (weights)` (−10.75 GB KV budget) unless the Engram tables are host-offloaded;
   TP8 buys KV headroom nothing needs. Never TP16: the scale-up domain is 8.
3. **Weight format actually executed: BF16** (NVFP4 nibbles unpacked in a Triton kernel on
   every step), **not** NVFP4 and **not** MXFP4. The one path that would reach the 10.1 PFLOPS
   matrix core — requantise to MXFP4 — is exactly the path that is unavailable for this
   architecture. Attention and Engram stay FP8/MXFP8 (native); **KV runs FP8 at 1,650 B/token,
   not the checkpoint's 890 B/token**, because `nvfp4_ds_mla` is `major == 10` only.
4. **Interactive (S1, 4K in / 512 out, TPOT ≤ 50 ms): $1.94 per 1M output tokens** (audit fix
   2026-09-19, was $1.89 — §3.1's decode-bytes table divided the replicated KV read by the TP
   degree; corrected) at the only published MI355X price (**OCI $8.60/GPU-hr**, simultaneously
   the `low` and the `high` planning row), conc 128, `est.` — and that figure **excludes the
   per-step dequantisation cost**, i.e. it is a ceiling the emulation path cannot reach.
5. **Max throughput (S4): $1.12 per 1M output tokens** `est.` at conc 256 (audit fix 2026-09-19,
   was $1.06), same caveat.
   **Confidence: `not-runnable`.** Every number in §3–§4 is the cost of the *bytes*; the
   executed *kernel* is unmeasured and vLLM's own code comment for the analogous MXFP8
   emulation path reads *"the dominant cost (conc1 ~1.3 tok/s)"*.

> **The nearest runnable alternative is the base checkpoint**, `deepseek-ai/DeepSeek-V4.1-Flash`
> — MXFP4 experts on CDNA4 scaled MFMA, FP8 32×32 on OCP-FP8, a published vLLM-ROCm TP4 recipe,
> a real 6-point MI355X measurement, 510.29 GB instead of 527.27 GB, and identical accuracy
> (NVFP4 is accuracy-neutral vs MXFP4, ±1.5 pts over 6 benchmarks,
> [architecture.md §10.1](./architecture.md)). See
> [`research/models/deepseek41f/mi355x.md`](../deepseek41f/mi355x.md). **There is no scenario in
> which the NVFP4 build is the right artifact on this GPU.**

**Minimum GPUs = 4. Recommended = 4.** Multi-node fabric is **not needed** at 4 or 8 GPUs —
every TP4 all-reduce stays on the 1,075 GB/s fully-meshed UBB baseboard. 16 GPUs means two
baseboards over 8 × 400G RoCE/IB, and [`gpus/mi355x.md §4`](../../gpus/mi355x.md) is explicit
that TP > 8 collapses; the shape this topology rewards is **TP ≤ 8 plus data-parallel
replicas** (MLPerf 6.0 measured 93 % offline / 98 % interactive scale-out at 11 nodes on
exactly that shape). **Wide-EP is architecturally unavailable**: there is no 32–72 GPU coherent
domain until Helios/MI400.

**The capacity penalty of choosing this build on this GPU, priced out:**

```
  NVFP4 527.27 GB vs base MXFP4 510.29 GB = +16.99 GB (+3.33 %)
  extra HBM at TP4: +4.25 GB/GPU -> KV budget 121.07 GB vs 125.31 GB for the base
  max_concurrency(128K, FP8 KV, TP4): 552 (NVFP4) vs 571 (base) = -3.3 %
  extra NVMe/network read at 10 GB/s: +1.7 s per cold start
```

### 1.3 What cannot be sharded

| Tensor / state | Shardable? | Bytes | Consequence |
|---|---|---|---|
| **Compressed main KV + indexer K (CSA2 latent)** | **No — replicated on every TP rank.** `num_key_value_heads: 1` is a single shared latent per layer, and MLA-family caches replicate under TP ([serving-optimizations.md §3.1](../../cross-cutting/serving-optimizations.md); §7.1 flags ⚠️ for V4.1) | 1,650 B/token/seq **per GPU** at FP8 | This is why the table above does **not** multiply by `n_gpus`, and why the decode KV read does not shrink with TP. The single strongest argument for DP-attention here (§2) |
| SWA ring buffers (43 layers × 128 slots) | Replicated (same reason) | 2.77 MiB/seq (FP8) – 5.38 MiB ⚠️ | dominates below ≈ 6.3 K context |
| MoE routers `ffn.gate` + `bias`/`bias_vl` (BF16 + FP32) | Replicated | 0.157 GB | negligible in bytes |
| mHC coefficient projections `hc_attn_fn` / `hc_ffn_fn` (**FP32**) | Replicated | 0.157 GB | negligible in bytes, **85 % of the decoder's kernel launches** before vLLM PR #56503 ([RFC #56506](https://github.com/vllm-project/vllm/issues/56506)) |
| RMSNorm weights, attention sinks, image tokens | Replicated | ≈ 0.0004 GB | — |
| **Routed experts (NVFP4, 305.77 GB)**, attention (FP8), shared experts (FP8), embeddings / `head` | Yes — EP / TP / vocab-parallel | the bulk | shards cleanly |
| **Engram lookup tables (202.76 GB / 188.83 GiB)** | **Yes, by row** (`ParallelEngramEmbedding`); a CUDA TP4 community run reports *"48 GB of rows per worker"* ([architecture.md §4.2](./architecture.md)) | 50.69 GB/GPU at TP4 | ⚠️ **TO BE VERIFIED for vLLM-ROCm specifically** — no ROCm document states the Engram sharding policy. If it replicates, TP4 does not fit (131.82 + 3 × 50.69 = 283.9 GB > 259.2 GB usable) and TP8 or `cpu_offload` becomes mandatory |

Total replicated non-KV bytes ≈ **0.32 GB/GPU**, already charged in §1.2.

## 3. Throughput and latency

### 3.1 MBU / MFU assumptions, and why there are three models

METHODOLOGY §4 plans MI355X/ROCm decode at **MBU 0.4–0.6** and FP4 prefill at **MFU 0.20–0.35**
([gpus/mi355x.md §9](../../gpus/mi355x.md) adds *"plan at the bottom of each band"*). The only
published MI355X measurements of this *architecture* sit at **≈ 0.107 MBU** — four to six times
below the band. Rather than discard either fact, three models are reported:

- **(A) Hardware ceiling** — roofline at MBU 0.4 / 0.5 / 0.6.
- **(B) Calibrated** — the two-parameter fit `step_ms = 4.963 + 1.1684 × bytes_GB_per_GPU`
  derived in [`deepseek41f/mi355x.md §3.1`](../deepseek41f/mi355x.md) from the six-point
  InferenceX MI355X sweep ([PR #3068](https://github.com/SemiAnalysisAI/InferenceX/pull/3068)):
  4.96 ms of fixed launch/sync overhead plus an effective 0.856 TB/s. It is reused here
  **unchanged** because the fit is a property of the ROCm stack and the model's kernel graph,
  both identical between the two builds; only the expert *bytes* differ. It therefore
  **excludes** the NVFP4 dequantisation pass, which the base checkpoint does not pay.
- **(C) Measured** — §3.4. There is none for this pair.

Prefill uses METHODOLOGY's bottom-of-band MFU per tensor group and an effective 500 TFLOPS for
attention/indexer, taken from the only published gfx950 attention numbers (436 CK / 497–509
AITER ASM TFLOPS at hd 256 — ⚠️ three of those four are **MI350X**, not MI355X;
[flash-attention.md §9.6, §15.3](../../cross-cutting/flash-attention.md)).

**Decode bytes per step.** Distinct-expert model `384 × (1 − (1 − 6/384)^b)`; one routed expert
is **19,906,584 B at NVFP4 gs16** vs **18,800,640 B at MXFP4 gs32**
([architecture.md §6.3](./architecture.md)); static non-expert traffic 18.75 GB; KV read per
sequence recomputed at FP8 ([deepseek41f/mi355x.md §3.1](../deepseek41f/mi355x.md)):

```

**Audit fix 2026-09-19:** the `tot/GPU TP4` column previously read `(wt GB + KV GB) / 4`, i.e. it
divided the KV-read bytes by the TP degree. Per §1.3 (this same document) the compressed
main KV, indexer K and SWA ring are **replicated on every TP rank, not sharded** — only the
routed-expert/attention/shared weight bytes shard across TP4. The corrected column is
`wt GB / 4 + KV GB` (weights shard, KV does not). The error is small at batch ≤ 32 (≤ 4.3 %)
but reaches **−13.0 % at batch 256** — a genuine per-GPU-vs-aggregate mix-up, not rounding.
This propagates into §3.2's roofline table and §3.3's NVFP4 columns, both corrected below.

**Read this row first: the NVFP4 build moves up to 5.5 % more bytes per decode step than the
base for identical work.** That is the finer scale layout showing up in the one place it can
never pay for itself on this GPU — because the finer scale is what the CDNA4 matrix core
cannot consume.

Four readings, in order of importance:

1. **The TPOT ≤ 50 ms SLO is never binding *with* DSpark and binds hard *without* it.** Without

document cannot bound it from a roofline and marks it ⚠️.

    batch   1:    35.74 GB/step vs    23.53 GB NVFP4-packed = 1.52x  -> TP8 step   10.18 ms

    batch 256:  1086.62 GB/step vs   319.09 GB NVFP4-packed = 3.41x  -> TP8 step  163.66 ms
```

It would **force TP8**, triple the decode traffic at batch ≥ 32, and land at ~164 ms per step at
batch 256 against the base checkpoint's 95 ms at TP4. The workaround that rescues MXFP8
emulation does not rescue this one — 4-bit weights are too far from BF16 for a load-time
unpack to be affordable on a 763 B-parameter model.

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

**One node, half of it.** TP4 on 4 of 8 GPUs is the shape with a published recipe (for the base);
the natural production layout is **two independent TP4 replicas per 8-GPU UBB baseboard**, which
is what the topology rewards — every TP4 all-reduce stays on the 1,075 GB/s mesh
([gpus/mi355x.md §4](../../gpus/mi355x.md)) and MLPerf 6.0 measured 92–98 % efficiency scaling
*replicas* out to 11–12 nodes. **Never TP16.** There is no NVL72 analogue, so the wide-EP decode
economics that make this model cheap on GB300 are simply unavailable here. TP8 is the fallback
if the Engram tables turn out to replicate rather than shard under vLLM-ROCm (§1.3 ⚠️) — or if a
load-time BF16 dequant ever ships, in which case TP8 becomes mandatory (§3.5).

### 5.2 When PD disaggregation or wide-EP pays — and why not here

The CED architecture is the textbook PD-disaggregation candidate: prefill activates **7.89 B**
parameters, decode **16.11 B** ([architecture.md §3.2](./architecture.md)), so the two phases
want different hardware ratios, and DeepSeek's own deployment runs EPD (encoder / prefill /
decode) disaggregation. **None of it is available on MI355X today**: Dynamo has no documented
ROCm support, TokenSpeed's V4.1-Flash 1P1D CI is **GB300-only and targets the base MXFP4 repo**,
and no published gfx950 PD run exists for either checkpoint
([gpus/mi355x.md §7](../../gpus/mi355x.md), [architecture.md §8.6](./architecture.md)).
Wide-EP needs a 32–72 GPU coherent domain that does not exist on this part.
⚠️ **TO BE VERIFIED**: whether SGLang's PD path works on gfx950 for this architecture at all —
moot while PR #39186 stays closed, and SGLang's own docs note *"PD and speculative decoding
cannot be combined"*, which would forfeit DSpark and with it §3.3's entire interactive envelope.

527.27 GB from NVMe, `est.` at the stated 5–20 GB/s:

## 6. Risks and open questions

**Blocking**

1. ⚠️ **No engine serves this checkpoint on gfx950.** SGLang has no `DeepseekV41` gfx950 support
   ([PR #39186 closed unmerged, 2026-09-12](https://github.com/sgl-project/sglang/pull/39186)),
   lists ModelOpt variants as unsupported on ROCm, and its eight-rank DSpark collective *"aborts
   inside RCCL graph capture"*. vLLM-ROCm serves the architecture but has no NVFP4 expert kernel
   for it beyond `EMULATION`. **Nobody has published a run of this pair.**
2. ⚠️ **The one path that would make this work — `quark_mxfp4` online requantisation — is
   blocked by model support, not by format support.** The format conversion is proven
   accuracy-neutral and throughput-neutral on five other models; this architecture simply is not
   one of them on SGLang-ROCm.
3. ⚠️ **The emulation path's throughput is unmeasured and structurally bad.** AMD calls it *"an
   accuracy reference … rather than a production serving deployment"*; vLLM's in-kind MXFP8
   datum is *"conc1 ~1.3 tok/s"*. Every §3.3 and §4.2 number **excludes** it.
4. ⚠️ **Mixed NVFP4 (backbone, emulated) + MXFP4 (MTP/DSpark, native) in one process** is the
   highest-risk untested combination in the checkpoint on *any* GPU
   ([architecture.md §7.3](./architecture.md)), and on ROCm the two halves take entirely
   different code paths.
5. ⚠️ **DSpark acceptance on ROCm is unmeasured, and §3.3's whole interactive envelope depends on
   it.** Without speculation the TPOT ≤ 50 ms ceiling is **batch 36**; with the assumed 3.51 it is
   past 2,048. NVIDIA did not exercise speculation for this checkpoint at all.

**Engine and kernel issues, all sourced**

6. `enable_adaptive_verification` **must be `false`** on ROCm (two failing checks in
   `maybe_create_adaptive_verification_manager`).
7. `torch.compile` is **unsupported for this model**; the ROCm sparse-SWA backend supports only
   uniform-batch graphs → `VLLM_USE_BREAKABLE_CUDAGRAPH=1` is mandatory.
8. `batched_gemm_a8w8_mxscale` **segfaults during HIP-graph capture on gfx950**
   ([PR #57081](https://github.com/vllm-project/vllm/pull/57081), open), and V4.1 *"segfaults on
   the 3rd decode token with FULL_DECODE_ONLY graphs unless `--no-async-scheduling` is set"*
   ([issue #56347](https://github.com/vllm-project/vllm/issues/56347)).
9. ⚠️ **No gfx950 DSA / hierarchical-indexer kernel is confirmed** — decides 1M-context
   viability, and no vendor has published a 1M-context decode step time on any GPU.
10. ⚠️ **Whether the compressed latent KV replicates or shards across TP ranks is unresolved.**
    This document takes the replicated (binding) reading; if it shards,
    `max_concurrency(128K, TP4)` rises from 552 to ~2,200 and the decode KV term falls 4×.
11. ⚠️ **Engram sharding policy on vLLM-ROCm is undocumented.** §1.2 assumes row-sharding
    (evidenced only on a CUDA TP4 community run). If it replicates, TP4 does not fit.
12. ⚠️ **Prefill throughput for this architecture on gfx950 has never been measured** — every
    published run sits at 94–100 % prefix-cache hit. §4.3's 16× input-cost band follows directly.
13. **TensorRT-LLM and Dynamo do not exist on ROCm**; TensorRT-LLM has no V4.1 row at all.
14. vLLM's verified-hardware list for this architecture says `"mi350x": "verified"` — **not**
    `mi355x`. Same `gfx950` target, so it carries over, but the vendor has not named this part.
15. AITER's support word for CDNA4 is *"Supported"*, not *"Fully supported"*, and AMD's
    [aiter#2493](https://github.com/ROCm/aiter/issues/2493) — *"we were incorrectly benchmarking
    decode attention using standard SDPA instead of the MLA decode kernel"* — has been open since
    2026-03-26.
16. **MXFP4 MoE kernels are shape-specialised** ([vllm#35637](https://github.com/vllm-project/vllm/issues/35637));
    TP4 is known-good for the base, but do not assume TP2 or TP8 inherits it.
17. ⚠️ **The checkpoint's own config contradicts itself**: `input_activations.dynamic = false`
    (static calibrated scales) against a sibling `activation_scheme: "dynamic"`
    ([architecture.md §1.2](./architecture.md)). Which one an emulation kernel honours — and
    therefore whether the fake-quant round trip uses the calibrated scales at all — is unresolved.
18. ⚠️ **NVIDIA's own recipe sets `--no-enable-prefix-caching`** for this checkpoint and does not
    say why (likely an SWA-Bounded-Replay interaction). On the agentic traces this model targets,
    that forfeits the largest available win.
19. ⚠️ **The ViT is unexercised on gfx950** by any published run of either checkpoint, and
    `--language-model-only` is in every published command.

**Accuracy caveats of the executed precision**

20. **The precision actually executed is BF16** (NVFP4 nibbles unpacked per step), so the
    numerics question is not "does FP4 hurt" but "does the fake quantize–dequantize round trip
    reproduce Blackwell's W4A4 result". AMD reports its emulation matches NVIDIA's checkpoints
    *"within statistical noise"* on GSM8K and MMLU-Pro for Kimi-K2.6 and Qwen3-8B; **nothing is
    published for this checkpoint**. The upside of this arrangement is real and worth stating:
    emulation is an *accuracy* path, and it is the correct tool if your goal is to validate the
    NVFP4 numerics of a Blackwell deployment on AMD silicon.
21. **If the requant path ever lands, you inherit MXFP4's accuracy, not NVFP4's**
    ([quantization-formats.md §3.2](../../cross-cutting/quantization-formats.md)) — which is the
    base checkpoint's accuracy, which NVIDIA's own table shows is within ±1.5 points of NVFP4's
    across six benchmarks ([architecture.md §10.1](./architecture.md)). **That is the whole
    argument against this build on this GPU in one sentence:** the only reachable execution
    format is the one the base checkpoint already ships.
22. **FP8 KV is a real precision change and it is forced here.** The model was designed around an
    FP4 main KV with an E4M3 scale per 16 channels; FP8 E4M3 with an E8M0 scale per 32 is a
    *different* quantiser. ⚠️ No published eval compares FP8-KV to FP4-KV accuracy for this
    checkpoint, and every layer carries an SWA component, which
    [quantization-formats.md §8.3](../../cross-cutting/quantization-formats.md) flags as
    *"more sensitive to KV-cache quantization"*.
23. **18 of 46,080 projection entries used fallback activation scales** during NVIDIA's
    calibration (0.04 %) — ⚠️ whether they sit on hot layers is unstated, and an emulation kernel
    that honours the static scales inherits them.
24. **SWA Bounded Replay** *"barely compromises response quality"* with no number published, and
    on SGLang it *"refuses prompt logprobs by design"*. Unquantified either way on ROCm.

**Open opportunities (upside, not risk)**

25. **MXFP6 (W4A6) is the one lever that could make MI355X beat Blackwell on this family** — FP6
    at the FP4 rate is unique to this silicon, and the published W4A6 evidence (Llama-3.1-8B
    GSM8K 62.55 → 76.4 %, offline throughput *above* FP8) is strong. No serving engine emits
    MXFP6 MFMA today ⚠️.
26. **A `quark_mxfp4` implementation for `DeepseekV41` on gfx950** would close this entire
    document: the format conversion is proven, the model support is what is missing. That is one
    PR, not a research programme.
27. **DP-attention** would remove the replicated-KV penalty in §1.3 and §3.5; no MI355X recipe
    for this family uses it ⚠️.
28. The ROCm decode stack is moving fast: #56503 merged, #56560, #56628 and #57081 were **open**
    on 2026-09-19. **Any MI355X number here older than a month is likely pessimistic** — for the
    base checkpoint. None of that work touches the NVFP4 emulation kernel.

column computed `(weight_GB + KV_GB) / 4`, dividing the **replicated** decode-KV read by the TP
degree — contradicting this same document's own §1.3 invariant ("the decode KV read does not
shrink with TP4 … 4 GPUs read the same bytes"). Correct: `weight_GB / 4 + KV_GB` (only the
weight bytes shard). Error was ≤ 4.3 % through batch 32, crossed 5 % at batch 64, and reached
**−13.0 % at batch 256**. Fixed in place, and propagated through every table that consumes it:
- §3.1 `NVFP4 tot/GPU TP4 GB` column (all 6 batches).

  and both TTFT columns are reused unchanged from `deepseek41f/mi355x.md`, outside this audit's
  reading scope, and were left alone — TTFT is dominated by the prefill term and moves < 5 % even
  at the worst-case cell, so leaving it does not reintroduce the same class of error).
