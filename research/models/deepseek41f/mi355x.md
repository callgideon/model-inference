Research date: **2026-09-19**. Formulas, markers, scenarios and planning constants follow
[`research/METHODOLOGY.md`](../../METHODOLOGY.md). Model facts are taken from
[`architecture.md`](./architecture.md); hardware facts from

## 0. Verdict

1. **Runnable today, and it is the *only* DeepSeek-V4.1-Flash target where the checkpoint's
   own format is native end to end** — MXFP4 experts on CDNA4 scaled MFMA, FP8 32×32 dense on
   OCP-FP8 — via **vLLM `main`/nightly on ROCm** (`vllm/vllm-openai-rocm:nightly`; the InferenceX
   run pins `…:nightly-eed1f3d0c6043bd494424a22443ee198dd56f657`). No numbered vLLM release
   carries the architecture; SGLang's gfx950 branch (PR #39186) is **closed, unmerged**.
2. **Minimum 4 GPUs, recommended 4** (`--tensor-parallel-size 4`, `--moe-backend aiter`, no
   expert-parallel flag in the published recipe). TP2 is **infeasible** with the Engram tables
   resident (−1.94 GB KV budget) and only works with `--engram-config '{"cpu_offload":true}'`;
   TP8 buys KV headroom nobody needs here. TP16 leaves the 8-GPU scale-up domain and is not a
   configuration for this part.
3. **Weight format actually executed: MXFP4 (native, A8W4 Composable Kernel) + FP8 E4M3 OCP —
   the base checkpoint, unconverted.** The NVFP4 sibling build has no CDNA4 path and would be
   requantised back to MXFP4 at load; it is larger and has no published speedup, so on MI355X
   there is no reason to use it. **The KV cache is the exception: the checkpoint's FP4 main-KV
   layout has no gfx950 kernel, so KV runs FP8 at 1,650 B/token, not the 890 B/token headline.**
4. **Interactive (S1, 4K in / 512 out, TPOT ≤ 50 ms): $1.07 – $1.85 per 1M output tokens** at
   the only published MI355X price (**OCI $8.60/GPU-hr**, which is simultaneously the `low` and
   the `high` planning row), concurrency 128–256 `est.`; **$9.22 per 1M output** at the one
   *measured* operating point (InferenceX agentic traces, concurrency 32).
5. **Max throughput (S4): $1.07 per 1M output tokens** `est.` at concurrency 256.
   **Confidence: `estimate`** — fit anchored on a real 6-point MI355X sweep, extrapolated 4–8×
   beyond it; the decode stack today runs at **≈10.7 % MBU**, so every number here is a software
   statement about ROCm in September 2026, not a statement about the silicon.

**Minimum GPUs = 4** (TP4). **Recommended = 4** — the recipe default
([architecture.md §8.4](./architecture.md), [inference-engines.md §3.9](../../cross-cutting/inference-engines.md)),

means two UBB baseboards over 8 × 400G RoCE/IB; do **not** run TP16 across it —
[`gpus/mi355x.md §4`](../../gpus/mi355x.md) is explicit that TP > 8 collapses and the shape the
topology favours is **TP ≤ 8 plus data-parallel replicas** (MLPerf 6.0 measured 93 % offline /
98 % interactive scale-out efficiency at 11 nodes on that shape).

### 1.3 What cannot be sharded

| Tensor / state | Shardable? | Bytes | Consequence |
|---|---|---|---|
| **Compressed main KV + indexer K (CSA2 latent)** | **No — replicated on every TP rank.** `num_key_value_heads: 1` means one shared latent per layer; MLA-family caches replicate under TP, as [serving-optimizations.md §3.1/§7.2](../../cross-cutting/serving-optimizations.md) states for Kimi-K3 and §7.1 flags ⚠️ for V4.1 | 1,650 B/token/seq **per GPU** | This is why `max_concurrency` in §1.2 does **not** multiply by `n_gpus`. It also means the KV read in the decode step does not get cheaper with TP — the single biggest argument for **DP-attention** here (§2) |
| SWA ring buffers (43 layers × 128 slots) | Replicated (same reason) | 2.77 MiB/seq | dominates below ~6.3 K context ([architecture.md §5.4](./architecture.md)) |
| MoE routers `ffn.gate` (384 × 5120 × 40, BF16) | Replicated | 0.157 GB | negligible |
| mHC coefficient projections `hc_*_fn` (F32, 24 × 20480) | Replicated | 0.157 GB | negligible in bytes, **85 % of the decoder's kernel launches** before vLLM PR #56503 ([RFC #56506](https://github.com/vllm-project/vllm/issues/56506)) |
| RMSNorm weights, `gate.bias` / `bias_vl`, `attn_sink` (F32) | Replicated | ≈ 0.001 GB | — |
| Routed experts, attention projections, embeddings/lm_head | Yes (EP / TP / vocab-parallel) | 500+ GB | the bulk shards cleanly |
| **Engram tables (188.83 GiB)** | **Yes, by row** — the DGX Spark TP4 community run reports *"48 GB of rows per worker"*, i.e. 4 × 48 ≈ the whole table ([architecture.md §4.1](./architecture.md), [repo](https://github.com/tonyd2wild/DeepSeek-V4.1-Flash-vLLM-DGX-Spark)) | 50.69 GB/GPU at TP4 | ⚠️ **TO BE VERIFIED** for vLLM-ROCm specifically; no ROCm document states the Engram sharding policy. If it replicates instead, TP4 becomes infeasible (127.57 + 3 × 50.69 = 279.6 GB > 259.2 GB usable) |

Total replicated non-KV tensors ≈ **0.32 GB/GPU** — small enough that §1.2's tables are
unchanged by it, which is why it is not a separate column.

## 3. Throughput and latency

### 3.1 MBU / MFU assumptions — and why the METHODOLOGY band does not apply here

METHODOLOGY §4 plans MI355X/ROCm decode at **MBU 0.4–0.6** and FP4 prefill at **MFU 0.20–0.35**
(the GPU doc adds: *"plan at the bottom of each band"*). **The published MI355X measurements for
this model sit at ≈ 0.10 MBU, four to six times below that band.** Rather than ignore either
fact, this section reports three models:

- **(A) Roofline ceiling** at MBU 0.4/0.5/0.6 — what the silicon could do.
- **(B) Calibrated model** — a two-parameter fit to the six-point InferenceX MI355X sweep. This
  is what the tables in §3.3 use.
- **(C) Measured** — §3.4.

Decode bytes per step (METHODOLOGY §4, distinct-expert model
`384 × (1 − (1 − 6/384)^b)`, one MXFP4 expert = 18,800,640 B, static resident non-expert weights
18.75 GB, KV read recomputed at **FP8** from [architecture.md §6.3](./architecture.md)'s FP4 terms
— `2.77 MiB SWA + 38×512×528 B main + 4×16384×132 B pool + 330 B/token × ctx`):

```
 batch  distinct exp/layer  weight GB | KVrd/seq@8K  @32K   @128K     @1M   (MiB)
     1                 6.0      23.26 |      23.40  31.13   62.07  350.82
     8                45.5      52.93 |      23.40  31.13   62.07  350.82
    32               152.0     133.07 |      23.40  31.13   62.07  350.82
    64               243.8     202.13 |      23.40  31.13   62.07  350.82
   128               332.8     269.06 |      23.40  31.13   62.07  350.82
   256               377.2     302.40 |      23.40  31.13   62.07  350.82
```

Weight bytes are divided by TP; **KV bytes are not** (§1.3, replicated latent).

**Calibration.** The InferenceX MI355X sweep ([PR #3068](https://github.com/SemiAnalysisAI/InferenceX/pull/3068),
TP4, 131,072 ctx, DSpark γ=5 with the synthetic acceptance constant 3.51) gives six
(concurrency, mean ITL) points. Decode step time = ITL × 3.51:

```
 conc  ITL ms  step ms  bytes/GPU GB  roofline ms@MBU1  implied MBU
    1    3.90    13.69         5.881             0.735        0.054
    2    4.17    14.64         7.056             0.882        0.060
    4    4.53    15.90         9.355             1.169        0.074
    8    5.24    18.39        13.754             1.719        0.093
   16    7.87    27.62        21.809             2.726        0.099
   32   13.80    48.44        35.349             4.419        0.091

fit: step_ms = 4.963 + 1.1684 * bytes_GB
     -> fixed 4.96 ms launch/sync overhead, effective BW 0.856 TB/s = MBU_eff 0.107
residuals: 1:-1.85  2:-1.43  4:-0.01  8:+2.64  16:+2.82  32:-2.17   (ms)
```

The independent cross-check is [InferenceX #3058](https://github.com/SemiAnalysisAI/InferenceX/pull/3058)'s
direct step traces at the same context: 18.31 / 18.40 / 25.92 ms at conc 1 / 4 / 16 against the
fit's 11.83 / 15.90 / 27.62 — the same shape, on a slightly earlier build.

**MFU for prefill.** No MI355X prefill measurement for this model isolates GEMM throughput. The

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

**One node, half of it.** TP4 on 4 of the 8 GPUs is the published shape; the natural production
layout is **two independent TP4 replicas per 8-GPU UBB baseboard**, which is also what the
topology rewards — every TP4 all-reduce stays on the 1,075 GB/s mesh
([gpus/mi355x.md §4](../../gpus/mi355x.md)), and MLPerf 6.0 measured 92–98 % efficiency scaling
*replicas* out to 11–12 nodes. **Never TP16.** There is no NVL72 analogue, so the wide-EP decode
economics that make this model cheap on GB300 are simply unavailable.

### 5.2 When PD disaggregation or wide-EP pays — and why not here

The CED architecture is the textbook PD-disaggregation candidate: prefill activates 7.89 B
parameters, decode 16.13 B ([architecture.md §6.1](./architecture.md)), so prefill and decode
want different hardware ratios, and DeepSeek's own deployment runs **EPD** (encoder / prefill /
decode) disaggregation. **None of it is available on MI355X today**: Dynamo has no documented
ROCm support, TokenSpeed's 1P1D CI is GB300-only, and vLLM's PD path (`vllm-router
--vllm-pd-disaggregation` + NIXL) has no published gfx950 run for this model
([gpus/mi355x.md §7](../../gpus/mi355x.md), [architecture.md §8.1](./architecture.md)).
Wide-EP needs a 32–72 GPU coherent domain that does not exist on this part. **⚠️ TO BE
VERIFIED**: whether SGLang's PD path works on gfx950 for this model — its own docs note
*"PD and speculative decoding cannot be combined"*, which would forfeit DSpark, and DSpark is
what makes §3.3's TPOT numbers work.

### 5.3 Launch command, quoted from the engine docs

vLLM ROCm, 4 × MI355X — verbatim from the
[vLLM recipe](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash), matching
[InferenceX #3058](https://github.com/SemiAnalysisAI/InferenceX/pull/3058) at commit `559ef756`:

```bash
export HIP_VISIBLE_DEVICES="$ROCR_VISIBLE_DEVICES"
export VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1
export AITER_TRITON_LOG_LEVEL=ERROR VLLM_USE_BREAKABLE_CUDAGRAPH=1
export OMP_NUM_THREADS=1 VLLM_ENGINE_READY_TIMEOUT_S=3600
export VLLM_USE_RUST_FRONTEND=1 PYTHONUNBUFFERED=1 GPU_COUNT=4
MODEL=deepseek-ai/DeepSeek-V4.1-Flash
SPEC_CONFIG='{"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"probabilistic","rejection_sample_method":"block","enable_adaptive_verification":false}'
exec vllm serve "$MODEL" --served-model-name "$MODEL" \
  --host 0.0.0.0 --port "$PORT" --tensor-parallel-size 4 \
  --language-model-only \
  --tokenizer-mode deepseek_v41 \
  --tool-call-parser deepseek_v41 --enable-auto-tool-choice \
  --reasoning-parser deepseek_v41 \
  --moe-backend aiter \
  --gpu-memory-utilization 0.9 \
  --speculative-config "$SPEC_CONFIG" \
  --max-model-len 1048576 \
  --max-num-seqs 128 \
  --max-cudagraph-capture-size 1024 \
  --max-num-batched-tokens 16384 \
  --disable-uvicorn-access-log
```

Image: `vllm/vllm-openai-rocm:nightly` (the benchmark pins
`…:nightly-eed1f3d0c6043bd494424a22443ee198dd56f657`, published 2026-09-12, which is the first
tag carrying both the AITER mHC fix and CK a8w4 expert selection). **No pip wheel serves this
architecture** — *"Serve from the image for your GPU vendor"*
([architecture.md §8.1](./architecture.md)).

Four deviations from the quoted command worth making deliberately:

- `--language-model-only` drops the ViT. **For multimodal traffic, swap it for
  `--mm-encoder-tp-mode data`** (they are mutually exclusive) and accept that no published
  gfx950 run has exercised the vision path ⚠️.
- `--moe-backend aiter` **by name**: *"Naming `aiter_triton_mxfp4_bf16` pins the Triton W4A16
  `_moe_gemm_a16w4` kernel"* and costs 4–9 % ([inference-engines.md §3.9](../../cross-cutting/inference-engines.md)).
- `rejection_sample_method` is `block` here — that is the real-rejection arm, and the one to
  serve production on. The throughput arm's `"synthetic"` + `3.51` is a benchmark fiction.
- Consider `--max-num-batched-tokens` **below** 16384 at first: SemiAnalysis found the ROCm
  default chunked-prefill size of 196,608 *"produced crash dumps; reducing to 32,768 resolved
  it"* ([gpus/mi355x.md §11](../../gpus/mi355x.md)).

### 5.4 Warm-up and load time

510.29 GB from NVMe, `est.` at the stated 5–20 GB/s:

```
   5 GB/s:  102.1 s   ;   61.5 s if the Engram tables stream to host instead
  10 GB/s:   51.0 s   ;   30.8 s
  20 GB/s:   25.5 s   ;   15.4 s
```

**Budget far more than that in practice.** The base environment sets
`VLLM_ENGINE_READY_TIMEOUT_S=3600` with the note *"Expect a long first load"*, 48 shards must be
deserialised and the MXFP4/FP8 tensors staged, and the ROCm path additionally captures breakable
HIP graphs up to size 1024. NVIDIA's own recipe for the same checkpoint reaches for
`--model-loader-extra-config '{"enable_multithread_load": true, "num_threads": 128}'`
([architecture.md §8.6](./architecture.md)) — ⚠️ **TO BE VERIFIED** whether that loader config is
honoured on the ROCm build. Cold-start is therefore a **minutes-scale**, not seconds-scale,
event: size autoscaling policies accordingly, and keep replicas warm.

## 6. Risks and open questions

**Blocking or near-blocking**

1. ⚠️ **DSpark acceptance on ROCm is unmeasured, and §3.3's entire interactive envelope depends
   on it.** Without speculation the TPOT ≤ 50 ms ceiling is **batch 39**; with the assumed 3.51
   it is past 2,048. 3.51 is a synthetic constant; the only real number for this checkpoint
   (3.57) is from 4 × GB10, a different architecture, with a 1.88–5.92 spread by workload type.
   **Measure `vllm:spec_decode_num_{accepted,draft}_tokens_total` on your own traffic before
   sizing anything from §3.3 or §4.2.**
2. ⚠️ **No gfx950 DSA / hierarchical-indexer kernel is confirmed.** AITER ships blockwise sparse
   Sage attention but no primary source confirms a DSA indexer kernel on gfx950
   ([gpus/mi355x.md §5](../../gpus/mi355x.md)). At 1M context the four Full-mode indexer scans
   cost 21.5 GFLOP/token — more than the entire encoder forward — so this decides 1M-context
   viability, and **no vendor has published a 1M-context decode step time on any GPU**.
3. ⚠️ **Whether the compressed latent KV replicates or shards across TP ranks is unresolved**
   ([serving-optimizations.md §7.1](../../cross-cutting/serving-optimizations.md)). This
   document takes the replicated (binding) reading. If it shards, `max_concurrency(128K, TP4)`
   rises from 573 to 2,292 and the decode KV-read term falls 4×, improving §3.3 materially at
   large batch.
4. ⚠️ **Engram sharding policy on vLLM-ROCm is undocumented.** §1.2 assumes it shards by row
   (evidenced only on a *CUDA* TP4 community run). If it replicates, TP4 does not fit and TP8
   or `cpu_offload` becomes mandatory.
5. ⚠️ **Prefill throughput for this model on gfx950 has never been measured** — every published
   run sits at 94–100 % prefix-cache hit. §4.3's 20× input-cost band is the direct consequence.

**Engine and kernel issues, all sourced**

6. `enable_adaptive_verification` **must be `false`** on ROCm (two failing checks in
   `maybe_create_adaptive_verification_manager`).
7. `torch.compile` is **unsupported for this model**, and the ROCm sparse-SWA backend supports
   only uniform-batch graphs → `VLLM_USE_BREAKABLE_CUDAGRAPH=1` is mandatory; without it
   *"default `FULL_AND_PIECEWISE` dies at capture."*
8. `batched_gemm_a8w8_mxscale` **segfaults during HIP-graph capture on gfx950**
   ([PR #57081](https://github.com/vllm-project/vllm/pull/57081), open).
9. **SGLang is not a viable path**: gfx950 PR #39186 is **closed and unmerged**, its eight-rank
   DSpark collective *"aborts inside RCCL graph capture"*, and the MI350X recipe must run
   `--disable-radix-cache`, forfeiting prefix caching.
10. **TensorRT-LLM and Dynamo do not exist on ROCm**; TokenSpeed's V4.1-Flash recipe is
    GB300-only in CI.
11. vLLM's verified-hardware list for this model says `"mi350x": "verified"` — **not** `mi355x`.
    Same `gfx950` target, so it carries over, but the vendor has not named this part.
12. AITER's own support word for CDNA4 is *"Supported"*, not *"Fully supported"* (MI300X/MI325X
    get the latter), and AMD's [aiter#2493](https://github.com/ROCm/aiter/issues/2493) —
    *"we were incorrectly benchmarking decode attention using standard SDPA instead of the MLA
    decode kernel"* — has been open since 2026-03-26.
13. **MXFP4 MoE kernels are shape-specialised**: an unrelated model hit *"device_gemm with the
    specified compilation parameters does not support this GEMM problem"* at TP4 + AITER on
    MI355X ([vllm#35637](https://github.com/vllm-project/vllm/issues/35637)). TP4 is exactly
    this model's shape — it is known-good here, but do not assume TP2 or TP8 inherits it.
14. ROCm 10.0.0 carries an AOTriton flash-attention **backward** regression on gfx950 (training
    only, but it indicates the kernel-selection heuristics are unsettled).

**Accuracy caveats of the executed precision**

15. The precision actually executed is the checkpoint's own (MXFP4 experts, FP8 dense), so
    there is **no quantisation delta to charge** — GSM8K 5-shot measured on MI355X at
    **0.9719 ± 0.0045 strict-match**, *"unchanged to four decimal places"* across the CK/Triton
    switch, and 0.9704 → 0.9735 across the vLLM ROCm fix stack. That is the cleanest accuracy
    story of any GPU in this repo for this model.
16. **FP8 KV is a real precision change, and it is forced here.** The model was designed around
    an FP4 main KV with an E4M3 scale per 16 channels; FP8 E4M3 with an E8M0 scale per 32 is a
    *different* quantiser, not a strictly better one. [quantization-formats.md §8.3](../../cross-cutting/quantization-formats.md)
    warns that *"sliding-window layers are more sensitive to KV-cache quantization"* and every
    layer here carries a 128-token SWA component. ⚠️ **No published eval compares FP8-KV to
    FP4-KV accuracy for this checkpoint.**
17. **SWA Bounded Replay** *"barely compromises response quality"* — no number published
    ([architecture.md §2.3](./architecture.md)), and on SGLang it *"refuses prompt logprobs by
    design"*. Unquantified either way on ROCm.
18. Reasoning effort is a cost lever, not a free knob: effort 25 → 100 lifts the 8-benchmark
    average 67.1 → 76.3 % for *"roughly 2.5× more output tokens"*; **effort 60–80 is the
    cost-efficient operating point** ([architecture.md §10.5](./architecture.md)). At $1.85/1M
    output that is the difference between $1.85 and ~$4.60 for the same task.

**Open opportunities (upside, not risk)**

19. **MXFP6 (W4A6) is the one lever that could make MI355X beat Blackwell on this pair** — FP6
    at the FP4 rate is unique to this silicon, and the published W4A6 evidence (GSM8K
    62.55 → 76.4 % on a dense model, offline throughput *above* FP8) is strong. No serving
    engine emits MXFP6 MFMA today ⚠️.
20. **DP-attention** would remove the replicated-KV penalty in §1.3 and §3.5; no MI355X recipe
    for this model uses it ⚠️.
21. The ROCm decode stack is moving fast: #56503 merged, #56560 (MXFP8 dequant, 11–12 % of
    kernel time), #56628 (candidate mask, *"2.7× / 4.3× / 6.0×"* at conc 1/4/16) and #57081
    (FP8 o-proj, −40.7 % TTFT) were **open** on 2026-09-19. **Any MI355X number in this document
    older than one month is likely pessimistic.**
