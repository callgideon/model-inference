## 0. Verdict

1. **Runnable today, and measured today.** vLLM `main`/nightly (`min_vllm_version 0.30.0`,
   `nightly_required: true`; image `vllm/vllm-openai:nightly-af1c0149…` in the sweep below)
   and SGLang `main` (commit `835c3909`, image `lmsysorg/sglang:dev-cu13-dsv41`) both serve
   this exact checkpoint on GB300; vLLM lists `"gb300": "verified"`. **TensorRT-LLM does not
   support V4.1** ([`inference-engines.md` §2.3/§6.1](../../cross-cutting/inference-engines.md)).
2. **Min 4 GPUs fully resident** (TP4, one GB300 compute tray, 128.96 GB weights/GPU,
   114.1 GB left for KV); **min 2 GPUs** only with `--engram-config '{"cpu_offload":true}'`
   pushing the 202.76 GB Engram tables onto Grace over the 900 GB/s C2C link (⚠️ not a
   published GB300 profile). **Recommended 4 GPUs, TP4 attention + EP4 or TP4 MoE**; the
   rack's value is 18 independent TP4 replicas, not one EP72 instance (§5).
3. **Weight format actually executed: native MXFP4 W4A8** on the sm_103 block-scaled
   datapath (E2M1 weights + MXFP8 activations), with the native **FP4 (E2M1 + one E4M3
   scale per 16) KV cache** — `nvfp4_ds_mla` via `FLASHMLA_MEGA_ATTN_DSV41`, which gates on
   `capability.major == 10` and therefore admits sm_103. No dequant, no requant.
4. **Interactive (S1, TPOT ≤ 50 ms): $5.64 per 1M output tokens** at the only published
   GB300 on-demand rate ($18.00/GPU-h, OCI `BM.GPU.GB300.4`) — low and high are the *same*
   number because OCI is the only seller. At the SemiAnalysis/on-prem anchors ($1.75–$5.00)
   it is **$0.55–$1.57**. **Max-throughput (S4): $4.03 ($0.39–$1.12)** `est.`
   **Blended (75 % in / 50 % of that cached / 25 % out) = $1.72 at $18.00, $0.17–$0.48 at
   the ownership anchors.**
5. **Confidence: measured** for fit, engine support, decode throughput and accuracy at
   concurrency 1–128 on one tray; **est.** for concurrency 256, for the rack-scale wide-EP
   shape, and for every 1M-context number. The two things nobody has published for this
   pair on this GPU: a 1M-context measurement of any kind, and any NVFP4-vs-MXFP4 speed
   comparison.

## 1. Fit

### 1.1 Method and the tensors that cannot be sharded

```
usable_hbm      = 279 GB × 0.90                         = 251.1 GB / GPU        (METHODOLOGY §3)
per_gpu_weights = checkpoint / N + replicated_tensors
activation_ws   = 8 GB / GPU                             est.  (see note)
kv_budget       = usable_hbm − per_gpu_weights − activation_ws
per_seq(ctx)    = ctx × kv_bytes_per_token + fixed_state(2.77 MiB, S = 1)
```

`activation_ws = 8 GB` rather than METHODOLOGY §3's generic 2–6 GB, for two model-specific
reasons: Single-Pass mHC carries the residual stream as **4 parallel copies**
(`hc_mult: 4`, [`architecture.md` §2.7](./architecture.md)), so activations are 4× the
usual hidden size in flight, and the vLLM B300/GB300 profiles capture a **26-size CUDA-graph
ladder up to 8190** for the DSpark-widened batch
([`architecture.md` §8.4](./architecture.md)). Treat 8 GB as `est.`; at 6 GB every KV budget
below gains 2 GB.

**Tensors that cannot be sharded, and the one that matters.**

| Tensor group | Bytes/GPU replicated | Why it cannot shard |
|---|---:|---|
| Vision tower + aligner | 0.97 GB | Only when the recommended `--mm-encoder-tp-mode data` is set — that flag *is* replication (data-parallel encoder). `--language-model-only` removes it entirely |
| MoE routers `ffn.gate` (384×5120, BF16) | 0.16 GB | Every EP rank must score all 384 experts to route |
| mHC coefficient projections `hc_*_fn` (F32) | 0.16 GB | Operate on the flattened 4×5120 residual; 20 Sinkhorn iterations on a 4×4 matrix |
| KV compressors, layers 2/8/14/20 (BF16) | 0.04 GB | `num_key_value_heads: 1` — there is one KV head, so there is no head axis to split |
| DSA indexer `wk` / `weights_proj` / `k_norm` | 0.05 GB | 32 index heads; shardable to N ≤ 32, replicated above that |
| RMSNorms, gate biases, `attn_sink` | 0.004 GB | Per-channel |
| **Total replicated weights** | **1.384 GB** | negligible |
| **KV cache + the 128-slot SWA ring** | **the whole thing, on every TP rank** | **`num_key_value_heads: 1`. MLA-shaped KV does not shard under TP — every rank holds a full copy ([`serving-optimizations.md` §3.1](../../cross-cutting/serving-optimizations.md)). Only DP-attention or DCP changes this.** |

Two further hard limits: **64 query heads caps TP at 64**, and **384 routed experts is not
divisible by 72**, so EP=72 needs EPLB padding (§5).

— except that on GB300 the offload target is **Grace LPDDR5X over a 900 GB/s NVLink-C2C
link**, not host DRAM over PCIe (§5.3).

### 1.3 Max concurrency

Two readings, and the difference is 4–72×. **The replicated reading is the binding one for
any TP-only deployment** and is what every number in §3 uses; the DP-attention reading
applies when each rank owns distinct requests.

- `rep` = `floor(kv_budget_per_gpu / per_seq(ctx))` — MLA KV replicated on every TP rank.
- `dp`  = `floor(kv_budget_per_gpu × N / per_seq(ctx))` — DP-attention / DCP, KV partitioned.

### 1.4 Measured cross-check — the engine reports its own KV pool

InferenceX's GB300 sweep (vLLM, TP4, 2026-09-16) reports
`kv_cache_pool_tokens = 68,443,500` `meas.`
([InferenceX API](https://inferencex.semianalysis.com/api/v1/benchmarks?model=DeepSeek-V4.1-Flash),
run [35073891536](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/35073891536/attempts/1)):

| Context | concurrent sequences the measured pool holds |
|---|---:|
| 8 K | **8,354** |
| 32 K | **2,088** |
| 128 K | **522** |
| 1 M | **65** |

68,443,500 × 890 B = **60.9 GB**, i.e. **37 % of my 164.83 GB TP4 Engram-offloaded KV
budget**. The engine is leaving 100 GB of HBM on the table — consistent with the
run's `gpu_kv_cache_usage_pct` never exceeding **22.6 %** even at concurrency 128 with
114 K-token prompts. **KV is nowhere near the binding constraint on this pair on this GPU**,
exactly as the vLLM recipe states: *"Weights and batch size, not cache, set the capacity
limit"* ([vLLM recipe](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash)). The
independent confirmation is that `gpu_kv_cache_usage_pct` × pool reproduces
`concurrency × mean_input_tokens` to within a few percent at every point in the sweep.

## 3. Throughput and latency

### 3.1 Stated assumptions (METHODOLOGY §4)

```
bytes_per_decode_step(batch, ctx) / GPU
  = weights_read(rows)/N                      rows = batch × (1+γ) with DSpark
  + batch × kv_read_per_seq(ctx)              NOT divided by N — MLA KV is replicated under TP
  + rows × 12,672 B                           Engram: 48 random 264-B gathers per token
weights_read(rows) = distinct_experts(rows) × 18,800,640 B × 40 layers + 18.75 GB static
distinct_experts(rows) = 384 × (1 − (1 − 6/384)^rows)
step = max( bytes/(8.0e12 × MBU), 2 × 16.13e9 × rows / N / (15e15 × MFU) ) × 1.08
```

- **MBU = 0.60.** [`gpus/gb300.md` §9.4](../../gpus/gb300.md) argues 0.60–0.75 is defensible
  for GB300; METHODOLOGY §4's generic Blackwell band is 0.5–0.7. **0.60 is also what the
  measurements below actually land on in the batch 8–32 range** (implied 0.56–0.67), so it
  is not a guess here — see §3.5.
- **MFU = 0.25 (NVFP4)**, METHODOLOGY §4's FP4 band 0.2–0.35. The compute branch never binds
  below concurrency 256 on this model.
- **Comm +8 %**, METHODOLOGY §4's 5–15 % for TP=8 over NVLink; TP4 inside one tray is the
  easy end.
- Decode KV-read bytes scale with `batch × ctx` per METHODOLOGY §3.
- `kv_read_per_seq(ctx)` = 2.77 MiB SWA + 5.34 MiB sparse main + 4.25 MiB reindex pool +
  170 B × ctx ([`architecture.md` §6.3](./architecture.md)):
  **13.03 MiB at 4K, 13.69 at 8K, 17.68 at 32K, 33.62 at 128K, 182.37 MiB at 1M.**
- **Feasibility (METHODOLOGY §3):** at TP4 with Engram offloaded and FP4 KV,
  `max_concurrency` = 25,159 (4K) / 5,139 (32K) / 1,378 (128K). No row in the tables below
  exceeds those, so no row is `infeasible (KV)` — which is itself the finding: **this model
  cannot be made KV-limited on a GB300 tray at any concurrency an engine will schedule.**

  **not** a decode-efficiency collapse. The InferenceX workload is *agentic traces* with
  114,200-token mean prompts and continuous batching, so at high concurrency a large
  fraction of every scheduler step is **chunked prefill of 114 K-token prompts interleaved
  with decode**; median ITL then measures a mixed step, not a decode step. The confirmation
  is in the same rows: input throughput keeps climbing (86,730 → 101,400 tok/s/GPU) exactly
  where "decode efficiency" appears to fall.

  **0.011**. That gap contains tokenisation, scheduling, radix-cache lookup and the KV reload
  of a 339 K prefix, so it is an upper bound on the inefficiency, not a kernel measurement.
  ⚠️ **No cold-prefill measurement exists for this pair on this GPU.**

**Planning rule that falls out.** For S1/S2/S3 at concurrency 8–64, use §3.2/§3.3 directly.
At concurrency ≥ 64 on long-context traffic, take the measured curve (§3.4a) and not the
estimate. At concurrency 1, use the measured 203 tok/s (no spec) / 873 tok/s (simulated
AL 5.5) rather than either.

### 4.4 Effect of speculative decoding and prefix caching

**DSpark.** Using the calibrated model at S1, concurrency 128, MBU 0.60:

| | tok/s/GPU | TPOT ms | $/1M output @ $18 |
|---|---:|---:|---:|
| no speculation | 2,061 | 15.53 | $2.43 |
| DSpark γ=5, acceptance 3.5 | 6,330 | 5.06 | $0.79 |

i.e. `est.` **3.07× throughput, 3.07× cheaper output**, if acceptance holds. It probably does
not hold at that batch: [`serving-optimizations.md` §2.4](../../cross-cutting/serving-optimizations.md)
records DeepSeek-R1 MTP on GB300 delivering **−0.9 % peak TPS/GPU but +87 % TPS/user** — on
Blackwell Ultra, speculation buys *latency*, not *throughput*, because the 1.5× NVFP4 rate
and 2× SFU move decode away from memory-bound and free verify slots stop being free. Two
mitigations both exist on this GPU and not on ROCm: vLLM **adaptive verification**
(`enable_adaptive_verification: true`, needs `AttentionCGSupport.ALWAYS`, which the NVIDIA
sparse-SWA backend has) and SGLang **verify trimming**.

**Prefix caching.** Measured hit rates on this pair on GB300 are **93.5–97.5 %** (§3.4a), and
the effect on input cost is linear in `(1 − h)`:

| GPU prefix-cache hit | effective $/1M input @ $18.00 |
|---:|---:|
| 0 % | $0.759 |
| 50 % | $0.379 |
| 90 % | $0.076 |
| **93.5 % (measured)** | **$0.049** |

This is a **15.4×** reduction in input cost between 0 % and the measured hit rate, and it is
the single largest cost lever on this pair — larger than speculation, larger than the choice
of GPU. The architecture is what makes it work: **SWA Bounded Replay** means a hit replays
only 128 tokens per layer rather than persisting SWA KV, and the cached KV is 890 B/token
([`serving-optimizations.md` §5.2](../../cross-cutting/serving-optimizations.md)). Note that
NVIDIA's own NVFP4 vLLM command carries `--no-enable-prefix-caching` — ⚠️ for benchmark
determinism, one hopes, but it is unstated (§6).

Break-even output throughput to match $0.60/1M output
(`price / (0.60 × 3600 / 1e6)` per GPU):

| Price tier | break-even tok/s/GPU | per 4-GPU tray | measured 887 tok/s/GPU reaches it? |
|---|---:|---:|---|
| **OCI $18.00** | **8,333** | 33,333 | **no — 9.4× short** |
| SemiAnalysis retail $5.00 | 2,315 | 9,259 | no — 2.6× short |
| On-prem 3-yr $2.57 ⚠️ | 1,190 | 4,759 | no — 1.34× short |
| SemiAnalysis volume $2.31 | 1,069 | 4,278 | no — 1.21× short |
| On-prem 5-yr $1.75 ⚠️ | 810 | 3,241 | **yes — 1.10× over** |

**Break-even utilisation.** Self-hosted cost scales as `1/utilisation`, so matching the API
at $18.00/GPU-h would need **939 % utilisation** — impossible; renting GB300 on the only
published rate to serve this model cheaper than DeepSeek's own API is not achievable at any
utilisation. At the SemiAnalysis volume anchor you need **121 %** — also impossible, but only
just. At the 5-year on-prem anchor you need **91 %**, which is achievable but implies owning
the rack and running it near flat out. If you must serve at peak-hour API rates ($1.20/M
output) every figure halves and the volume-ownership case closes comfortably.

Three honest caveats on that comparison. (i) $18.00 is a hyperscaler list price sitting
2.2–2.4× above neocloud rates for identical silicon, and **no neocloud publishes a GB300
rate at all** — a negotiated price is the realistic input, and this document cannot source
one. (ii) DeepSeek's own $0.60/M output is below what a *rented* Blackwell tray can deliver
at any published cloud rate, which is already noted in
[`serving-optimizations.md` §7.1](../../cross-cutting/serving-optimizations.md) for B300;
GB300 does not change it. (iii) The reasons to self-host this model are data residency,
1M-context prefix-cache locality and the **97.5 % cache hit on your own traffic** — not the
per-token price.

**Power, as a sanity check on ownership costs.** The measured sweep reports
`avg_total_gpu_power_w` for the 4-GPU pool rising 1,201 W → 3,659 W, i.e.
**300 → 915 W per GPU**, and `joules_per_output_token` falling **7.13 → 1.03 J**. 915 W at
full load is consistent with [`cloud-pricing.md` §11](../../cross-cutting/cloud-pricing.md)'s
corrected **1,100 W per GPU in a GB300 NVL72** (Lenovo) and **not** with
[`gpus/gb300.md` §1.1](../../gpus/gb300.md)'s **1.4 kW** — both are cited here per
METHODOLOGY §8; the measurement favours the 1,100 W row, though this workload may not be the
power-maximal one. ⚠️

## 5. Scaling and deployment shape

### 5.1 The four shapes, and which one to pick

| Shape | GPUs | Status | Use it when |
|---|---:|---|---|
| **TP4, one compute tray** | 4 | **`"gb300": "verified"`** (vLLM); the only shape any published GB300 measurement uses | **Default. Pick this.** 128.96 GB of weights/GPU, 114 GB of KV budget, 18 independent replicas per rack |
| TP2, one Grace superchip + Engram on Grace | 2 | ⚠️ **untested on GB300** — but it is vLLM's *default* on HGX B300, and B300 TP2 is the fastest measured configuration anywhere in §3.4(c) | Worth trying first if you can measure. Fewer ranks = less synchronisation on a launch-bound model; 36 replicas per rack |
| TEP4 / DEP4 (one tray, expert-parallel) | 4 | recipe published, **not measured**; DEP4 **does not fit** if Engram replicates (§1.5) | Only with `--engram-config '{"cpu_offload":true}'`. SGLang's own BS=1 data says MoE **TP4 beat EP4** on this model |
| **Wide-EP across the rack** | 8–72 | ⚠️ **no measurement, no recipe beyond a 2-node DEP8 command** | See §5.2 — the case is weak for *this* model |

### 5.2 When wide-EP pays for this pair — and why it mostly does not

The canonical NVL72 argument is DeepSeek-R1: 256 routed experts at ~4/GPU needs **64 GPUs**
to hold the routed experts once during decode, which fits one NVL72 domain and does not fit
an 8-GPU node ([`gpus/gb300.md` §10.6](../../gpus/gb300.md)). **That argument does not
transfer to DeepSeek-V4.1-Flash**, for three reasons this document can quantify:

1. **The whole model already fits on four GPUs.** 510.29 GB against 4 × 251.1 = 1,004 GB.
   There is no capacity reason to go wider; at EP72 each GPU holds 8.47 GB of weights and the
   rack runs one instance where it could run eighteen.
2. **384 experts do not divide by 72.** 384/72 = **5.33**. Integer splits are EP ∈ {4, 8, 16,
   32, 48, 64, 96}; EP=72 needs EPLB replication (e.g. 6 slots/GPU × 72 = 432, with 48
   redundant experts) at **≈ 2.4 GB per redundant expert per EP rank** for a DeepSeek-V3-class
   model ([`serving-optimizations.md` §3.3](../../cross-cutting/serving-optimizations.md)).
   And **DeepEP publishes no SM103 row at all** ⚠️.
3. **Expert reads saturate late but the model is launch-bound early.** With 384 experts and
   top-6, batch 32 still touches only 40 % of experts (§3.1) — the wide-MoE regime that
   rewards EP. But the two published GB300 measurements both say the binding cost at the
   batch sizes engines actually run is *kernel launches and rank synchronisation*, not
   all-to-all bandwidth: SGLang measured MoE **TP4 beating EP4 by 2.22 %** at BS=1 with the
   rank-sync gap falling 11.14 → 3.40 µs.

**Where the rack does earn its keep:** eighteen TP4 replicas sharing one 130 TB/s domain and
**17 TB of Grace LPDDR5X at 14 TB/s aggregate** as a second-tier KV and Engram store, with
KV-aware routing steering requests to the replica already holding their prefix. On agentic
traffic with a measured 93.5–97.5 % hit rate, that routing is worth far more than expert
parallelism (§4.4). **⚠️ No measurement of this shape for this model exists.**

### 5.3 The Engram tables and the Grace link — GB300's real structural advantage

202.76 GB (188.83 GiB) of the checkpoint — **40 % of it** — is two hash tables read by
**48 random 264-byte gathers per token**, 12,672 B/token
([`architecture.md` §4.1](./architecture.md)). On GB300:

- One Grace CPU has **≈ 472 GB of LPDDR5X** and serves **two** Blackwell Ultra GPUs over
  **NVLink-C2C at 900 GB/s bidirectional** — the whole Engram table fits in one Grace with
  269 GB to spare, and the rack has **17 TB** of it.
- At batch 128 × 6 DSpark rows that is **9.73 MB/step → 10.8 µs over C2C** versus 1.2 µs from
  HBM `est.` — against a measured 88 ms step. **Negligible either way.**
- The measured InferenceX GB300 run *did* offload Engram to host DRAM via UVA and still
  produced the best numbers in §3.4(c). This is the direct evidence.
- ⚠️ 36,864 random 264-B gathers per step is a pathological access pattern; the 10.8 µs figure
  assumes streaming efficiency over C2C, which nothing published measures.

For contrast, on a PCIe-attached part the same offload cost the DGX Spark cluster
**5.9–7.8 ms/step over NFS versus 2.8 ms node-local**, and moving Engram from NVMe to pinned
RAM on 2× RTX PRO 6000 was worth **2.16×**
([`architecture.md` §4.1/§10.2/§10.4](./architecture.md)). **GB300 is the one platform in
this roster where the Engram offload is genuinely free**, and that — not FP4 rate, not HBM
bandwidth — is the architectural reason to prefer it for this model.

## 6. Risks and open questions

**Everything marked ⚠️ TO BE VERIFIED in this document**

1. **No 1M-context measurement of any kind, on any hardware.** Every 1M number here (176
   concurrent sequences at TP4, 1,663 ms cold TTFT, 182.37 MiB/seq/step of KV reads) is
   `est.` The indexer's full scan of all 170 B/token of indexer K in four Full-mode layers,
   every step, is 5.70 GiB/step at batch 32 × 1M and dominates everything else
   ([`architecture.md` §6.3](./architecture.md)). vLLM's own warning for the sibling model
   applies: *"1M context is advertised, not measured."*
2. **No TP2 row for GB300.** B300 at TP2 is the fastest measured configuration in the whole
   §3.4(c) table (1.27× GB300's TP4 at concurrency 128). GB300 has more memory per GPU and a
   900 GB/s C2C Engram path, so TP2 should be at least as good — and nobody has run it.
   **This is the highest-value missing experiment for this pair.**
3. **How Engram is sharded under DP-attention.** If it replicates, vLLM's own published
   `single_node_dep` GB300 command does not fit (§1.5). No engine document states it.
4. **NVFP4 vs MXFP4 on this GPU.** NVIDIA validated `nvidia/DeepSeek-V4.1-Flash-NVFP4` on
   **4× GB300** with both vLLM and SGLang, published an accuracy table showing parity
   (GPQA 91.288 vs 91.035, Terminal-Bench 82.16 vs 81.60, MMMU-Pro 73.699 vs 74.046 — within
   noise), and published **no throughput or latency comparison whatsoever**. The build is
   **+17 GB** (527.27 vs 510.29 GB). Every measurement in §3 is of the **base MXFP4**
   checkpoint. So: **on GB300, does NVFP4 W4A4 beat MXFP4 W4A8 for this model? Unanswered.**
   The priors cut both ways — W4A4 halves activation traffic through the MoE and
   `flashinfer_trtllm_routed` is a well-trodden path, but §3.5 shows this model is
   launch-bound rather than GEMM-bound at the batch sizes that matter, and NVIDIA's own
   validation did **not** exercise DSpark. **Default to the base checkpoint** until someone
   publishes a paired benchmark: it is smaller, it is what every GB300 measurement used, and
   it is the one artefact that also runs on Hopper, sm_120 and MI355X.
5. **DSpark acceptance on real traffic.** 3.51 is a synthetic benchmark constant; 5.5 in the
   SGLang GB300 post is an explicit simulation (`SGLANG_SIMULATE_ACC_LEN`); 3.57 (DGX Spark,
   GB10) is the only measurement of this checkpoint and it is on different silicon. vLLM's
   guidance is to *"measure it on your own traffic before sizing a deployment around it."*
   All of §3.3 inherits this.
6. **Speculation may not pay at throughput on Blackwell Ultra.** MTP on GB300 gave
   DeepSeek-R1 **−0.9 % peak TPS/GPU** while giving **+87 % TPS/user**
   ([`serving-optimizations.md` §2.4](../../cross-cutting/serving-optimizations.md)). Nobody
   has measured DSpark's throughput-vs-latency trade for *this* model on *this* GPU.
7. **No FlashMLA or FA4 TFLOPS number on sm_103.** The 1.11× scaling from B200 in §2 is
   `est.` and the FlashMLA decode kernel is known to lose efficiency going Hopper → Blackwell
   (41.4 % → 31.1 % of peak), so treat the decode estimate as an upper bound
   ([`flash-attention.md` §5.2/§15.2](../../cross-cutting/flash-attention.md)).
8. **FlashMLA's support matrix says SM100 for V4.1 sparse decode and lists no SM103 row**, as
   does DeepEP. Both work in practice on GB300 (the measurements prove it), but you are
   running outside the vendor's stated support surface.
9. **PD disaggregation on GB300 for this model is unmeasured.** The recipe exists; the only
   *verified* 1P1D runs are on GB200 NVL4 and were text-only. And
   [`serving-optimizations.md` §3.5](../../cross-cutting/serving-optimizations.md) is blunt:
   *"disaggregation is a thousand-GPU problem"*, with a measured **−20–30 %** on small or
   untuned deployments. On a 4- or 8-GPU slice it will very likely lose.
10. **Multimodal is entirely unmeasured on GB300 for this checkpoint.** Every published run
    is text-only, most with `--language-model-only`. A max-resolution image costs 18.86
    TFLOP, as much as ~1,200 prefill tokens, for 1,024 tokens of context
    ([`architecture.md` §6.4](./architecture.md)).
11. **`--no-enable-prefix-caching` in NVIDIA's own vLLM GB300 command** for the NVFP4 build.
    Benchmark determinism, or a real incompatibility? Unstated, and it matters a great deal
    given §4.4.
12. **The fixed SWA state is 2.77 MiB or 5.38 MiB** depending on whether the engine stores
    the 128-slot ring as true FP8 + E8M0 scales or in a BF16 container as the reference
    implementation does. Every concurrency figure in §1.3 uses 2.77 MiB; at 5.38 MiB the 8K
    column loses ~28 % of its slots. No vLLM or SGLang document states the dtype
    ([`architecture.md` §5.3/§12.4b](./architecture.md)).
13. **`S = 1`** is assumed for the state-slot multiplier (METHODOLOGY §2). If a future engine
    allocates ring-buffer slots for the 5 DSpark draft positions, multiply the fixed state by
    that `S`.
14. **Neither vLLM 0.30.0 nor an SGLang release containing this model exists.** vLLM's latest
    release is 0.29.0 (2026-09-09) and `min_vllm_version` is 0.30.0 with
    `nightly_required: true`; SGLang's latest is 0.5.20 (2026-09-18) and the model is on
    `main` only. **You are pinning a nightly container**, and the measured GB300 runs used
    three different images in six days
    ([`inference-engines.md` §6.1](../../cross-cutting/inference-engines.md)).
15. **Benchmark half-life.** SGLang moved this pair 35 → 873 tok/s at BS=1 by kernel work
    alone, and MLPerf moved GB300 2.77× in six months on unchanged silicon. **Every number in
    §3 and §4 should be re-measured before it is acted on.**
16. **One price.** Every cost figure at the on-demand tier rests on a single OCI list price.
    `cloud-pricing.md` §5.9 says it plainly: *"That single price is therefore doing a lot of
    work … and should be treated with appropriate suspicion."*
17. **Per-GPU power disagreement**, stated per METHODOLOGY §8: `gpus/gb300.md` §1.1 says
    1.4 kW/GPU, `cloud-pricing.md` §11 says 1,100 W (Lenovo, "total graphics power per GPU").
    The measured 915 W/GPU at concurrency 128 on this workload supports the lower figure but
    does not settle it.

**Accuracy caveats of the executed precision**

- **The MXFP4 W4A8 path on sm_103 is not lossy.** Four independent GSM8K runs on GB300 in the
  InferenceX harness returned `em_strict` **0.9742 / 0.9757 / 0.9719 / 0.9727** (n = 1,319,
  SE ≈ 0.0044), indistinguishable from B200/B300/GB200/H200/MI355X on the same harness and
  from the MI355X `gsm8k strict-match 0.9719 ± 0.0045` in
  [`architecture.md` §10.1](./architecture.md).
- **NVFP4 conversion is accuracy-neutral**, not an accuracy win: +0.253 GPQA, +1.442 SciCode,
  +0.600 IFBench, −0.125 AA-LCR, −0.347 MMMU-Pro, +0.56 Terminal-Bench. NVIDIA's own
  wording: *"Lossless weight conversion does not imply identical inference outputs."*
- **The architecture's own approximations are untested at the accuracy level.** **SWA Bounded
  Replay** — the mechanism that makes 890 B/token cacheable and the 93.5 % prefix-cache hit
  economics work — is described by DeepSeek as *"barely compromis[ing] response quality"*
  **with no number attached**, and SGLang's implementation
  (`--enable-decoder-swa-bounded-replay`) is *"validated on the decode path only, refuses
  prompt logprobs by design, is not numerically equivalent to full prefill, and is excluded
  at launch with the prefill CUDA graph and with DP attention."*
- **Determinism**: `--enable-deterministic-inference` is **refused** on SGLang's `dsv4`
  backend for this model; *"output is not bitwise stable across batch composition today."*
- **Reasoning effort forks between engines**: vLLM defaults thinking **on at effort 50**,
  SGLang defaults it **off**, and the DeepSeek API maps `low/high/max` to 50/75/100 while the
  open encoder and vLLM map `low/high/xhigh/max` to 25/50/75/100. Since effort 25 → 100 costs
  **~2.5× the output tokens** ([`architecture.md` §10.5](./architecture.md)), a silent
  default difference is a silent 2.5× cost difference. **Effort 60–80 is the cost-efficient
  operating point.**
