## 0. Verdict

1. **Runnable today, yes** — vLLM `main`/nightly (recipe declares `min_vllm_version 0.30.0`, `nightly_required: true`; the image actually measured is `vllm/vllm-openai:nightly-cd10ed6f9f6b37a8ace9cf380007e66fe12ec0c3`, 2026-09-16) and SGLang preview `lmsysorg/sglang:dev-dsv41`; **no numbered release of either engine serves it** ([inference-engines.md §6.1](../../cross-cutting/inference-engines.md), [InferenceX run 35020525087](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/35020525087/attempts/1)).
2. **Min 4 GPUs, and only with `--engram-config '{"cpu_offload":true}'`** (vLLM's own TP4 H200 profile ships *without* it and is **1.07 GB/GPU over** the 0.90-utilisation budget before a single KV byte, §1); **recommended 8 × H200 in one HGX node, TP8** (vLLM) or **TP8/EP8** (SGLang) — the shape every published measurement uses.
3. **Weight format actually executed: MXFP4 experts dequantised to BF16 via Marlin W4A16** (no FP4 tensor core on sm_90), non-expert FP8 32×32 native; **KV runs at FP8 ≈ 1,650 B/token, not the checkpoint's 890 B FP4 cache** — `nvfp4_ds_mla` needs `FLASHMLA_MEGA_ATTN_DSV41`, which is `major == 10` only ([flash-attention.md §11, §16.1](../../cross-cutting/flash-attention.md)).
4. **Interactive (S1, TPOT ≤ 50 ms): $1.29 – $2.56 per 1M output tokens `est.`; max-throughput: $0.46 – $0.91 `est.`** (low = Hyperstack $3.99, high = AWS p5en $7.912). The only *measured* operating point — a 118 K-input agentic trace — costs **$5.95 – $11.79 per 1M output tokens**, i.e. **10–20× DeepSeek's own $0.60/M API price**.
5. **Confidence: `estimate`.** Fit, kernel support, accuracy and one 118 K agentic operating point are **measured**; the S1–S4 grid is a roofline calibrated against those measurements (achieved fraction 0.29–0.39 of the MBU-0.70 roofline) and is `est.`

## 1. Fit

### 1.1 Topology and what "N GPUs" may be

An HGX H200 baseboard is **4- or 8-GPU**, and **8 GPUs is the largest NVLink domain that
exists on Hopper** — there is no NVL72-class rack fabric
([gpus/h200.md §4](../../gpus/h200.md)). So the admissible set here is
**{1, 2, 4, 8, 16, 32, …}**, where anything above 8 crosses a node boundary onto
400 G-class InfiniBand/EFA (~50 GB/s per GPU versus 900 GB/s on NVLink — an 18× drop,
METHODOLOGY's 20–40 % multi-node overhead band).

Each concurrency cell is **FP8 KV / BF16 KV**. Formula, verbatim from METHODOLOGY §3:
`max_concurrency(ctx) = floor( kv_budget × n_gpus / (ctx × kv_bytes_per_token + fixed_state) )`.

**Minimum GPUs = 4, and only with Engram host offload.** At TP4 the resident checkpoint is
`510.29/4 + 0.40 = 127.97 GB/GPU` against `126.90 GB` usable — **1.07 GB over before any KV
cache**, needing `--gpu-memory-utilization ≥ 0.9076` just to hold the weights. This is the
same arithmetic [`inference-engines.md` §6.1](../../cross-cutting/inference-engines.md)
reached ("**TP4, H200 … no — 0.6 GiB over**"; the small difference is that this document adds
the 0.40 GB of replicated tensors and that document works in GiB). It matters because
**vLLM's shipped H200 profile is TP4 with no Engram offload**:
`"command": "vllm serve deepseek-ai/DeepSeek-V4.1-Flash --tokenizer-mode deepseek_v41
--tensor-parallel-size 4 …"`, `"vram_gb": 1128`
([`hw/h200.json`](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash/hw/h200.json)).
That profile cannot serve a useful context at any concurrency. **Every published H200
measurement of this model runs TP8**, not TP4 (§3.2) — which is the empirical resolution of
the ⚠️ `inference-engines.md` §3.4 left open ("whether the vLLM H200 TP4 profile is validated
at a useful context/concurrency or only at boot": the benchmark that exists is TP8).

**Recommended: 8 GPUs, one node, Engram resident.** 8 × 141 = 1,128 GB, and the vLLM recipe
says so directly — *"fits one 8-GPU H200 node (1128 GB) with room for KV cache"*
([vLLM recipe](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash)). The measured
InferenceX runs confirm Engram stays in HBM: `offload_mode: "off"`,
`kv_offloading: "none"`, `allocated_cpu_dram_gb: 0` (§3.2). **This is the single thing H200
buys over H100 for this model** — H100 at TP8 has 74.51 GiB usable against 59.41 GiB of
weights and *must* push the 188.83 GiB Engram table to host over PCIe
([architecture.md §8.4](./architecture.md), [gpus/h200.md](../../gpus/h200.md)).

### 1.3 Tensors that cannot be sharded — and the KV-replication caveat

| Tensor group | Bytes | Shards under TP/EP? | Why |
|---|---:|---|---|
| Routed + DSpark experts (MXFP4) | 278.59 GB + scales | ✅ EP or TP | 384 experts × 40 layers; EP is the natural axis |
| **Engram tables (FP8 + E8M0)** | **202.76 GB** | ✅ by row | the DGX Spark community deployment shards them **48 GB per worker × TP4 ≈ 192 GB** ([DGX Spark repo](https://github.com/tonyd2wild/DeepSeek-V4.1-Flash-vLLM-DGX-Spark)); alternatively `--engram-config '{"cpu_offload":true}'` |
| Attention / dense projections (FP8 32×32) | 5.07 GB | ✅ TP | standard column/row split |
| Embedding + lm_head (BF16) | 2.65 GB | ✅ vocab-parallel | |
| **`ffn.gate` routers (BF16, 384×5120 × 40)** | **0.157 GB** | ❌ **replicated** | every rank must score every expert before dispatch |
| **mHC coefficient projections (`hc_*_fn`, F32, 24×20480)** | **0.157 GB** | ❌ **replicated** | Single-Pass mHC mixes the 4 residual copies globally; the 20-iteration Sinkhorn is a whole-tensor op ([architecture.md §2.7](./architecture.md)) |
| `attn.compressor.wkv/wgate/norm` (BF16) | 0.037 GB | ❌ replicated | only 4 layers own a compressor; splitting 512-d latents across 8 ranks is not worth it |
| RMSNorm weights, `gate.bias`, `gate.bias_vl`, `attn_sink` (F32) | ≈ 0.001 GB | ❌ replicated | elementwise |
| **Total replicated** | **≈ 0.40 GB/GPU** | | used as `+repl` in the table above |
| **The compressed KV latent and indexer K cache** | 1,650 B/token | ❌ **replicated per TP rank** | `num_key_value_heads: 1` — MLA/MQA has **one** KV head, so TP has no head axis to split. *"KV sharded by head — **but not for MLA**, which has one KV head, so every rank holds a full copy"* ([serving-optimizations.md §3.1](../../cross-cutting/serving-optimizations.md)) |

**⚠️ TO BE VERIFIED — the concurrency numbers above are the METHODOLOGY §3 aggregate
reading, and the replicated reading is 8× smaller.** METHODOLOGY §3 multiplies the per-GPU
KV budget by `n_gpus`, which is correct when KV shards (by head under TP, or by sequence
under DP-attention / EP). For this model under **pure TP** it does not: with one KV head
every rank holds a full copy, so the real ceiling is `floor(kv_budget_per_gpu / per_seq)`.
[`serving-optimizations.md` §7.1](../../cross-cutting/serving-optimizations.md) flags exactly
this for the B300 pair and calls the replicated reading "the binding one". Both are printed
here; pick by parallelism:

| N = 8, Engram resident, FP8 KV | 8 K | 32 K | 128 K | 1 M |
|---|---:|---:|---:|---:|
| **(A)** METHODOLOGY aggregate — valid with EP8 + DP-attention (SGLang's shape) | 28,457 | 8,202 | 2,132 | 269 |
| **(R)** MLA-replicated — valid with plain TP8 (vLLM's shape) | **3,557** | **1,025** | **266** | **33** |
| same at FP4 KV (counterfactual, no sm_90 kernel) | 45,832 / 5,729 | 14,572 / 1,821 | 3,908 / 488 | 499 / 62 |

Measurement lands between the two and closer to (R) in practice: the InferenceX vLLM TP8 run
reports `kv_cache_pool_tokens = 31,006,342`, which at 1,650 B/token is **51.16 GB per GPU**
= 87 % of the 58.82 GB per-GPU budget — the same fill fraction vLLM achieves on B200 TP4
(26.14 GB of a 30.13 GB budget, 87 %). Dividing 31.0 M tokens by a 118 K mean context gives
**≈ 263 resident sequences**, which reproduces the replicated 128 K figure of 266 almost
exactly. Use **(R)** for a vLLM TP8 deployment.

### 1.4 Cross-check: what the measured KV pool says about the KV dtype

This is the load-bearing inference of the whole document, so the arithmetic is shown:

| Run (InferenceX, `benchmark_type: agentic_traces`) | `kv_cache_pool_tokens` | pool @ 890 B | pool @ 1,650 B | KV budget/GPU | verdict |
|---|---:|---:|---:|---:|---|
| vLLM TP4, **B200** 180 GB | 29,372,139 | 26.14 GB ✅ | 48.46 GB ❌ | 30.13 GB | **890 B proven** |
| vLLM TP4, **B300** 268 GB | 78,110,198 | 69.52 GB ✅ | 128.88 GB ❌ | 109.33 GB | **890 B proven** |
| **vLLM TP8, H200** 141 GB | **31,006,342** | 27.60 GB (47 % fill) | **51.16 GB (87 % fill)** | 58.82 GB | both fit — **1,650 B is the 87 %-fill match**, and is the only layout with an sm_90 kernel |
| SGLang TP8/EP8, H200 | 36,672,256 | 32.64 GB | 60.51 GB | ⚠️ `--mem-fraction-static` unknown for this run | ⚠️ inconclusive |

On B200/B300 the pool *excludes* 1,650 B arithmetically, which independently confirms
METHODOLOGY §8's "890 B/token **with the FP4 KV cache**" and that the FP4 cache is live on
`major == 10`. On H200 the pool is consistent with either, so the kernel gate (§2) decides:
`nvfp4_ds_mla` is reachable only through `FLASHMLA_MEGA_ATTN_DSV41`, whose runtime check
returns *"FlashMLA mega attention requires sm_10x GPUs"*
([flash-attention.md §6.2](../../cross-cutting/flash-attention.md)). **Plan H200 at
1,650 B/token.** ⚠️ TO BE VERIFIED — InferenceX does not publish `--kv-cache-dtype` per run.

## 3. Throughput and latency

### 3.1 Assumptions (METHODOLOGY §4)

```
decode_step_time = max( bytes_per_decode_step / (HBM_BW × MBU) ,
                        2 × active_params × batch / (peak_FLOPS × MFU) )
bytes_per_decode_step(batch) = weights_read(batch)/N + batch × kv_read(ctx)
  weights_read(batch) = distinct_experts(batch) × 40 × 18,800,640 B + 18.75 GB static
  distinct_experts(b) = 384 × (1 − (1 − 6/384)^b)                    [architecture.md §6.3]
  kv_read(ctx) @FP8  = 2.77 MiB (SWA)
                     + 38 × 512 × 528 B      (sparse main KV,  9.80 MiB)
                     + 4 × 16,384 × 132 B    (reindex pool,    8.25 MiB)
                     + 330 B × ctx           (Full-mode indexer scan)
prefill_time(T)  = (2 × 7.895e9 × T + idx_flops(T) + sel_flops(T)) / (peak × MFU × N)
```

| Parameter | Value used | Why |
|---|---|---|
| **MBU (decode)** | **0.70** | METHODOLOGY §4 band 0.6–0.8 for H100/H200; [gpus/h200.md §9](../../gpus/h200.md) recommends 0.65–0.75 for dense decode with CUDA graphs. The 0.85–0.90 FlashMLA figure is **not** used — it is for dense MLA decode on V3/V3.1, a kernel that is SM90-only for *those* models |
| **MFU (decode compute branch)** | 0.30 | METHODOLOGY §4 band 0.25–0.40 for FP8; used here against the **BF16** peak because MXFP4 experts execute as W4A16 (§2) |
| **MFU (prefill)** | 0.40 | METHODOLOGY §4 BF16 band 0.35–0.50 |
| **Peak used** | **BF16 989.5 TFLOPS**, not FP8 1,979 | the dominant GEMM is the dequantised MXFP4 expert matmul |
| KV dtype | **FP8, 1,650 B/token** | §1.4 |
| Spec-dec | **off** in the roofline; measured rows have DSpark **on** | keeps the two tables comparable |
| **Calibration factor** | **0.35** (achieved fraction of this roofline; observed range **0.29–0.39**) | derived from the measured H200 rows at concurrency 8/16/32/64 in §3.2: 0.341 / 0.386 / 0.378 / 0.293 |

(bytes computed at `batch × 6` verify positions because DSpark drafts 5 + 1;

Four things this settles:

1. **DSpark is demonstrably on and accepting.** At concurrency 8 and 16 the `a = 1` column
   gives **MBU 1.145 and 1.109 — physically impossible**. A single forward step cannot move
   more bytes than the HBM delivers. The only resolution is that each step emits more than
   one token: **`a ≥ 1.15` at concurrency 8**, a lower bound derived here, not published.
   ⚠️ **TO BE VERIFIED** — no measured DSpark acceptance exists for this model on H200. The
   only real measurement anywhere is the DGX Spark community mean of **3.57** tok/step; the
   widely quoted **3.51 is a synthetic benchmark constant** the MI355X harness is *told* to
   assume ([architecture.md §7.3](./architecture.md)).
2. **At bs = 1 the model is launch-bound, not bandwidth-bound.** 2.78 ms/token at
   concurrency 1 against a 1.68 ms roofline *for the whole step* implies an effective MBU of
   0.12 at `a = 3.5`. This is the same signature SGLang documented on Kimi-K3 — at bs = 1 a
   sparse MoE of this shape *"is not compute-bound — it is a launch-count and latency
   problem"* ([serving-optimizations.md §4.4](../../cross-cutting/serving-optimizations.md))
   — and H200 is exactly where it bites, because the `FLASHMLA_MEGA_ATTN_DSV41` fusion that
   collapses the norm/RoPE/attention/RoPE/cast chain into one launch **has no sm_90
   instantiation** (§2).
3. **The InferenceX TPOT is not a clean decode TPOT.** The trace drives
   `input_tput_per_gpu` of 22,451 tok/s at concurrency 64 — 179,611 tok/s aggregate of
   reported input against 1,491 tok/s of output. Even at the measured 93.3 % cache-hit rate
   that is **≈ 12,055 tok/s of genuinely uncached prefill**, chunk-interleaved into every
   decode step. Part of the 3–8× gap is prefill sharing the step, not decode inefficiency.
   The estimated grid in §3.2 assumes a steady-state decode phase and will therefore always
   look optimistic against this particular trace.
4. **The concurrency-128 row is a scheduler collapse, not a KV wall.** 128 × 118 K = 15.1 M
   tokens against a 24.0 M-token pool, so KV is not the limit; TTFT goes to **200 s** and
   throughput falls 4× — the node simply cannot absorb 1.5 QPS × 118 K of prefill at that
   queue depth. **The measured feasible ceiling on this stack is concurrency 64 at 118 K
   context.** Anything in §3.2 above batch 256 is an extrapolation past every measured point
   and is marked ⚠️.

The same sanity check on prefill: measured TTFT at concurrency 1 is **417 ms** for a 118 K
prompt at 93.3 % hit, i.e. ~8,265 uncached tokens; the roofline for 8,265 tokens at MFU 0.40
across 8 GPUs is **41 ms**. A **10.1× gap**, the same order as the decode gap at low batch,
and the same explanation (launch count, the un-fused indexer chain, the Full-mode scan).
For reference, [`architecture.md` §10.1](./architecture.md) records a **12.6×** roofline gap
on MI355X that remains unexplained; H200's 3–10× is the same phenomenon, smaller.

**Planning rule for this pair: use the measured curve, not the roofline.** The §3.2
calibrated column applies the measured achieved-fraction of 0.35 and is the number to plan
with; the raw roofline is shown only so the gap is visible.

### 4.3 What prefix caching and DSpark do to the number

**Prefix caching** (self-hosted, cached input at ~10 % of uncached per METHODOLOGY §6 —
*not* DeepSeek's 2.1 % vendor ratio, which applies only to the API comparison):

| cache hit rate | blended $/1M at low, S1 batch 256 |
|---:|---:|
| 0 % | $0.4261 |
| 50 % (the METHODOLOGY blend) | **$0.3794** |
| 90 % (the realistic agentic rate — the measured trace hits **93.3 %**) | $0.3419 |

Only **−20 %** from 0 % to 90 %, because at a 75/25 mix with output at $1.289/1M the output
term dominates. **For this model prefix caching is a TTFT optimisation, not a cost
optimisation** — it takes S3 TTFT from 2,142 ms to 206 ms (§3.2). That is the opposite of
the API economics, where DeepSeek's 50× cache discount makes caching the whole game.

**DSpark**, applied to the output term at low price, S1 batch 256:

| effective decode multiplier | $/1M output |
|---:|---:|
| 1.0× (none) | $1.289 |
| 1.3× | $0.991 |
| 2.0× | $0.644 |
| 3.5× (the DGX Spark measured mean, at bs = 1) | $0.368 |

**At batch 256 expect the low end of that range.** The mechanism is explicit: *"at low
concurrency, GPUs are memory-bound with spare compute, making draft tokens nearly free. At
concurrency 256, draft tokens compete with real tokens"*
([serving-optimizations.md §2.5](../../cross-cutting/serving-optimizations.md)). The one
mitigating factor specific to this model is that expert reads do **not** saturate until
~batch 128 ([architecture.md §6.3](./architecture.md)), so the crossover lands later than
usual. ⚠️ **TO BE VERIFIED** — no acceptance measurement for this pair; the multiplier above
is a sensitivity, not a result.

### 4.4 Versus the vendor API, and break-even utilisation

DeepSeek first-party `deepseek-flash` = DeepSeek-V4.1-Flash, per 1M tokens
([architecture.md §11](./architecture.md),
[api-docs.deepseek.com](https://api-docs.deepseek.com/quick_start/pricing)):
**output $0.60 off-peak / $1.20 peak; input cache-miss $0.15/$0.30; input cache-hit
$0.003/$0.006.** Per METHODOLOGY §6, the vendor comparison uses the **vendor's own** cached
ratio (2.1 %), not the generic 10 %: vendor blended at 75/25 with DeepSeek's own 2.1 %
cache-hit rate =
**$0.2602/1M off-peak, $0.5204 peak**. *(Corrected 2026-09-19 — audit: the previous
$0.2074/$0.4147 was computed with a 50 % cache-hit rate, the self-hosted assumption, not
DeepSeek's stated 2.1 %; `python3`: `0.75*((1-0.021)*0.15+0.021*0.003)+0.25*0.60 = 0.2602`.)*

| Self-hosted point | blended $/1M | vs vendor $0.2602 | **break-even utilisation** (blended) | (output-only vs $0.60) |
|---|---:|---:|---:|---:|
| S1 interactive, b=256, **low $3.99** | $0.3794 | **1.46× more expensive** | **146 %** — unreachable | 215 % |
| S1 interactive, b=256, high $7.912 | $0.7523 | 2.89× | 289 % | 426 % |
| S1 interactive, b=256, **res1y $2.79** | $0.2653 | 1.02× | **102 %** — still unreachable | 150 % |

| S4 max-throughput, b=1024, high $7.912 ⚠️ | $0.3407 | 1.31× | 131 % | 152 % |
| S4 max-throughput, b=1024, **res1y $2.79** ⚠️ | $0.1201 | **0.46× — cheaper** | **46 %** | 53 % |
| **Measured** agentic conc 64, low $3.99 | $1.507 | 5.79× | **579 %** | 991 % |

Break-even utilisation `u = self_hosted_cost_at_100% / vendor_price`; a value above 100 %
means **no utilisation, however high, makes self-hosting cheaper at that operating point**.

**The verdict is unambiguous. At an interactive SLO, self-hosting DeepSeek-V4.1-Flash on
H200 cannot beat DeepSeek's own API at any utilisation, on any published H200 rate.** It
only closes at max-throughput batch on a reserved or on-prem-amortised rate — and there the
supporting numbers are extrapolations past every measured point. On the one operating point
that *is* measured, self-hosting is **5.8× more expensive** than the API.

This is not an H200-specific indictment; [`serving-optimizations.md` §7.1](../../cross-cutting/serving-optimizations.md)
reaches the same conclusion for 4×B300 ("DeepSeek's list output price is **below** what a
*rented* B300 tray can deliver at any published cloud rate"). H200 is simply further from it.
The colo-amortised H200 rate — **$1.50/GPU-hr at 100 % utilisation, $2.14 at 70 %** on a
$370 k HGX system ([gpus/h200.md §8](../../gpus/h200.md), [cloud-pricing.md §8](../../cross-cutting/cloud-pricing.md))
— is the only tier where the interactive point approaches parity: at $1.50 the S1 blended
cost is $0.143/1M, a 55 % break-even. **Owning the silicon is what makes this work, not
renting it.** ⚠️ that $1.50 rests on a secondary purchase-price estimate.

Reasons to self-host anyway that this arithmetic does not price: data residency, the MIT
licence on both repo and weights, freedom from DeepSeek's 2,500-request concurrency cap, and
the reasoning-effort knob (effort 60–80 recovers most of effort-100's accuracy at **under
half the token budget** — [architecture.md §10.5](./architecture.md) — which is a ~2× cost
lever in its own right, available on either side).

**Energy anchor**, from the measured rows: **3.12 J per output token** at concurrency 64
(node 4,645 W), improving monotonically from 11.49 J at concurrency 1. At $0.08/kWh that is
$0.0000694 per 1M output tokens in electricity — three orders of magnitude below the
GPU-hour cost, i.e. irrelevant to the rental economics and relevant only to a colo plan.

## 5. Scaling and deployment shape

### 5.1 Single node versus multi-node

**Stay on one node.** 8 × H200 = 1,128 GB holds the whole 510.29 GB checkpoint with the
188.83 GiB Engram table resident and 467 GB of aggregate KV budget left (§1.2). Crossing to
16 GPUs buys 3.1× the KV budget but pays METHODOLOGY's 20–40 % multi-node overhead on every
layer's all-reduce, because **Hopper's largest NVLink domain is 8 GPUs** — there is no
NVL72 equivalent ([gpus/h200.md §4](../../gpus/h200.md)). Given that the measured ceiling is
concurrency 64 at 118 K, the extra KV budget has no buyer.

Go to two nodes only for **1M-context serving**: at 8 GPUs the replicated reading gives
**33 concurrent 1M-token sequences** (aggregate reading 269), and at 16 it gives 52/833.
Even then, prefer **TP8 × DP2** over TP16 — SGLang's own Hopper guidance for the V3.2 family
reaches for `--tp 16 --dp 2 --enable-dp-attention` rather than naive TP16, replacing
cross-node all-reduce with data/expert parallelism
([gpus/h200.md §4](../../gpus/h200.md)).

### 5.2 When PD disaggregation or wide-EP pays

**Wide-EP: yes, and it is already the SGLang shape — but it does not currently pay on
H200.** The model's 384-expert / top-6 routing is the canonical wide-EP case: batch 32 still
touches only 40 % of experts, so throughput scales well to ~batch 64 and EP beats TP
([architecture.md §6.3](./architecture.md)). And EP + DP-attention is what would convert the
replicated KV reading of §1.3 into the aggregate one, a real 8× on concurrency. **Yet the
measured SGLang TP8/EP8 H200 build is 15.7× slower than vLLM's TP8** on the same trace and
harness (§3.3). Until that inverts, the EP argument on H200 is theoretical. ⚠️ **TO BE
VERIFIED** — cause unknown; SGLang's own cookbook warns that *"overriding [backends] is the
most common cause of a disappointing measurement"*
([inference-engines.md §6.1](../../cross-cutting/inference-engines.md)), and the InferenceX
SGLang config is not published per-run.

**PD disaggregation: no, not at this size.** The clean rule from the literature is that
*"disaggregation is a thousand-GPU problem"*, with Modular reporting a **20–30 % performance
drop** on small or untuned workloads; at 8–16 GPUs you cannot allocate fractional roles and
the rounding losses eat the specialisation gain
([serving-optimizations.md §3.5](../../cross-cutting/serving-optimizations.md)). The model's
*only* verified 1P1D layout is GB200 NVL4 — one 4-GPU tray per role, TP4 each, KV over NIXL
— with the note that *"on 8-GPU nodes the same layout becomes TP8 per role"*, i.e. **two
H200 nodes minimum**, and *"the verified GB200 runs were text-only"*. Two further constraints
if you try it anyway: **DSpark must run in both pools** so the transferred KV stays
compatible, and SGLang cannot combine PD with speculative decoding at all. ⚠️ **No PD
measurement on H200 exists.**

The one disaggregation axis that *is* cheap here is **EPD** — splitting the vision encoder
off — because a max-resolution image costs 18.86 TFLOP for 1,024 tokens, as much as ~1,200
language prefill tokens ([architecture.md §6.4](./architecture.md)). For text-only traffic
`--language-model-only` achieves the same thing for free.

### 5.3 Launch commands

**vLLM — the shipped H200 profile, quoted verbatim** from
[`hw/h200.json`](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash/hw/h200.json)
(`"docker_image": "vllm/vllm-openai:nightly"`, `"strategy": "single_node_tp"`,
`"vram_gb": 1128`):

```bash
VLLM_ENGINE_READY_TIMEOUT_S=3600 VLLM_USE_RUST_FRONTEND=1 \
vllm serve deepseek-ai/DeepSeek-V4.1-Flash \
  --tokenizer-mode deepseek_v41 \
  --tensor-parallel-size 4 \
  --tool-call-parser deepseek_v41 \
  --enable-auto-tool-choice \
  --reasoning-parser deepseek_v41 \
  --mm-encoder-tp-mode data
```

**Do not run that as written.** §1.2 shows TP4 is 1.07 GB/GPU over the weight budget before
any KV. Use **TP8**, which is what every measured run uses:

```bash
VLLM_ENGINE_READY_TIMEOUT_S=3600 VLLM_USE_RUST_FRONTEND=1 \
vllm serve deepseek-ai/DeepSeek-V4.1-Flash \
  --tokenizer-mode deepseek_v41 \
  --tensor-parallel-size 8 \
  --tool-call-parser deepseek_v41 --enable-auto-tool-choice \
  --reasoning-parser deepseek_v41 \
  --mm-encoder-tp-mode data \
  --speculative-config '{"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"probabilistic","rejection_sample_method":"block","enable_adaptive_verification":true}' \
  --max-num-seqs 64 \
  --max-cudagraph-capture-size 1024
```

Everything above the `--tensor-parallel-size` line is quoted from the recipe; the
`--speculative-config` is the recipe's NVIDIA default
([architecture.md §7.4](./architecture.md)); `--max-num-seqs 64` is this document's
recommendation from the measured collapse at 128 (§3.4); and 1024 is the recipe's own
arithmetic for the widened DSpark batch (*"128 × (1 + 5) = 768 rounds up to 1024"*).
If you must run TP4, add `--engram-config '{"cpu_offload":true}'`.

**SGLang — H200 Low-Latency, quoted verbatim** from the cookbook via
[inference-engines.md §6.1](../../cross-cutting/inference-engines.md)
([src](https://docs.sglang.io/cookbook/autoregressive/DeepSeek/DeepSeek-V4_1.md)):

```bash
sglang serve --trust-remote-code --model-path deepseek-ai/DeepSeek-V4.1-Flash \
  --tp 8 --ep-size 8 --mem-fraction-static 0.8 \
  --attention-backend dsv4 --moe-runner-backend flashinfer_mxfp4 \
  --enable-decoder-swa-bounded-replay \
  --cuda-graph-max-bs-decode 64 \
  --reasoning-parser auto --tool-call-parser auto --host 0.0.0.0 --port 30000
```

Caveats attached to that cell by its own source: `--enable-decoder-swa-bounded-replay` *"is
validated on the decode path only, **refuses prompt logprobs by design**, is not numerically
equivalent to full prefill, and is excluded at launch with the prefill CUDA graph and with
DP attention"*; `--enable-deterministic-inference` is **refused** on the `dsv4` backend; and
SGLang defaults thinking **off** while vLLM defaults it **on at effort 50**.

Image pins that have actually been run on H200:
`vllm/vllm-openai:nightly-cd10ed6f9f6b37a8ace9cf380007e66fe12ec0c3` (2026-09-16) and
`lmsysorg/sglang:dev-dsv41` (2026-09-18). **No pip wheel carries this architecture** —
Docker is mandatory ([architecture.md §8.1](./architecture.md)). Floor for the host:
**driver 580.xx+, CUDA 13.0** ([gpus/h200.md §1](../../gpus/h200.md)).

### 6.2 Known engine issues that bite this pair on H200

- **Not in any numbered release.** vLLM `main` only (`min_vllm_version: 0.30.0`, which
  **does not exist** — latest is 0.29.0); SGLang preview image only. A nightly is your
  production dependency ([inference-engines.md §2.1, §6.1](../../cross-cutting/inference-engines.md)).
- **vLLM's shipped H200 profile is arithmetically unservable** (TP4, no Engram offload) —
  §1.2. This is the single most likely way to lose a day.
- **vLLM MRV2 fallbacks**: sequence parallelism, dual-batch overlap, elastic EP, custom
  logits processors and some speculative-decoding methods silently drop to MRV1
  ([gpus/h200.md §11](../../gpus/h200.md)). Check which path DSpark takes on your nightly.
- **Dynamo is three vLLM minor versions behind** (1.4.2 pins vLLM 0.26.0, which does not
  contain `vllm/models/deepseek_v41/` at all), and the only V4.1 Dynamo artefact is the
  experimental tag `v1.6.0-deepseek-v4.1-flash-dev.1`, SGLang-backend, **8× GB200**
  ([inference-engines.md §2](../../cross-cutting/inference-engines.md)).
- **TensorRT-LLM does not support V4.1** at 1.2.1 stable or 1.3.0rc27; NVIDIA's own NVFP4
  card lists only vLLM and SGLang ([architecture.md §8.1](./architecture.md)).
- **SGLang specifics**: `--enable-deterministic-inference` refused on `dsv4`; output *"is not
  bitwise stable across batch composition today"*; `--enable-decoder-swa-bounded-replay`
  refuses prompt logprobs and is excluded with the prefill CUDA graph and with DP attention;
  PD and speculative decoding cannot be combined
  ([inference-engines.md §6.1](../../cross-cutting/inference-engines.md)).
- **Reasoning-effort fork**: the DeepSeek API maps `low/high/max` → 50/75/100 while vLLM maps
  `low/high/xhigh/max` → 25/50/75/100, and SGLang defaults thinking **off** while vLLM
  defaults it **on at 50**. Same prompt, different token bill on each engine
  ([architecture.md §1.3](./architecture.md)).
- **No Jinja chat template ships.** Prompt encoding lives in `encoding/encoding.py` and the
  Rust `deepseek-recipe`; vLLM implements it behind `--tokenizer-mode deepseek_v41`. Tool
  calls use DSML tag blocks with a **leading space** (`<｜DSML｜ calls>`) — the breaking
  change from V4 ([architecture.md §1.3](./architecture.md)).

### 6.3 Accuracy caveats of the precision actually executed

The good news first: **the executed precision costs nothing measurable.** H200's
Marlin W4A16 path scores GSM8K `em_strict` **0.9712–0.9750** across three InferenceX dates,
against 0.9704–0.9712 on B200's native FP4 and 0.9727–0.9757 on GB300 — all within ±1 SE
(≈0.0045) of each other. Dequantising MXFP4 to BF16 is **numerically the more accurate
path**, not the less; what it loses is throughput, not quality.

Three caveats remain:

1. **FP8 KV is not free.** Uncalibrated FP8 KV gives *"1–2 % accuracy recovery or better"* on
   most models, but *"Kimi-K2.5 with FlashMLA showed consistent modest degradation"*, and
   *"some attention layer types (e.g. sliding-window) are more sensitive"*
   ([gpus/h200.md §6](../../gpus/h200.md),
   [quantization-formats.md §8.3](../../cross-cutting/quantization-formats.md)). This model
   is 100 % sliding-window-augmented — every one of its 43 layers carries a 128-token SWA
   component. **Calibrate with llm-compressor before trusting FP8 KV at long context**, and
   consider `--kv-cache-dtype-skip-layers sliding_window`. ⚠️ no published FP8-KV accuracy
   delta for this model.
2. **SWA Bounded Replay** (SGLang's `--enable-decoder-swa-bounded-replay`, and TokenSpeed's
   FlatKV default) is an **approximation**: a query at position *i* attends only to SWA keys
   in `[max(s, i−W+1), i]` for a replay starting at *s*. The tech report says it *"barely
   compromises response quality"* and **gives no number**
   ([architecture.md §2.3](./architecture.md)). It is also what makes a prefix-cache hit
   cheap, so on an agentic workload you are almost certainly running it.
3. **The 1M context is advertised, not measured.** No vendor has published a 1M-context
   decode step time on any hardware ([architecture.md §12.7](./architecture.md)), and at
   1M the Full-mode indexer scan reaches 170 MiB/seq/step at FP4 — **330 MiB at the FP8 KV
   H200 is forced to use**, which dominates everything else. If 1M matters, measure it before
   you size for it.

### 6.4 The one-line risk

**H200 runs this model correctly and cheaply per GB, and slowly per token.** It is the only
Hopper part that holds the whole checkpoint with the Engram tables resident — 2.1× H100's
measured output throughput for a ~2 % price premium — and it is **3.6× slower per GPU than
B200 on the identical trace** (186.4 vs 669.6 output tok/s/GPU at concurrency 64), because
it loses the FP4 expert GEMM, the 890 B/token KV cache, and the fused mega-attention kernel
all at once. Every one of those three is an `sm_10x` gate, none is a software gap that time
will close.
