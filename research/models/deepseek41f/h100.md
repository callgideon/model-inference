## 0. Verdict

1. **Yes, runnable today, and it is the only Hopper config that works at all**: vLLM
   `main`/nightly (`vllm/vllm-openai:nightly`, ≥ 2026-09-10; `min_vllm_version 0.30.0`
   which **does not exist yet** — latest release is 0.29.0), `"h100": "verified"` in
   vLLM's own hardware map. SGLang `dev-dsv41` also runs but is **8× slower** on the same
   node (§3.4). No pip wheel, no numbered release, no TensorRT-LLM.
2. **Min = recommended = 8 GPUs (one HGX node), TP8, EP1, with `--engram-config
   '{"cpu_offload":true}'` mandatory.** 1/2/4 GPUs do not fit at any setting; 16 and 32
   GPUs fit but cross InfiniBand for no throughput gain (§5.2).
3. **Weight format actually executed: MXFP4 stored, dequantised to BF16 in registers by
   Marlin W4A16.** H100 has no FP4 tensor core, so the 4-bit checkpoint buys the 8×80 GB
   fit and nothing else. KV runs at **BF16 3,200 B/token**, not the advertised 890 —
   the FP4 KV record needs `nvfp4_ds_mla` → `FLASHMLA_MEGA_ATTN_DSV41` → sm_10x (§2, §1.4).
4. **Interactive (S1, TPOT ≤ 50 ms): $1.87–$4.73 per 1M output tokens `est.`** at batch 64
   — but that is an extrapolation 2.7× beyond any measured concurrency. The **measured**
   agentic operating point (conc 20, 128K-class prompts) costs **$8.41–$21.28 per 1M
   output tokens `meas.`**.
5. **Max-throughput (S4): $0.82–$2.07 per 1M output `est.`** (batch 256). **Confidence:
   `measured` for the agentic envelope §3.4 and the fit §1; `estimate` for every
   short-context row in §3.3 and for §4's S1/S4 cost, which no published run covers.**

> **The one-line planner's answer.** On measured numbers, 8×H100 delivers **89.8 output
> tok/s/GPU**, which is **1/12.9 of a 2-GPU B300** and **1/9.9 of a 4-GPU GB300** on the
> identical benchmark, and costs **$9.90/1M output** against DeepSeek's own API list price
> of **$0.60/1M**. H100 is the *compatibility* answer for this model, never the economic one.

both shown). Activation workspace 4 GB at n ≥ 4, 6 GB at n < 4 (METHODOLOGY §3 band,
upper end at n < 4 because the per-GPU prefill chunk is larger). `python3` output:

**Note the 4-GPU row.** Even with the whole 188.83 GiB Engram table pushed to host RAM,
TP4 is **8.88 GB/GPU short** before a single KV byte. TP8 is not a preference on H100, it
is the arithmetic floor — which is exactly why vLLM's `strategy_overrides.single_node_tp`
pins `"h100": 8` while defaulting to 4 elsewhere
([vLLM recipe](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4.1-Flash)).

**And note the 8-GPU full-checkpoint row.** Without offload, 63.79 GB/GPU of weights
leaves **+4.21 GB** at util 0.90 (**+9.81 GB** at the recipe's 0.92) for activation
workspace *and* KV *and* CUDA-graph pools combined. That is why
`--engram-config '{"cpu_offload":true}'` is listed as a **required override** for H100 and
not as advice ([inference-engines.md §3.3](../../cross-cutting/inference-engines.md)).

### 1.3 Tensors that cannot be sharded

| Tensor / structure | Size | Why it cannot shard |
|---|---:|---|
| **Engram hash tables** | **202.76 GB (188.83 GiB)** | 24 random single-row gathers per token per module. vLLM's H100 profile runs **EP1**, so there is no expert-parallel axis to spread them over; they are either replicated in HBM (impossible here) or pinned in host RAM. |
| **Main compressed KV cache** | ctx-dependent | `num_key_value_heads: 1`. There is exactly one 512-d latent per position — nothing to split across TP ranks, so it is **replicated on every rank** (same property `serving-optimizations.md` §7.2 records for Kimi-K3's MLA). |
| **Indexer K cache** | ctx-dependent | one 128-d key per position, read by all 32 index heads → replicated. |
| **128-slot SWA ring buffer, 43 layers** | 2.77–5.38 MiB **per sequence per rank** | same single-KV-head reason. |
| mHC coefficient projections `hc_*_fn` (24 × 20480, F32) | 0.157 GB | consumed by the *next* sublayer (single-pass mHC) — replicated. |
| Routers `ffn.gate` (384 × 5120 BF16) × 40 | 0.157 GB | every rank must score every token → replicated. |
| `attn_sink` (F32, 64/layer), RMSNorms, gate biases/`bias_vl` | 0.0006 GB | replicated. |
| `attn.wo_a` | +1.34 GB at runtime | *"convert.py dequantizes it to bf16; an fp8 grouped GEMM would halve the memory"* — block-diagonal `einsum`, not a `Linear` ([`model.py`](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/raw/main/inference/model.py)). Reference-impl behaviour; ⚠️ whether vLLM does the same is unstated. |

**Consequence for §1.4:** because KV is replicated, METHODOLOGY §3's
`max_concurrency = kv_budget × n_gpus / (…)` **over-counts by 8× here**. The binding form
is `kv_budget_per_GPU / (ctx × kv_bytes_per_token + fixed_state)`. The sharded reading
(×8) is given as the alternative, as `serving-optimizations.md` §7.1 does for B300.
**§1.4 shows the measured data settles it in favour of the replicated reading.**

### 1.4 Max concurrency — and an empirical determination of the KV dtype

The InferenceX H100 runs report `kv_cache_pool_tokens` per row. Solving for the KV budget
three ways at the recipe's `--gpu-memory-utilization 0.92` (usable 73.6 GB, resident
weights 38.44 GB/GPU with Engram offloaded, measured pool at conc 1 = **7,957,495 tokens**):

| Assumed KV record | Pool bytes | Implied activation workspace | Plausible? |
|---|---:|---:|---|
| FP4, 890 B/token | 7.08 GB | **28.08 GB** | no |
| FP8 `fp8_ds_mla`, 1,650 B/token | 13.13 GB | **22.03 GB** | unlikely |
| **BF16 `auto`, 3,200 B/token** | **25.46 GB** | **9.70 GB** | **yes** |

`est.`, and independently corroborated two ways:

- **The pool is per-GPU, i.e. KV is replicated.** At conc 20, `gpu_kv_cache_usage_pct`
  0.528 × 6,435,008 = 3.398 M tokens ÷ 20 seqs = **169,884 tokens/seq**; at conc 28,
  0.832 × 5,788,028 ÷ 28 = **171,987 tokens/seq**. Two independent rows agree, and both
  match the trace's own `total_prompt_tokens / total_requests_completed` =
  362,843,663 / 2,572 = **141,074 tokens of prompt** plus generation and retained prefix
  blocks. If the pool were the *aggregate* over 8 GPUs these would come out at ~21 K
  tokens/seq, which contradicts the trace.
- **B200 cross-check.** The same sweep on 4×B200 (180 GB, TP4, weights 127.57 GB/GPU,
  usable 162 GB → 34.4 GB free) reports a pool of 29,372,139 tokens. At 890 B/token that
  is 26.1 GB — fits. At 1,650 it is 48.5 GB and at 3,200 it is 94.0 GB — both impossible.
  **So Blackwell gets the 890 B/token cache and Hopper does not**, from the same engine,
  the same image, the same week. That is the §1.1 disagreement resolved by measurement.

**⚠️ TO BE VERIFIED:** neither InferenceX nor the vLLM recipe states `--kv-cache-dtype` for
the H100 profile; the H100 profile JSON (fetched this session) contains no KV flag at all,
so vLLM's default `auto` applies. The 22 GB-workspace reading (FP8) cannot be excluded
outright, only judged implausible.

`max_concurrency`, replicated KV, measured-calibrated budget **25.46 GB/GPU**, pessimistic
5.38 MiB BF16 ring (`python3`):

| Context | **BF16 KV (what runs)** | FP8 KV (`fp8_ds_mla`, opt-in) | FP4 KV (not reachable on sm_90) |
|---|---:|---:|---:|
| 8 K | **799** | 1,329 | *(1,969)* |
| 32 K | **230** | 426 | *(731)* |
| 128 K | **59** | 114 | *(208)* |
| 1 M | **7** | 14 | *(27)* |

At METHODOLOGY §3's own 0.90 utilisation and 4 GB workspace (KV budget 29.56 GB/GPU) the
same table reads 928 / 267 / 69 / 8 (BF16), 1,543 / 495 / 133 / 17 (FP8), 2,286 / 849 /
241 / 31 (FP4) with the 5.38 MiB ring, and 1,015 / 274 / 69 / 8 (BF16) with the 2.77 MiB
one. **Sharded-KV alternative: multiply every cell by 8** — e.g. 6,392 at 8 K. The
replicated reading is the binding one and is the one §3 uses.

**1 M context seats 7 sequences per node.** That is the headline capacity fact for H100:
the model advertises 1 M and DeepSeek's own KV design makes 1 M cheap, but on Hopper you
pay 3.6× the advertised per-token cost and the node holds single-digit long sessions.

## 3. Throughput and latency

### 3.1 MBU / MFU assumptions (METHODOLOGY §4)

- **MBU 0.30–0.40 at TP8**, midpoint **0.35**. This is a **stated deviation** from
  METHODOLOGY §4's 0.6–0.8 Hopper band, taken from
  [`gpus/h100.md`](../../gpus/h100.md) §9.3's revised, KV-inclusive measurement:
  *"MBU falls with TP, not with concurrency … at TP8 the weight slice per GPU is 8.75 GB,
  collectives and kernel-launch overhead stop being hideable, and even KV-inclusive MBU
  only reaches 30–37 %."*
- **MFU 0.30 for prefill.** Below h100.md §9.4's 0.35–0.50 BF16 band, because (a) the
  expert GEMM is Marlin W4A16 — a dequant in registers before a BF16 MMA, (b) the
  non-expert FP8 is software-block-scaled on Hopper, (c) TP8 collectives, (d) the mHC
  residual is 4× the usual hidden width.
- **Comm overhead 10 %** (METHODOLOGY §4's 5–15 % for TP=8 over NVLink).
- **Peak used: 989.5 dense BF16 TFLOPS**, because Marlin's math is BF16. Using the FP8
  peak here would be wrong.
- Decode bytes per step per GPU = `weights_read(batch)/8 + kv_read(batch, ctx)`, with
  `weights_read = 384 × (1 − (1 − 6/384)^batch) × 18.80 MB × 40 + 18.75 GB` and KV read
  scaling with `batch × ctx` (METHODOLOGY §3/§4) — **KV is not sharded (§1.3), so the full
  KV read lands on every rank.**
- Speculative decoding: compute branch uses `Q = batch × (γ+1) = batch × 6`; the weight
  read stays at `distinct_experts(batch)`. **Acceptance 2.82** [src](https://github.com/vllm-project/vllm/issues/56797).

### 3.5 Explaining the gaps

**(a) Roofline vs measurement: 2.11×.** The calibration in §3.2 is remarkably *stable*
across conc 1–24 (1.54–2.96), which means the gap is a roughly constant per-step overhead,
not a modelling error that compounds. The candidates, none of them individually measured
on H100 ⚠️:

- **The missing `FLASHMLA_MEGA_ATTN_DSV41` fusion.** On sm_10x it collapses Q-norm, Q-RoPE,
  core attention, O-RoPE and the FP8 cast into one launch *"while retaining the same
  performance"* [src](https://github.com/deepseek-ai/FlashMLA). H100 pays all five launches
  separately, 43 layers deep, every step. FlashMLA's own note that *"at decode batch sizes,
  launch overhead is often the real cost"* applies directly.
- **Engram gathers over PCIe.** 48 random 264-byte host reads per token, not overlapped with
  anything the roofline counts. The only isolated datum anywhere is **2.8 ms/step** on DGX
  Spark; if even a fraction of that lands here it dominates the batch-1 step (8.18 ms measured
  vs 2.86 ms modelled — a 5.3 ms hole).
- **TP8 collectives on 43 layers.** h100.md §9.3 measures KV-inclusive MBU dropping from
  66.7 % at TP2 to 37.4 % at TP8 on a *conventional* 70 B model; this model has more layers
  and a 4× mHC residual to all-reduce.
- **Marlin's dequant is not free.** It unpacks 4-bit to BF16 in registers before every MMA;
  the HBM traffic is unchanged (so the roofline's byte count is right) but the SM-side cost
  is real.

**(b) The conc 24 → 28 cliff is a prefix-cache-eviction cliff, not a Marlin workspace knee.**
[`gpus/h100.md`](../../gpus/h100.md) §10.1 attributes it to *"the Marlin FP4 workspace, not
the cache"*, reasoning that 31.39 GiB of KV seats thousands of 8 K sequences. The per-row
metrics fetched this session show a different and fully self-consistent mechanism:

| conc | KV pool (tok) | KV usage | **achieved** cache hit | **theoretical** cache hit | median TTFT | out tok/s/GPU |
|---:|---:|---:|---:|---:|---:|---:|
| 16 | 6,686,467 | 44.8 % | 0.9471 | 0.9732 | 0.306 s | 78.75 |
| 20 | 6,435,008 | 52.8 % | 0.9380 | 0.9737 | 0.358 s | 89.81 |
| 24 | 6,014,511 | 72.5 % | 0.8870 | 0.9705 | 0.404 s | 76.84 |
| **28** | 5,788,028 | **83.2 %** | **0.7931** | 0.9522 | **2.502 s** | **19.64** |

The trace's sequences are ~170 K tokens each (§1.4). At conc 28 the live working set is
**4.82 M of the 5.79 M-token pool**, leaving nothing for retained prefixes: the achieved hit
rate falls 0.938 → 0.793 while the *theoretical* rate barely moves (0.974 → 0.952), so the
uncached prefill work roughly triples, TTFT goes 0.358 → 2.502 s, and output collapses 4.6×.
**It is a KV-capacity limit after all — just of the prefix cache, not of the in-flight
sequences.** That reframes the fix: `--kv-cache-dtype fp8_ds_mla` would nearly double the
pool and should push the cliff out; ⚠️ untested. (This does not *disprove* a Marlin
workspace component; it shows a sufficient cause that h100.md's reasoning did not consider.
Both readings are recorded.)

**(c) SGLang is 8× slower than vLLM on identical hardware.** 11.06 vs 89.81 out tok/s/GPU
best-case, TTFT 1.065–1.979 s vs 0.298–0.480 s, and the cache hit rate is erratic
(0.9319 → 0.5385 → 0.6298). SGLang's own cookbook **does not list H100** in
`supportedHardware` (`["h200","b200","b300","gb300","mi350x"]`, fetched this session), and
h100.md notes the DSA sub-backend table is documented for V3.2, not V4.1's CSA2 ⚠️. On
H100, **use vLLM.**

**(d) The agentic trace is input-dominated, which flatters `tput/GPU` and hides decode.**
At conc 20: 362.8 M prompt tokens against 2.59 M generated — a **140 : 1** ratio — at a
93.8 % cache hit. The 12,673 `tput/GPU` headline is 99.3 % input, of which ~94 % is a cache
read. Never quote it as a decode number; the decode number is **89.81**.

### 4.4 Effect of speculative decoding and prefix caching

- **Prefix caching is worth ~16× on the input side and is the reason the trace runs at all.**
  At conc 20, 93.8 % of 362.8 M prompt tokens were served from the GPU cache. Without it the
  uncached prefill load would be 16× higher; the conc-28 row is the natural experiment —
  the hit rate falls to 0.793 and total throughput drops 4.6×. Per METHODOLOGY §6 a hit is
  charged at 10 % of uncached prefill for **our own** serving; the measured `theoretical_cache_hit_rate`
  of 0.952–0.982 says the ceiling is even higher than what the pool can currently hold, so
  **FP8 KV (bigger pool) is a cost lever, not just a capacity lever.**
- **DSpark is worth up to 2.82× on output** at the measured acceptance
  ([vLLM #56797](https://github.com/vllm-project/vllm/issues/56797), sm_90) — but that is a
  low-batch number. Per-position acceptance is 0.724 / 0.516 / 0.301 / 0.180 / **0.096**, so
  positions 4–5 are nearly wasted; the reporter compares against the recipe's synthetic 3.51
  and a V4-Flash-on-H100 figure of 3.86 and calls the 2.82 *"~20 % lower than golden"*.
  **Do not plan with 3.51** — [architecture.md §7.3](./architecture.md) establishes it is a
  benchmark constant (`"rejection_sample_method":"synthetic","synthetic_acceptance_length":3.51`),
  not a measurement. The other real measurement is the DGX Spark community mean of **3.57**
  on GB10. Cutting γ from 5 to 3 would drop the verify width 33 % for ~10 % of the accepted
  length — worth measuring on your traffic ⚠️.

**input** side dominates — at 93.8 % cache hit the measured input cost is **$0.0706/1M**
against DeepSeek's $0.15/1M cache-miss and $0.003/1M cache-hit, i.e. self-hosting is
2.1× cheaper than a vendor cache **miss** and 24× more expensive than a vendor **hit**.
With a 140:1 input:output trace the blended comparison is $2.53 (self, low) vs roughly
$0.012/1M blended on the API at the same hit rate — **the API wins by two orders of
magnitude on this workload.**

From vLLM's H100 profile, fetched this session

Add DSpark ([architecture.md §7.4](./architecture.md), NVIDIA default — `true` is correct
here; the `false` variant is the ROCm requirement):

```bash
  --speculative-config '{"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"probabilistic","rejection_sample_method":"block","enable_adaptive_verification":true}' \
  --max-cudagraph-capture-size 1024   # round max_num_seqs x (1+5) up to a captured size
```

Two additions worth testing against your own traffic, neither measured on this pair ⚠️:

```bash

  --flashinfer-mxfp4-moe-precision fp8         # W4A8 Humming experts; ~9% prefill on H200/V4-Flash
  --language-model-only                        # text-only: frees the ViT's VRAM for KV
```

than exists.

SGLang runs but is not recommended (§3.5c); it has no H100 cell in its cookbook, and the
cookbook warns *"Do not override backends … Overriding them is the most common cause of a
disappointing measurement"* ([SGLang DeepSeek-V4_1 cookbook](https://docs.sglang.io/cookbook/autoregressive/DeepSeek/DeepSeek-V4_1.md)).

### 5.2 Single node vs multi-node

**Stay on one node.** §1.2 shows 16 and 32 GPUs fit comfortably, and they buy KV budget
(29.56 → 48.78 → 58.39 GB/GPU). What they do not buy is throughput:

- The H100 NVLink domain is **8 GPUs**. TP16 crosses InfiniBand/RoCE at ~400 Gb/s per NIC
  and takes METHODOLOGY §4's **20–40 % multi-node TP penalty** on every layer of a 43-layer
  model — against a measured baseline that is already only 17 % MBU.
- Wide-EP, the thing that makes a 384-expert MoE fly, needs a large NVLink domain. H100 does
  not have one. [`gpus/h100.md`](../../gpus/h100.md) §4: *"This is the single biggest
  structural gap versus GB200/GB300 NVL72, where 72 GPUs sit in one NVLink domain."*
- The better use of a second node is **DP2 × TP8** — two independent replicas behind a
  KV-aware router — which doubles throughput linearly and doubles the prefix-cache pool per
  replica without any cross-node collective. That is also the only configuration in which
  the extra KV budget of §1.2 is actually reachable.
- 16 GPUs *would* let Engram stay resident (19.22 GB/GPU offloaded vs 31.89 GB/GPU full,
  both fit), removing the PCIe gather path. Given that Engram placement was worth **2.16×**
  on RTX PRO 6000 ([architecture.md §10.2](./architecture.md)), **a 2-node TP8×DP2 layout
  with Engram resident is the one multi-node shape worth measuring** ⚠️ — nobody has.

### 5.3 When PD disaggregation or wide-EP pays here

**Neither pays on H100 for this pair.**

- **Wide-EP**: impossible, no NVLink domain > 8.
- **PD disaggregation**: each role needs the full 510.29 GB checkpoint, so 1P1D is
  **2 nodes / 16 GPUs minimum** and the KV must cross IB. The only verified V4.1-Flash PD
  layout is 1P1D on GB200 NVL4, text-only
  ([serving-optimizations.md §3.5](../../cross-cutting/serving-optimizations.md)). The
  governing rule from the same section: *"disaggregation is a thousand-GPU problem"*, and
  Modular reports a **20–30 % performance drop** on small or untuned workloads. With DSpark
  on, *"DSpark must run in both pools so the transferred KV stays compatible."*
  **⚠️ No H100 PD recipe exists.**
- The one disaggregation that *would* pay is **EPD** — splitting the vision encoder off — for
  multi-image traffic, since a max-res image costs ≈1,200 prefill tokens' worth of FLOPs for
  1,024 tokens. SGLang ships EPD with Mooncake; ⚠️ untested for this model on H100. For
  text-only traffic, `--language-model-only` is the cheap version.

### 5.4 Warm-up and load time

510.29 GB of safetensors from NVMe (`python3`):

| NVMe read rate | Pure weight read | Note |
|---:|---:|---|
| 5 GB/s | **102.1 s** (1.7 min) | single consumer drive |
| 10 GB/s | **51.0 s** | typical server NVMe |
| 20 GB/s | **25.5 s** | striped array |

That is the *floor*. Add:
- **188.83 GiB pinned into host RAM** for the Engram tables — budget ≥ 300 GB of free host
  RAM (the diffbot RTX PRO 6000 recipe asks for exactly that).
- Marlin repacking of 557.2 B four-bit expert params at load, and FlashInfer JIT/autotune.
- vLLM's own guidance: **`VLLM_ENGINE_READY_TIMEOUT_S=3600`** is an always-on base env for
  this model — *"Expect a long first load"* ([architecture.md §8.3](./architecture.md)).
  `--model-loader-extra-config '{"enable_multithread_load": true, "num_threads": 128}'`
  appears in NVIDIA's GB300 command and is worth carrying over.

**Plan 5–15 minutes to first token on a cold node**, not the 25–102 s the disk arithmetic
alone suggests. ⚠️ No measured H100 load time is published.

## 6. Risks and open questions

**⚠️ TO BE VERIFIED — newly raised by this document**

1. **The KV dtype actually used by the H100 runs.** §1.4 infers BF16 (3,200 B/token) from
   the KV-pool arithmetic; FP8 cannot be excluded, only judged implausible (it would imply
   a 22 GB activation workspace). Nobody publishes `--kv-cache-dtype` for this profile.
   Everything in §1.4, §3.3 and §4.3 moves if this is wrong.
2. **Whether `--kv-cache-dtype fp8_ds_mla` works on this model on sm_90 at all**, and
   whether it pushes the conc-28 cliff out as §3.5b predicts. Not measured anywhere.
3. **Whether `--flashinfer-mxfp4-moe-precision fp8` (W4A8 Humming) works for V4.1-Flash on
   H100.** The only Hopper measurement is on **DeepSeek-V4-Flash** (different checkpoint) on
   **H200** at TP2 — ~9 % prefill over FP4-Marlin
   [src](https://huggingface.co/endnai/DeepSeek-V4-Flash-W4A8-FP8).
4. **Engram-over-PCIe cost on H100.** Zero published figures. The 2.11× roofline gap has a
   5.3 ms/step hole at batch 1 that this is the leading candidate to fill. The DGX Spark
   node-local figure is 2.8 ms/step on utterly different hardware.
5. **Whether a 2-node TP8×DP2 layout with Engram resident recovers the 2.16× that Engram
   placement was worth on RTX PRO 6000** (§5.2).
6. **Vision on H100 is entirely unmeasured.** Every InferenceX H100 row is text-class
   agentic traffic. `--mm-encoder-tp-mode data` is in the shipped command but no multimodal
   run exists on this GPU.
7. **1M context on H100 is advertised, not measured.** §1.4 says 7 seats per node at BF16 KV.
   [architecture.md §12.7](./architecture.md): *"No measured 1M-context decode step time on
   any hardware."* At 1 M the four Full-mode indexer layers scan 170 B/token every step —
   182.37 MiB/seq/step at FP4 record sizes, ~3.6× that at BF16 — which on 3.35 TB/s at the
   measured 17 % MBU is ~1.1 s/step for a single sequence. Treat 1 M on H100 as unusable
   until somebody measures it.

**⚠️ Carried over from the foundation documents**

8. **FlashMLA's README says V4.1 sparse *decode* is SM100-only**, while vLLM's
   `FLASHMLA_SPARSE_DSV41` gate allows `major == 9` and the H100 runs demonstrably decode.
   Unresolved ([flash-attention.md §16.1](../../cross-cutting/flash-attention.md)).
9. **DSpark acceptance.** 2.82 measured on H20/sm_90; 3.51 is a **synthetic constant**;
   3.57 is a GB10 community mean; 3.86 is a figure the #56797 reporter attributes to
   V4-Flash on H100 without a link. DeepSeek publishes none.
10. **SWA ring-buffer dtype** — 2.77 MiB (FP8) vs 5.38 MiB (BF16 reference impl), a 1.94×
    on a term that dominates below ~6.3 K context. No engine document states it. §1.4 uses
    the pessimistic 5.38 MiB.
11. **`S = 1` state slots** assumed; if an engine ever allocates slots for the 5 DSpark
    draft positions, multiply.
12. **vLLM is nightly-only.** `min_vllm_version: 0.30.0` does not exist; the architecture
    merged to `main` in [PR #56228](https://github.com/vllm-project/vllm/pull/56228) on
    2026-09-10 and `v0.29.0`/`v0.28.0` both 404 on the model directory
    ([inference-engines.md §6.1](../../cross-cutting/inference-engines.md)). You are pinning
    a nightly image hash in production.

**Known engine issues that bite on H100 specifically**

13. **[vLLM #51326](https://github.com/vllm-project/vllm/issues/51326)** — `DeepSeek-V4-Flash-0731`
    on **8×H100 with TP8 + expert parallelism** produces *"malformed or semantically
    nonsensical output"* on vLLM 0.26.0 while 0.25.0 is correct, on both the Marlin and the
    Triton unfused backends. Different checkpoint (V4, not V4.1) and no maintainer diagnosis,
    but note that **every InferenceX H100 vLLM row runs `decode_ep: 1`** — i.e. the measured,
    working configuration is TP8 *without* EP. Do not turn on `--enable-expert-parallel` on
    H100 without an end-to-end correctness check.
14. **NVFP4 MoE on Hopper has live correctness bugs** — garbage output at conc 1 and a
    `fused_marlin_moe` illegal memory access at conc ≈ 8
    ([vLLM #49070](https://github.com/vllm-project/vllm/issues/49070), H100/H200). This is the
    Marlin FP4 MoE path, which is exactly what this model uses. Validate end-to-end on your
    exact build.
15. **FP8 KV + FA3 on Hopper**: systematic decode/prefill logprob mismatch
    (vLLM #54035) ⚠️ — relevant if you take open question 2's advice.
16. **`--max-num-batched-tokens 4096`** means a 128 K prompt is 32 chunks. Measured p95 TTFT
    at conc 20 is **6.98 s** against a 0.358 s median. Long-prompt tail latency on H100 is
    poor and the §3.3 TTFT column does not capture it.
17. **CUDA floors**: FA3 ≥ 12.3, FlashMLA ≥ 12.8, and MXFP4/Marlin needs CUDA ≥ 12.8 **and
    the same CUDA at build and serve time** — *"mismatch produces garbage output, not an
    error"* ([gpus/h100.md](../../gpus/h100.md) §11).
18. **SGLang on H100 is not a supported target** (absent from `supportedHardware`) and
    measures 8× slower. Treat its H100 rows as a lower bound, not a choice.

**Accuracy caveats of the executed precision**

19. **None found, and that is a real result.** GSM8K on 8×H100 with Marlin W4A16 measures
    **0.9757 / 0.9750 `em_strict`** (vLLM conc 28 / SGLang conc 8) against **0.9704** on
    4×B200 with native NVFP4 — every cell within one standard error (±0.0042–0.0047). The
    dequant path costs throughput, not quality.
20. Two model-level caveats apply on every GPU: **SWA Bounded Replay** *"barely compromises
    response quality"* with no published number, and the reference implementation's
    `attn.wo_a` BF16 dequantisation is a memory, not an accuracy, note
    ([architecture.md §2.3, §3.4](./architecture.md)).
21. **Reasoning effort is a cost dial, not a quality switch.** Effort 25 → 100 lifts the
    8-benchmark average 67.1 → 76.3 % at *"roughly 2.5× more output tokens"*; effort 60–80
    recovers most of it at under half the budget ([architecture.md §10.5](./architecture.md)).
    On a GPU where output tokens cost $8.41–$21.28/1M measured, **that dial is worth more
    than any kernel flag in this document.**

## Arithmetic

All derived numbers were produced with `python3`; the scripts live in this session's
scratchpad and their output is pasted verbatim into §1.2, §1.4, §3.2, §3.3, §4.2–4.5 and
§5.4. Key formulas, per METHODOLOGY:

```
usable_hbm        = 80 GB × 0.90   (recipe uses 0.92 → 73.6 GB)
per_gpu_weights   = (510.286_023_000 GB − 202.76 GB engram) / n_gpus
kv_budget/GPU     = usable − per_gpu_weights − activation_ws
max_concurrency   = kv_budget_per_GPU / (ctx × kv_bytes_per_token + fixed_state)   # KV REPLICATED
weights_read(b)   = 384 × (1 − (1 − 6/384)^b) × 18_800_640 B × 40 + 18.75 GB
bytes/GPU/step    = weights_read(b)/8 + b × (fixed + 38×512×288×s + 4×16384×68×s + 170×ctx×s),  s = 3200/890
step_time         = max( bytes / (3.35e12 × MBU),  (2×16.13e9 + attn)×b×(γ+1) / (8 × 989.5e12 × MFU) ) × 1.10 × 2.11
TPOT              = step_time / accept_len          (accept_len = 2.82)
prefill_time(T)   = (2 × 7.89e9 × T + indexer(T) + selected(T)) / (8 × 989.5e12 × 0.30) × 2.11
cost_per_1M       = n_gpus × $/GPU-hr / (aggregate_tok_s × 3600) × 1e6
blended           = 0.75 × 0.5 × in + 0.75 × 0.5 × in × 0.10 + 0.25 × out
```
