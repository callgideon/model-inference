## 0. Verdict

1. **Yes, runnable today and verified by the vendor** — SGLang **v0.5.19+** (H200 is the *only*
   datacentre-Hopper cell anyone has actually run: `verified: true`, BF16 and FP8, single GPU) and
   vLLM **≥ 0.17.0** (`hw/h200.json`, TP1) [src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md) [src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/h200.json).
2. **Minimum 1 GPU; recommended 1 GPU (TP1) × 8 replicas per HGX node** — the model fits one card
   in every precision, so replication beats sharding for interactive traffic; TP2/TP4 exist only
   to buy KV headroom and are ⚠️ unverified for this pair.
3. **Weight format actually executed: FP8 E4M3 block-128** (`Qwen/Qwen3.8-27B-FP8`), native on
   sm_90. NVFP4 loads but degrades to Marlin **W4A16 dequant** and SGLang greys out every H200
   NVFP4 cell; MXFP4 does not load on NVIDIA at all.
4. **Interactive (S1, TPOT ≤ 50 ms): $0.159–0.452 per 1M output tokens** ($3.99 Hyperstack raw
   roofline → $7.912 AWS p5en derated ×0.70); **max-throughput (S4): the same numbers**, because
   on H200 this model hits its KV+GDN-state ceiling (168 concurrent 4.6K sequences) long before it
   hits the TPOT budget (24.2 ms raw / 34.5 ms derated at that ceiling).
5. **Confidence: estimate.** Every throughput and TTFT figure here is `est.` from the
   METHODOLOGY §4 roofline. **No tok/s, TPOT or TTFT measurement for Qwen3.8-27B on H200 exists
   anywhere** — the only H200-specific measurement found is a speculative-decoding *speedup ratio*
   table, and even that is secondary-sourced (§3.2).

## 1. Fit

### 1.1 Inputs and the topology set

```
usable_hbm      = 141e9 × 0.90                    = 126.90 GB per GPU   (METHODOLOGY §3)
activation_ws   = 4 GiB                           =   4.295 GB per GPU
kv_budget/GPU   = 126.90 − weights/GPU − 4.295
kv_bytes/token  = 32,768 (FP8) | 65,536 (BF16)    — 16 full-attention layers only
fixed_state/seq = S × 78,446,592 B (bf16 state)   — S = 5 SGLang default, S = 1 floor
max_conc(ctx)   = floor( kv_budget/GPU / (ctx × kv_per_gpu + S × state/n) ) × n
```

**Topology.** HGX H200 is an 8-GPU NVSwitch baseboard, 1,128 GB HBM3e, 900 GB/s NVLink per GPU,
all-to-all single hop ([gpus/h200.md §4](../../gpus/h200.md)). The allowed GPU counts are
therefore **{1, 2, 4, 8}** inside one node and **16, 24, 32 …** across nodes over 400G-class IB /
EFA. **There is no NVL72-style rack domain on Hopper** — anything past 8 GPUs pays METHODOLOGY
§4's 20–40 % multi-node overhead. For a 27.78 B dense model that fits one card, crossing a node
boundary is never the right answer; the 16-GPU row below exists only to show that.

### 1.2 Which tensors cannot be sharded

| Tensor group | Params | Shardable under TP? | Why |
|---|---:|---|---|
| MLP `gate/up/down_proj` (64 layers) | 17,112,760,320 | ✅ column/row-parallel | 17408 % 8 = 0 |
| Full-attention `q/k/v/o_proj` (16 layers) | 1,677,729,792 | ✅ **but only to TP 4** | `num_key_value_heads = 4`. At TP 8 the 4 KV heads must be **replicated ×2**, so per-GPU KV bytes stop falling past TP 4 (⚠️, §1.5) |
| GDN `in_proj_qkv / in_proj_z / out_proj` (48 layers) | 5,562,051,072 | ✅ head-parallel | 48 value heads, 16 key heads — divide evenly by 1/2/4/8 |
| `embed_tokens` + `lm_head` | 2,542,796,800 | ✅ vocab-parallel | 248,320 % 8 = 0 |
| **Vision encoder (27 ViT blocks + merger)** | **460,730,096** | ❌ **replicated** under the verified H200 recipe | vLLM's H200 command passes `--mm-encoder-tp-mode data` [src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/h200.json), i.e. the encoder is **data-parallel, one full copy per rank** = **0.921 GB of BF16 on every GPU**. `--mm-encoder-tp-mode weights` would shard it; no H200 recipe uses that. |
| All RMSNorms / LayerNorms, `q_norm`/`k_norm`, GDN `A_log`, `dt_bias`, `in_proj_a`, `in_proj_b` | ≈ 700 K + ViT norms | ❌ replicated | ~1.4 MB — negligible but never zero |
| `conv1d` (depthwise, 10240×1×4) | 1,966,080 (48 layers) | ✅ channel-parallel, aligned to heads | 10240 = 16·128 + 16·128 + 48·128 |
| **MTP head** (0.425 B) | 424,699,392 | ⚠️ **TO BE VERIFIED** | vLLM's `--speculative-config` draft placement under TP is not documented for this model. Method: boot TP2 with MTP and read per-rank weight bytes. |
| **GDN recurrent state** (runtime, not weights) | — | ✅ head-parallel | 48 value heads / n; this is why TP scales concurrency **super-linearly** at short context (§1.4) |

So `weights_per_GPU(n>1) = (checkpoint_bytes − 0.921 GB) / n + 0.921 GB`.

### 1.5 Three things the table hides

1. **TP scales concurrency super-linearly at short context, because the GDN state shards too.**
   At 8K FP8/FP8-KV, one GPU holds 138 sequences but a TP2 pair holds **646**, not 276. The reason
   is in METHODOLOGY §2's two terms: at 8K the per-sequence cost is 268.4 MB of KV **plus
   392.2 MB of state** (`S = 5` × 78.45 MB), and TP halves *both* per GPU while you also gain a
   second GPU's budget. By 128K the KV term dominates and TP2 gives the expected ~2×·(weights
   saved) — 90 vs 2×19 = 38, still better than linear but for the ordinary reason.
2. **Per-GPU KV stops shrinking past TP 4.** `num_key_value_heads = 4`, so a TP8 rank must
   replicate a KV head. The `n = 8` rows above already apply `kv_per_gpu = 1/4`. This is standard
   engine behaviour but is **⚠️ TO BE VERIFIED for this model** — method: boot TP4 and TP8 at a
   fixed `--max-model-len` and compare the reported KV-pool token counts; TP8 should report
   roughly 2× TP4's per-GPU pool, not 1×. Related and sourced: DCP is capped at `TP // n_kv_heads
   = TP // 4` for this model ([serving-optimizations.md §7.3](../../cross-cutting/serving-optimizations.md)).
3. **The activation workspace is understated for the H200 recipe.** SGLang's H200 cells pin
   `--chunked-prefill-size 32768 --max-prefill-tokens 32768` ([architecture.md §8.3](./architecture.md)),
   and `gpus/h200.md` §11 says to budget **6+ GiB** at long prefill with large chunks. Re-running
   the FP8/TP1 row at 6 GiB instead of 4 GiB moves 8K from 138 → 133 and 128K from 19 → 19. It is
   a ~4 % effect at short context and zero at long; the tables stay at 4 GiB for comparability
   with `gpus/h200.md` §2 and `architecture.md` §10.2.

**Multi-node fabric needed?** **No, never, for this pair.** One GPU is the minimum and 8 GPUs of
one HGX node is the maximum that makes sense. The 16-GPU rows are printed for completeness and
would require 400G IB/EFA with METHODOLOGY §4's 20–40 % overhead for a model whose weights are
2.2 % of a single node's HBM.

### 3.4 Why the estimates and the (absent) measurements will diverge — and the precision result

Nothing here can be compared to a measurement, so the honest statement is about *direction*:

1. **The roofline is an optimistic ceiling.** The one calibration point in the whole tree
   (`architecture.md` §10.2, RTX 5090) shows it over-predicts by ~35 %. The derated table is the
   one to plan against.
2. **TTFT will be worse than Table 3 under load.** Table 3 is a cold single sequence. With
   `--chunked-prefill-size 32768`, each prefill chunk stalls the decode loop; SGLang's own guidance
   that SM120 must drop to 2048 chunks *because* *"decode steps stall behind each prefill chunk on
   hybrid GDN models"* is an admission that the effect is real and merely cheaper on SM90.
3. **The GDN prefill kernel's MFU is unknown.** 20 % of this model's parameters live in 48
   recurrent layers whose prefill is a chunked scan, not a GEMM. The 0.30–0.45 MFU band is
   borrowed from dense FP8 GEMM benchmarks and is the weakest assumption in this document.
4. **Speculative decoding does not rescue the throughput point.** The measured H200 curve
   (§3.3 rows 1–3) falls from 3.43× at c=1 to ~1.0–1.45× at c=32 and the S1 operating point is
   c=168. `architecture.md` §7.4 puts the crossover at **bs ≲ 100 at 8K with FP8 weights**.
   Speculation on H200 is a *latency* feature for low-concurrency tiers, not a cost feature.

**The precision result — W4A16 is slower than FP8 at the throughput point.** This is the
non-obvious H200 finding and it falls straight out of §2's "dequant" rows:

```
======================================================================================================================
TABLE 13  BF16 vs FP8 vs W4A16 on 1 x H200 at S1 (decode only; H200 has no FP4 tensor core)
======================================================================================================================
  BF16 55.563 GB                   max_conc  123  TPOT  27.5 ms  tok/s/GPU   4473   (t_mem  27.5 / t_cmp   9.9)
  FP8 30.870 GB                    max_conc  168  TPOT  24.2 ms  tok/s/GPU   6953   (t_mem  24.2 / t_cmp  13.5)
  NVFP4->Marlin W4A16 21.923 GB    max_conc  185  TPOT  23.0 ms  tok/s/GPU   8038   (t_mem  23.0 / t_cmp  14.9)
  INT4 W4A16 19.453 GB             max_conc  189  TPOT  22.6 ms  tok/s/GPU   8349   (t_mem  22.6 / t_cmp  15.2)
  note: t_cmp for the two W4A16 rows is optimistic - Marlin/Machete dequantise to BF16 (989.5 TF), not FP8.
  NVFP4->Marlin W4A16 21.923 GB    BF16-compute recompute: TPOT  29.8 ms  tok/s/GPU   6206  (t_cmp  29.8)
  INT4 W4A16 19.453 GB             BF16-compute recompute: TPOT  30.5 ms  tok/s/GPU   6206  (t_cmp  30.5)
```

The first four rows assume the arithmetic still runs at FP8 rate, which is wrong for a
dequantising kernel: Marlin/Machete unpack 4-bit weights into **BF16** MMAs at 989.5 dense
TFLOPS. Redo the compute term at 989.5 and both 4-bit rows flip from memory-bound to
**compute-bound** and land at **6,206 tok/s/GPU — 11 % below FP8's 6,953**, while buying only
10–13 % more concurrency. **On H200, FP8 is the format; 4-bit is a capacity tool for long-context
tiers, not a throughput tool.** (This is the opposite of the Blackwell conclusion in
`quantization-formats.md` §9.4, and the reason is one line of silicon: sm_90 has no FP4 tensor core.)

### 4.4 Effect of prefix caching and speculative decoding on cost

```
================================================================================================================
TABLE 11  PREFIX CACHING effect on input cost, S1 (prefill 10956 tok/s @MFU .30, Hyperstack $3.99)
================================================================================================================
  hit   0%  $/1M input = 0.1012   (uncached 0.1012, cached tokens charged at 10% per METHODOLOGY §6)

```

Prefix caching is **by far the larger of the two levers for this pair on H200**, for a reason that
is specific to the architecture: it cuts input cost 5.3× at a 90 % hit rate *and* it is what
`preserve_thinking: true` exists to enable — each agentic turn is a strict extension of the
previous prompt, so the radix match runs to the end of the last turn and both the KV **and** the
GDN checkpoint are reused. Turning it off does not merely cost a re-prefill; it re-runs 48
recurrent layers over the whole prefix (`architecture.md` §5.6). Set against that, the `S = 5 → 1`
capacity win (+91 % concurrency at 8K, −22 % on `$/1M out`) is **not** worth taking on
prefix-structured traffic; it is worth taking on independent batch jobs.

**Speculative decoding does not lower the cost floor on H200.** It lowers per-user latency
dramatically at low concurrency — at c=1 DFlash2 takes the derated TPOT from ~13.3 ms to ~4–5 ms —
and it costs you `D` extra GDN state slots per request (4 for MTP, 8 for DFlash2/DSpark), which
*reduces* max concurrency. Run it on a dedicated low-concurrency latency tier; leave it off on the
throughput tier. Distinguish the numbers carefully: the acceptance figures in
`architecture.md` §7.2 (MTP mean 4.28, DSpark 3.62, DFlash2 4.80) are **measured per-request
acceptance lengths**, not synthetic constants — unlike the identical-looking **3.51** that appears
as `"rejection_sample_method":"synthetic"` in the DeepSeek-V4.1-Flash MI355X recipe. Different
model, different provenance, coincident number.

```
Hyperstack res. $2.79  vs OpenRouter aggregate   out 0.159/2.55=  6.2%  blended 0.069/0.726=  9.5%
Hyperstack res. $2.79  vs Darkbloom fp4          out 0.159/1.80=  8.8%  blended 0.069/0.491= 14.0%
```

Read the break-even column as: *the fraction of the rented hour you must actually keep busy for
self-hosting to beat the API.* On the cheapest reputable on-demand rate you need to keep an H200
**~10–14 % busy** to beat the market blended price, and **~20 %** to beat the cheapest FP4
endpoint on the board. That is an unusually forgiving threshold — it is a direct consequence of
this model being small enough that one card serves 168 concurrent sessions.

Two caveats on that verdict:
- **The margin is much thinner on input than on output.** Self-hosted input is $0.071–0.201/1M
  against an API floor of $0.100 (Darkbloom) and a cached-read floor of $0.024–0.05. For
  **input-heavy, high-cache-hit agentic replay, the API is close to fairly priced** and can be
  cheaper than an under-utilised H200. For output-heavy reasoning — and remember
  `reasoning_effort` defaults to **`xhigh`** with a recommended 262K reasoning budget — self-hosting
  wins by 8–13×.
- **Only two listed providers serve the full 1M window** (Novita, Alibaba). If you need 1M
  context, the API comparison narrows to those two and the self-host option needs FP8 KV plus
  ~68.9 GB per sequence (one, maybe two, per H200).

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

**Single node, always.** 55.56 GB of BF16 weights against 126.9 GB of usable HBM means one GPU is
the minimum *and* the natural unit. Crossing a node boundary for a 27.78 B dense model would pay
METHODOLOGY §4's 20–40 % multi-node overhead for zero capability. The only real question is how to
spend the eight GPUs of one HGX board, and it has two different answers depending on the SLO:

```
==========================================================================================================
TABLE 12  NODE SHAPE at a FIXED SLO (derated TPOT <= 50 ms), S1 4K/512, FP8/FP8-KV/bf16 state, S=5, 8 GPUs
==========================================================================================================
shape                    max_conc     batch   TPOT ms  derated ms   node tok/s    node conc
TP1 x 8 replicas              168       168      24.2        34.5        55623         1344
TP2 x 4 replicas              784       641      35.0        49.9        73332         2564
TP4 x 2 replicas             3360      1315      35.0        50.0        75171         2630
TP8 x 1 replicas            10872      1766      35.0        50.0        50458         1766

  same, but with --disable-radix-cache (S=1):
TP1 x 8 replicas              399       289      34.9        49.9        66155         2312
TP2 x 4 replicas             1860       641      35.0        49.9        73332         2564
TP4 x 2 replicas             7960      1315      35.0        50.0        75171         2630
TP8 x 1 replicas            19840      1766      35.0        50.0        50458         1766
```

- **TP1 × 8 replicas** is the verified shape (both vLLM's `hw/h200.json` and every SGLang H200
  cell are single-GPU), it is the simplest to operate, and it gives the best *latency* (34.5 ms
  derated at its ceiling, 13.3 ms at batch 1). It leaves ~26 % of the node's achievable throughput
  on the table because each replica is capacity-capped at 168.
- **TP4 × 2 replicas** is the throughput shape: **+35 % node tokens/s and ~2× node concurrency**
  at the same 50 ms derated SLO, because sharding the GDN state and the KV across 4 GPUs is what
  lifts the ceiling. **⚠️ Unverified for this pair** — no vendor has published a TP > 1 cell.
- **TP8 is worse than TP4** on both counts: per-GPU KV stops shrinking at TP 4 (§1.2), the comm
  overhead rises to 15 %, and per-GPU throughput falls.
- `--disable-radix-cache` only helps the TP1 shape (55.6k → 66.2k node tok/s). At TP2/TP4 the
  state pool is already sharded enough that `S` stops binding.

**Does PD disaggregation or wide-EP pay here? No.** Wide-EP is not applicable — there are no
experts. PD disaggregation has no published layout for this model, vLLM's `compatible_strategies`
is `single_node_tp` only, and the prefill/decode imbalance that justifies disaggregation on a
600 B MoE does not exist on a 27.78 B dense model that fits one card. The one genuinely
interesting alternative the H200 recipe exposes is a **Mooncake KV store**
(`kv_store_centralized_mooncake`, `kv_store_distributed_mooncake`
[src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/h200.json)) — a cross-replica KV tier that would
let 8 TP1 replicas share one prefix cache instead of eight private ones. That is the shape worth
evaluating for agentic traffic, and it is **⚠️ TO BE VERIFIED** whether the **GDN state
checkpoints** travel with the KV blocks in that store; if they do not, a cross-replica hit still
forces a full recurrent re-prefill and the store buys much less than it appears to.

### 5.2 Launch commands, quoted from the engine docs

**vLLM — H200, TP1 (verbatim from the recipe's `hw/h200.json`)**
[src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/h200.json):

```bash
# env: VLLM_USE_RUST_FRONTEND=1      # docker_image: vllm/vllm-openai:qwen38
vllm serve Qwen/Qwen3.8-27B \
  --tensor-parallel-size 1 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_xml \
  --reasoning-parser qwen3 \
  --mm-encoder-tp-mode data
```

Note what the verified H200 profile does **not** pass: `--kv-cache-dtype fp8`, `--max-model-len`,
and any speculative config. Both are recommended additions from the same recipe page — *"Add
`--speculative-config '{"method":"mtp","num_speculative_tokens":3}'` for MTP"* — and the FP8-KV
flag is what every SGLang cell pins. For the FP8 checkpoint the recipe's low-latency template is
[src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B):

```bash
vllm serve Qwen/Qwen3.8-27B-FP8 \
  --tensor-parallel-size 1 \
  --max-model-len 262144 \
  --kv-cache-dtype fp8 \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice --tool-call-parser qwen3_xml
```

**SGLang — H200, BF16 or FP8, single GPU** (the cookbook's `cells` template, placeholders as
published) [src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md):

```
--trust-remote-code --model-path {{MODEL_NAME}} --kv-cache-dtype fp8_e4m3
--mem-fraction-static 0.85 --attention-backend flashinfer
--chunked-prefill-size 32768 --max-prefill-tokens 32768
--reasoning-parser qwen3 --tool-call-parser qwen3_coder --host {{HOST_IP}} --port {{PORT}}
```

Add `--attention-backend fa3` as the documented alternative (*"measured slightly faster at bs=1"*),
`--mamba-ssm-dtype bfloat16` to halve the state pool (**on sm_90 this is purely a memory and
accuracy choice — the FlashInfer-GDN *fast-path* dtype gate is an SM100 feature**), and
`--mamba-radix-cache-strategy no_buffer` (`S = 3`) or `--disable-radix-cache` (`S = 1`) to trade
prefix caching for concurrency. For 1M context, the model card's YaRN override verbatim
[src](https://huggingface.co/Qwen/Qwen3.8-27B/raw/main/README.md):

```shell
SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1 python -m sglang.launch_server ... --json-model-override-args '{"text_config": {"rope_parameters": {"mrope_interleaved": true, "mrope_section": [11, 11, 10], "rope_type": "yarn", "rope_theta": 10000000, "partial_rotary_factor": 0.25, "factor": 4.0, "original_max_position_embeddings": 262144}}}' --context-length 1000000
```

Two flags that pay for themselves and are easy to forget: **`--reasoning-parser qwen3` is
effectively mandatory** (*"the chat template opens every assistant turn with `<think>`, so without
it the entire reasoning block lands in `message.content` and a 2048-token budget can be spent
before the answer starts"* [src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B)), and the tool-call
parser differs between engines — `qwen3_xml` in vLLM, `qwen3_coder` in SGLang, for the *same* chat
template (⚠️, `architecture.md` open question 1).

### 5.3 Warm-up and loading

```
================================================================================================
TABLE 9  WEIGHT LOAD FROM NVMe (METHODOLOGY: 5-20 GB/s)
================================================================================================
  BF16 Qwen/Qwen3.8-27B         55.56 GB ->   2.8 s @20 GB/s     5.6 s @10 GB/s    11.1 s @5 GB/s
  FP8 Qwen/Qwen3.8-27B-FP8      30.87 GB ->   1.5 s @20 GB/s     3.1 s @10 GB/s     6.2 s @5 GB/s
  INT4 RedHatAI                 19.45 GB ->   1.0 s @20 GB/s     1.9 s @10 GB/s     3.9 s @5 GB/s
```

Those are **pure I/O floors** and they are not what you will see. The one published figure for
this checkpoint is SGLang's: **~6.5 minutes to load its 18 shards from NVMe on a DGX Spark**, with
advice to *"budget ~10 minutes to READY before calling a boot hung"*
[src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md). A DGX Spark is a
unified-memory GB10 box, so its I/O path is not an H200 server's — but the gap between 2.8 s of
theoretical NVMe time and 390 s of observed wall clock is safetensors deserialisation, dtype
handling and the shard layout (`architecture.md` §1.1: shards alternate ~3.98 GB / ~2.11 GB from
shard 6 onward, one full-attention block plus three GDN blocks per pair), not the disk. **Budget
2–5 minutes to READY on an H200 with warm page cache, 10 minutes cold, plus FlashInfer JIT
warm-up on first boot and CUDA-graph capture.** ⚠️ No H200 load-time measurement is published.

### Accuracy caveats of the executed precision (FP8 E4M3 block-128)

- **Weights.** Qwen's own claim for the first-party FP8 build is that *"performance metrics are
  nearly identical to those of the original model"* [src](https://huggingface.co/Qwen/Qwen3.8-27B-FP8)
  — a vendor claim with **no published eval table**. The nearest independent evidence is the
  *INT4* build (RedHatAI), which recovers 98.5–101.1 % across IFEval / MMLU-Pro / GSM8K-Platinum /
  MATH-500 / GPQA-Diamond / AIME-2025; FP8 should be strictly better than INT4, so 98.5 % is a
  conservative floor. **⚠️ No FP8-specific accuracy table for this model exists.**
- **KV cache.** `--kv-cache-dtype fp8_e4m3` is uncalibrated by default. vLLM's cross-model study
  reports *"most models: 1–2 % accuracy recovery or better"* and long-context MRCR at *"97–98 % of
  the baseline AUC"*. On this model the exposure is above average: only **4 KV heads at head_dim
  256** means there is little head-level redundancy to absorb quantisation error, and the
  262K/1M context claim is exactly the regime where MRCR-style degradation shows up. Calibrate
  with llm-compressor if long-context retrieval accuracy matters, and note that per-head FP8 KV
  scales are available **only with the FlashAttention backend**.
- **GDN state dtype.** `--mamba-ssm-dtype bfloat16` halves the state pool (78.45 vs 153.94 MB per
  slot) and SGLang explicitly frames it as *"an accuracy gate"* to validate for your workload — it
  is not a free memory win. It is also **not** a one-way speed trade: SGLang measured fp32 winning
  on one precision (NVFP4+EAGLE 152.9 vs 144.5 tok/s/user) and losing on another (FP8+EAGLE 106.3
  vs 116.1) on the same card. Measure both.
- **Static YaRN at 1M.** Qwen's own warning: *"All the notable open-source frameworks implement
  static YaRN … potentially impacting performance on shorter texts."* Do not run a 1M-configured
  H200 replica for 4K traffic; run two tiers, or set `factor` to match your real context.
- **The 4,097th risk nobody prices:** `reasoning_effort` defaults to **`xhigh`** and
  `preserve_thinking` defaults to **true**. The do-nothing configuration is the most
  output-token-expensive one, and on the cost table in §4 output tokens are 1.6–2.2× the price of
  input tokens. Reasoning-budget misconfiguration will cost more than every serving optimization
  in §2 saves.
