# Qwen/Qwen3.8-27B on NVIDIA A100 SXM 80GB (HGX 8-GPU; no FP8/FP4 tensor cores)

**Research date: 2026-09-19.** Follows [`research/METHODOLOGY.md`](../../METHODOLOGY.md) —
§1 weight memory, §2 KV/state and the slot multiplier `S`, §3 fit and the consistency rule,
§4 roofline, §6 cost and the standard scenarios S1–S4, §8 pinned inputs. Model facts are

## 0. Verdict

1. **Runnable, unverified, and nobody ships it.** Every kernel this model needs exists on
   sm_80 — FA2 covers `head_dim 256`, vLLM's fused CUDA Gated-DeltaNet decode kernel is gated
   at `has_device_capability(80)`, GDN prefill falls to Triton/FLA — but **no engine publishes
   an A100 profile**: `recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/a100.json` is 404, every vLLM
   variant's `supported_hardware` omits `a100`, and SGLang's `supportedHardware` is
   `["h200","rtx6000","rtx5090","dgx-spark","gb300"]`. Engine of record: **vLLM ≥ 0.17.0**
   (0.29.0 current) — **⚠️ TO BE VERIFIED end-to-end**.
2. **Min 1 GPU, recommended 1 GPU per replica × 8 replicas per HGX node (TP1 + DP8).** The
   model fits one A100 in every precision; TP2/TP4 exist only to cut the 1.6 s TTFT or buy KV
   budget, and TP8 duplicates the 4 KV heads.
3. **Weight format actually executed: INT4 W4A16 via Marlin** (`RedHatAI/Qwen3.8-27B-INT4`,
   19.45 GB), dequantised to FP16 in-register. BF16 is the only *native* format; FP8 runs
   W8A16 Marlin (memory win, no math win); NVFP4 is a known-broken A100 path. **No format on
   Ampere increases compute throughput.**
4. **Interactive (S1, 4K/512, TPOT ≤ 50 ms): $0.218 – $0.469 per 1M output tokens**
   ($1.59 RunPod Secure SXM – $3.431 AWS p4de; $0.186 at Hyperstack's $1.36 reserved).
5. **Max throughput (S4): the same $0.218 – $0.469**, because decode saturates at the
   compute ceiling (2,030 tok/s/GPU at MFU 0.35) before capacity or the SLO binds.
   **Confidence: `estimate`** — roofline only, validated against one third-party Ampere
   (sm_86) measurement of this exact model to within 1 %.

([gpus/a100.md §4](../../gpus/a100.md)). There is no NVLink domain larger than one baseboard,

### 1.2 What cannot be sharded

```
Tensors that do NOT shard under TP (replicated on every rank), BF16 bytes:
  LM + GDN + QK norms, A_log, dt_bias : 679,424 params = 1.30 MiB
  MTP norms                           : 25,600 params = 0.05 MiB
  vision tower under --mm-encoder-tp-mode data (replicated, DP): 460,730,096 params = 0.921 GB per GPU
  KV heads: n_kv_heads = 4, so TP>4 duplicates them (TP8 -> 2x, TP16 -> 4x KV bytes/token/GPU)
  GDN value heads 48, key heads 16 -> TP in {1,2,4,8,16} divides both; the recurrent state shards with the 48 value heads
  DCP ceiling for this model: TP // n_kv_heads = TP // 4
```

Explicitly:

- **`num_key_value_heads = 4` is the hard sharding limit.** Past TP4 both engines replicate KV
  heads rather than split a head, so **KV bytes per token per GPU stop falling at TP4** and
  total KV memory doubles at TP8, quadruples at TP16. Table 1's "KV-head dup" column is that
  factor and Table 2 applies it. Decode context parallelism is capped at `TP // n_kv_heads`
  = `TP // 4` for the same reason
  ([serving-optimizations.md §7.3](../../cross-cutting/serving-optimizations.md),
  [vLLM DCP post](https://vllm.ai/blog/2026-08-07-decode-context-parallelism)).
- **All per-layer norms, `q_norm`/`k_norm` `[256]`, `linear_attn.norm` `[128]`, `A_log` `[48]`,
  `dt_bias` `[48]`, and the five MTP norms are replicated on every rank** — 1.35 MiB total,
  negligible but non-zero.
- **The vision tower (460.73 M params, 0.921 GB BF16) is replicated** whenever you follow the
  cross-model recommendation `--mm-encoder-tp-mode data`
  ([serving-optimizations.md §6.2](../../cross-cutting/serving-optimizations.md)). Text-only
  serving should pass `--language-model-only` instead and hand that 0.921 GB to KV — measured
  at **+49 % KV pool** on a 1×RTX 5090 at 32 K
  ([vLLM recipe](https://recipes.vllm.ai/Qwen/Qwen3.8-27B)). The two flags are mutually
  exclusive.
- **`embed_tokens` and `lm_head` (1.271 B params each) shard fine** as vocab-parallel columns
  (248,320 / TP), but note they are BF16 in *every* published quantisation
  ([architecture.md §3.2](./architecture.md)), so the 2.54 GB BF16 floor is real at TP1.
- **The GDN recurrent state shards with the 48 value heads**, so `S × 78.45 MB` per request
  divides by TP. The conv state (10,240 channels = 16·128 q + 16·128 k + 48·128 v) shards the
  same way.

Readings that matter:

- **1 M context is out of reach at BF16 weights on one A100** (0 concurrent sequences at any
  KV or state dtype) and needs INT4 + FP8 KV to reach exactly **1**. The YaRN-to-1M mode of
  [architecture.md §8.5](./architecture.md) is a TP4-or-more proposition on this card.
- **BF16 weights on one A100 are a trap**: 12.44 GB of budget buys 18 concurrent 8 K sequences
  at the friendliest settings and 9 at the config-default fp32 state. That is the single
  strongest argument for INT4 here, and it is a *capacity* argument, not a speed one.
- **The `S` multiplier roughly doubles concurrency when you drop it**, exactly as
  [architecture.md §5.4](./architecture.md) predicts: INT4/FP8-KV/bf16-state at 8 K goes
  73 → 139 between `S` = 5 and `S` = 1. That trade costs every prefix re-prefill, and on this
  architecture a re-prefill also re-runs the 48 recurrent layers over the whole prefix.
- **fp32 → bf16 recurrent state is worth ~1.6× concurrency at 4–8 K** (INT4/FP8-KV/8K/`S`=5:
  46 → 73) and nothing at 128 K. On Blackwell that same switch also unlocks the FlashInfer GDN
  prefill fast path; **on A100 it does not** — that gate is SM100/SM103 only
  ([flash-attention.md §14.3](../../cross-cutting/flash-attention.md)), so here bf16 state is
  purely a memory-vs-accuracy decision.
- **Multi-node fabric needed? No.** Never, for this model, on this GPU.

**The three things this table says.**

1. **A100 decode saturates at ~2,030 tok/s/GPU and no quantisation moves that number.**
   The bandwidth branch stops being the binding one at bs ≈ 64; past that, `decode_step_time`
   is `2 × 26.896e9 × batch / (312e12 × MFU)` and INT4-Marlin, FP8-Marlin and BF16 all execute
   FP16 MMA. This is the A100-specific result: on H200/B200 the format choice buys math, here
   it buys only capacity. INT4 still matters enormously — it is what gets you *to* the ceiling
   (BF16 tops out at 527 tok/s/GPU because it runs out of KV at bs=23).
2. **TTFT, not TPOT, is the weakness.** 1.6 s to first token on a 4 K prompt at TP1, 86 s at
   128 K, 245 s at 262 K. TP4 divides that by 3.7 and TP8 by 7.3, and a 90 % prefix-cache hit
   divides it by 9.8. **Long-context serving on this pair is a prefix-caching strategy, not a
   hardware strategy** — exactly the conclusion [gpus/a100.md §9](../../gpus/a100.md) reaches
   for its 70 B example. Note the model's saving grace: only 16 of 64 layers do quadratic
   attention, so the attention share is still only 42 % at 128 K where an all-attention model
   of the same width would be ~74 %.
3. **TP does not buy throughput, it buys latency and capacity.** Per-GPU decode throughput is
   flat-to-declining from TP1 to TP8 (2,030 → 1,845) because the compute ceiling is per-GPU
   and collectives only add. For throughput, run **8 independent TP1 replicas**; for TTFT or
   for 128 K+ contexts, use TP4.

### 3.4 Estimated vs measured — closing the gap

```
SANITY CHECK vs the one published Ampere measurement (RTX 3090, sm_86, 936 GB/s,
  ~20 GB requantised Qwen3.8-27B, vLLM 0.28.0, spec on, 7 drafts / 15 verified):
  roofline bs=1 4K ctx:  32.1 tok/s autoregressive; x accept 4.0 =   128 tok/s
  measured: 127 tok/s single-stream  ->  roofline x 4.0 reproduces it to 0.9 %
  roofline bs=64 (128 in/512 out):    868 tok/s; measured ~1,035 -> roofline is 1.19x conservative
```

This is the most useful thing in the document. Two independent checks on the same third-party
data point:

- **At batch 1**, the roofline predicts 32.1 tok/s of autoregressive decode on a 3090.
  The reported 127 tok/s is **4.0× that** — and the reported configuration is speculative
  decoding with 7 drafts proposed and 15 tokens verified per step, i.e. an effective accept
  length of about 4, which is exactly the 4.28 mean that inco.ai measures for this model's MTP
  head ([architecture.md §7.2](./architecture.md)). The roofline and the measurement agree to
  **0.9 %** once speculation is accounted for.
- **At batch 64**, where speculation has mostly stopped paying, the roofline predicts 868 tok/s
  and the measurement is ~1,035 — the real machine is **1.19× better** than the model,
  implying MBU nearer 0.83 or MFU nearer 0.42 than the planning defaults.

**Consequence for this document: do not apply the ~30 % derate that
[architecture.md §10.2](./architecture.md) recommends on the basis of its RTX 5090 check.**
That derate exists because the 5090 comparison mixed a speculative measurement against a
non-speculative estimate. Corrected for speculation, the roofline here is *conservative* on
Ampere at batch, and exact at batch 1. The remaining honest uncertainty is in MFU on the
compute branch — the ±0.05 band around 0.35 moves the ceiling from 1,740 to 2,320 tok/s/GPU,
about ±14 %.

Two gaps the roofline cannot model, both of which are **risks, not conservatism**:

- **The long-context decode cliff.** llama.cpp measures a 24× decode collapse on this exact
  model past ~80 K KV positions on CUDA. If an analogous threshold exists in the vLLM sm_80
  path, the S3 (128 K) rows above are optimistic by more than an order of magnitude.
  ⚠️ TO BE VERIFIED before committing any long-context capacity.
- **Triton GDN prefill on sm_80 is unmeasured.** The 0.45 GEMM MFU assumes the 48 linear layers
  prefill at roughly GEMM efficiency. They are Triton kernels with no sm_80 tuning and no
  published number anywhere.

```
high $3.431 AWS p4de             3.431        0.469        0.469     0.373     0.0373     0.271
res1y $1.36 Hyperstack res.      1.360        0.186        0.186     0.148     0.0148     0.108
```

**S1 and S4 are the same operating point on this GPU.** Decode reaches the 2,030 tok/s/GPU
compute ceiling at bs ≈ 64, TPOT is still only 45.3 ms at the bs=92 capacity limit, and
throughput does not improve past the ceiling — so the SLO never binds before capacity, and
capacity never buys more tokens. Dropping the SLO (S4) gains nothing. This is unusual: on
every Blackwell part in [architecture.md §11.3](./architecture.md) the max-throughput point is
a materially larger batch than the interactive one.

Blended per METHODOLOGY §6, verbatim: **75 % input (50 % of it cached at ~10 % of uncached
cost) / 25 % output, at the S1 operating point** →
**$0.126 / 1M blended at $1.59, $0.271 at $3.431, $0.108 at $1.36 reserved.**

### 4.3 What speculation and prefix caching do to the bill

```

  accept 2.5  vcr 0.0 :  2.50x -> S1 tok/s/GPU   5075, $/1M out (low) $ 0.087
  accept 2.5  vcr 0.25:  1.43x -> S1 tok/s/GPU   2900, $/1M out (low) $ 0.152
  accept 2.5  vcr 0.5 :  1.00x -> S1 tok/s/GPU   2030, $/1M out (low) $ 0.218
  accept 3.0  vcr 0.0 :  3.00x -> S1 tok/s/GPU   6090, $/1M out (low) $ 0.073
  accept 3.0  vcr 0.25:  1.71x -> S1 tok/s/GPU   3480, $/1M out (low) $ 0.127
  accept 3.0  vcr 0.5 :  1.20x -> S1 tok/s/GPU   2436, $/1M out (low) $ 0.181
  accept 4.28 vcr 0.0 :  4.28x -> S1 tok/s/GPU   8689, $/1M out (low) $ 0.051
  accept 4.28 vcr 0.25:  2.45x -> S1 tok/s/GPU   4965, $/1M out (low) $ 0.089
  accept 4.28 vcr 0.5 :  1.71x -> S1 tok/s/GPU   3475, $/1M out (low) $ 0.127

Effect of prefix caching on the input side (S1, low tier):
  hit 0%: TTFT   1605 ms, effective prefill   2,553 tok/s, $/1M prompt tokens $ 0.173
  hit 50%: TTFT    811 ms, effective prefill   2,525 tok/s, $/1M prompt tokens $ 0.087
  hit 90%: TTFT    164 ms, effective prefill   2,503 tok/s, $/1M prompt tokens $ 0.018
```

**Speculation is the biggest single lever and the least trustworthy one on this GPU.**
The acceptance figures are real and published for *this model* — mean accept length 4.28 for
MTP across five benchmarks ([inco.ai](https://inco.ai/blog/dflash2/)), 0.754–0.897 per-token
acceptance from vLLM's own `spec_decode_num_{accepted,draft}_tokens_total` counters — but **none
of them was measured on an A100**, and the only sm_80 report that exists is an *open
speculation fault* ([src](https://github.com/syv-ai/qwen38-27b-rtx3090)). The `vcr` column is
the marginal cost of a verify token relative to a real decode token
([serving-optimizations.md §2.5](../../cross-cutting/serving-optimizations.md)); at the S1 point
A100 is already **compute-bound**, which is precisely the regime where `vcr → 1` and
speculation stops paying. Realistic planning range: **$0.09 – $0.22 / 1M output** at the low
tier, i.e. somewhere between "2× cheaper" and "no change". These are *modelled* multipliers on
a published acceptance length, not measurements — ⚠️.

**Prefix caching pays on the input side and is nearly free to model.** A 90 % hit takes the
cost of a prompt token from $0.173 to $0.018 per 1M — **10.4 % of uncached**, which independently
reproduces METHODOLOGY §6's "assume 10 %" rule from the FLOP arithmetic, and matches Qwen
Cloud's own explicit-cache read price of exactly 10 % of input ([architecture.md §11.1](./architecture.md)).
It also takes TTFT from 1,605 ms to 164 ms, which on this card is the difference between usable
and not. The A100-specific caveat is the downside case: vLLM measured **−36.7 % throughput on
an A100** with zero prefix overlap ([src](https://blog.squeezebits.com/vllm-vs-tensorrtllm-12-automatic-prefix-caching-38189)),
so this is a workload decision, not a default.

### 4.4 Versus the vendor API

```
Qwen Cloud list on the same blend: $0.956/1M   (OpenRouter fp8 market $0.659/1M)
Break-even utilisation u* = self-hosted blended / API blended:
  low $1.59 RunPod Secure SXM  vs Qwen Cloud  13.2 %   vs OpenRouter fp8  19.1 %
  high $3.431 AWS p4de         vs Qwen Cloud  28.4 %   vs OpenRouter fp8  41.2 %
  res1y $1.36 Hyperstack res.  vs Qwen Cloud  11.2 %   vs OpenRouter fp8  16.3 %
Output-token gross margin vs Qwen Cloud $3.00: 6.4x (hyperscaler) to 16.1x (reserved)
```

Qwen Cloud list is **$0.50 in / $3.00 out / $0.05 explicit-cache read** per 1M
([architecture.md §11.1](./architecture.md)); the real market for FP8-served third parties is
$0.20–0.30 in / $2.20–2.55 out ([architecture.md §11.2](./architecture.md)).

- **Output tokens: self-hosting wins by 6.4× to 16.1×** against Qwen's list price. Even the
  cheapest OpenRouter provider (Darkbloom, fp4, $1.80/1M out) is 3.8× the A100's $0.469
  hyperscaler cost.
- **Input tokens are close.** $0.173–$0.373 self-hosted at 0 % cache hit against $0.20–0.50 API
  — the API is roughly fairly priced on input, and A100's weak prefill is exactly why. Add a
  90 % cache hit and self-hosting pulls ahead again ($0.018).
- **Break-even utilisation is 11–28 % against Qwen Cloud and 16–41 % against the market.**
  In plain terms: a reserved A100 that is busy more than ~1 hour in 9 beats Qwen's list price
  on a 75/25 blend; a rented hyperscaler A100 needs to be busy more than ~2 hours in 7. Those
  are low bars, and they hold even before speculation. **But** they assume the pair works,
  which §0 says nobody has demonstrated, and they exclude the engineering cost of being the
  first person to run this combination.

## 5. Scaling and deployment shape

**Single node, and usually a single GPU.** The recommended shape is **8 independent TP1
replicas on one HGX A100 8-GPU baseboard** behind a router: the model fits one GPU at every
precision, per-GPU decode throughput *falls* from TP1 to TP8 (§3.2 Table 3d), and every
collective is pure overhead against a dense 27 B. Use TP only to buy something TP actually
gives you:

| Use | Shape | Why |
|---|---|---|
| Throughput-oriented API | **TP1 × DP8** | 8 × 2,030 = **16,240 tok/s/node** est., no collectives, no KV-head duplication |
| TTFT-sensitive, ≤ 32 K prompts | **TP2** or **TP4** | TTFT at 8 K: 3,280 → 1,722 → 885 ms; KV heads still shard exactly at TP4 |
| 128 K–1 M context | **TP4** | The only shape that holds a useful number of long sequences (53 at 128 K, 7 at 1 M, INT4 + FP8 KV + bf16 state, `S`=5) and the only one with tolerable prefill |
| Anything | **not TP8, not TP16, not multi-node** | TP8 duplicates the 4 KV heads; 16 GPUs means 200 Gb/s InfiniBand at 24× less bandwidth than NVLink |

**Neither PD disaggregation nor wide-EP ever pays for this pair.** There are no experts (the
model is dense), vLLM's `compatible_strategies` for it is `["single_node_tp"]` only, no Dynamo
recipe exists, disaggregation is measured at **−20–30 % on small or untuned deployments**
([src](https://towardsdatascience.com/disaggregation-is-a-thousand-gpu-problem/)), and it is
an open question whether the GDN recurrent state survives a NIXL handover at all. The one
disaggregation idea with a real case here is **E/PD for multimodal traffic** — the ViT is
O(N²) and can cost 6+ seconds per max-resolution image on this card — but no A100 recipe for it
exists. ⚠️

### 5.1 Launch commands

There is **no published A100 command for this model**. The two below are the published
commands closest in kind, adapted for sm_80; the adaptations are marked and unverified.

vLLM — nearest published form is the RTX PRO 6000 TP1 recipe
[src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/rtx_pro_6000.json), quoted verbatim:

```bash
VLLM_USE_RUST_FRONTEND=1 vllm serve Qwen/Qwen3.8-27B \
  --max-num-seqs 8 --tensor-parallel-size 1 \
  --enable-auto-tool-choice --tool-call-parser qwen3_xml \
  --reasoning-parser qwen3 --mm-encoder-tp-mode data
# + optional: --speculative-config '{"method":"mtp","num_speculative_tokens":5}'
```

Adapted for A100 (⚠️ **unverified, no vendor publishes this**):

```bash
vllm serve RedHatAI/Qwen3.8-27B-INT4 \
  --tensor-parallel-size 1 \
  --max-model-len 262144 \
  --kv-cache-dtype fp8 \
  --mamba-ssm-cache-dtype bfloat16 \
  --max-num-batched-tokens 2048 \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice --tool-call-parser qwen3_xml \
  --language-model-only                      # drop for image/video traffic; then use --mm-encoder-tp-mode data
```

Changes from the published recipe and why: `RedHatAI/Qwen3.8-27B-INT4` because Marlin W4A16 is
the only 4-bit path on sm_80 and BF16 leaves 12.4 GB of budget (§1.3); `--kv-cache-dtype fp8`
because it is the highest-leverage A100 flag ([gpus/a100.md §6](../../gpus/a100.md)) —
storage-only here, no FP8 attention math; `--mamba-ssm-cache-dtype bfloat16` for the 1.6×
concurrency of §1.3, noting it is an accuracy gate and buys no kernel on sm_80; chunked prefill
pinned small because a 4 K prefill is 1.6 s and will stall decode. `--reasoning-parser qwen3` is
effectively mandatory — *"the chat template opens every assistant turn with `<think>`, so
without it the entire reasoning block lands in `message.content`"*
[src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B). ⚠️ Tool-call parser: vLLM pins `qwen3_xml`,
SGLang pins `qwen3_coder`, for the same chat template ([architecture.md §1.4](./architecture.md)).

SGLang — the H200 cell, quoted verbatim from the cookbook's `cells` table
[src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md):

```
--trust-remote-code --model-path {{MODEL_NAME}} --kv-cache-dtype fp8_e4m3
--mem-fraction-static 0.85 --attention-backend flashinfer
--chunked-prefill-size 32768 --max-prefill-tokens 32768
--reasoning-parser qwen3 --tool-call-parser qwen3_coder --host {{HOST_IP}} --port {{PORT}}
```

For A100, drop `--chunked-prefill-size` to 2048 (the SM120 guidance, because A100 prefill is
slow like SM120's, not fast like SM90's — *"decode steps stall behind each prefill chunk on
hybrid GDN models"*), add `--linear-attn-backend triton` explicitly, and consider
`--mamba-radix-cache-strategy no_buffer` (`S` = 3) or `--disable-radix-cache` (`S` = 1) to buy
back the concurrency in §1.3. **⚠️ SGLang does not list A100 in this model's
`supportedHardware`, and [sglang#11421](https://github.com/sgl-project/sglang/issues/11421)
reports a published `sgl_kernel` wheel shipping only SM90/SM100 binaries — verify an sm_80
cubin exists before rollout.**

### 5.2 Warm-up and loading

```
TABLE 5 — cold start from NVMe (weights only; add ~1-2 min CUDA graph capture + warm-up)
  BF16          55.56 GB :   2.8 s @ 20 GB/s ...  11.1 s @ 5 GB/s
  FP8 W8A16     30.87 GB :   1.5 s @ 20 GB/s ...   6.2 s @ 5 GB/s
  NVFP4 W4A16   21.92 GB :   1.1 s @ 20 GB/s ...   4.4 s @ 5 GB/s
  INT4 W4A16    19.45 GB :   1.0 s @ 20 GB/s ...   3.9 s @ 5 GB/s
```

**Do not plan against those numbers.** They are the NVMe-bandwidth floor. The measured reality
for this checkpoint is far worse: SGLang reports the BF16 build takes **~6.5 minutes to load
its 18 shards from NVMe** on a DGX Spark and advises budgeting **~10 minutes to READY** before
calling a boot hung ([architecture.md §1.1](./architecture.md), citing the
[SGLang cookbook](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md)). The gap
is safetensors deserialisation, dtype conversion and shard-by-shard host→device copy, not disk.
On A100 add the Marlin repack of the INT4 weights at load and the CUDA-graph capture pass.
**Budget 10 minutes to first token on a cold replica; scale replicas ahead of demand, not
reactively.**

## 6. Risks and open questions

Everything below is ⚠️ **TO BE VERIFIED** unless marked otherwise.

**Blocking / would invalidate the verdict**

1. **Nobody has run this pair.** No vLLM A100 profile (404), no SGLang A100 cell, no MLPerf
   row, no InferenceX row, no blog. Every number in §1 and §3 is derivation. The first
   experiment is `vllm serve RedHatAI/Qwen3.8-27B-INT4` on one A100 and `vllm bench serve
   --dataset-name random --random-input-len 4096 --random-output-len 512` at c ∈ {1,8,32,64,92}.
2. **The sm_80 speculation fault.** *"Two owners are mid-bisect on a speculation fault that only
   their cards produce"* for exactly this model
   ([src](https://github.com/syv-ai/qwen38-27b-rtx3090)). Speculation is the largest cost lever
   in §4.3 (up to 2.5× at the S1 point) and it is the one thing reported broken on A100.
3. **The long-context decode cliff.** 35.6 → 1.4 tok/s past ~80 K KV positions on this exact
   model, measured in llama.cpp on CUDA
   ([llama.cpp#27623](https://github.com/ggml-org/llama.cpp/issues/27623), open). If an
   analogous threshold exists in the vLLM sm_80 decode path, every S3 row in §3.2 is wrong by
   an order of magnitude. Settle it by sweeping decode rate against KV position past 80 K.
4. **FP8 checkpoint kernel selection on SM80.** [vllm#55008](https://github.com/vllm-project/vllm/issues/55008)
   (open, 2026-09-02): CUTLASS FP8 is selected on Ampere and asserts at profile-run; the
   correct path is `MarlinFP8ScaledMMLinearKernel`. Until that is gated to SM89+, treat
   `Qwen/Qwen3.8-27B-FP8` on A100 as **likely to fail at boot**, not merely slow. This is why
   INT4 and not FP8 is the recommendation, despite FP8 being the better-supported checkpoint
   everywhere else.

**Documentation conflicts inside this repo that affect the numbers**

5. **The 80 GB vs 80 GiB basis** — **RESOLVED 2026-09-19 to 80 GB decimal** tree-wide
   ([METHODOLOGY §8](../../METHODOLOGY.md#gpus), [gpus/a100.md §2](../../gpus/a100.md)); the
   `nvidia-smi` 80 GiB reading is a labelled ⚠️ +7.4 % sensitivity, not a live conflict. This
   document already planned on the decimal basis, so nothing here moved.
6. **Does FP8 KV work on A100 at all?** Four repo documents disagree:
   [gpus/a100.md §5/§6](../../gpus/a100.md) says yes, storage-only, *"the single
   highest-leverage A100 flag"*;
   [quantization-formats.md §8.1](../../cross-cutting/quantization-formats.md) says "✅ store";
   [flash-attention.md §9.1](../../cross-cutting/flash-attention.md) says ✅ via
   TRITON_ATTN/FlashInfer but **❌ via FlashAttention**;
   [inference-engines.md §4](../../cross-cutting/inference-engines.md) says plainly **"no"**;
   and [architecture.md §8.4](./architecture.md) says *"on A100 the KV pool would be BF16,
   doubling §5.3"*. This document plans **FP8 KV = yes, storage-only**, following the GPU doc
   and the quantisation doc, and flags that if the FA2-backend cell is right you must pin
   `--attention-backend triton` or `flashinfer` to get it — which costs FA2's 230 TFLOPS on
   the 16 full-attention layers. **If FP8 KV turns out to be unavailable, halve every
   FP8-KV column in §1.3 and use the BF16-KV column instead: the INT4/8K/`S`=5 figure drops
   from 73 to 52 and the S1 operating point from bs=92 to bs=73.**
7. **`S` for vLLM is unpublished.** SGLang documents 5/4/3/1 by strategy; vLLM exposes no slot
   count ([architecture.md §12](./architecture.md), open question 19). Since vLLM is the only
   plausible engine here, every fit cell in §1.3 is engine-specific until someone reads the
   mamba-cache allocation out of a vLLM boot log and divides by 78.45 MB.

**Accuracy of the executed precision**

8. **INT4 W4A16 recovery is published and good — but not for this quantiser on this card.**
   RedHatAI's INT4 build recovers 98.5–101.1 % across IFEval / MMLU-Pro / GSM8K-Platinum /
   MATH-500 / GPQA-Diamond / AIME-2025
   ([src](https://huggingface.co/RedHatAI/Qwen3.8-27B-INT4/raw/main/README.md)); AMD's Quark
   AWQ build recovers 97.7–100.9 % on GSM8K with Wikitext perplexity 8.83 vs 8.44
   ([src](https://huggingface.co/amd/Qwen3.8-27B-Quark-AWQ-INT4-W4A16)). Both were evaluated on
   non-Ampere hardware; Marlin is numerically deterministic given the same weights, so the
   recovery should transfer, but nobody has re-scored GSM8K on an A100. Budget one 1,319-question
   GSM8K run to confirm.
9. **bf16 recurrent state is an accuracy gate, not a free win.** SGLang treats it as such and
   says *"measure both for your quantization"*; vLLM logs a state-drift warning when an explicit
   non-fp32 `--mamba-ssm-dtype` is combined with `--enable-linear-replayssm-spec`
   ([architecture.md §8.6](./architecture.md)). On A100 it unlocks no kernel — only memory — so
   the case for it is weaker here than on Blackwell. If §1.3's fp32 column is good enough for
   your concurrency target, stay on fp32.
10. **FP8 KV accuracy.** GQA with only 4 KV heads has little redundancy; vLLM's own measurement
    is *"at most 1–2 points"* degradation on reasoning tasks for Qwen models
    ([src](https://vllm-project.github.io/2026/04/22/fp8-kvcache.html)). Calibrate scales with
    llm-compressor; the default (all scales = 1.0) is the accuracy-risky option, and per-head
    scales are unavailable without FA3.

**Performance unknowns in the model**

11. **Triton GDN prefill on sm_80 has no published throughput.** 48 of 64 layers run it. The
    0.45 GEMM MFU in §3.1 assumes they behave like GEMMs. If they do not, §3's TTFT column and
    the S2/S3 rows move.
12. **Decode MFU on the compute branch.** The 2,030 tok/s/GPU ceiling is the single most
    load-bearing derived number in this document and rests on MFU 0.35 for a skinny decode
    GEMM. The band 0.30–0.50 spans 1,740–2,900.
13. **INT8 W8A8 is the unexplored upside.** It is the only format that raises A100's *compute*
    ceiling (624 TOPS vs 312 TFLOPS), which is exactly the wall §3 identifies. No first-party
    W8A8 build of this model exists, SmoothQuant on GDN projections is unevaluated, and the
    only Ampere speedup figure anywhere is an unverified secondary "1.3–1.7×". If someone wants
    one experiment that could move this pair's cost materially, it is this one, not speculation.
14. **Marlin tuning is measured on sm_86, not sm_80** ([src](https://github.com/syv-ai/qwen38-27b-rtx3090)),
    and A100 in a dense chassis at sustained load drops below boost clock — Marlin's own study
    found clock reduction *"has no effect on Marlin's virtually optimal performance"* while
    harming prior kernels ([src](https://github.com/IST-DASLab/marlin)), which is reassuring but
    was not measured on GA100.
15. **Power SKU.** MLPerf v3.1 shows a 500 W HGX A100-80GB **CTS** part beating a 400 W part by
    **1.56×** on the identical benchmark ([gpus/a100.md §10/§11](../../gpus/a100.md)). When
    renting you usually cannot tell which you got. Run `nvidia-smi -q -d POWER` and record the
    enforced limit next to every number.
16. **A100 rental supply is thinning.** Vast.ai showed **zero** A100 SXM4 and zero A100 PCIe
    offers on 2026-09-19 ([gpus/a100.md §8/§11](../../gpus/a100.md)). The low price tier is
    real today and may not be in a year; price a migration path to H200 (which *is* a verified
    SGLang cell for this model) into any A100 plan.
17. **Multimodal at high resolution is untested and expensive.** No window attention in the ViT:
    590 TFLOP for one 16.78 Mpx image, 91 % quadratic ([architecture.md §6.4](./architecture.md))
    ≈ 6.3 s on this card at MFU 0.30. Whether the engines chunk the ViT score matrix at all is
    an open question in the architecture doc; an unchunked 65,536-patch matrix would be 8.6 GB.
18. **The `--enable-linear-replayssm-spec` / ReplaySSM path** directly attacks the state
    read/write traffic that is 24 % of a decode step at bs=128/8 K, and nobody has measured it
    on any GPU for this model, let alone A100.
