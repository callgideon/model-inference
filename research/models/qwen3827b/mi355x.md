## 0. Verdict

1. **Runnable today, on vLLM.** vLLM publishes a generated MI355X launch command for this
   exact model (`hw/mi355x.json`, TP1, `vllm/vllm-openai-rocm:latest`) and lists `mi355x` in
   the FP8 variant's `supported_hardware`; **`mi355x` is *not* in the recipe's `meta.hardware`
   verified list and SGLang's cookbook has no AMD cell for it at all** (`supportedHardware:
   ["h200","rtx6000","rtx5090","dgx-spark","gb300"]`) — supported, unverified
   [src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/mi355x.json)
   [src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md).
2. **1 GPU minimum and 1 GPU recommended, TP1, scale by replicas (DP×8 per node).** TP exists
   only to enlarge the KV pool, and TP8 is actively counter-productive for KV (4 GQA KV heads
   → each head duplicated on 2 ranks, §1).
3. **The weight format actually executed is MXFP4** — and this document corrects
   [architecture.md §9.2](./architecture.md) / its open question 14: **an AMD first-party MXFP4
   checkpoint for this model does exist**, `amd/Qwen3.8-27B-Quark-AWQ-MXFP4`, 19.798 GB,
   W4A4 g32 E8M0, GSM8K recovery 101.8 % thinking / 99.2 % non-thinking
   [src](https://huggingface.co/amd/Qwen3.8-27B-Quark-AWQ-MXFP4). That is the native
   10.1 PFLOPS dense path on gfx950. FP8 (5.0 PF) is the conservative fallback;
   NVFP4 and INT4-W4A16 are both *worse* than either here (§2).
4. **Interactive (S1, TPOT ≤ 50 ms): $0.211 per 1M output tokens** at the only published
   MI355X rate, which is both the `low` and the `high` tier ($8.60/GPU-hr, OCI
   `BM.GPU.MI355X.8`). **Max throughput (S4): $0.195 per 1M output tokens.** Blended
   (75 % in / 50 % of that cached / 25 % out) **$0.080 per 1M tokens**. Against Qwen Cloud's
   $3.00 output list price, break-even utilisation is **7.0 %**.
5. **Confidence: `estimate`.** No one has published a throughput number for *this* checkpoint
   on *this* GPU. But AMD has published a full measured run of **Qwen3.5-27B on one MI355X**
   (TP1, vLLM-ROCm, ROCm 7.2.3), and that model is **bit-for-bit the same shape** — identical
   `config.json` geometry and identical 27,781,427,952-parameter total (§3.2). The roofline
   below reproduces that measurement to within ~10 %.

### 1.1 The MXFP4 checkpoint, reconciled byte-for-byte

Read directly from the safetensors header of
`amd/Qwen3.8-27B-Quark-AWQ-MXFP4/model.safetensors` over an HTTP range request (1,695
tensors), then re-derived from `config.json` with `python3`:

```
dtype census   : BF16 3,430,871,792 elems (6,861,743,584 B) + U8 12,936,232,960 B
payload total  : 19,797,976,544 B = 19.798 GB = 18.44 GiB   (repo total 19.821 GB)

MXFP4-quantised tensor set (METHODOLOGY §1: 0.53125 B/param = 0.5 + one E8M0 per 32):
  MLP,  64 layers           17,112,760,320 params -> 9,091,153,920 B   (header: 9,091,153,920) ✅
  GDN projections, 48 layers 5,560,074,240 params -> 2,953,914,240 B   (+ bf16 conv/A_log/dt_bias/norm)
  Full-attn q/k/v/o, 16 lyr  1,677,721,600 params ->   891,290,000 B
  quantised subtotal        24,350,556,160 params
BF16 remainder            =  27,781,427,952 - 24,350,556,160 = 3,430,871,792  ✅ exactly the header's BF16 count
  of which: embed_tokens 2.543 GB · lm_head 2.543 GB · MTP head 0.849 GB · vision tower 0.921 GB · norms 0.001 GB
total = 24,350,556,160 × 0.53125 + 3,430,871,792 × 2 = 12,936,232,960 + 6,861,743,584
      = 19,797,976,544 B  ✅ delta 0 against the file
file  = 8 (length prefix) + 219,632 (header JSON) + 19,797,976,544 = 19,798,196,184 B ✅ exact
```

**One apparent discrepancy, resolved.** The HF API's safetensors census reports
`U8: 12,175,278,080`, not the 12,936,232,960 U8 bytes the header actually holds. The gap is
**760,954,880 B**, and it is exactly `24,350,556,160 ÷ 32` — the E8M0 scale bytes. The API
counts only the packed `*.weight` tensors (`N ÷ 2`) and omits every `*.weight_scale`. Both
numbers are right; `12,175,278,080 + 760,954,880 = 12,936,232,960`. Quote the header, not the
API summary.

The packing is visible in the shapes: `mlp.gate_proj.weight U8 [17408, 2560]` (5120 ÷ 2, two
E2M1 per byte) with `weight_scale U8 [17408, 160]` (5120 ÷ 32, one E8M0 per 32) — MXFP4 g32,
exactly METHODOLOGY §1's row. Note what stays BF16 and therefore never reaches the 10.1 PF
path: **`lm_head` (1.271 B params), the entire MTP head, and the whole vision tower.** The
NVFP4 exports pack `lm_head` into FP4 and drop the MTP head to BF16; AMD's MXFP4 export does
the opposite. That is why 19.798 GB > the "MXFP4 est. 21.349 GB" row in
[architecture.md §4](./architecture.md) is *wrong in the other direction*: architecture.md
estimated MXFP4 by re-quantising the **NVFP4 layer map** (which includes `lm_head`), AMD's real
build quantises a **different, larger** set (all attention + all GDN projections, but not
`lm_head`), and lands 1.55 GB lower. Use **19.798 GB**, the measured file.

### 1.2 Fit over the GPU counts this topology allows

MI355X's scale-up domain is a **fully-meshed 8-GPU UBB 2.0 baseboard, 8 GPUs maximum** —
there is no NVL72 equivalent until Helios/MI400
([gpus/mi355x.md §4](../../gpus/mi355x.md)). So the allowed set is {1, 2, 4, 8} on one node,
and {16, 32, …} only as multiple nodes over 8 × 400G RoCE v2 / InfiniBand. The GB300-only
18/36/72 rows do not exist here.

Script: `fit.py`. Cells read **`S = 5` / `S = 1`**; FP8 KV, bf16 GDN state.

```
## 1. Fit — MXFP4 (AMD Quark AWQ), FP8 KV, bf16 GDN state, S=5 / S=1

| GPUs | parallelism | weights/GPU GB | KV+state budget/GPU GB | 8K | 32K | 128K | 1024K | multi-node? |
|---|---|---|---|---|---|---|---|---|
| 1 | TP1 (1 replica) | 19.80 | 235.4 | 356 / 678 | 160 / 204 | 50 / 53 | 6 / 6 | no |
| 2 | TP2 | 10.36 | 244.8 | 741 / 1411 | 334 / 424 | 104 / 111 | 14 / 14 | no |
| 4 | TP4 | 5.64 | 249.6 | 1510 / 2877 | 680 / 866 | 212 / 228 | 28 / 28 | no |
| 8 | TP8 | 3.28 | 251.9 | 2169 / 3275 | 793 / 905 | 224 / 232 | 29 / 29 | no |
| 16 | TP8 x 2 nodes | 3.28 | 251.9 | 4338 / 6550 | 1586 / 1810 | 448 / 464 | 58 / 58 | YES (400G RoCE/IB) |
| 32 | TP8 x 4 nodes | 3.28 | 251.9 | 8676 / 13100 | 3172 / 3620 | 896 / 928 | 116 / 116 | YES (400G RoCE/IB) |
```

Per-GPU weights charge the **replicated vision tower** (0.921 GB BF16 on *every* rank, because
the published command runs `--mm-encoder-tp-mode data`) plus replicated norms; the rest divides
by TP. The 1-GPU row's **356 / 678** at 8 K reconciles with
[architecture.md §10.2](./architecture.md)'s MI355X INT4 cell (**356 / 679**) — same
arithmetic, on a checkpoint 0.345 GB heavier, which moves the `S` = 1 cell by one sequence and
the `S` = 5 cell not at all. The FP8 row's **339** matches that table's MI355X FP8 cell exactly.

**Per weight format on one GPU** (S = 5):

```
| weight format | weights GB | budget GB | 8K fp8kv | 8K bf16kv | 32K fp8 | 128K fp8 | 262K fp8 | 1M fp8 |
|---|---|---|---|---|---|---|---|---|
| BF16 | 55.56 | 199.6 | 302 | 214 | 136 | 42 | 22 | 5 |
| FP8 | 30.87 | 224.3 | 339 | 241 | 153 | 47 | 24 | 6 |
| MXFP4 (AMD Quark AWQ) | 19.80 | 235.4 | 356 | 253 | 160 | 50 | 26 | 6 |
| INT4 W4A16 | 19.45 | 235.7 | 356 | 253 | 160 | 50 | 26 | 6 |
```

**Read the spread, not the rows.** 288 GB is so much capacity for a 27.78 B model that going
from BF16 to MXFP4 buys only **+18 % concurrency at 8 K** (302 → 356) and **+20 % at 1 M**
(5 → 6). On MI355X, quantisation is a *speed* decision, not a fit decision — the opposite of
every 80–96 GB card in [architecture.md §10.2](./architecture.md). This is the single most
important structural fact about this pair.

### 1.3 The `S` multiplier and the state dtype

```
### State dtype / S sensitivity, MXFP4 TP1, FP8 KV, 8K ctx

| state dtype | S=1 | S=3 | S=4 | S=5 |
|---|---|---|---|---|
| bf16 (78.45 MB/slot) | 678 | 467 | 404 | 356 |
| fp32 (153.94 MB/slot) | 557 | 322 | 266 | 226 |
```

At 8 K context the GDN state pool is still the dominant per-sequence term: fp32 state at
`S = 5` costs **3.0×** the concurrency of bf16 state at `S = 1`. `mamba_ssm_dtype` ships as
`float32` in `config.json`, so **`--mamba-ssm-dtype bfloat16` is the single highest-leverage
flag on this GPU** — and unlike SM100, where it also unlocks the FlashInfer GDN prefill fast
path ([architecture.md §8.4](./architecture.md)), on gfx950 it is **purely a memory and
accuracy trade**: both dtypes run the same AITER Triton GDN kernels
([flash-attention.md §14.3](../../cross-cutting/flash-attention.md)). SGLang calls bf16 state
"an accuracy gate" to validate per workload.

### 1.4 The AITER usable-memory correction — AMD-specific, and it moves every cell

SGLang's Qwen3.8 (2.4 T sibling, same hybrid-GDN family) page states:
*"With the aiter backend above 8192 context SGLang multiplies [`--mem-fraction-static`] by
**0.85** before allocating, so MI355X's `0.9` lands at ≈0.765"*
[src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8.md). If you serve this model
through SGLang-ROCm at long context, the effective usable fraction is 0.765, not 0.90:

```
### SGLang/AITER effective-usable correction (0.90 x 0.85 = 0.765), MXFP4 TP1, FP8 KV, S=5

| basis | usable GB | budget GB | 8K | 32K | 128K | 1M |
|---|---|---|---|---|---|---|
| METHODOLOGY 0.90 | 259.2 | 235.4 | 356 | 160 | 50 | 6 |
| SGLang+AITER >8K ctx 0.765 | 220.3 | 196.5 | 297 | 134 | 41 | 5 |
```

−17 % concurrency across the board. The vLLM path (`--gpu-memory-utilization 0.9`) has no such
multiplier documented, so the 0.90 row is the planning basis and the 0.765 row is the SGLang
haircut. ⚠️ **TO BE VERIFIED** that the multiplier also applies to a *dense* GDN model and to
the 27 B page (it is documented on the 2.4 T page only).

### 1.5 What cannot be sharded

| Tensor group | Shardable? | Consequence on MI355X |
|---|---|---|
| MLP `gate/up/down` (17.11 B) | ✅ column/row TP | clean at any TP |
| GDN `in_proj_*` / `out_proj` / `conv1d` / `A_log` / `dt_bias` (5.56 B) | ✅ by head — 48 V heads, 16 K heads | clean to TP16; TP8 gives 6 V / 2 K heads per rank |
| Full-attention `q_proj`/`o_proj` (24 Q heads) | ✅ | 24 ÷ 8 = 3 heads/rank at TP8 |
| **Full-attention `k_proj`/`v_proj` — 4 KV heads** | ❌ **beyond TP4** | at TP8 each KV head is **duplicated on 2 ranks**; aggregate KV storage doubles |
| `embed_tokens` / `lm_head` (1.271 B each) | ✅ vocab-parallel (248,320 rows) | — |
| All RMSNorms, `q_norm`/`k_norm`, GDN `norm` (660,480 params) | ❌ **replicated** | 1.3 MB/rank — negligible |
| **Vision tower (460.73 M params, 0.921 GB BF16)** | ❌ **replicated under `--mm-encoder-tp-mode data`** | 0.921 GB on *every* rank; this is the published MI355X command's setting, and the right one ([serving-optimizations.md §6.2](../../cross-cutting/serving-optimizations.md)) |
| MTP head (0.425 B, BF16 in the MXFP4 build) | ✅ like a normal layer | `lm_head` is shared with the main model |

```
### KV-head replication penalty (4 KV heads)

| TP | replication | aggregate KV bytes/token FP8 | 8K max conc (MXFP4, S=5) |
|---|---|---|---|
| 1 | 1x | 32,768 | 356 |
| 2 | 1x | 32,768 | 741 |
| 4 | 1x | 32,768 | 1510 |
| 8 | 2x | 65,536 | 2169 |
```

**TP8 is the worst KV deal on the node**: 8 GPUs buy 2,169 concurrent 8 K sequences where 8
independent TP1 replicas buy 8 × 356 = **2,848**, and the replicas have no all-reduce in the
decode loop. TP4 is the only sharded shape that is KV-neutral. Unless a single request needs a
KV pool larger than one GPU can hold (which at 288 GB means > ~50 concurrent 128 K sequences,
or a single 1 M-token request plus friends), **TP1 × N replicas wins on every axis.**

## 3. Throughput and latency

### 3.1 Assumptions, stated per METHODOLOGY §4

```
bytes_per_decode_step(batch) = weights + batch × ctx × kv_bytes_per_token + batch × 2 × state_bytes
                                                                            ^ read + write, live slot only
decode_step_time ≈ max( bytes / (8.0e12 × MBU) , compute_time(batch) )
prefill_time(T)  ≈ 2 × active_params × T / (peak × MFU) + 16 × 2 × 24 × 256 × T² / (2500e12 × MFU_attn)
```

The `batch × 2 × state_bytes` term is [architecture.md §6.3](./architecture.md)'s correction to
METHODOLOGY §4 and it is **not** multiplied by `S`: only the live slot is read and written each
step; the other `S − 1` buffers are prefix checkpoints sitting idle in HBM. (`S` is a **memory**
multiplier in §1, not a **bandwidth** one here.)

| Parameter | Value used | Basis |
|---|---|---|
| **MBU** | **0.50** | METHODOLOGY §4 gives 0.4–0.6 for MI355X/ROCm. **Calibrated against a real measurement** — see §3.2, which implies 0.47–0.55 |
| MFU, MXFP4 prefill | 0.20 | METHODOLOGY's 0.2–0.35 FP4 band, at the bottom, per [gpus/mi355x.md §9](../../gpus/mi355x.md)'s *"plan at the bottom of each band until you have a measurement, because the FP4/FP6 rates are the newest kernels in the stack"* |
| MFU, FP8 prefill | 0.25 | bottom of METHODOLOGY's 0.25–0.4 |
| MFU, BF16 prefill and all attention FLOPs | 0.35 | bottom of METHODOLOGY's 0.35–0.5 |
| MXFP4 compute split | 24.351 B params at 10,100 TF; `lm_head` 1.271 B at 2,500 TF | §1.1 — `lm_head` is **not** quantised in AMD's build |
| Comm overhead | 0 (TP1) | recommended shape is TP1; add METHODOLOGY's 5–15 % for TP2–8 on the 1,075 GB/s mesh |
| ctx used | prompt + output (the peak) | conservative; the mean would be ~½ the output shorter |

**Back-solving MBU from the measurement.** The blog publishes no autoregressive absolute, but
it bounds it two ways: `396 ÷ 5.02 = 78.9 tok/s` is a **floor** on the bf16 bs=1 baseline (5.02×
is the stated *maximum* speedup, on MATH500), and scaling HumanEval's 396 tok/s by the
MATH500/HumanEval acceptance ratio gives `396 × 8.829/10.377 ÷ 5.02 = 67.1 tok/s` as the other
end. Inverting METHODOLOGY §4 on `weights 55.563 GB + 2 × 78.45 MB`:

```
67.1 tok/s -> 14.9 ms/step -> 3,729 GB/s effective -> MBU 0.47
78.9 tok/s -> 12.7 ms/step -> 4,397 GB/s effective -> MBU 0.55
```

**MBU 0.47–0.55 `est.`, squarely inside METHODOLOGY's 0.4–0.6 MI355X/ROCm band.** The roofline
below runs at **0.50** and predicts **72 tok/s** for bf16 bs=1 — 9 % *below* the implied
measurement. That is the opposite sign from
[architecture.md §10.2](./architecture.md)'s RTX 5090 check, where the same roofline
**over**-predicted by ~35 %. So: **do not apply architecture.md's blanket "derate ~30 %" to
this document.** On this GPU the model is calibrated, marginally conservative, and the residual
uncertainty is ±10 %, not −30 %.

```

| MXFP4 | 256 | 24.7 | 10,384 | 35,796 | grid max (METHODOLOGY 4) |

| BF16 | 367 | 42.1 | 8,709 | 16,026 | KV ceiling S=5 |

TPOT hits 50 ms at batch ~592 (50.5 ms); KV ceiling S=5 is 433, S=1 is 1025
```

**Capacity binds before latency does.** The interactive SLO (TPOT ≤ 50 ms) is satisfied
*everywhere* up to batch 592, but `S = 5` runs out of memory at 433. On a 288 GB card serving
a 27.78 B model, **S1 and S4 are almost the same operating point** — a situation that does not
arise on any 80–96 GB GPU in this repo. Dropping to `S = 1` with `--disable-radix-cache` lifts
the ceiling to 1,025 and lets S4 run past the SLO:

| point | config | batch | TPOT | tok/s/GPU |
|---|---|---:|---:|---:|
| **S1 interactive** (TPOT ≤ 50 ms, radix cache **on**, `S = 5`) | MXFP4 TP1 | **433** | **38.3 ms** | **11,312** |
| S1 at the METHODOLOGY §4 grid maximum | MXFP4 TP1 | 256 | 24.7 ms | 10,384 |
| **S4 max throughput** (no SLO, `--disable-radix-cache`, `S = 1`) | MXFP4 TP1 | **1,025** | **83.8 ms** | **12,225** |
| S4 intermediate | MXFP4 TP1 | 592 | 50.5 ms | 11,719 |

Note the flatness: 433 → 1,025 concurrency (2.4×) buys **+8 % throughput**, because decode
KV-read bytes scale with `batch × ctx` and the weight stream is already amortised. **Past ~400
concurrent 4 K sequences this GPU stops rewarding batch**, and the S4 config's loss of prefix
caching will cost more in re-prefill than the 8 % is worth on any real agentic workload.

### 4.2 Cost per 1M tokens

`cost_per_1M = $/GPU-hr ÷ (tok/s/GPU × 3600) × 1e6`. Input cost uses the scenario's prefill
rate at 0 % cache hit. Blended is METHODOLOGY §6 verbatim: **75 % input (50 % of it cached at
~10 % of uncached cost) / 25 % output**, i.e.
`0.75 × 0.55 × cost_in + 0.25 × cost_out`.

### 4.3 Effect of speculative decoding

```
| config | tok/s/GPU | $/1M output | note |
|---|---|---|---|
| bs=1 autoregressive est. | 199 | $12.01 | latency config, not a cost config |
| meas. Qwen3.5-27B proxy, bs=1: MTP steps=15, bf16 target | 245 | $9.75 | measured, 1x MI355X TP1 |
| meas. Qwen3.5-27B proxy, bs=1: DFlash block=16, bf16 target | 396 | $6.03 | measured, 1x MI355X TP1 |
| meas. Qwen3.5-27B proxy, bs=1: DFlash block=16, mxfp4 target | 460 | $5.19 | measured, 1x MI355X TP1 |
| est. MXFP4 bs=433 (KV ceiling) | 11,312 | $0.21 | batch beats speculation by 25x on cost |
```

**Speculative decoding is a latency product on this GPU, not a cost product.** DFlash2 at
block=16 is a genuine **5×** and the best single-stream result AMD has published for this
architecture — and it still costs **25× more per token** than simply filling the 288 GB of HBM
with concurrent requests. AMD's own conclusion agrees: *"DFlash or more generally, speculative
decoding is more beneficial for low-concurrency scenarios… at high concurrency the arithmetic
intensity is high enough that the hardware is much more saturated [and] verification time of
the target model will increase by a large margin damaging the overall speedup."* Run
speculation for a premium single-user tier; run batch for the bill. MI355X's 288 GB makes that
choice more lopsided here than on any other GPU in this repo.

### 4.4 Effect of prefix caching

```
| hit rate | effective prefill tok/s | $/1M input |
|---|---|---|
| 0% | 35,796 | $0.0667 |
| 50% | 71,593 | $0.0334 |
| 90% | 357,963 | $0.0067 |
```

At a 90 % hit rate, input tokens cost **$0.0067 per 1M** and the blended figure falls from
$0.080 to **$0.056**. Caching is by far the cheapest optimisation available. But on this
architecture a hit also has to restore a **GDN state checkpoint** — the reason `S` = 5 —
and §1.3 shows that costs 47 % of the concurrency at 8 K. The trade is quantified here:
dropping to `S = 1` buys +90 % concurrency and +8 % throughput (§3.4), and costs every
prefix re-prefill. **At any prefix-hit rate above ~10 % the cache wins; keep `S` = 5.**
(⚠️ the hit-rate → TTFT curve for a hybrid-GDN model is unpublished on any GPU;
[architecture.md §5.6](./architecture.md) open question 4.)

Qwen's own `preserve_thinking: true` default exists precisely to keep each agentic turn a
strict extension of the last, so the radix match runs to the end of the previous turn.
Leave it on.

**Break-even utilisation** — the fraction of the hour a rented MI355X must be *serving* for
self-hosting to match the API (`self_cost_at_100% ÷ api_price`):

| API | Output break-even | Input break-even |
|---|---:|---:|
| Qwen Cloud list ($3.00 / $0.50) | **7.0 %** | 13.3 % |
| OpenRouter fp8 floor ($2.20 / $0.20) | **9.6 %** | 33.4 % |
| Darkbloom fp4 ($1.80 / $0.10) | **11.7 %** | **66.7 %** |

Self-hosting wins on output at any plausible utilisation — even against the cheapest FP4
reseller you only need the box busy **12 %** of the time. On **input** the margin is far
thinner: against Darkbloom's $0.10 you need **67 %** sustained prefill utilisation, which no
real deployment hits. The economics say: **self-host the output-heavy reasoning traffic
(`reasoning_effort: xhigh` is this model's default), and be relaxed about buying input tokens
from a reseller.** And note this verdict holds despite MI355X being, at $8.60, the
*second-most-expensive* GPU-hour in cloud-pricing.md §5.14 after GB300's $18.00 — a 27.78 B
model is so cheap to serve that the rate barely matters.

At the ⚠️ TensorWave $2.95 quote the output figure falls to **$0.072/1M** and MI355X becomes
the cheapest row in [architecture.md §11.3](./architecture.md)'s cross-GPU table, ahead of B200
NVFP4's $0.215. **The MI355X cost verdict for this model is a procurement question, not a
silicon question** — exactly as gpus/mi355x.md §8 and architecture.md open question 18 warn.

## 5. Scaling and deployment shape

### 5.1 The shape

**One GPU, TP1, eight independent replicas per node, a load balancer in front.** That is the
whole recommendation. Justification, in order of weight:

1. The model fits one GPU **with 235 GB spare** in every precision (§1.2). There is no fit
   argument for sharding.
2. TP8 *reduces* aggregate KV capacity per node versus 8 replicas (2,169 vs 2,848 at 8 K),
   because 4 GQA KV heads cannot shard past TP4 (§1.5).
3. TP adds an all-reduce to every decode step. On the 1,075 GB/s mesh that is METHODOLOGY's
   5–15 %, for nothing.
4. vLLM's `compatible_strategies` for this model is `["single_node_tp"]` — no PD, no EP, no
   published multi-node layout. And there is nothing to expert-parallelise: it is dense.
5. MLPerf 6.0 measured **93 % offline / 93 % server / 98 % interactive** scale-out efficiency
   from 1 to 11 MI355X nodes on Llama-2-70B — *"that is replica scaling with per-node TP ≤ 8,
   which is the shape the topology favours"* ([gpus/mi355x.md §4](../../gpus/mi355x.md)).

**Use TP4 only** if a single deployment must hold more KV than one GPU can — e.g. > 50
concurrent 128 K sessions, or a fleet of 1 M-token requests. TP4 is KV-neutral and gives
1,510 concurrent 8 K sequences behind one endpoint.

**Multi-node** is never needed for capacity; it is only replica count. Inter-node traffic is
8 × 400G RoCE v2 or InfiniBand, and the NIC (50 GB/s) rather than the 128 GB/s scale-out IF
link is the bottleneck. Nothing in this workload crosses nodes.

**When does PD disaggregation or wide-EP pay for this pair? Never.** Wide-EP is undefined (no
experts). PD is *"a thousand-GPU problem"* that moves the Pareto frontier **inward** below that
scale, and Dynamo has no documented ROCm support at all. If prefill is stalling decode — the
real symptom people reach for PD to fix — the fix on this model is `--chunked-prefill-size`,
not a second cluster.

### 5.3 Warm-up and load time

Weights from NVMe at METHODOLOGY's 5–20 GB/s:

| Checkpoint | Bytes | @ 20 GB/s | @ 5 GB/s |
|---|---:|---:|---:|
| MXFP4 (1 shard) | 19.798 GB | **1.0 s** | 4.0 s |
| FP8 | 30.870 GB | 1.5 s | 6.2 s |
| BF16 (18 shards) | 55.563 GB | 2.8 s | 11.1 s |

Those are the **floor**, and the published reality is far worse: SGLang reports the BF16
checkpoint taking **~6.5 minutes to load its 18 shards** on a DGX Spark and advises budgeting
**~10 minutes to READY** before calling a boot hung ([architecture.md §1.1](./architecture.md)).
Loading is dominated by safetensors parsing, HIP allocation and kernel autotuning, not by NVMe.
Two MI355X-specific additions: `SAFETENSORS_FAST_GPU=1` is in AMD's own recommended env
([gpus/mi355x.md §5](../../gpus/mi355x.md)), and
`FLASH_ATTENTION_TRITON_AMD_AUTOTUNE="TRUE"` buys peak throughput *"at a warm-up cost"*
([flash-attention.md §8.1](../../cross-cutting/flash-attention.md)). AMD's MXFP4 build is a
**single 19.8 GB `model.safetensors`**, which should load materially faster than 18 shards.

Budget **5 minutes** to first token on a cold node, and pre-warm the HF cache; if you ever run
the NVFP4 requant path instead, add SGLang's **10–55 s** online conversion on top.

## 6. Risks and open questions

**Blocking-ish, verify before committing capacity**

1. ⚠️ **Nobody has run this checkpoint on this GPU.** vLLM's `mi355x` cell is *generated*, not
   verified — `meta.hardware` lists only gb300, rtx_5090, rtx_5090_2x, rtx_pro_6000,
   dgx_spark_gb10, ascend_950pr. SGLang has no AMD cell. **Settle it:** serve
   `amd/Qwen3.8-27B-Quark-AWQ-MXFP4` on `vllm/vllm-openai-rocm:latest`, run
   `lm-eval --tasks gsm8k`, then `vllm bench serve --random-input-len 8192
   --random-output-len 1024` at concurrency 1/32/128/256.
2. ⚠️ **The MXFP4 decode win is unquantified in isolation.** AMD measured `mxfp4 + DFlash` at
   +10–20 % over `bf16 + DFlash`, never MXFP4 vs FP8 vs BF16 at matched batch with no
   speculation. §3.3's 2.8× at bs=1 and 1.11× at bs=256 are `est.` **Settle it:** A/B the three
   checkpoints at bs ∈ {1, 32, 256}, ctx 8 K.
3. ⚠️ **AMD's own caveat: *"the mxfp4 models are not fully optimized on vLLM."*** Taken at face
   value, today's MXFP4 numbers are a floor that should improve — but also that the fused FP4
   GEMM path is young. Related: `AMD/MiniMax-M2.1-MXFP4` on MI355X failed at **TP=4** with
   *"device_gemm with the specified compilation parameters does not support this GEMM problem"*
   in the AITER fused-MoE kernel ([vllm#35637](https://github.com/vllm-project/vllm/issues/35637));
   that was a MoE path and this model is dense, but the lesson — **MXFP4 kernels are
   shape-specialised** — applies. Our recommended shape is TP1, the best-covered case.
4. ⚠️ **`S` for vLLM is unpublished.** Every concurrency cell in §1 is given at SGLang's
   documented `S` = 5 and the `S` = 1 floor. vLLM exposes `--mamba-cache-mode` and
   `--enable-mamba-fine-grained-prefix-cache`, both implying `S > 1`, and publishes no slot
   count. Since vLLM is the *only* engine with an MI355X command for this model, **this is the
   largest single uncertainty in §1.** **Settle it:** boot at a fixed `--max-num-seqs`, read
   the mamba-cache allocation from the startup log, divide by 78.45 MB.
5. ⚠️ **The AITER 0.85 `mem-fraction-static` multiplier** (§1.4) is documented on SGLang's 2.4 T
   page for a **MoE** model. Whether it applies to a dense GDN model, and whether vLLM's
   `--gpu-memory-utilization` has an analogue, is unverified. If it does apply, every §1 cell
   drops 17 %.
6. ⚠️ **Radix caching on ROCm.** SGLang forces `--disable-radix-cache` on its DeepSeek-V4.1
   MI350X recipes and consequently refuses HiCache there. No such constraint is documented for
   Qwen3.8-27B — but if it turns out to apply to the AITER path generally, `S` drops to 1, §4.4
   evaporates and every prefix is re-prefilled.
7. ⚠️ **CUDA/HIP graph capture** on gfx950 for a hybrid-GDN dense model is untested; no
   `VLLM_USE_BREAKABLE_CUDAGRAPH` guidance exists for this model. On a 31.4 GiB RTX 5090 graph
   capture allocates **outside** `--gpu-memory-utilization` and OOMs; 288 GB makes that
   unlikely here, but the capture path itself is unexercised.

**Kernel-level gaps**

8. ⚠️ **The tuned hd256 attention kernel does not apply.** AITER's ASM FMHA hd256 forward
   ([aiter#5403](https://github.com/ROCm/aiter/pull/5403)) is **still an open PR** and is
   *"MHA only; GQA/MQA falls back to CK"* — and its 497/509 TFLOPS figures are measured on
   **MI350X**, not MI355X. This model is 24:4 GQA, so its full-attention layers get **CK FA2**
   at the 436 TFLOPS class, ~17 % of the 2,500 TF dense peak.
9. ⚠️ **No achieved-TFLOPS number exists for the GDN Triton kernels on gfx950** — and 48 of 64
   layers are GDN. The entire §3 prefill column rests on METHODOLOGY's MFU bands, not a
   measurement. This is the largest unmodelled term.
10. ⚠️ **FlashInfer GDN prefill and the fused CUDA GDN decode kernel are CUDA-gated**, so
    MI355X runs the Triton tier for both halves of the linear-attention path while
    H200/B200/B300/GB300/RTX PRO 6000 all get a faster one. Any MI355X-vs-Blackwell comparison
    for *this* model is comparing an optimised GDN path to an unoptimised one.
11. ⚠️ **MXFP6 (W4A6) is unexplored.** MI355X is the only part where FP6 runs at the FP4 rate,
    AMD has measured it recovering most of MXFP4's accuracy loss at FP8-beating throughput, and
    no engine recipe emits it. For a model whose MXFP4 build already recovers 99–102 % of GSM8K
    this may be unnecessary — but nobody has checked on a *vision* or long-context task.
12. ⚠️ **FP8 prefill attention in FlashInfer-ROCm is WIP**, and the CK FA2 backend documents
    fp16/bf16 only. FP8 **KV storage** works; FP8 **QK/PV** in prefill may not.
13. ⚠️ **Whether engines chunk the ViT attention at max resolution.** The vision tower has **no
    window attention**, so a 16.78 Mpx image is 65,536 patch tokens and an unchunked score
    matrix would be 8.6 GB. 288 GB hides this better than any other GPU, which is a reason to
    *test* it here rather than assume it.

**Accuracy caveats of the executed precision**

14. **MXFP4 W4A4 is a real quantisation, and AMD's published evidence is thin but positive.**
    `amd/Qwen3.8-27B-Quark-AWQ-MXFP4` reports GSM8K 5-shot flexible-extract **94.996 %
    thinking (101.8 % recovery)** and **89.92 % non-thinking (99.2 % recovery)** against the
    BF16 base — but that is **one benchmark**, and the non-thinking mode was *"approximated
    with a custom task that pre-closes an empty `<think></think>` block"*, not a real
    non-thinking run. **No MMLU-Pro, no GPQA, no AIME, no MMMU, no long-context, and — for a
    model whose headline feature is image and video understanding — no multimodal eval at
    all.** By contrast `RedHatAI/…-INT4` publishes six benchmarks at 98.5–101.1 % recovery.
    ⚠️ **Before shipping MXFP4 on a vision workload, run MMMU-Pro yourself.**
15. **W4A4 quantises activations too**, unlike the W4A16 INT4 builds. AMD's cross-model
    evidence is that MXFP4 PTQ on a *dense* model is genuinely lossy — Llama-3.1-8B GSM8K
    **62.55 % at MXFP4** vs **80.44 % at FP8** — recovered to 76.4 % only by moving activations
    to MXFP6. The AWQ algorithm plus 128 calibration samples is what closes that gap here, and
    AWQ calibration was done on `pileval` at `seq_len 512` — **512-token calibration for a
    262 K-context model.** ⚠️ Long-context degradation is untested.
16. **The vision tower is left BF16** in AMD's build (0.921 GB), which is the right call and
    matches every other published quantisation of this model. It also means the encoder gets no
    FP4 speedup — and §6.4 of architecture.md shows the ViT is 7–67 % of prefill cost depending
    on resolution.
17. ⚠️ **`amd/Qwen3.8-27B-Quark-AWQ-MXFP4` is a 2026-08-26 checkpoint with 29,266 downloads**
    and no engine has declared it verified. Sibling AMD builds exist and are better-trodden:
    `amd/Qwen3.8-27B-Quark-AWQ-INT4-W4A16` (99,956 downloads — but INT4 is the *slow* path
    here), `amd/Qwen3.8-27B-Quark-Qronos-INT4-W4A16`, `amd/Qwen3.8-27B-w8a8-llmcompressor`.

**Commercial**

18. ⚠️ **One published price.** OCI's $8.60 is `low` **and** `high`; a $2.95 TensorWave quote
    circulates from a secondary source, and at that rate MI355X becomes the cheapest row in
    architecture.md §11.3 instead of a mid-table one. `res1y` is unpublished. **Every cost
    number in §4 inherits a single-vendor dependency.** Do not plan against $2.95 without a
    signed quote, and do not substitute DigitalOcean's MI350X $4.76/$4.50 — different SKU.
19. ⚠️ **Procurement lead time.** AWS, GCP and Azure have no MI355X SKU. Crusoe, Vultr and
    TensorWave are contact-sales. Budget a conversation, not a `terraform apply`.
20. ⚠️ **1,400 W liquid-cooled.** If the facility cannot take DLC, the alternative is MI350X at
    1,000 W — same 288 GB, same 8 TB/s, **~8.3 % less of every matrix rate** (the 2200/2400
    clock ratio). Every §3 cell scales by 0.917 on MI350X; §1 is unchanged. vLLM emits the
    identical launch command for both.

**Documents this one corrects**

21. [`architecture.md §9.2`](./architecture.md) and its open question 14 state *"**No MXFP4
    checkpoint exists** for this model despite MXFP4 being the fast path on MI350X/MI355X. That
    is a real gap for AMD deployment."* **That gap closed on 2026-08-26** with
    `amd/Qwen3.8-27B-Quark-AWQ-MXFP4`. The §4 MXFP4 size estimate of **21.349 GB** should be
    replaced with the measured **19.798 GB**, and the §8.4 "Practical MI355X plan" (FP8 or
    Quark AWQ **INT4**) should be re-pointed at MXFP4 — INT4 on gfx950 is a Triton dequant path
    with no published MFMA rate.
22. [`architecture.md §10.2`](./architecture.md)'s advice to *"treat every `est.` above as an
    optimistic ceiling and derate ~30 %"* is calibrated on an RTX 5090 point. **On MI355X the
    same roofline is 9 % conservative, not 35 % optimistic** (§3.2). Do not stack the derate.
23. [`gpus/mi355x.md §2`](../../gpus/mi355x.md)'s model table says for Qwen3.8-27B: *"Dense, so
    plan FP8 over INT4 here: on gfx950 INT4 buys bytes and loses speed."* Correct on INT4, but
    it should now read **plan MXFP4 over FP8** — the checkpoint exists and doubles the prefill
    rate.
