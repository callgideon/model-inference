# Qwen/Qwen3.8-27B on NVIDIA H100 SXM 80GB (HGX 8-GPU)

**Research date: 2026-09-19.** Follows [`research/METHODOLOGY.md`](../../METHODOLOGY.md) — §1 weight
memory, §2 KV/state with the engine slot multiplier `S`, §3 fit and the consistency rule, §4
roofline, §6 cost and the standard scenarios S1–S4, §8 pinned inputs. Legend: `[src]` + URL /
**⚠️ TO BE VERIFIED** / `est.` / `meas.`. Dense TFLOPS only; SXM is never mixed with PCIe.

Inputs are taken from the already-fact-checked
[`models/qwen3827b/architecture.md`](architecture.md), [`gpus/h100.md`](../../gpus/h100.md) and
the `research/cross-cutting/` documents, cited by relative path + section. Every derived number
was computed in `python3` and the script's output is pasted verbatim.

## 0. Verdict

1. **Runnable today, but nobody has published a run.** vLLM ≥ 0.17.0 ships an H100 hardware
   profile for this model (`hw/h100.json`, TP1, image `vllm/vllm-openai:qwen38`) and lists `h100`
   in the `supported_hardware` of both the **fp8** and **int4** variants; SGLang serves the
   architecture but its cookbook's only Hopper cell is **H200**. No cell on either engine is
   marked `verified` for H100 [src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B.json).
2. **Minimum 1 GPU; recommended 2 (TP2), 4 (TP4) if 128 K traffic dominates.** TP ∈ {1, 2, 4, 8}
   only — 24 query heads and 16 GDN key heads make TP16 illegal, so a replica never leaves one
   HGX node and **no multi-node fabric is ever needed** (§1.4).
3. **Weight format actually executed: FP8 E4M3 block-128** (`Qwen/Qwen3.8-27B-FP8`), native on
   sm_90 tensor cores. NVFP4 checkpoints load but fall back to **Marlin W4A16** — memory win, no
   FLOPS win — and SGLang greys out every NVFP4 cell on SM90
   ([architecture.md §8.4](architecture.md), [gpus/h100.md §6](../../gpus/h100.md)).
4. **Interactive (S1, TPOT ≤ 50 ms): $0.221–$0.475 per 1M output tokens** `est.` at 2×H100 TP2,
   concurrency 128 (TPOT 15.9 ms) — $0.315–$0.678 after the ÷0.7 roofline derate of
   [architecture.md §11.3](architecture.md). **Max throughput (S4): $0.188–$0.403** `est.`
   ($0.268–$0.576 derated), at concurrency 193.
5. **Confidence: `estimate`.** Zero measurements exist for this (model, GPU) pair anywhere;
   the closest published H100 runs are the same-family `Qwen-3.5-397B-A17B` (§3.2).

### 1.3 Max concurrency

`max_concurrency(ctx) = floor( kv_budget_per_gpu / (ctx × kv_bytes_per_token / min(n,4) + S × state_bytes / n) )`.

in one way, and the deviation is stated because it is real: **this model has only 4 KV heads**, so
at TP8 the engines replicate the K/V projections and every rank holds a **full quarter** of the KV
cache rather than an eighth (§1.4). For n ≤ 4 the two formulas are identical. `python3`:

Per-request footprint, global bytes (the denominator above, before sharding):

```
  ctx     8192: FP8-KV   0.661 GB   BF16-KV   0.929 GB   (S=1: 0.347 / 0.615)
  ctx    32768: FP8-KV   1.466 GB   BF16-KV   2.540 GB   (S=1: 1.152 / 2.226)

  ctx   262144: FP8-KV   8.982 GB   BF16-KV  17.572 GB   (S=1: 8.668 / 17.258)
  ctx  1048576: FP8-KV  34.752 GB   BF16-KV  69.112 GB   (S=1: 34.438 / 68.798)
```

**Three things fall out of this table.**

- **BF16 weights are not a serving configuration on 80 GB.** 55.56 GB of weights leave 12.44 GB,
  which is 18 concurrent 8 K sequences and **one** 128 K sequence. Both engines' published H100
  profile is the BF16 default checkpoint — it boots, it is not a fleet.
  ([gpus/h100.md §2](../../gpus/h100.md) reaches the same conclusion: *"Qwen3.8-27B BF16 at
  128 K seats exactly one sequence on a single H100."*)
- **FP8 KV is not optional.** It is the difference between 39 and 56 seats at 8 K on one GPU, and
  between 3 and 7 at 128 K. Every published recipe for this model pins `--kv-cache-dtype fp8_e4m3`
  or `fp8` ([architecture.md §5.5](architecture.md)), and FP8 KV is native on FA3/sm_90
  ([gpus/h100.md §5](../../gpus/h100.md)).
- **bf16 GDN state is worth more on H100 than on any bigger card**, because the state term is a
  bigger share of a small budget. `python3`, 1 GPU FP8, `S = 5`:

```
  ctx    8192: fp32 state  35  bf16 state  56  (+60%)
  ctx   32768: fp32 state  20  bf16 state  25  (+25%)
  ctx  131072: fp32 state   6  bf16 state   7  (+17%)
```

  A 60 % concurrency swing at 8 K from one dtype flag (`--mamba-ssm-dtype bfloat16` /
  `--mamba-cache-dtype`). SGLang measures 97,280 vs 68,588 KV tokens on an RTX 5090 for the same
  change (+42 %) [src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md) and
  warns it is an accuracy gate to validate, not a free win ([architecture.md §5.4](architecture.md)).
  Note that on Hopper this flag is **purely** memory/accuracy: SGLang's FlashInfer GDN prefill
  fast path gates on SM100/SM103, so unlike on Blackwell, bf16 state does not unlock a faster
  kernel here ([cross-cutting/flash-attention.md §14.3](../../cross-cutting/flash-attention.md)).

### 1.4 Which tensors cannot be sharded, and why TP is capped at 8

From `config.json` shapes ([architecture.md §2.2](architecture.md)) plus the standard
vLLM/SGLang sharding rules. `est.` — ⚠️ **TO BE VERIFIED** against
`vllm/model_executor/models/qwen3_5.py` for this exact class; the rules below are the generic
ones and no engine publishes a per-TP compatibility table for `Qwen3_5ForConditionalGeneration`.

| Axis | Count | TP values that divide it | Consequence |
|---|---:|---|---|
| `num_attention_heads` (query) | **24** | 1, 2, 3, 4, 6, 8, 12, 24 | TP must divide 24 → **TP16 is illegal** (24 % 16 = 8) |
| `num_key_value_heads` | **4** | 1, 2, 4 | TP > 4 must be a **multiple of 4** and replicates each KV head; at TP8 each rank holds ¼ of the KV cache, not ⅛ |
| `linear_num_key_heads` (GDN) | **16** | 1, 2, 4, 8, 16 | excludes TP = 3, 6, 12 |
| `linear_num_value_heads` (GDN) | **48** | 1,2,3,4,6,8,12,16,24,48 | not binding |
| ViT `num_heads` | 16 | — | run **data-parallel** (`--mm-encoder-tp-mode data`), so replicated |
| RMSNorms, `q_norm`/`k_norm`, GDN `norm` | — | **never sharded** | ~1 MB/rank, not a planning term |

**Intersection: TP ∈ {1, 2, 4, 8}.** A replica therefore always fits inside one HGX H100
NVLink domain (world size 8, 900 GB/s bidirectional per GPU,
[gpus/h100.md §4](../../gpus/h100.md)). **No multi-node fabric is required, at any context
length, in any precision.** More than 8 GPUs means more *replicas*, never a wider TP group —
which also sidesteps METHODOLOGY §4's 20–40 % multi-node-TP comm penalty entirely.

The KV-replication penalty at TP8 is the reason TP8 buys much less than its GPU count suggests:
going TP4 → TP8 doubles the GPUs but raises max concurrency at 8 K only from 364 to 552
(1.52×), and costs 15 points of MBU ([gpus/h100.md §9.3](../../gpus/h100.md): 0.50 at TP4 vs
0.30–0.40 at TP8).

### 1.5 Node shapes — replicas beat a wide TP group

`python3`, FP8, 8 K ctx, FP8 KV, `S = 5`, on one 8-GPU HGX node:

```
  TP1: 56 concurrent; as 8 x TP1 replicas on one node: 448 concurrent
  TP2: 159 concurrent; as 4 x TP2 replicas on one node: 636 concurrent
  TP4: 364 concurrent; as 2 x TP4 replicas on one node: 728 concurrent
  TP8: 552 concurrent; as 1 x TP8 replica  on one node: 552 concurrent
```

vLLM's own `compatible_strategies` for this model is `["single_node_tp"]`
[src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B.json), so replication is an orchestration-level
decision, not an engine flag. **4 × TP2 is the shape to default to on an HGX H100 node**: it is
within a point of TP4's node-level concurrency and it keeps MBU in the 0.60–0.70 band.

**Decode is bandwidth-bound at every batch we can fit.** `python3`, TP1 FP8, ctx 4352:

```
  bs=  1: bandwidth  14.31 ms   compute   0.09 ms   -> BW-bound
  bs= 32: bandwidth  18.58 ms   compute   2.90 ms   -> BW-bound
  bs= 64: bandwidth  22.98 ms   compute   5.80 ms   -> BW-bound
  bs=128: bandwidth  31.78 ms   compute  11.60 ms   -> BW-bound
  bs=256: bandwidth  49.39 ms   compute  23.19 ms   -> BW-bound
```

**Prefill rate, and the one number that decides FP8 vs INT4 on this card.** `python3`, 8192-token
chunk, one GPU:

```
  BF16  math  989.5 TF x MFU 0.4:     7144 tok/s/GPU
  FP8   math 1979.0 TF x MFU 0.3:    10716 tok/s/GPU
  INT4  math  989.5 TF x MFU 0.4:     7144 tok/s/GPU
```

INT4 and NVFP4 on H100 are **W4A16**: the weights are unpacked to FP16 before the MMA, so prefill
runs at the **BF16** rate. 4-bit on Hopper buys decode bandwidth and costs 33 % of prefill
throughput. That trade is the whole FP8-vs-INT4 argument in §4.

**TTFT caveats.** These are *unqueued* prefills: one prompt of `ISL` tokens getting the whole
replica, plus one decode step. Under real load with chunked prefill, decode steps interleave with
prefill chunks and TTFT rises with offered concurrency — the measured H100 pattern is stark
(Llama-3.3-70B FP8 TP2 goes from 0.113 s at conc 4 to **8.475 s** at conc 64,
[gpus/h100.md §10.1](../../gpus/h100.md)). Treat the columns above as a floor. The 90 %-hit
column uses METHODOLOGY §5.4's model `TTFT(h) ≈ TTFT(0)·(1−h) + KV_load`, with the KV-load term
dropped; for this model a hit also restores a ~78–154 MB GDN state checkpoint, ~19 µs at
8 GB/s — negligible ([architecture.md §5.6](architecture.md)).

**MBU sensitivity.** TPOT scales as 1/MBU: at 0.60 multiply every TPOT above by 1.083, at 0.70
by 0.929.

### 3.4 Why the estimates and the measurements differ

| Gap | Direction | Explanation |
|---|---|---|
| Proxy bs=1 TPOT **6.36 ms** (Qwen-3.5-397B) vs this model's `est.` **14.31 ms** at TP1 FP8 | proxy faster | the proxy is **MoE**: at bs=1 it reads attention + shared + ~10 of 512 experts, a few GB, spread over 8 GPUs. Qwen3.8-27B is **dense** — all 30.87 GB every step, on one GPU. This is the single largest structural difference and it does not transfer |
| Proxy TP8 ceiling ~668 out tok/s/GPU vs this model's `est.` 2,084 at TP8 | this model faster | 397 B of FP8 weights ÷ 8 = ~49.6 GB/GPU against 3.86 GB/GPU for the 27 B. A small dense model at high batch is exactly where per-GPU decode throughput peaks |
| Proxy TTFT 11.3 s at conc 256 (1k/1k) vs this model's `est.` TTFT columns of 50–400 ms | proxy far worse | the `est.` figures are **unqueued**. The proxy rows are steady-state under offered load, with the scheduler queueing. The honest read: the `est.` TTFT column is a floor and the proxy shows what the ceiling looks like |
| Roofline vs the one comparable measurement of *this* model | roofline **~35 % optimistic** | [architecture.md §10.2](architecture.md) applies this roofline to the RTX 5090 NVFP4+MTP bs=1 point and predicts 207 tok/s against a measured 152.9 — *"treat every `est.` as an optimistic ceiling and derate ~30 %"*. §4 carries that derate through to cost |
| MTP on the proxy: bs=8 1k/1k, 92.8 → **122.8** out tok/s/GPU (+32 %); bs=32, 147.4 → **233.6** (+58 %) | — | speculative decoding is demonstrably worth 1.3–1.6× on this family on H100 at moderate batch. My §3.2 tables are **without** speculation; §4 prices the effect separately |
| MBU on a hybrid-GDN model | ⚠️ unknown | every MBU figure in [gpus/h100.md §9.3](../../gpus/h100.md) comes from a **pure-attention** dense model (Llama-3.3-70B). The GDN recurrent kernel is a bandwidth-bound non-GEMM that may achieve less than a GEMM does. This is the largest single uncertainty in §3.2 |

**When speculation stops paying here.** [architecture.md §7.4](architecture.md) gives the
crossover as `batch × (ctx × 32,768 + 2 × state_bytes) < weights_bytes`. Per GPU at TP2, ctx 4352:
`batch × (4352 × 32,768/2 + 78.45e6) = batch × 149.7e6` against 15.435 GB of weights →
**bs ≲ 103**. So at the recommended S1 point (bs 128) MTP is past its crossover; below bs 64 it is
worth having. The proxy data above is consistent with that shape.

**Reading the table.**

- **Interactive (S1, TPOT ≤ 50 ms): 2 × H100 TP2 FP8 at concurrency 128 is the operating point** —
  15.89 ms TPOT, 4,027 out tok/s/GPU, **$0.221 / $0.475 per 1M output tokens** (low / high),
  $0.188 reserved. 4×TP4 is within 1 % ($0.223) and 1×TP1 is 44 % more expensive ($0.319) because
  a single GPU can only hold 68 sequences while re-reading 30.87 GB of weights every step.
- **Max throughput (S4): 2 × H100 TP2 FP8 at concurrency 193 — $0.188 / $0.403.** The SLO never
  binds on this pair; **capacity does.** Every S4 row above is still under 50 ms TPOT, so "max
  throughput" here means "the largest batch the KV + state pool can hold", not "the batch where
  latency gives out". That is the defining fact about this model on an 80 GB card.
- **TP8 is the worst shape**, not the best: $0.427 at S1 against $0.221 at TP2. Two causes
  compound — MBU falls to 0.35 ([gpus/h100.md §9.3](../../gpus/h100.md)) and the 4-KV-head
  replication (§1.4) means the eighth GPU does not buy an eighth of the cache.
- **Long context is brutally expensive on this card.** S3 (128 K in / 2 K out) costs
  **$2.89–$6.22 per 1M output tokens at TP4** and $14.43–$31.03 at TP1 — 13–65× the S1 price.
  At 128 K a single sequence needs 4.687 GB of KV+state, so one H100 seats 7.
- **INT4 wins on output and loses on input.** At 4×TP4 INT4 gives the cheapest output token in
  the table ($0.181) but the most expensive input token ($0.124 vs FP8's $0.083), because
  W4A16 prefill runs at the BF16 rate (§3.1). On the METHODOLOGY §6 blend (75 % input) FP8 wins:
  **$0.083 vs $0.097** at S4/TP4, and **$0.081 (FP8 TP2)** is the cheapest blended cell in the
  whole table. **Use FP8 unless your traffic is output-dominated.**
- **`S = 1` gives back what `S = 5` takes, for one GPU.** `1xH100 FP8 S=1` at S1 bs=128 matches
  `2xH100 FP8 S=5` exactly on $/token ($0.221) — you can buy the same unit economics with
  `--disable-radix-cache` on one GPU instead of two, at the cost of every prefix re-prefill
  (§2, [architecture.md §5.6](architecture.md)). For agentic traffic with `preserve_thinking`
  on, that is a bad trade; for stateless single-turn traffic it is a good one.

### 4.4 Effect of speculative decoding and prefix caching on cost

- **Prefix caching is already priced in** to the blended figure (half the input at 10 %). Its
  marginal value: raising the hit rate from 50 % to 90 % moves blended S1 cost from $0.089 to
  `0.75 × (0.1 + 0.9 × 0.1) × 0.083 + 0.25 × 0.221 = $0.067` (low) — a **25 % reduction**. Its
  cost on this model is the `S = 5` state reservation, which is what forces bs 128 instead of
  bs ~290 on the same two GPUs. On an 80 GB card **prefix caching is a capacity purchase, not a
  free optimisation**; measure your actual hit rate before paying for it. ⚠️ No hit-rate → TTFT
  curve has been published for any hybrid-GDN model ([architecture.md §12](architecture.md), open
  question 4).
- **Speculative decoding does not reduce cost at the recommended operating point** — it is past
  its crossover at bs 128 (§3.4). Below bs ~64 it converts idle bandwidth into interactivity: the
  same-family proxy gains **+32 % at bs 8 and +58 % at bs 32** on 8×H100 (§3.3a), which at bs 32
  TP2 would move $/1M output from $0.581 to roughly **$0.368** (low). If your fleet runs at low
  concurrency because of a tail-latency SLO, MTP (γ=3, in-checkpoint, zero extra weights) is the
  cheapest thing you can turn on. Prefer **MTP or DFlash2**; **not DSpark on H100**, whose draft
  checkpoint is NVFP4 and therefore Marlin-bound here (§2).

### 4.5 Versus the vendor API, and break-even utilisation

From [architecture.md §11](architecture.md): **Qwen Cloud list $0.50 in / $3.00 out**, explicit
cache read $0.05 (exactly 10 % of input); the OpenRouter FP8 market cluster is $0.20–0.30 in /
$2.20–2.55 out, and Darkbloom's FP4 endpoint is $0.100 / $1.800. Blending each at the same
75 / 25 with 50 % cached, using **each vendor's own cached-input ratio** (METHODOLOGY §6 forbids
a generic 10 % for API comparisons):

```
   Qwen Cloud list           = 0.75x(0.5x0.50 + 0.5x0.05) + 0.25x3.00 = $0.9563 /1M
   OpenRouter cheapest fp8   = 0.75x(0.5x0.20 + 0.5x0.05) + 0.25x2.50 = $0.7188 /1M
   OpenRouter aggregate      = 0.75x(0.5x0.214+ 0.5x0.15) + 0.25x2.55 = $0.7740 /1M
   Darkbloom fp4             = 0.75x(0.5x0.10 + 0.5x0.01) + 0.25x1.80 = $0.4913 /1M
```

Gross margin on **output** tokens: Qwen's $3.00 against a self-hosted $0.221–$0.475 is
**6.3× – 13.6×** (4.4× – 9.5× after the ÷0.7 derate). On **input** it is much thinner: $0.50
against $0.083–$0.178 is 2.8× – 6.0×.

**Break-even utilisation** — the fraction of wall-clock time the rented GPUs must actually be
producing tokens for self-hosting to match the API, `self_blended / api_blended`:

```

  Qwen Cloud list                        api $0.9563  self $0.1917 (high)  break-even 20.0%
```

self-hosting on two-generation-old silicon still wins comfortably — provided you have the load.

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

**Always single node.** §1.4 caps TP at 8 on shape grounds, and every precision fits one GPU, so
there is no configuration in which a replica crosses an InfiniBand hop. METHODOLOGY §4's 20–40 %
multi-node-TP penalty never applies to this pair. Scaling past 8 GPUs means more replicas behind
a router.

**Recommended shapes, in order:**

1. **4 × (2-GPU TP2)** per HGX H100 node — 636 concurrent 8 K sequences per node, $0.221/1M output
   at S1, MBU in the 0.60–0.70 band. This is the default.
2. **2 × (4-GPU TP4)** if 128 K traffic is a real share — 728 concurrent 8 K, and it is the only
   shape that makes S3 bs 32 feasible (307 out tok/s/GPU vs TP2's bs 8 at 261).
3. **8 × (1-GPU TP1)** only for a stateless, short-context, cost-insensitive fleet, or with
   `--disable-radix-cache` where §4.2 shows it matches TP2's unit economics.
4. **1 × TP8** — do not. §4.2.

### 5.2 When PD disaggregation or wide-EP pays

- **Wide-EP / DeepEP / EPLB: never.** The model is dense; there are no experts.
  ([architecture.md §8.6](architecture.md): *"TP only; no published PP, EP (there are no
  experts), DP-attention or P/D layout."*)
- **P/D disaggregation: not for this pair.** vLLM's `compatible_strategies` is
  `["single_node_tp"]` [src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B.json). The economic case is
  also weak: prefill and decode both fit the same 1–2 GPUs, and the thing you would transfer
  across the P/D boundary includes a **78–154 MB recurrent state per slot** that no published
  NIXL/Mooncake path is documented to carry. ⚠️ open question 12 in
  [architecture.md §12](architecture.md).
- **What *is* published for H100 is a KV-store layout**, and it is the one scaling lever worth
  trying on a multi-replica fleet: vLLM's recipe ships
  `hw/h100/strategies/kv_store_centralized_mooncake.json` and
  `…/kv_store_distributed_mooncake.json`
  [src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/h100/strategies/kv_store_distributed_mooncake.json).
  It lets replicas share a prefix cache instead of each paying its own re-prefill — directly
  attacking §4.4's hit-rate lever. ⚠️ whether the GDN state travels with the KV is unverified.

### 5.4 Warm-up and loading

`python3`, checkpoint bytes ÷ NVMe rate:

```
  BF16   55.56 GB @  5 GB/s =   11.1 s | @ 10 GB/s =    5.6 s | @ 20 GB/s =    2.8 s
  FP8    30.87 GB @  5 GB/s =    6.2 s | @ 10 GB/s =    3.1 s | @ 20 GB/s =    1.5 s
  INT4   19.45 GB @  5 GB/s =    3.9 s | @ 10 GB/s =    1.9 s | @ 20 GB/s =    1.0 s
```

**Do not plan against those numbers.** SGLang measures **~6.5 minutes** to load the 18 BF16
shards from NVMe (on a DGX Spark) and advises budgeting **~10 minutes to READY before calling a
boot hung** [src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md) — two orders
of magnitude above the raw-bandwidth figure, because the cost is per-shard open/parse, host→device
staging and CUDA-graph capture, not sequential read. The shard layout is also awkward: shards
alternate ~3.98 GB / ~2.11 GB from shard 6 onward ([architecture.md §1.1](architecture.md)).
⚠️ **TO BE VERIFIED** on H100 specifically — the 6.5 min figure is a GB10 unified-memory part with
very different storage and staging characteristics. On top of loading, add FlashInfer's **GDN
prefill JIT warm-up** on the first request under vLLM
([flash-attention.md §9.2](../../cross-cutting/flash-attention.md)).

**Accuracy caveat of the executed precision, stated plainly.** The recommended path is
FP8 E4M3 block-128 weights with an **FP8 E4M3 KV cache** and FA3 running attention itself in the
quantised domain ([gpus/h100.md §5](../../gpus/h100.md)). vLLM's FP8-KV study measures ≤ 1–2 points
on reasoning benchmarks and 97–98 % of baseline long-context MRCR AUC at 128 K on other models
[src](https://vllm.ai/blog/2026-04-22-fp8-kvcache). **That is not this model**, which has only
4 KV heads at `head_dim` 256 — very little head redundancy to absorb quantisation error — and
whose default `reasoning_effort` is `xhigh` with a recommended 262 K reasoning budget. Validate
long-context accuracy before shipping FP8 KV at 128 K+.

- **§5.3, prose.** "Per §1.3 that is **18** concurrent 8 K sequences with a BF16 KV pool" cited

- **§3.2, the "1 × H100 — BF16 (the checkpoint vLLM's `hw/h100.json` actually launches)" table's
  three `infeasible (KV/state), max N` annotations.** That table's own TPOT/tok-s/bytes-step
  columns are computed with **BF16 KV** (verified: 55.85 GB/step at bs=1 reproduces only with
  BF16 KV bytes, not FP8), but its printed feasibility ceilings (22 / 6 / 2 at S1/S2/S3) reproduce
  only under **FP8 KV** — a mismatched-KV-dtype bug between the byte model and the capacity
  model in the same table. Recomputed consistently with BF16 KV, `S=5`, bf16 state, the correct
  ceilings are **17 / 4 / 1** (errors of 29%, 50% and 100% respectively). **Fixed** to 17 / 4 / 1.
  This does not change which rows the table prints as feasible vs. infeasible (bs 1 and 8 stay
  feasible at S1 under either ceiling; only bs 1 stays feasible at S2/S3 under either) — only the
  stated ceiling was wrong.

**Checked and left as-is (below the 5% fix threshold).** The `1×H100 FP8 S=5, S4, bs=68` cost
