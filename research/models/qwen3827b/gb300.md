## 0. Verdict

1. **Runnable today, on one GPU.** vLLM ≥ 0.17.0 marks `"gb300": "verified"` at **TP1**
   ([recipes.vllm.ai](https://recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/gb300.json), docker
   `vllm/vllm-openai:qwen38`); SGLang **v0.5.19** publishes `verified: true` GB300 cells for **all five
   checkpoints** (BF16, FP8, both RadixArk NVFP4 and NVIDIA's NVFP4 — DFlash2 cells only
   `in-progress`) [src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md);
   NVIDIA's own `nvidia/Qwen3.8-27B-NVFP4` names **"Test Hardware: NVIDIA Grace Blackwell GB300"**
   [src](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4); RadixArk's export was "produced and
   validated on GB300" [src](https://huggingface.co/RadixArk/Qwen3.8-27B-NVFP4).
2. **Min 1 GPU, recommended 1 GPU per replica** (TP1). TP4 exists only to buy a single request more
   KV or a 4× lower TPOT; 18 trays × 4 GPUs = **72 independent replicas** is the rack shape.
   **Wide-EP is not applicable — this model is dense and has no experts** (§5.3).
3. **Weight format actually executed: NVFP4 W4A4** on the MLPs + `lm_head` (71.7 % of GEMM params)
   and **FP8** on the attention/GDN projections, both native on `tcgen05`/sm_103, with BF16 vision
   tower, MTP head and norms, and an **FP8 KV cache**. 21.92 GB of weights in a 279 GB GPU.
4. **Interactive (S1, TPOT ≤ 50 ms): $0.347 per 1M output tokens** at OCI's $18.00/GPU-h — the only
   published on-demand GB300 rate anywhere — falling to **$0.045–0.050** at SemiAnalysis's
   $2.31/chip-h volume anchor or a colo build. Derate ×0.7 for the roofline's known optimism:
   **$0.50 / $0.064**. Input: $0.115 per 1M at $18.00.
5. **Max throughput (S4) lands on the same operating point** — at 4.6 K context the 50 ms SLO never
   binds before the KV/state pool does (bs = 414, TPOT 28.7 ms). **Confidence: `estimate`.** No
   throughput, TTFT or TPOT number has ever been published for this model on this GPU; what exists
   on GB300 is accuracy only (GSM8K 97.27 %, Terminal-Bench 2.1 73.81 %, 4×GB300 TP4 SGLang
   [src](https://huggingface.co/RadixArk/Qwen3.8-27B-NVFP4)).

**Planning basis for every table below:** NVFP4 weights, **FP8 KV**, **bf16 GDN state**, `S = 5`.
bf16 state is not only a memory choice on this GPU — it is the gate on SGLang's FlashInfer GDN
prefill fast path, which requires `head_k_dim == 128` (✅ here), CUDA ≥ 13, Triton as the base
linear-attention backend and a **BF16 recurrent state**
[src](https://docs.sglang.io/docs/advanced_features/attention_backend.md),
[flash-attention.md §14.3](../../cross-cutting/flash-attention.md). Note that NVIDIA's own
SGLang line for GB300 ships `--mamba-ssm-dtype float32`
[src](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4), which turns that path off — §6.

### 1.2 What cannot be sharded

| Tensor group | Bytes (NVFP4 build) | Shardable? |
|---|---:|---|
| Vision tower (27 ViT blocks + merger), BF16 | **0.921 GB** | Replicated on every rank under vLLM's `--mm-encoder-tp-mode data` (the flag in the published GB300 command). TP-sharding it instead is possible but the recipe does not. |
| LM norms, `q_norm`/`k_norm`, `A_log`, `dt_bias` | 0.0013 GB | **No** — per-channel/per-head scalars, replicated in every TP scheme |
| KV cache (4 KV heads) | — | **Shards only to TP4.** At TP > 4 the engine replicates KV heads, so per-GPU KV bytes stop falling. This is the single most important topology fact for this model. |
| GDN recurrent state (16 key / 48 value heads) | — | Shards to **TP16** cleanly (16 key heads); TP 8 and 16 divide both 16 and 48. TP ∈ {18, 36, 72} does not divide 16 → **not expressible as TP**; those GPU counts are replica counts. |
| MTP draft head (0.425 B, BF16 in both NVFP4 exports) | 0.849 GB | TP-shardable in principle; whether either engine shards it is ⚠️ **TO BE VERIFIED** |
| `lm_head` / `embed_tokens` | 1.27 B params each | Vocab-parallel shardable (`lm_head` is NVFP4-packed in the FP4-head exports; `embed_tokens` stays BF16) |

vLLM's own strategy record for this model is `single_node_tp` with `"max_gpus": 8`
[src](https://recipes.vllm.ai/Qwen/Qwen3.8-27B/hw/gb300.json); no PP, EP, DP-attention or P/D
layout is published ([architecture.md §8.6](./architecture.md)).

```
 72 72 x TP1 replicas          21.92     225.2 | 24480/46728 11016/14040   3456/3672     432/432
```

Read the TP8/TP16 rows carefully: **concurrency barely improves past TP4** (1,458 → 2,672 at 8 K,
205 → 222 at 128 K) because the KV cache stops sharding at 4 KV heads while the weights — already
trivial — keep shrinking. **TP8 and TP16 are a latency instrument, not a capacity one.** And 18 / 36 /
72 GPUs are *replicas*, not a TP group: 72 × TP1 gives 24,480 concurrent 8 K sequences per rack
against TP16's 2,672 per 16-GPU group (≈ 12,000 per rack) — replication wins outright.

**Multi-node fabric: never needed.** The model fits one GPU in every precision; a 4-GPU tray, an
8-GPU pair of trays and the full 72-GPU NVLink domain are all reachable inside one rack at
1.8 TB/s/GPU ([gpus/gb300.md §4.1](../../gpus/gb300.md)). The 800 Gb/s ConnectX-8 scale-out path
(§4.2 there) is irrelevant to this pair.

Per weight format and per KV dtype, at TP1:

```
1b. FIT — TP1, every weight format, FP8 KV vs BF16 KV, S=5
fmt                W GB  budget |               8K              32K             128K               1M
bf16              55.56   191.5 |        289 / 206         130 / 75          40 / 21            5 / 2
fp8               30.87   216.2 |        327 / 232         147 / 85          46 / 24            6 / 3
nvfp4_bf16head    23.75   223.3 |        338 / 240         152 / 87          47 / 24            6 / 3
nvfp4             21.92   225.2 |        340 / 242         153 / 88          48 / 25            6 / 3
int4              19.45   227.6 |        344 / 245         155 / 89          48 / 25            6 / 3
(cells are FP8-KV / BF16-KV concurrency; bf16 GDN state, S=5)
```

The NVFP4 row reproduces [architecture.md §10.2](./architecture.md)'s GB300 line
(340 / 153 / 48 / 6 at `S = 5`) exactly. ✅ Cross-check passed.

**On this GPU the weight format barely matters for capacity.** BF16 → NVFP4 buys 289 → 340
concurrent 8 K sequences (+18 %), because 33.6 GB of saved weights is 15 % of a 225 GB budget.
That is the opposite of the RTX 5090 story in [architecture.md §10.1](./architecture.md), where
NVFP4 was worth 2.4× the KV pool. **On GB300 you choose NVFP4 for the 3× FP4 tensor-core rate in
prefill, not for fit.**

### 1.4 Where the budget actually goes — the state pool, not the KV pool

```
1c. TP1 NVFP4 FP8-KV S=5 bf16 state
ctx      4608: conc  414  KV    62.5 GB (27.8%)  state   162.4 GB (72.2%)
ctx      8192: conc  340  KV    91.3 GB (40.6%)  state   133.4 GB (59.4%)
ctx     32768: conc  153  KV   164.3 GB (73.2%)  state    60.0 GB (26.8%)
ctx    131072: conc   48  KV   206.2 GB (91.6%)  state    18.8 GB ( 8.4%)
ctx   1048576: conc    6  KV   206.2 GB (98.9%)  state     2.4 GB ( 1.1%)
```

At the S1 context (4,608 tokens) **72 % of a GB300's usable HBM is GDN recurrent state, not KV** —
414 requests × 5 slots × 78.45 MB = 162 GB. The per-request crossover is `S × token_equiv` =
5 × 2,394 = **11,970 tokens at bf16 state**, 23,490 at fp32
([architecture.md §5.2](./architecture.md)). Dropping to `S = 1` with `--disable-radix-cache`
takes 8 K concurrency 340 → 649, at the cost of every prefix re-prefill — and on this architecture
a re-prefill re-runs 48 recurrent layers over the whole prefix
([architecture.md §5.6](./architecture.md)). **On a 279 GB GPU, paying 4 extra state slots per
request to keep radix caching is almost always the right trade; on a 32 GB card it was not.**

1 M context, for completeness: 6 concurrent sequences on one GPU (34.4 GB of FP8 KV each), 27 on a
TP4 tray. No GPU in the repo holds a 1 M sequence at BF16 weights + BF16 KV
([architecture.md §10.2](./architecture.md)); GB300 holds six per GPU at NVFP4 + FP8 KV.

| **CUDA graphs** | **native, and safe here** | The RTX 5090 failure (`--enforce-eager` required because capture allocates outside `--gpu-memory-utilization`) was a 31.4 GiB-card problem [serving-optimizations.md §4.2](../../cross-cutting/serving-optimizations.md). With 225 GB of headroom, capture is not memory-constrained on GB300 | Size capture to `max_num_seqs × (1 + num_speculative_tokens)` when speculating |

**Net:** every optimization that matters for this model is native on sm_103, with three exceptions —
FP4 KV (⚠️ untested), PD disaggregation (no recipe) and wide-EP (meaningless for a dense model).

### 3.7 Explaining the gaps between est. and meas.

1. **The only same-model measurements are on 1,592–1,792 GB/s consumer/workstation Blackwell.**
   GB300 has 8,000 GB/s — 4.5–5× the bandwidth — and decode here is bandwidth-bound at every
   feasible batch (§3.3 marks every non-spec cell `mem-bound`). Scaling the RTX 5090's measured
   152.9 tok/s/user (NVFP4 + MTP, bs = 1) by 8,000/1,792 = 4.46× predicts **682 tok/s/user** on
   GB300 against this doc's 868 `est.` — a 22 % gap, the same direction and rough size as the
   ~30–35 % over-prediction [architecture.md §10.2](./architecture.md) found. **Derate every `est.`
   here by ~0.7 before committing capacity.**
2. **MBU 0.65 is inferred, not measured.** [gpus/gb300.md §9.4](../../gpus/gb300.md) states plainly
   that **no end-to-end MBU or MFU figure for GB300 exists** ⚠️. At 414 concurrent sequences each
   carrying a separate 78 MB recurrent state plus paged KV, the real MBU is more likely near the
   bottom of the 0.60–0.75 band than the top.
3. **Queueing and chunked prefill are excluded from TTFT.** With `--chunked-prefill-size 2048`
   (SGLang's GB300 pin) and hundreds of concurrent requests, a new request's prefill is interleaved
   with every running decode. SGLang's own guidance is that on hybrid-GDN models decode stalls
   behind prefill chunks and 8192-token chunks stall them ~600 ms at a time. Real p99 TTFT under
   load will be several times the isolated numbers in §3.3.
4. **The GDN prefill kernel's MFU is unknown.** The 0.25 GEMM MFU is a generic Blackwell planning
   default; the FlashInfer GDN prefill fast path engaging on SM103 (§2) could move it either way,
   and no one has published a GDN-kernel efficiency number on any GPU
   ([architecture.md](./architecture.md) open question 10).
5. **Benchmark half-life on this rack is about two quarters.** DeepSeek-R1 server throughput rose
   2.77× on identical GB300 silicon in six months, software only
   [gpus/gb300.md §10.1](../../gpus/gb300.md). Any estimate here ages fast in the *optimistic*
   direction.

| Scenario | max bs | TPOT | tok/s/GPU | $/1M out @ $18.00 | prefill tok/s | $/1M in |
|---|---:|---:|---:|---:|---:|---:|
| S2 (32K in / 1K out) | 150 | 40.7 ms | 3,687 | **$1.356** | 37,389 | $0.134 |
| S3 (128K in / 2K out) | 47 | 45.1 ms | 1,043 | **$4.794** | 25,233 | $0.198 |

**Long context is where the money goes**, exactly as [gpus/gb300.md §8.4](../../gpus/gb300.md)
found for DeepSeek-R1 (128 K costs ~40× more per token than 8 K). Here S3 output is **13.8× S1**.

### 4.3 Effect of speculative decoding and prefix caching

```
4d. at OCI $18.00/GPU-h
bs=  64: no-spec    7,995 t/s $0.625/1M   MTP (acc 4.28) 31,635 t/s $0.158/1M
bs= 128: no-spec   10,852 t/s $0.461/1M   MTP            44,010 t/s $0.114/1M
bs= 256: no-spec   13,214 t/s $0.378/1M   MTP            45,182 t/s $0.111/1M
bs= 414: no-spec   14,411 t/s $0.347/1M   MTP            45,182 t/s $0.111/1M

prefix-cache hit  0%: effective $/1M input 0.1149
prefix-cache hit 50%: effective $/1M input 0.0632
prefix-cache hit 90%: effective $/1M input 0.0218
```

⚠️ The MTP column is a roofline ceiling built on RTX-class acceptance (§3.4) and is compute-bound
above bs = 256; **[architecture.md §7.4](./architecture.md) expects the gain to be gone by
bs ≈ 71 at this context**, so the honest reading is: *speculation cuts S1 output cost by roughly
2–2.5× at bs ≤ 64 and by little or nothing at the bs = 414 operating point.* If your service runs at
low concurrency for latency reasons, MTP is the single best cost lever; if it runs at the capacity
ceiling, it is not.

Prefix caching is the more reliable lever for this workload class: input is 75 % of blended tokens,
and a 90 % hit takes effective input cost from $0.115 to $0.022 per 1M. On this model a hit also
restores the GDN state checkpoint — the mechanism `preserve_thinking: true` exists to keep working
([architecture.md §5.6](./architecture.md)) — and the ~78 MB state restore is ~19 µs at 4 TB/s,
negligible against any prefill. ⚠️ No hit-rate → TTFT curve has been published for a hybrid-GDN
model ([serving-optimizations.md §1.2](../../cross-cutting/serving-optimizations.md) gives curves
for pure-attention models only).

### 4.4 Versus the vendor API, and break-even

Qwen Cloud list ([architecture.md §11.1](./architecture.md)):
**$0.50 in / $3.00 out / $0.05 explicit-cache read per 1M.** The market fp8 cluster on OpenRouter is
$0.20–0.30 in / $2.20–2.55 out; the cheapest listed endpoint is Darkbloom fp4 at $0.10 / $1.80.

```
4c. break-even utilisation vs Qwen Cloud API ($3.00/1M out)
OCI $18.00        self-host $0.347/1M out -> break-even at 11.6 % utilisation
SemiAnalysis $2.31 self-host $0.045/1M out -> break-even at  1.5 %
colo 3-yr $2.57    self-host $0.050/1M out -> break-even at  1.7 %
API blended (75/25, 50 % cached at $0.05):  $0.956/1M
```

Read the break-even as: *a GB300 rented at $18.00/GPU-h pays for itself against the API once it is
producing output tokens for **11.6 %** of the hour at the S1 operating point* — i.e. ~7 minutes of
saturated decode per hour. Derated ×0.7 that becomes **16.5 %**. Against the cheapest third-party
endpoint ($1.80/1M out) it is 19.3 % (27.6 % derated). **Self-hosting this model on GB300 wins
decisively on output tokens at any plausible duty cycle**, and the margin against Qwen's own list
price is 8.6× undertated / 6.0× derated at $18.00 — far below the 14× that a B200 achieves
([architecture.md §11.3](./architecture.md)), because GB300's $18.00 is a hyperscaler list price
sitting 2.2–2.4× above neocloud rates for comparable silicon.

Blended: **$0.134/1M** self-hosted (derated $0.192) against **$0.956/1M** at Qwen's API with the same
mix — a **7.1×** gap (5.0× derated).

**The honest caveat, restated:** GB300 is *not* the cheapest way to serve this model. Every
published on-demand alternative is cheaper per token for a 27 B dense model that fits one GPU:
[architecture.md §11.3](./architecture.md) puts B200 NVFP4 at **$0.215/1M out** ($6.00/GPU-h,
Hyperstack), B300 HGX at $0.219 ($7.40), H200 FP8 at $0.236. The GB300 case rests entirely on three
things this pair may or may not need: 279 GB per GPU (2.4× B200's usable KV budget → 340 vs 205
concurrent 8 K sequences), the 130 TB/s NVLink domain for KV pooling and P/D, and 15,000 dense FP4
TFLOPS for prefill-heavy multimodal traffic. **If you are buying GB300 for a 27 B dense text model,
you are buying the wrong rack.** If you already have the rack for a 2.4 T sibling or DeepSeek-V4.1,
running this model on spare trays at $0.347/1M out is excellent.

## 5. Scaling and deployment shape

### 5.1 Single node vs multi-node

The model fits one GPU in every precision, so **multi-node never applies**. The topology question is
only how to fill a tray and a rack:

| Shape | When | Aggregate (ctx 4,608, MBU 0.65, `est.`) |
|---|---|---|
| **1 × TP1 (recommended default)** | Everything | 414 concurrent, 14,411 tok/s, 28.7 ms TPOT |
| 4 × TP1 (one tray, 4 replicas) | Standard serving unit; OCI sells `BM.GPU.GB300.4` as a 4-GPU slice | 1,656 concurrent, 58,001 tok/s |
| 1 × TP4 (one tray, one replica) | A single user who needs ≤ 2 ms TPOT, or one request at 1 M context with 27 concurrent slots | 1,458 concurrent @8K, 5.47 ms at bs = 256 |
| 72 × TP1 (full rack) | Fleet | **29,808 concurrent, 1.04 M tok/s, $1,296/h → $0.345/1M output** |
| **Wide-EP (EP8…EP72)** | **Never** | Dense model, no experts. The NVL72 domain's headline advantage ([gpus/gb300.md §10.6](../../gpus/gb300.md)) is inaccessible to this pair. |

The rack figure — ~1.04 M tok/s `est.` — is worth putting beside Azure's measured
**~1.1 M tok/s per ND GB300 v6 rack** for general LLM inference
[src](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/gpu-accelerated/nd-gb300-v6-series)
and Nebius's MLPerf v6.0 **1,096,770 tok/s** for gpt-oss-120b on 72 GPUs
[gpus/gb300.md §10.2](../../gpus/gb300.md). Landing in the same place as two measured rack totals for
different models is a weak but real sanity check.

### 5.2 When PD disaggregation pays — and why it does not here

PD disaggregation pays when prefill and decode have incompatible optimal parallelism and the KV
handoff is cheap. Both halves fail for this pair:

- **No engine publishes a P/D layout for Qwen3.8-27B** (vLLM: `compatible_strategies:
  ["single_node_tp"]`). TRT-LLM's row for this architecture class says **EPD Disaggregated Serving:
  Yes** but **KV Cache Reuse: No**, because *"KV cache reuse for hybrid recurrent-attention models
  requires an explicit recurrent-state snapshot policy"* ([architecture.md §8.4](./architecture.md)).
- ⚠️ It is unknown whether the **GDN recurrent state** transfers over NIXL/Dynamo at all
  ([architecture.md](./architecture.md) open question 12). A P/D handoff that moves the KV but not
  the 48 recurrent states hands the decode worker a wrong state.
- The economic case is weak anyway: prefill and decode both run TP1 on one GPU here, and the
  measured ~1.5× PD gain on NVL72 was for a 671 B MoE where prefill wanted TP16 and decode wanted
  EP32 ([gpus/gb300.md §10.7](../../gpus/gb300.md)).

**Where the rack *does* help this model:** (a) **KV pooling** — 20 TB of HBM plus 17 TB of Grace
LPDDR5X at 14 TB/s over 900 GB/s C2C makes host-memory KV offload unusually attractive
([gpus/gb300.md §10.7](../../gpus/gb300.md)), and vLLM already reports `offloading_cpu`/
`offloading_fs` verified for this model; (b) **KV-aware routing** across 72 replicas (SGLang HiCache
/ Dynamo KV-aware router), which is what turns a 90 % prefix-hit workload into a 5× cheaper one;
(c) **a TP4/TP8 prefill group** for 1 M-token jobs (168 s → 42 s / 21 s `est.`).

### 5.4 Warm-up and load time

```
5. weight load from NVMe at 5-20 GB/s
bf16     55.56 GB ->   2.8 s @20 GB/s ..   11.1 s @5 GB/s
fp8      30.87 GB ->   1.5 s @20 GB/s ..    6.2 s @5 GB/s
nvfp4    21.92 GB ->   1.1 s @20 GB/s ..    4.4 s @5 GB/s
```

That is the *bandwidth floor*. The measured reality on the one platform anyone reported is far
worse: SGLang observes the **BF16 checkpoint takes ~6.5 minutes to load its 18 shards from NVMe** on
a DGX Spark, and advises budgeting **~10 minutes to READY** before calling a boot hung
[src](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B.md). The shard layout is
awkward — 18 shards alternating ~3.98 GB / ~2.11 GB from shard 6
([architecture.md §1.1](./architecture.md)) — and the gap between 11 s of raw I/O and 6.5 minutes is
safetensors parsing, host-to-device staging and (on GB10) unified memory. ⚠️ **No GB300 load-time
measurement exists**; a GB300 tray with a real NVMe array and 900 GB/s C2C should do far better than
GB10, and the NVFP4 build moves 2.5× fewer bytes. Budget **2–4 minutes to READY** and measure.
Add CUDA-graph capture (seconds to tens of seconds, and unlike the RTX 5090 case it has ample memory
here) and SGLang's server warm-up, which `--skip-server-warmup` can bypass.

| 2 | **MBU 0.65 and decode MFU 0.30 are inferred.** [gpus/gb300.md §9.4](../../gpus/gb300.md) states no end-to-end MBU/MFU for GB300 has been published | The whole §3 table scales linearly with MBU; the 0.60–0.75 band is a ±13 % swing on every cost figure | Back MBU out of a measured tok/s with §3.1's byte model |
| 3 | **No FA4 or FlashMLA TFLOPS number on B300/GB300.** The FA4 paper explicitly declined to benchmark B300 | The 1,500 TFLOPS attention figure is B200's 1,613 derated by hand. Matters most at S3/1 M, where attention is 32–79 % of prefill | Microbenchmark the hd256 2-CTA kernel on sm_103 |
| 4 | **flash-attn-4 arch check.** Some builds reject sm_103 with `Only SM 10.x and 11.x are supported` at warmup [src](https://github.com/sgl-project/sglang/issues/25564) | The fix is [Dao-AILab #2572](https://github.com/Dao-AILab/flash-attention/pull/2572) / `fa4-v4.0.0.beta22`; older SGLang v0.5.12-cu130 images crash | Check your flash-attn-4 pin before the fleet, or use `trtllm_mha`/`triton` |
| 5 | **The FA4 block-size trap.** `--block-size` not a multiple of 128 makes FA4 ineligible for hd256 and vLLM silently drops to FA2 | A silent ~2× attention regression with no error | Read the selected backend from the server log |
| 6 | **`--mamba-ssm-dtype`: NVIDIA says fp32, the fast path wants bf16.** NVIDIA's SGLang line pins `float32`; the FlashInfer GDN prefill fast path on SM100/SM103 requires a **BF16** recurrent state | fp32 doubles the state pool (153.9 → 78.4 MB/slot) *and* forgoes the Blackwell GDN prefill kernel — but SGLang measured fp32 *winning* with NVFP4+EAGLE on a 5090 (152.9 vs 144.5 tok/s/user). | 7 | **vLLM's state-slot count `S` is unpublished.** SGLang publishes 5/4/3/1 by strategy | Every fit cell and every feasibility verdict in §1 and §3 is engine-specific until this is known | Boot vLLM at a fixed `--max-num-seqs`, read the mamba-cache allocation from the startup log, divide by 78,446,592 |

| 9 | **FP4/NVFP4 KV cache on this model.** No recipe, checkpoint or benchmark; GQA with only 4 KV heads has little redundancy | Would take KV to 16 KiB/token and 8 K concurrency to ~471 | `--kv-cache-dtype fp4` on a Triton/FA4/TRTLLM-MHA backend, then re-score GSM8K |

| 11 | **PD disaggregation / Dynamo: no recipe, and GDN-state transfer over NIXL is unknown** | A handoff that moves KV but not the 48 recurrent states is silently wrong, not slow | Attempt a 1P1D layout and check whether the recurrent state survives |

| 18 | **`qwen3_xml` (vLLM) vs `qwen3_coder` (SGLang) tool-call parser** — the two engines pin different parsers for the same chat template | A silent failure mode: tool calls land in `message.content` instead of `tool_calls` | Send a tool-calling request to each and inspect |

**Known engine issues that are not open questions:**

- **INT8/W8A8 fails at the first forward pass, after the weights have loaded**
  [src](https://arxiv.org/html/2608.11693v1). If you inherited a W8A8 pipeline (e.g. the Ascend
  `Eco-Tech/Qwen3.8-27B-w8a8` build), it does not run here. Use FP8 or NVFP4.
- **MXFP4 does not load on NVIDIA devices** and no MXFP4 Qwen3.8-27B checkpoint exists anyway.
- **`--reasoning-parser qwen3` is effectively mandatory** — without it the whole `<think>` block
  lands in `message.content` and a 2,048-token budget is spent before the answer starts. With
  `reasoning_effort: xhigh` as the shipped default and a 262 K recommended reasoning budget, this
  wastes more output tokens than any serving optimization saves
  [serving-optimizations.md §7.3](../../cross-cutting/serving-optimizations.md).
- **TensorRT-LLM: KV Cache Reuse = No** for `Qwen3_5ForConditionalGeneration` unless you configure
  `kv_cache_config.mamba_state_config.periodic_snapshot_interval` yourself. Given that agentic
  multi-turn traffic on this model lives or dies on prefix reuse (§4.3), **TRT-LLM is the wrong
  engine for this pair** despite being the most mature GB300 stack overall.

**Accuracy caveats of the executed precision.** The NVFP4 W4A4 MLP + FP8 attention recipe is the one
NVIDIA validated **on GB300 itself**, and it is close to lossless: GPQA-Diamond 88.01 vs 88.92 BF16,
Terminal-Bench 74.02 vs 75.56, MMMU-Pro 74.86 vs 75.14, IFBench 78.93 vs 80.07, with AA-LCR (73.38 vs
72.63) and SciCode (48.41 vs 47.93) *above* BF16 — worst case −1.5 points
[src](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4). RadixArk's GB300 TP4 run scores GSM8K
97.27 % and Terminal-Bench 2.1 73.81 % [src](https://huggingface.co/RadixArk/Qwen3.8-27B-NVFP4).
Two residual concerns: (a) **FP8 KV** is universally used but its accuracy effect is measured only
jointly with the weight quantisation, never isolated; (b) **bf16 GDN state** is an accuracy change
SGLang explicitly calls *"an accuracy gate"* that you must validate for your workload — and it is
the setting this document recommends, because it unlocks the SM103 GDN prefill kernel. Validate it
on your traffic, not on GSM8K alone.
