| Test ID | Invariant demonstrated |
|---|---|

### Stale responses cannot overwrite current filters

| Test ID | Invariant demonstrated |
|---|---|
| `V1-S01 the response to the newest request is applied` | The reader's choice shows immediately; its own response settles. |
| `V1-S02 a response that lost the race cannot put the older filter back` | Two changes, the *first* response arriving last: not applied, the current filters survive, the sequence is unchanged, and the newest response still applies afterwards. This is the acceptance criterion. |
| `V1-S03 a duplicate delivery of a response already applied changes nothing` | A replayed response, and tokens nobody issued (`99`, `0`, `-1`), cannot rewrite the filters. |
| `V1-S04 an arrival with nothing outstanding is the truth, whoever navigated` | A page link or the back button, with no change in flight, is accepted — the guard does not freeze the page. |
| `V1-S05 an arrival that does not answer the outstanding request is dropped` | Including a page of the *same* filters at a different position in the walk, which is a different request. |
| `V1-S06 the controls draw the newest request while one is outstanding` | A page arriving mid-flight for the previous filters does not move the controls; once settled, the URL is what they draw. |

## Limits

- **Fake-backed, therefore implemented and not integrated.** Pagination and tenant filtering are
  demonstrated against fixtures (`V1-Q10`); the same assertions must be re-run against C1's
  PostgreSQL/ClickHouse services before V1 is integrated (CONSOLE-FLOWS, TRACE-TENANT). The page's
  two marked lines are the only thing that changes.
- **The page currently renders the fake's owner session**, not the signed-in one. Anyone who opens
  `/traces` before C1 lands sees fixture data, which is why the sidebar entry is an integration
  request rather than part of this commit.
- **No component/DOM test exists** — F2 added no DOM stack (08 §6) and this task added no
  dependency. Keyboard access is implemented as a real `<Link>` per row plus `<Link>` pagination
  and `aria-label`led controls, and is therefore *asserted by construction, not measured*: E's
  browser suite is what proves it. The view-model cases prove the row href and the action hrefs
  exist; they cannot prove focus order.
- **Indicators are page-scoped**, not window-scoped: the console contract has no trace aggregate
  (`usageSummary` has no trace equivalent), so "3 captures lost in the last 24 h" cannot be said
  honestly. The copy says "On this page". Contract-revision request below.
- **The time filter is the shared `RANGES` set** (5 m … 30 d) reused from Usage so the two pages
  carry over, so the longest window a reader can select is 30 days although metadata is retained
  for 13 months and content up to 90 days. Absolute from/to pickers were not built.
- **`model` has no allowlist**: nothing in `ConsoleServices` enumerates the served models, so the
  filter offers the models present in the current page and the parser only bounds the value. A
  model id from another tenant's traffic would produce an empty page, never another tenant's rows
  (the service binds the tenant).
- The `size` change drops the cursor although the contract's cursor is deliberately *not* bound to
  `limit`; that is this page being conservative, not a contract requirement.
- Performance is unmeasured: 07-console-spec §4.1's "first page < 1 s p95 over 10k rows" is a
  ClickHouse property of C1/T2, not of this view model. Not claimed.

### Contract-revision requests (for the coordinator, not made unilaterally)

None is required for V1 as accepted; each of these is a *smaller page* than it could be, not a
broken one.

1. **`TraceQuery.http_status_class`** (`2 | 4 | 5`). 07-console-spec §3.1 filters by status class
   and the fixture data supports it, but `TraceQuery` has only `job_state`. A reader looking for
   "everything that 5xx'd" currently has to filter by `job_state: failed`, which is a different
   question (a 4xx refusal is not a failed job). Cheap for C (`intDiv(status, 100)`), and T2's
   `status` skip index already exists.
2. **A trace aggregate for the window** — e.g. `traceSummary(session, TraceQuery)` returning
   `{rows, pending, lost, lost_by_reason, metadata_only, off_requests}`. Without it the lag/loss
   indicators can only describe the page in hand, which understates loss exactly when it matters
   (a reader on page 1 of 40). `off_requests` in the same object would let the page say "and 53
   requests were not traced" without implying they were lost.
3. **`TraceListItem.key_name`** (or a `keys` map on `Page`) — declined for now: joining
   `keys.list` costs one extra service call the page already makes for the filter, so the 16-field
   row is fine. Recorded only because the join is a page concern C1 will see in its query plan.
4. **A quality/score filter** (`has_score`, `score_above`) is deliberately **not** requested until
   V3/J2 exist: `score_count` is on the row, but filtering on a judge score before the judge
   pipeline is integrated would be a filter nobody can satisfy. V1 offers `has_feedback` (which is
   in the contract) and shows `score_count`.
