## What the ingress now does (order of a `POST /v1/chat/completions`)

1. **Identity from the key row only** (`AuthResolver.context`): F1's bounded caches, then
   `auth_context(audience, org_id, key_id, user_id=user_id or created_by, provider_org_id,
   endpoint_id)`. A consumer key is its individual (the wallet owner, R66; a pre-0009 key
   is its `created_by`, exactly D2's `coalesce(user_id, created_by)`); a provider dev key is
   its provider + private endpoint and no individual; an operator key is neither. Unknown
   audience or a consumer key naming nobody → `invalid_api_key`; a scope-less provider row
   → `internal_error` (our data), values never in the message. No header is read.
2. Bounded body, structure caps, parse, closed parameter set, R58 message allow-list — the
   retained G1 intake, unchanged.
3. **Model resolution for the audience** (`catalog.resolve`): consumer → public ∧ `active`
   (D1R `resolve_admission_pins` reads the same rule); provider_dev → private ∧
   `ready_private`, its own endpoint/provider only, never production; operator →
   `forbidden` (spends no wallet). Anything else is the contract's `pin_admission`
   refusal: unknown/unpublished/private/other-endpoint → one byte-identical `not_found`
   (R70); unpriced, non-CREDIT card (R64: `unit` and both rates must be `Credit`), card of
   another revision, no policy → `invalid_request` (R69). A catalog exception →
   `dependency_unavailable` 503 + `Retry-After`, driver text logged only.
4. **Capabilities** the serving revision declares: part types ⊆ `input_modalities`
   (`unsupported_media`), `stream` needs `stream_output` (`unsupported_parameter`).
5. **Ceilings**: output ≤ min(pilot, deployment), input = min(deployment,
   context − output); deadline = created_at + budgets, no margin (R79: admit clamps).
6. `accept(auth: AuthContextV2, request: NormalizedRequest, idem)` gets the credential,
   the name the caller asked for (`model_revision`, untouched — admission re-resolves and
   pins it, R78) and the idempotency scope. No wallet, rate, pin or policy is handed over,
   and no body field can supply one (closed set).

### Invariants that are layered or structural (no single G edit breaks them; stated, not claimed as G kills)

- **Headers cannot name a wallet/org/provider**: structural — no code path reads such a header. The header half of `…no_body_field_or_header…` is asserted, not mutant-killed.
- **Consumer → private dev endpoint**: three layers (catalog visibility filter, G's `CALLABLE`, contract `pin_admission`). The case uses a leaky catalog so G's layer is exercised; its kill (`refusal_confirms_the_artifact`) proves the *same-answer* property, while removing G's check alone leaves `pin_admission`'s identical refusal.
- **Provider scoped to another endpoint / rival provider**: the catalog lookup plus `pin_admission` (F2P's contract mutants); G adds nothing there.
- **Provider dev key never spends a consumer wallet**: the wallet choice is admission's (D2; here the stand-in using the contract `resolve_wallet`). G's part is the key identity it hands over (`key_id_not_passed_to_the_store`) and never reaching production (`audience_rule_ignored`).
- **Store-side race/replay/capacity/no-write**: D2's transaction on SQL; the stand-in mirrors 0011. G's half (hand the *name*, the key and the idempotency scope; relay Retry-After) is what the G mutants kill.

## Limits

1. **Fakes only.** Identity = PostgREST stand-in, catalog = `FakeCatalogDirectory`,
   admission = `tests/g/credit.py`. Integrated only when D2's `PgJobStore.admit_credit` and
   a real `CatalogDirectory` adapter are wired by G2 (requests below).
2. **Capability is checked against the revision resolved at validation.** If the alias
   moves to a revision with fewer capabilities between validation and admission, D2 pins
   the new revision without a capability check (D2 has no capability input). The engine
   adapter still refuses non-text/video parts (R58); a stream on a non-streaming revision
   would not be caught. Owner: G2 (compare `admission.pins.serving_version_id` to the
   ingress's resolution) or D2.
3. **Key cache.** A key revoked after caching passes the ingress until `KEY_TTL`; admission
   rechecks revocation in its transaction (tested against the stand-in; D2's
   `admission_checks` does it on SQL). Suspension is not checked at the ingress at all —
   admission rechecks it (D2 `org_suspended`).
4. **Rollout order.** The ingress reads 0009's `api_keys` columns through PostgREST; the
   hosted project has 0001–0002 only. Against a pre-0009 schema PostgREST refuses the
   unknown columns, the lookup raises, and an uncached key gets 503 — fail closed, never
   open. `INFRX_MODE=pilot` therefore requires D1R's 0006–0009 applied first.
5. **Provider dev admission is not built in D2** (its evidence: `admit_credit` refuses
   `provider_dev` as `not_found`). The ingress admits a provider dev key to its own ready
   private endpoint; end to end it is refused with no side effects until D2 adds endpoint
   pins and the provider dev wallet path.
6. **Specified, not served**: `infrx-upload:` media and `Prefer: respond-async` pass the
   ingress but have no G3/G4U routes; not smoked.
7. **Cross-lane tests assert the old hazard.** Four `tests/contracts/test_config_and_imports.py`
   cases and E3B's dr16/dr17 assume `pilot` starts on the legacy composition; on this branch
   they fail, and because DEPLOY-03 names one of them, the contracts mutant list's pristine
   baseline refuses (see results). The exact, verified diff is integration request 4/5.
8. `entitlement_version` stays 0 (no D source yet); `validate_runtime` imports
   `infrx.gateway.app` lazily in its pilot branch (config ← gateway is otherwise a cycle).
