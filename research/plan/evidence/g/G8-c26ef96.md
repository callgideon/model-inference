## Round 1 — Fix: transition lock bound on the D10 schema (2026-09-25)

Branch `codex/g8-transition-lock` from `bd556c5f` (`codex/m6-merge`: integration + D10 + M5 + M6; D10's 0019–0021 present). Lane G8-TRANSITION-LOCK.

**Defect.** D10 applied wiring request 1: `infrx.require_feature` (0021) reads the flag `FOR SHARE`. An admission in flight now holds the flag row until it commits. The transition's freeze `UPDATE infrx.feature_flags` therefore waited on it (Lock/transactionid) with no bound. In the straddle case the admission is parked on `infrx.credit_holds`, so the run never returned. This is the 76-minute hang in the D10 merged-tree cross-track run.

**Fix** (`infrx/operations/transition.py`). `PgTransition.set_flag` runs its UPDATE in a transaction with `set local lock_timeout = <ms>`. The ms value is `max(1, …)`, because PostgreSQL reads 0 as no limit. It maps SQLSTATE 55P03 to a new `FlagLocked`. `apply` computes the deadline before the freeze and passes the drain's remaining bound to every flag write (the freeze and the enables). `FlagLocked` becomes the existing `open_transactions` refusal: exit 1, the flags already changed stay, nothing else is applied and nothing is audited. The `pg_locks` wait after the freeze is kept for schemas without the FOR SHARE read. D10's DB-side guard is unchanged.

On the D10 schema a straddling admission now blocks the freeze itself, so the refusal reports `applied: []` with the source flag still on. The earlier behaviour (freeze committed, then wait) was pre-D10. This is stricter and consistent with R117: bounded wait, then `open_transactions`, with nothing enabled and nothing audited.

**Tests.**
- `tests/g/ops/test_transition_pg.py::…an_admission_open_across_the_freeze_is_waited_for`:
  - the CLI now runs in a daemon thread with a hard `HARD_S = 30` join, so a regression fails instead of hanging (`pytest-timeout` is not pinned);
  - the assertions are now `applied == []` and `legacy_usd_admission` still true.
- New fake-level case `test_credit_cutover__a_flag_an_admission_holds_is_waited_for_within_the_bound` (`tests/g/ops/test_transition.py`). It checks that every flag write gets a finite bound ≤ the drain timeout, and that a locked freeze or a locked enable refuses with `open_transactions`, keeps what it applied and audits nothing. `ScriptedStore.set_flag` now takes `lock_timeout_s` and a `locked` set.
- Mutants (`tests/g/ops/mutants.py`):
  - new `flag_lock_unbounded` (the bound becomes `inf`) and `flag_lock_timeout_unmapped` (`FlagLocked` escapes; declared `dies_by`);
  - `freeze_skipped` and `freeze_only_still_enables` were re-anchored to the new code.
- The SQL-level bound, not mutated in the list: PG cases are outside the list by `case_names()`. It was verified by hand: with the `set local lock_timeout` line removed, the timed PG case fails `the transition did not return within 30.0s`, exit 1 in 34 s.

## Round 2 — total bound on the flag writes (V-G8TL-1, -6, -7)

Code head `c26ef96`, on top of round 1 (`15b5c863`/`1b1fc11a`).

**V-G8TL-1 (blocking).** `set local lock_timeout` bounds each lock wait, not the UPDATE as a whole. When admissions overlap, each holding the flag FOR SHARE (0021), the UPDATE waits on one MultiXact after another, and the whole write can run far past the bound.

Fix, in `PgTransition.set_flag`:
- `ms = max(1, int(lock_timeout_s*1000))`.
- The transaction runs `set local lock_timeout = {ms}` and `set local statement_timeout = {ms + STATEMENT_MARGIN_MS}`, with `STATEMENT_MARGIN_MS = 1000`. Both are SET LOCAL (R120).
- SQLSTATEs 55P03 and 57014 both become `FlagLocked`.
- The margin is required. A hand check with the margin at 0 fails two existing PG cases (`…freeze_drain_enable_never_converts_usd…` and `…a_rollback_drains_credit…`): a drain bound of 0 gives a 1 ms statement bound, which the UPDATE and its triggers overrun.

**Regression.** New timed PG case `test_credit_cutover__overlapping_admissions_cannot_stretch_a_flag_write_past_its_bound` (`tests/g/ops/test_transition_pg.py`).
- Eight threads loop `require_feature('legacy_usd_admission'); pg_sleep(0.2); commit`, then `set_flag(..., lock_timeout_s=2.0)` runs.
- It asserts the write returns (refused or done) in under 2 + 1 + 1.5 s, under a hard 30 s join.
- The reviewer's probe used four 50 ms lockers. That version passed once by luck on a lock-only build (4.77 s), so the lockers were raised to eight at 200 ms. A lock-only build then failed 4 of 4 runs.
- At the fix the case takes about 5.5–6.4 s of call time: 0.3 s start, a write refused at about 3 s, then the lockers' join.

**Wiring request V-G8TL-2 (D10, filed by the coordinator; text for the D10 lane).**

> The transition's flag UPDATE is not fair against a stream of FOR SHARE readers. New share lockers join the MultiXact ahead of the waiting updater, so under sustained admission traffic the freeze can only time out (bounded now, but it may never succeed). Give the operator one fair, bounded writer.
>
> Option A (preferred): in a new D10 migration, add `create function infrx.set_feature_flag(p_name text, p_enabled boolean, p_actor text, p_reason text) returns boolean language plpgsql volatile security definer set search_path = infrx, public, pg_temp`. It runs `lock table infrx.feature_flags in share row exclusive mode;` (a table lock queues fairly and conflicts with the ROW SHARE that `select … for share` takes, so new admissions queue behind it), then `update infrx.feature_flags set enabled = p_enabled, updated_by = left(p_actor, 200), reason = left(p_reason, 500), updated_at = infrx.now() where name = p_name and enabled <> p_enabled;` and returns `found`. Then `revoke all on function infrx.set_feature_flag(text, boolean, text, text) from public, anon, authenticated; grant execute on function infrx.set_feature_flag(text, boolean, text, text) to service_role;`. G8 then calls `select infrx.set_feature_flag(%s, %s, %s, %s)` under the same SET LOCAL `lock_timeout`/`statement_timeout`.
>
> Option B: `grant lock`-equivalent access, i.e. `grant update on infrx.feature_flags to service_role` at table level, so G8 can itself run `lock table infrx.feature_flags in share row exclusive mode` before the UPDATE. This is weaker, because it broadens the grant from the four columns of 0006.
>
> Proving test (G8 writes it once the SQL lands): the overlapping-lockers probe above, with the assertion tightened from "returns within the bound" to "`changed is True` within the bound".
