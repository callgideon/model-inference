## What was built

The new file is `apps/infrx-api/infrx/gateway/routes/jobs.py`. `register(app, rt)` reads
`rt.relay` (G2's `Relay`) and `rt.ingress` (its `IngressDeps`). With no relay it mounts nothing
and returns `None` (M-FAILCLOSED: there is no fake fallback). With a relay it mounts five
routes and sets `relay.on_async = jobs.accepted`:

- **202 path.** Two requests reach it: `Prefer: respond-async` on `/v1/chat/completions` (the
  ingress's own route), and `POST /v1/jobs`.
  - `POST /v1/jobs` goes through the ingress's intake verbatim (`Ingress.validated`: the same
    auth, bounds, parser and validator). The route passes a header view whose `Prefer` is
    `respond-async`: that route **ignores** any `Prefer` the client sent and reports no
    preference applied. A `stream: true` body is refused there (`invalid_request`).
  - `Relay.accept` → `Relay.admit` (G2's durable half, now shared by every mode) →
    `Jobs.accepted` builds the 202 only after `admit` has returned: the admission is committed
    and a fresh job's staged refs are attached. `JobAccepted` has the fields of
    `job_accepted.json`.
  - Headers: `Preference-Applied: respond-async` (chat only), `Location: /v1/jobs/{handle}`,
    `Retry-After: 2` (`POLL_AFTER_S`, a `ponytail` constant: no `limits` setting names a poll
    interval), `Inference-Id` (the job's request id), `Server-Timing`, and
    `Idempotency-Replayed: true` on a replay.
  - Nothing watches the connection after the 202, so a client that leaves never cancels.
  - A replay answers the original acceptance as it stands now: the handle, id, created and
    deadline instants, and the current state (`job_idempotent_replay.json`), read through
    `Relay._owned`. A store outage on that read is a retryable 503, and the job is left for
    the retry.
- **`GET /v1/jobs/{handle}`** returns `JobStatus` from `get_owned`/`get_owned_credit`:
  - `cause` only when terminal;
  - `updated_at` = `settled_at` when terminal, else `admitted_at`;
  - `result_available` / `result_expires_at` = a committed success with authoritative usage and
    a result ref, within `result_ttl_s` of `settled_at`, judged on the **store clock**
    (`db_now`);
  - `usage` only from the outcome (`authoritative`); a `held_unknown` outcome reports
    `usage_certainty: unknown` and no usage.
- **`GET …/result`:**
  - 409 `result_pending` while the job is not terminal;
  - a committed success: 200 `JobResult`, whose `response` is the `read_result` object in the
    chat shape and whose `completed_at` is the settlement instant;
  - a failed, cancelled or expired job: 200 `JobResult` with its state and cause and no
    `response`;
  - 410 `result_expired` once the store clock passes `settled_at + result_ttl_s`.
- **`GET …/events`:**
  - Order: `Last-Event-ID` is parsed with `Cursor.parse` before any read (400
    `invalid_cursor`); the ownership read comes next; a one-row `read_owned` probe then makes a
    gap, an expired journal or a never-issued cursor a status (410 `replay_gap` / 410
    `journal_expired` / 400 `invalid_cursor`) before any SSE header.
  - The stream: the identity frame (`infrx.progress`, phase = the committed state, no `id`),
    then `Relay.pump(…, cursor=, cancel_on_gone=False)`, which relays the committed journal
    (`visible` only) to `[DONE]` at the terminal cursor.
  - Errors after the headers are an `infrx.error` frame. The response never cancels.
- **`DELETE /v1/jobs/{handle}`:**
  - A request that declares a body (a length or chunked) is 400. This is decided from the
    headers, which are never read as a body.
  - Then the ownership read, then `Relay.cancel(org, handle, cause=client_cancelled)`
    (shielded).
  - The answer is 200 `JobStatus` of the committed outcome: `cancelled`, or whatever won the
    race.
- **Every handle route** authenticates first. It then refuses an operator audience and a
  handle that fails `ids.JOB_HANDLE_RE`, both before any store read, as the same 404 an unknown
  or foreign handle gets from the store.

`relay.py` (G2's), additive only:
- `Relay.admit(auth, request, idem) -> (job, admission, headers)` is G2's `_accept` body moved
  verbatim. It returns a triple rather than the brief's pair because the headers are built
  from the measured prepare timing.
- `on_async: Callable | None = None`. In `_accept`, `async_` with no hook keeps G2's refusal
  verbatim, before anything durable; with a hook it runs `await on_async(*await admit(…))`.
- `pump(…, *, cursor=None, cancel_on_gone=True)`.

G2's mutant anchors were left intact. The G list's `async_admitted`, `stream_disconnect_not_cancelled` and the rest
are still killed (below).

`ingress.py`, additive only: `JOBS_ROUTES`/`JOBS_MODULE`. `assert_route_table` now also requires
the jobs routes to be mounted all or none, each with exactly one handler, the jobs module's.
G2's chat check is unchanged.

`client_example.py --respond-async` is now the served flow: 202 → `GET /v1/jobs/{h}` at the
202's `Retry-After` (bounded by `MAX_RETRY_AFTER_S`) → `GET …/result`, with a 410 answered as
`rerun_required`. The key is read from the environment only (unchanged, G6B's).
`--follow-events` was **not** built: the brief marks it optional, and the events resume is
covered by the route cases.

**Choices the brief left open, and one deviation.** Each is pinned by a case and a mutant.
- `POST /v1/jobs` **ignores** `Prefer`: `jobs_route_follows_prefer` and
  `preference_applied_always` pin it.
- A DELETE **carries no body**. `{}` is refused too, because any declared length or chunked
  encoding is 400 (`delete_body_accepted`).
- **Deviation:** a nonterminal result is 409 `result_pending`, not the brief's `state_conflict`.
  The frozen table has a dedicated code for exactly this case: `errors.py` `result_pending`,
  message "The result is not available yet.", in 08 §3's 409 row, and it is 01's "pending
  conflict". `pending_code_wrong` pins it.
- A queue-expired job is a terminal **result** (200, no `response`). The 410 is the result's
  own TTL. `job_expired.json` is a `JobStatus` (state `expired`, cause `queue_wait_expired`,
  `result_available: false`), which is what the status route answers; no fixture exists for a
  410 on an expired job.
