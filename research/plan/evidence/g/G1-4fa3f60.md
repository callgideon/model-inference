## What was built

| Module | Responsibility |
|---|---|
| `infrx/gateway/routes/intake.py` | Bounded, deadlined body read before any parse; the one public error envelope; `guard()` so no handler can leak an exception |
| `infrx/gateway/routes/validate.py` | Body → `NormalizedRequest`: closed parameter set, text/video shapes, derived token ceilings, derived `deadline_at`, idempotency scope, off-mode trace policy |
| `infrx/gateway/routes/ingress.py` | `register(app, rt, deps)`, `IngressDeps`, startup reachability assertions, `/healthz`, `/readyz`, the new `POST /v1/chat/completions` |
| `infrx/auth/context.py` | `AuthResolver`: F1's bounded caches → `AuthContext`; pilot's refusal of a shared key and of a missing identity source |

Design decisions worth reviewing rather than assuming:

1. **No anonymous request, in any mode.** F1's `Auth.authenticate` answers
   `(None, None)` — allowed, with no row — both for the shared `GATEWAY_API_KEY` and
   for a process with neither the legacy key nor Supabase configured (`O-FAILOPEN`).
   The new ingress cannot build an `AuthContext` from that and refuses `401`, rather
   than refusing only in `pilot`. One rule, one code path.
2. **Two independent pilot refusals.** `config.validate_runtime` (coordinator-owned,
   R44/R51) refuses at the composition root; `AuthResolver.__init__` refuses again
   where the decision is used, so a settings object mutated after startup or a
   composition root that forgot the hook still cannot serve. Both raise
   `config.RuntimeMisconfigured`, which names setting names and never values.
3. **Startup reachability is fail-closed and injectable.** `IngressDeps.checks` holds
   the `price_source` and `journal` probes; in `pilot` a missing probe, a falsy probe
   and a raising probe all refuse to start (a missing probe is not a passing probe).
   `dev`/`test` start and report the state through `/readyz`.
4. **Ceilings are derived, so `admit` accepts them.** `max_output_tokens` is the
   validated request ceiling (1..`MAX_OUTPUT_TOKENS`) and `max_input_tokens` is
   `MAX_CONTEXT_TOKENS` minus it, so the pair always satisfies R55's range check and
   the hold the store derives from it (R53) covers the whole envelope. `deadline_at`
   is `created_at` plus the mode's preparation + queue + generation budgets from the
   same `Budgets.of`, which is exactly the ceiling R29 lets `admit` accept.
5. **The parameter set is closed.** An unknown name is `unsupported_parameter` naming
   itself; `tools`, `tool_choice`, `functions`, `function_call`, `response_format`,
   `logprobs`-family and `price_snapshot` (R45) are additionally named so the refusal
   is deliberate rather than a side effect of the allow-list.
6. **Messages are an allow-list, not a deny-list (r1 R58).** A message must *equal*
   `{role, content}` and a part must *equal* `{type: "text", text}` or
   `{type: "video_url", video_url: {url}}` — key-set equality, exact type spelling
   compared with `==` against a literal. So `tool_calls`, `name`,
   `mm_processor_kwargs`, an `image_url` beside a `text`, a `detail` on a video part,
   a bare-string `video_url`, the old `input_video` spelling and `"Text"` are all
   refused before admission rather than ignored, and no caller URL can reach the
   engine. Parts keep the caller's order, so R58's one-part-per-staged-ref pairing
   holds downstream.
7. **Sampling parameters are typed *and* ranged here.** `temperature`, `top_p`,
   `presence_penalty`, `frequency_penalty`, `seed`, the `stop` list length and each
   entry's length, and the output ceiling. The engine adapter forwards them, so a value
   the engine rejects would come back as an engine 400 and settle as a
   platform-absorbed `engine_error` (R21) — the platform paying for a bad request.
8. **Nothing is reported as accepted before durable acceptance exists.** With no
   acceptor wired the route answers `503 dependency_unavailable` with retry guidance.

## Limits

- **Not integrated.** Every result above is against fakes and injected stand-ins.
  Integration needs D2 (real `JobStore.admit`), and the acceptor itself is G2/G3 work.
- **No conformance suite applies to this task.** The exported suites
  (`infrx.contracts.conformance.run_*`) are per durable port; G1 implements no port
  adapter, so there is nothing to run them against. What replaces them here is
  stronger than a self-written assertion and is reported as such: the ingress's own
  `NormalizedRequest` and `IdempotencyRef` are admitted by the executable
  specification (`FakeJobStore`), so R53/R55/R29 are judged by the store's code. No
  conformance case was skipped, because none was applicable.
- `context_length_exceeded` is never raised by the ingress: prompt tokens are not
  countable before preparation/tokenisation, so the context limit is enforced as the
  reserved envelope (`max_input_tokens = MAX_CONTEXT_TOKENS − max_output_tokens`) and
  the code belongs to the preparation path. Owner: M1/W for the counted check.
- Media is validated by *reference shape only* (part shape per R58, scheme or `upl_`
  prefix, one video). No fetch, no DNS, no redirect, no decode, no ownership check of
  an upload handle happens here, so the MEDIA-SEC rows about DNS rebinding,
  redirect-to-private and IPv6/mapped addresses remain M1's and are **not** claimed by
  this task. The ingress's contribution to MEDIA-SEC is the byte/time bound, the
  allow-listed part shapes and the scheme refusal.
- R58's "one media part per staged ref, in order, the part kind matching the ref's MIME
  class" is only half-enforceable here: at ingress there are no staged refs yet (M
  stages during preparation), so this task enforces *at most one video part* and
  preserves part order, and the ref-to-part pairing and MIME-class match are the
