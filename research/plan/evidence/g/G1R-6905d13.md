## What the ingress now does (order of a `POST /v1/chat/completions`)

1. **Identity from the key row only** (`AuthResolver.context`): F1's bounded caches, then
   `auth_context(audience, org_id, key_id, user_id=user_id or created_by, provider_org_id,
   endpoint_id)`. A consumer key is its individual (the wallet owner, R66; a pre-0009 key
   is its `created_by`, exactly D2's `coalesce(user_id, created_by)`); a provider dev key is
   its provider + private endpoint and no individual; an operator key is neither. Unknown
   audience or a consumer key naming nobody → `invalid_api_key`; a scope-less provider row,
   a provider row whose org is not its provider, or a consumer row carrying provider scope
   → `internal_error` (our data), values never in the message. A row cached by the legacy
   route's narrower select is re-read, not used. No header is read.
2. Bounded body, structure caps, parse, closed parameter set, R58 message allow-list — the
   retained G1 intake, unchanged.
3. **Model resolution for the audience** (`catalog.resolve`): consumer → public ∧ `active`
   (D1R `resolve_admission_pins` reads the same rule); provider_dev → private ∧
   `ready_private`, its own endpoint/provider only, never production; operator →
   `forbidden` (spends no wallet). Anything else is the contract's `pin_admission`
   refusal: unknown/unpublished/private/other-endpoint → one `not_found` envelope, identical modulo `request_id`
   (R70); unpriced, non-CREDIT card (R64: `unit` and both rates must be `Credit`), card of
   another revision, no policy → `invalid_request` (R69). A catalog exception →
   `dependency_unavailable` 503 + `Retry-After`, driver text logged only.
4. **Capabilities** the serving revision declares: part types ⊆ `input_modalities`
   (`unsupported_media`), `stream` needs `stream_output` (`unsupported_parameter`).
5. **Ceilings**: output ≤ min(pilot, deployment), input = min(deployment,
   context − output); deadline = created_at + budgets, no margin (R79: admit clamps).
6. `accept(auth: AuthContextV2, request: NormalizedRequest, idem)` gets the credential,
   the name the caller asked for (`model_revision`, untouched — admission re-resolves and
   pins it, R78) and the idempotency scope. No wallet, rate, pin or policy is handed over,
   and no body field can supply one (closed set).

### Invariants that are layered or structural (no single G edit breaks them; stated, not claimed as G kills)

- **Headers cannot name a wallet/org/provider**: structural — no code path reads such a header. The header half of `…no_body_field_or_header…` is asserted, not mutant-killed.
- **Consumer → private dev endpoint**: three layers (catalog visibility filter, G's `CALLABLE`, contract `pin_admission`). The case uses a leaky catalog so G's layer is exercised; its kill (`refusal_confirms_the_artifact`) proves the *same-answer* property, while removing G's check alone leaves `pin_admission`'s identical refusal.
- **Provider scoped to another endpoint / rival provider**: the catalog lookup plus `pin_admission`. Since S2 the G case runs over a leaky catalog, so G's list kills both `pin_admission` checks itself (`other_endpoint_reached`, `rival_provider_reached`), not only F2P's contract mutants.
- **Provider dev key never spends a consumer wallet**: the wallet choice is admission's (D2; here the stand-in using the contract `resolve_wallet`). G's part is the key identity it hands over (`key_id_not_passed_to_the_store`) and never reaching production (`audience_rule_ignored`).
- **Store-side interleaving/replay/capacity/no-write**: D2's transaction on SQL; the stand-in mirrors 0011. G's half (hand the *name*, the key and the idempotency scope; relay Retry-After) is what the G mutants kill.
