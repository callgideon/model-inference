## Per finding

### F-1: vkharness adopted a foreign listener, and the gate gave D2 and Q one port

- **Defect.** `vkharness.ensure()` did `if not _listening(): start…` and then `_started = True`, so any
  server on its port was adopted. Later, `kill_and_restart()` sent `docker kill` to a container that it never
  created. This contradicts R63 ("only ever this lane's own container"). The E2C gate env (`gates.py:297`)
  set `INFRX_Q_VALKEY_PORT` to e2c's only Valkey port (55493), which D2's `vkstore` (`infrx-e2c-valkey`)
  also holds. `make check` runs both in one pytest process.
- **Fails-before.** On the unfixed `vkharness.py`, `pytest -q tests/q/test_vkharness.py` gave
  `2 failed` (`E Failed: DID NOT RAISE RuntimeError` at `test_vkharness.py:33` and `:43`). The listener is a plain
  socket on an ephemeral port, and the container name is random. `_started` was set to True, which means it adopted the listener.
  The gate-env test, updated first, then ran `tests/integration/test_preflight.py`:
  `1 failed, 57 passed` (`{'INFRX_Q_VALKEY_PORT': '55493'} != {'INFRX_Q_VALKEY_PORT': '55430'}`).
- **Change.**
  - `ensure()`: if the port is listening, `docker port <CONTAINER> 6379` must show `:<PORT>`. Otherwise it raises
    `RuntimeError("127.0.0.1:<port> is held by <docker ps --filter publish=<port> names | 'a process that is not a container'>, not <CONTAINER>: refusing to adopt it (R63; give this harness its own INFRX_Q_VALKEY_PORT)")`.
    Nothing is killed. Mutation copies still adopt the parent's container, because the copy derives the same name from the port that `tests/q/mutants.py` writes into it.
  - `tasklocal`: e2c `valkey-q` = **55430**. Why this port: it is below D1's 55432, outside every D-harness decoy (+40), outside the
    55472-55490 decoy band and the 555xx E block, and it appears in no committed file. 55439/55440 are free in the table,
    but the revoke lane used them ad hoc (`d10-merge-2-9e4e34c.md`), so they were avoided. `all_host_ports()`
    stays collision-free (`tests/contracts/test_config_and_imports.py`, `tests/d/test_pgharness.py`,
    `tests/i/test_pooler.py` port cases: 284 passed).
  - `gates.py`: `INFRX_Q_VALKEY_PORT` is read from the one registry through `pf.namespace({**spec, "services": ["valkey-q"]})`.
- **Passes-after.**
  - `pytest -q tests/q/test_vkharness.py`: 2 passed.
  - `tests/integration/test_preflight.py`: 58 passed.
  - One process, split ports:
    `INFRX_D_TASK=e2c INFRX_D2_VALKEY_PORT=55493 INFRX_D2_VALKEY_CONTAINER=infrx-e2c-valkey INFRX_Q_VALKEY_PORT=55430 uv run --frozen --no-sync pytest -q -rs tests/d/test_outbox_relay.py tests/q/test_reconcile.py`
    gave exit 0 and **93 passed**, with no skip, in 17 s. Both q3 drills that failed in G-GATES are included.
    (The brief's `tests/d/test_vkstore*.py` does not exist. `test_outbox_relay.py` is the suite that
    drives `tests/d/vkstore.py`.)
  - The same command with the old shared port (`INFRX_Q_VALKEY_PORT=55493`) now fails loudly: exit 1,
    `39 failed, 54 passed`, each failure with `RuntimeError: 127.0.0.1:55493 is held by infrx-e2c-valkey, not
    infrx-q3-valkey-55493: refusing to adopt it (R63; …)`. Before the fix it was 2 failures, `docker kill … No such container`.

### F-5: `tests/i` under `INFRX_D_TASK=i8`

- **Reproduction with i8 free.**
  `cd apps/infrx-api && INFRX_D_TASK=i8 uv run --frozen --no-sync pytest -q -rsxX tests/i` (17:11:50Z-17:15:45Z)
  gave exit 0 and **239 passed, 1 xfailed**. Docker events during that run show only this run's own
  `infrx-i8-postgres` (2 creates, one per `Stack`) and `infrx-i8-pgbouncer` (20 restarts, from `write_bouncers`).
  There was no second owner and no `-supabase`/`-migrated` name.
- **Cause.** `tests/i` never reads `INFRX_D_TASK`. Nothing under `tests/i` imports `tests/d/pgharness.py`, and its only
  subprocess users of `tests/d` (`test_known_good_proof.py`) run scratch suites without docker. `conftest.py` reaches
  i8 through `tests/i/pooler.py`, whatever the variable says. So the task value cannot cause a conflict inside one run, and
  G-GATES' two failures were host contention. The shared mechanism is the flock
  `/tmp/infrx-i8-postgres-55450.lock`: `pooler.Stack.up()` takes it with `LOCK_NB`, and so does
  `tests/d/pgharness.py` under `INFRX_D_TASK=i8` (WR-KGP2-4).
  Demonstration: with the lock held by another process
  (`flock -n /tmp/infrx-i8-postgres-55450.lock -c "… pytest -q tests/i/test_pooler.py -k session_state_is_lost"`), the case
  errors at setup with `BlockingIOError: [Errno 11] Resource temporarily unavailable` (`tests/i/pooler.py:110`), `1 error`.
  At G-GATES time, other lanes held D-harness containers under task i8 (`infrx-i8-postgres-supabase`,
  `infrx-i8-migrated-supabase`; G-GATES F-4). The same lock and name contention would occur inside `make check`
  if it ran with `INFRX_D_TASK=i8`, because api-test then runs `tests/d` (pgharness on i8) and `tests/i` (pooler on i8) in one process.
- **Settled form (README §0 G2).** `INFRX_D_TASK=e2c` for both `make check` and `tests/i`. Never
  `INFRX_D_TASK=i8`. i8 must be free for the whole run: no `infrx-i8-*` container and no other holder of the lock.
  No harness change was needed. `pooler.py` is correct, and the lock is its guard.
