## The defect

`pytest tests/integration --co -q` exited 2: an "import file mismatch" on
`lab_{evaluate,observe,operate,rollout,improve}/test_mutants.py` (all five share the basename
`test_mutants.py`, and pytest's default "prepend" import mode requires unique basenames without
an `__init__.py`).

Adding `--import-mode=importlib` alone (tried directly, no code change) fixed that collection
error but did not fix running two packages together: `pytest tests/integration/lab_rollout
tests/integration/lab_improve` still failed 4 cases. Root cause (confirmed by tracing collection
order, not guessed): `tests/integration/lab_improve/test_e7l_runner.py` and
`tests/integration/lab_rollout/test_e8l_runner.py` (and other files in each package) run
`sys.path.insert(0, str(HERE))` at import time, where `HERE` is their own package directory.
pytest imports every collected file's module before running any test, so by the time any test
*executes*, every collected package's `sys.path.insert(0, ...)` has already run, and the
**last-collected** package's directory sits at `sys.path[0]` - not the directory of whichever
file is executing. `lab_evaluate/lab_operate/lab_rollout/lab_improve` each carry an identically
named `lab_world.py`; a bare `import lab_world` anywhere in the process (inside a test function,
a fixture, or `runner.py`/`mutants.py`'s own internals) resolves through `sys.path` in that
polluted order, finds whichever package's `lab_world.py` comes first, and caches it under
`sys.modules["lab_world"]` for the rest of the process - regardless of which package's file
performed the import. Proven (before the fix, `--co -q` and the two-directory run together):
`lab_rollout`'s own "NOT RUN names the exact rerun" case reported `lab_improve`'s `runner.py`
path in its rerun message, because its bare `import lab_world` returned lab_improve's module,
whose own `RUNNER` constant is hardcoded to lab_improve's own path.

`lab_observe` is not part of this defect: it is the only package whose world module is named
`observe_world.py`, and no other package defines a module by that name, so its bare imports have
no same-named sibling to collide with (confirmed: it never appears in the fail-first red run).
Scenario files other than `scenarios_pending.py` (present in `lab_evaluate`/`lab_improve`/
`lab_rollout`) are never imported in-process alongside a sibling package - `runner.py` always
runs them as an isolated subprocess per package - so they carry no cross-package risk and were
left untouched, per the brief ("change nothing in their scenario logic"). The one exception,
`scenarios_pending.py`, *is* loaded in-process (`lab_improve`'s i07 tripwire test calls
`_load("e7l_pending", "scenarios_pending.py")`), so its own `import lab_world as lw` needed the
same fix.

## Deviations from the brief's literal wording

* The brief lists "runner.py x5, mutants.py x5, lab_world.py x4, scenarios_pending.py x3" as the
  colliding files. Tracing the actual in-process call graph shows `lab_observe`'s equivalent
  module is named `observe_world.py`, which no other package defines, so it has no collision
  partner and needed no change; and the *other* ten scenario files (`scenarios_{iterate,faults,
  workers,data,eval,checkpoint,route,recover,parity,split,access,publish,judge,trace}.py`) are
  never imported in-process alongside a sibling package (only by `runner.py`'s own isolated
  subprocess), so they carry no cross-package risk and were left untouched, consistent with
  "change nothing in their scenario logic." The fix instead touches every file whose bare import
  actually executes in a shared process: `conftest.py`'s `lab` fixture (3 packages that have
  one), `runner.py` (5), `mutants.py` (5), `test_e*_runner.py` (5), and `scenarios_pending.py`
  (3, the one scenario file that is `_load`-ed in-process).
* No `research/plan/tasks.json`, `Makefile`, `infrx/**`, `apps/lab/**` or migration file was
  touched, per "Do NOT touch product code (infrx/**), migrations, apps/lab, Makefile."
