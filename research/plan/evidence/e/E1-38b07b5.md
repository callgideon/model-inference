## Results

- **Corpus:** 64/64 clips and 4/4 negative fixtures built; 64 distinct sha256
  values; 4 sources fetched and probed (Big Buck Bunny 634.6 s, Tears of Steel
  734.167 s, Sintel 888.032 s, NASA STEVE 132.885 s — each probed duration within
  1 s of the pinned expectation). Geometry coverage: 14 distinct (w,h) pairs,
  10 distinct aspect ratios (16:9, 9:16, 1:1, 64:27, 12:5, 4:3, 4:1, 240:427,
  427:240, 71:40); durations 2.0–112.0 s over 13 distinct values; 5/10/15/24/30/60
  fps; 16 prompts. 16 clips are flagged `source_upscaled` so they are never quoted
  as native-resolution parity evidence.
- **Reproducibility proof:** one clip (`c005-…-720x1280-portrait`) was re-derived
  twice in a separate process; both re-derivations produced
  `c20457e3b0c8bafd91480bd517d2c491082a4015edd5ee0437a04d6d90fe5f47`, equal to the
  manifest hash written by the original parallel build. `verify` then recomputed
  all 72 cached files with 0 mismatches.
- **Benchmark dry runs:** raw JSONL carries one line per attempt with
  `scheduled_s/send_s/first_byte_s/first_token_s/last_token_s/end_s`, HTTP status,
  outcome, `error_class`/`error_code`, `Inference-Id`, `Retry-After`,
  `server_timing` (parsed `Server-Timing` → `{"queue":12.5,"prep":340.0,"gpu":880.25}`
  from the fake), `prompt_tokens`/`completion_tokens`, `cold`, `retries`,
  `upload_s`. Two independent runs of the same seeded command produced identical
  `(seq, clip_id, form, scheduled_s, cold)` tuples for all 40 requests.
- **Percentile guard in practice:** at 40 accepted samples the summary reported
  p50 and p90 and suppressed all six p95/p99 entries with an explicit reason
  string; legacy `ttft_p95`/`latency_p95`/`tpot_p95_ms` keys were written as
  `null` rather than a maximum dressed up as a tail.
- **Secret handling:** `grep -c` for the throwaway key across the summary JSON,
  `bench.jsonl`, the raw JSONL and stderr returned 0 in every file. The upload
  handshake sends the `Authorization` header only to the API host, never to the
  returned upload destination.

## Failure drill

Injections actually exercised (all local, no durable state involved — E1 owns no
database, queue or money path):

| Injection | Observed behaviour |
|---|---|
| Scripted 429 / 402 / 500 / 503 from the fake gateway | 429+402 classified `rejected`, 500+503 classified `failed`, none counted as accepted; `Retry-After: 3` captured; latency denominator stayed at the 4 accepted requests |
| Upstream exception whose text echoes the bearer header | Row recorded `failed` with the key replaced by `[redacted]`; key absent from stdout, JSONL and summary |
| Stream with no `usage` object | `accepted_without_usage: 2`, token fields null, `out_tok_per_s` 0.0 — never a chunk-count estimate |
| Stream with no content delta / SSE `error` event | Classified `failed` (`no_content_delta` / `stream_error_event`) with a complete row schema, same fields as an accepted row |
| Real source fetch refused (Cloudflare 403 to urllib during the first build attempt) | All four sources stayed `status: unfetched` with the error recorded and **every clip stayed `unbuilt` with sha256 null** — the builder fabricated nothing. Fixed by sending an explicit User-Agent; the 403 path remains the honest failure path |
| Non-UTF-8 bytes in ffmpeg stderr (real crash during the first build) | Build aborted with `UnicodeDecodeError`; fixed with `errors="replace"` on all three subprocess calls, then rebuilt with `--force` so no partially written clip could be hashed |
| Claimed-but-absent container rotation metadata | Reprobe showed ffmpeg 7's mp4 muxer silently drops `-metadata rotate=`; the recipe field was **removed** rather than left as an untrue claim. Re-derivation with and without the flag produced identical bytes, so the affected hashes were unchanged (verified) |
| Corrupt-media fixtures | Built with real hashes: truncated (65,536 B), wrong container (`.mkv` holding mp4 bytes), zero-length (0 B), text payload (20 B). They are inputs for a future server-side drill; **no server has rejected them yet** |

**Contract assumptions made (need G/M confirmation, not changes by me):**

1. Upload flow shaped as `POST /v1/uploads` → `{handle, upload:{method,url,headers}}`
   → `PUT` to that destination → `POST /v1/uploads/{handle}/complete`, then the
   handle referenced from chat content as
   `{"type":"video_url","video_url":{"url":"upload://<handle>"}}`. Contracts v1
   fixes the endpoints but not the response body or the reference syntax; the
   client is marked "implemented against contracts v1, not verifiable until
   M3/G4".
2. Error bodies are OpenAI-style `{"error":{"code","message","type"}}`; `code` is
   what the summary counts.
3. `Inference-Id` (already emitted by today's gateway) and `Retry-After` are read
   from response headers; `Server-Timing` is read if present — today's gateway
   does not emit it.

## Limits

- **Nothing here is measured performance.** No GPU, no vLLM, no gateway was
  contacted; every timing in the dry runs is fake-gateway latency.
- The client cannot yet measure: server-side queue/preparation/decode phases
  (needs G to emit `Server-Timing` or equivalent), engine-side multimodal cache
  state (cold/warm is client-side first-use only, not engine cache truth), upload
  storage timing beyond wall-clock `upload_s`, and anything about admission,
  holds or settlement.
- The upload and `video_url` forms are unexercised against a real server; the
  `video_url` form additionally needs a publicly reachable media host, which does
  not exist for this corpus (clips are local and must never be published without
  re-checking the CC-BY attribution obligations for redistribution).
- Corpus gaps: no container display-matrix rotation (ffmpeg 7 drops it), single
  codec/container family (H.264/MP4 only — no HEVC/VP9/AV1/WebM), no audio, three
  of four sources are animated films, and segments are keyframe-accurate cuts of
  four films rather than 64 independent productions.
- The percentile rule (≥3 samples beyond the quantile) is a judgement call
  recorded in the summary as `percentile_rule`; it is stricter than the four
  historical rows, whose p95 values came from 5–32 samples.
- `models/marlin2b/tests/` is a new directory; whether the coordinator's future
  shared test discovery picks it up is F2's decision, not proven here.
- The existing `apps/infrx-api/tests` baseline was **not run** (missing
  dependency in this deliberately minimal venv). E1 changes no code under `apps/`.

### How E4 should run this

1. Build and verify the corpus on the pilot host first
   (`build.py build` then `verify`); record the manifest sha256 alongside the
   engine image, model revision, driver and GPU in the run label.
2. Use `--target gateway` (never send `mm_processor_kwargs` through the gateway)
   with the key in `$MARLIN_API_KEY`.
3. Open-loop sweep: fix `--seed`, step `--rate` through a ladder (e.g. 0.5, 1, 2,
   4, 8 req/s) at a fixed duration per step, and let the rejected/failed counts —
   not throughput — define the pilot envelope. Keep the closed-loop
   `--concurrency` runs only as a comparison to the four historical rows.
4. Interleave cold and warm: the `--subset full` schedule visits each clip once
   before repeating, so a run of 64 is all-cold and a run of 128 is half-warm;
   compare `cold_ttft_s` against `warm_ttft_s` rather than a single blended p50.
5. Sample sizes: ≥60 accepted requests per cell to report p95 and ≥300 for p99.
   Anything smaller reports p50 only — the client enforces this, so plan the run
   length around the percentile you intend to publish.
6. Run the negative fixtures against the media path separately (MEDIA-PARITY
   failure cases); they are inputs, not load.
