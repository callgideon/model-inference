## What was built

`apps/lab/tests/e2e/` — the built Lab app (`next build` + `next start`, production config with an https
origin) driven over HTTP by a no-JS cookie-jar browser (`harness.ts`): it signs in through the Lab's own
sign-in form and submits the pages' own server-action forms exactly as a browser without JavaScript does
(Next's progressive enhancement: hidden `$ACTION_*` fields, multipart, 303 back), and reads pages as served
HTML. No Playwright and no new dependency.

Per suite a `backend.py` on l4 (`stack.py` shared): R186's control factory (`infrx.lab.control.app:create_app`)
plus the suite's surface as the gateway composes it (`pilot._lab` with that one switch ON in this process
only; LAB_TRACES is registered directly — see stand-ins), and the Supabase stand-in on the same port:
GoTrue's `/auth/v1/token|user|logout` for the world's users and `/rest/v1/rpc/<fn>`, which runs the REAL
`public.<fn>` of the migrated database as `authenticated` with the caller's claims (0030 memberships, 0038
feedback review, 0043 judge runs). The route's verifier is the real `lab_auth.GoTrueSessions` pointed at it.

## Proposed ruling (propose, never number)

**LAB-E2E-CELL:** A Lab gate's UI cell is its `apps/lab/tests/e2e/<suite>` run on the l4 key against the built
Lab app, signed in through the Lab's own form and driven through the pages' own forms. The cell is PASS only
when the suite passes whole over the gateway's own composition of that surface (stand-ins allowed: the
session verifier and PostgREST RPC door, in-memory stores where l4 has no such service, and whatever the
gate's own API half already runs over); a passing suite over test-local ports the composition lacks is NOT
RUN naming them; a failing suite is FAIL; a busy key or Docker is INVALID.
