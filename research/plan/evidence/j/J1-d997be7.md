## Failure drill

There is no durable state in J1: the module is pure plus one injected read port, and
durable judge state (runs, reservations, consent history) belongs to
`JudgeCoordinator`, which D6 implements. The drills below therefore exercise (a) the
in-process state that *does* accumulate, (b) the refusal boundaries, and (c) the
mutation harness, which is this task's injection mechanism.

### Drill A — 35 injected single-edit defects

Injection point: one textual edit per mutant in `infrx/judge/{sampling,rubric,cost}.py`,
applied to a **copy** of `infrx/` + `tests/` + `pyproject.toml` in a
`tempfile.TemporaryDirectory`. Durable state before: worktree clean. After: worktree
clean (`git status --short` empty; the temp directory is removed by its context
manager). Outcome: 35/35 killed, quoted above. A kill requires pytest exit 1, at least
one failure, and **every** failing test naming one of that mutant's own cases, so a
syntax error or an import failure is `broken_runner` and fails the run exactly as a
survivor would — which the five `test_the_runner_cannot_report_a_false_kill` cases
demonstrate against this runner.

The two first-run survivors, both fixed in `d997be7`:

1. `missing_criterion_counts_as_a_pass` survived because `Rubric.passes` has two
   overlapping guards — "a media-dependent criterion cannot pass without media" and "a
   criterion in the rule with no score fails it" — and each masked the other, so the
   case proved neither. `test_the_pass_rule_belongs_to_the_rubric_version` now asserts
   both separately, and there is a mutant for each.
2. `zero_budget_can_submit` survived because `test_the_defaults_can_never_authorize_a_submission`
   asserted only that *some* `BudgetExceeded` was raised, and with the zero-budget
   guard removed the over-budget guard raised instead. The case now matches the
   message, so each of the three guards is refused on its own account. This is the
   money path, so the weaker assertion mattered: it would also have hidden a future
   edit that made a zero budget fall through whenever the worst case happened to be

## Limits

1. **Fake-only.** Every result here is against fakes and pure functions. The `judge`
   conformance suite passed against the **shared fake**, which the contracts README
   defines as *implemented*; there is no real `JudgeCoordinator` (D6), no ClickHouse
   candidate source (T2) and no PostgreSQL. J1 must not be marked integrated.
2. **No approved provider price exists.** `research/cross-cutting/cloud-pricing.md` is
   the only permitted price source and it has **no per-MTok row for any judge model** —
   it prices GPU capacity. `APPROVED_RATES` is therefore empty, every estimate is
   unpriced, and live submission is disabled by the guard. Marked
   **⚠️ TO BE VERIFIED**; the owner is the coordinator, who must add an approved price
   row (or name another approved source) before J2 can submit anything. The
   `5.67700000` USD figure in the drill comes from a **test** rate row and is not a
   price claim. `research/traces/06` §3.8's tables ($5/$25 per MTok for Opus 5, ×0.5 for
   batches) are `est.` in a research document, not an approved price row, and were
   deliberately **not** copied into the code.
3. **The default ceilings are `est.`** `DEFAULT_CEILINGS` (7,348 input / 2,048 output /
   1,024 reasoning) come from `06` §3.4/§3.8's estimates for K=8 frames at 1000 px.
   Nothing has measured them. In particular `06` marks the adaptive-thinking token count
   `⚠️` and unmeasured; a reservation computed from an ordinary-looking thinking budget
   is only as safe as that number. J2 must re-derive them from the actual
   `max_tokens`/thinking configuration it sends and from measured usage, and treat any
   increase as a new reservation, not an adjustment.
4. **The rubric is a draft.** `MARLIN_VIDEO_V1` is `06` §3.3's first-draft rubric and
   its pass rule; `06` marks it draft until validated on ~50 human labels, which is J3's
   job. Its scores must not be promoted to a quality claim before then.
5. **The batch discount is not modelled**, on purpose (a worst case must not carry an
   average's discount). J2's reconciliation is where the actual, discounted cost is
   recorded against the reservation.
6. **`plan_dry_run` takes `now` and `since` from the caller.** There is no clock in the
   module, which keeps the unit tests deterministic, but it means whoever schedules the
   run owns the window. When D6 exists, `now` must be the database clock (r1 R7), not a
   host clock — an earlier `now` would let a revoked consent look current.
7. **Stratum sizes are a fixed design, not adaptive.** An undersupplied stratum is
   reported as a shortfall, so a tenant with few failures yields fewer than 50 labels;
   J3 must read `Selection.shortfall` and `counts` rather than assume 50.
8. **The candidate scan is bounded at 200** (`06` §3.4's batch item ceiling). A tenant
   with more eligible traces than that in the window is sampled from the first 200 the
   source returns, so the *source's* ordering, not just the seed, decides which 200 are
   considered. T2 should return them in a stable order; otherwise selection is
   reproducible only for a fixed candidate set, which is what the determinism cases
   assert.
9. **No console, no route, no migration touched**, so console tests and lint were not
   run at all (recorded as "not run"). E owns any cross-module test of this path.
