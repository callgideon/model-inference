## Behaviour
- **R3.a Registration.**
  - `Identity` has no defaults and forbids extras. It contains: checkpoint digest, tokenizer digest, served model, engine, engine version, quantization, hardware, preprocessor, and a capability set from `text`, `finite_video`, `structured`, `tools`.
  - `serving_ref(provider, identity)` = `lab:serving:<provider>:<uuid4 from digest>@sha256:<JCS sha256 of the identity>`. Any identity change is a distinct serving identity; the same identity is the same ref, and capability order does not matter.
  - `register` asks the variant's engine through W3 `capabilities()`. W3 raises `EngineUnsupported` for an unserved model or a pinned version it is not. R3 additionally refuses (`InvalidRequest`) a probe whose version or model list is not the declared one.
  - The result is a validated F3 `lab.optimization_variant.1`: `changes` names exactly the differing fields, and the same identity is refused by F3 as not a variant.
- **R3.b Comparison.** `compare(variant, base, candidate, *, report, runs, loads=None)` refuses mismatched workloads (`InvalidRequest`):
  - Identities must re-derive to the registered refs.
  - The runs go through H1's pairing: one case universe, and an untagged second factor (harness or seed) is refused. They must serve the base and then the variant.
  - The report must carry its own digest and name these two runs.
  - Loads: one profile digest on both sides, each on its registered serving ref, engine version and hardware. The source must be `(models/)?<exp>/results/<path>@<commit sha>` for one of the five experiments.
- **R3.c Verdict.**
  - B2 `reject` gives `rejected`, whatever the throughput; the throughput is still reported.
  - A changed tokenizer or a lost base capability gives `not_equivalent`. An added capability is reported, not refused.
  - A non-accepting report gives `inconclusive`. Otherwise the verdict is `equivalent`.
  - `optimization_claimed` only when the verdict is equivalent **and** measured.
  - Performance is reported as the throughput ratio, the p99 delta, the memory delta and the sources. There is no cost column (ponytail, marked).

## Oracle
- OPT-PARITY (fake engine server, real W3 and H1):
  - a lying engine is refused;
  - a tokenizer change is never equivalent;
  - a different corpus, harness, seed or load regime is refused;
  - throughput cannot override a failed slice;
  - optimization is claimed only when measured, from an experiment `results/` path at a commit.

## Proposed ruling (propose, never number)
- R3 serving identity and comparison:
  - The serving identity is the JCS sha256 of checkpoint, tokenizer, served model, engine, engine version, quantization, hardware, preprocessor and the capability set.
  - Registration trusts W3's probe, not the claim.
  - A variant comparison is single-factor serving over one H1 case universe with a report bound to its runs.
  - A failed required slice rejects regardless of performance. A tokenizer change or a lost capability is never equivalent.
  - GPU evidence comes only from `<exp>/results/…@<sha>` on experiment branches.

## Fix round (0a239a5d, 2026-09-27)
- **0-RC-C2 (major) fixed, engine kind and capability lies:**
  - **Engine kind.** `register` refuses (`InvalidRequest`) a variant whose declared `engine` is not the probing adapter's kind. `ADAPTERS = {"vllm": VllmEngine}` is the W3 adapter per engine, and only vLLM has one today. An `sglang`-declared variant probed through `VllmEngine` is now refused. The identity test still proves that another engine yields another serving ref, via `serving_ref` directly.
  - **Capabilities.** W3's `capabilities()` returns only `{version, models, served_model}`, and the paired B2 report covers only the base's workload. A capability the variant claims beyond the base is therefore unverified. `compare` reports it as `capability_unverified:<c>`, and the outcome is `inconclusive` (never `equivalent`, no optimization claimed). A lost capability is still `not_equivalent`. Claims inside the base's set are checked by the paired report's required slices.
