## Behaviour
- **R2.a Frozen plan.**
  - `Plan` has no defaults. It holds `horizon_s`, `min_requests`, `max_error_rate`, `max_p99_ms`, `max_skew_bp`, `min_quality_coverage`, `max_lag_s`, `budget` (a unit-tagged `lab.Amount`) and `protocol` (B2's `Protocol`).
  - `plan_digest` is the JCS sha256 of the plan. D9 stores it with the policy revision at launch.
  - A plan whose digest differs from the stored one is refused (`StateConflict`) before anything else happens.
  - The protocol is a **fixed horizon**: nothing expands before `started_at + horizon_s`, so peeking never becomes a win. Sequential looks are a marked ponytail.
- **R2.b `evaluate` (pure).**
  - Operational triggers roll back with no judge and no report: candidate unhealthy, error rate above the bound, p99 above the bound, or spend past the budget. Every bound is inclusive.
  - Spend in another unit raises `InvalidRequest`; units never mix.
  - A B2 report rolls back on `reject` (a failed required slice) only if it is **bound**:
    - its own digest matches;
    - its protocol digest is the frozen protocol's;
    - its run refs are the runs given;
    - the baseline run served the policy baseline and the candidate run served a policy candidate.
  - An unbound report decides nothing.
  - These conditions hold instead of expanding: stale metrics; fewer candidate requests than the minimum; too little quality telemetry ("failure to collect quality telemetry halts expansion"); a cohort share off the policy weight (sample-ratio mismatch, both directions); before the horizon; no report; an unbound report; an inconclusive report.
  - Only then is the verdict `expand`, and it names both run refs as evidence.
- **R2.c `Controller`.**
  - All decisions go through D9's CAS (`transition` with the fence read), as F3 `lab.rollout_decision.1` records carrying their reasons.
  - The controller **never expands by itself**. `approve(operator_id, …)` records an expansion, only on an `expand` verdict and only for a running release.
  - A rollback is one D9 transition. On a lost race the controller rereads and accepts a rollback made by another controller, so exactly one decision is recorded. Losing to any other transition raises.
  - Then `_converge` runs: while the endpoint alias is one of **this policy's candidates**, it CASes the alias back to the baseline. A conflict is reread (3 tries, then `StateConflict`). An alias that someone else moved elsewhere is left alone, so there is no flapping.
  - `rolled_back` is terminal: a restarted controller only converges, whatever the metrics or report say later. An `approved` revision is settled for its controller.
  - `emergency_rollback` is the operator's, from any live state, with no plan, report or metrics needed.
  - Queued and running jobs keep their admitted serving and rate pins (R1/L3). Only future admissions follow the policy and alias; that proof is owed at integration (below).

## Oracles
- ROLLOUT-RECOVER (fake D9/L3):
  - concurrent controllers produce one decision and one alias CAS;
  - a controller killed between D9 and L3 converges on restart with no second decision;
  - recovered metrics do not re-expand;
  - a lost serving race is reread;
  - a CAS that never lands is raised;
  - a stale release read never overwrites a newer decision.
- EVAL-COMPARE (B2-shaped report): a failed slice rolls back with its run evidence; inconclusive or unbound reports hold; peeking before the horizon holds.

## Proposed ruling (propose, never number)
- R2 rollout control:
  - The plan (thresholds, horizon, minimum evidence, budget, B2 protocol) is frozen by digest at launch, with a fixed horizon.
  - Operational triggers roll back with no judge. Only a report bound to this release's runs and protocol decides quality.
  - Missing, delayed, skewed or early evidence holds. The controller never expands, and only an operator approves.
  - Rollback is one D9 CAS decision followed by L3 alias convergence, only while the alias is a candidate of the policy. `rolled_back` is terminal.
