## What R1 does (brief items 1-5)

1. **Stable assignment from the policy at admission; explicit pins win.** A requested R62 pin
   (`<model>@<revision>`) is served as asked and the store is not asked. An alias is looked up
   (`ReleaseStore.active`). The subject is the account, bucketed by F3 `assign` over the policy id,
   so retries land the same and raising a weight only moves baseline subjects. Eligibility is read
   now (`ReleaseStore.eligible`): a revoked subject is on the baseline at its next request and is not
   assigned. Each eligible admission records its `RolloutAssignment` (with request id), for D9.
   A `session` cohort serves the baseline: there is no declared session unit on the wire.
2. **Shadow: suppressed output, no settlement or charge.** In `shadow` mode the user's request is
   admitted unchanged. After a fresh admission (not replayed, not refused), each candidate gets a
   duplicate through the provider-funded `ShadowRunner`, and its result is dropped. The router holds
   no job store, journal or wallet. A duplicate never passes through `accept`. Duplicates have their
   own bound (`Release.shadow_limit` in flight per policy); past it a duplicate is skipped and counted.
   A failing duplicate is logged and counted and never reaches the caller.
3. **Canary/A-B bounded by the policy.** A candidate subject's request is admitted on the
   candidate's pin, so admission resolves, prices and pins that revision (the rate is frozen in the
   admission). Candidate traffic is the policy weight (the F3 validator caps it at 10000 bp; shadow
   policies carry 0). A release must name a pin (never an alias) for every candidate.
4. **Admission hook = coordinator wiring behind `ROLLOUT_ROUTING` (default off)**: WR-R1-1 below.
5. **Public shadow/canary waits on P-12**: the switch is `preflight.NOT_SETTABLE` and names P-12.

A release-store failure is a retryable 503 `dependency_unavailable`. It never silently falls back to
the baseline, because that would drift a promised cohort. Telemetry is `Router.counts[(policy_id, arm)]`
(baseline, candidate, ineligible, shadow, shadow_skipped, shadow_failed), with no org, user or key label.

## Schema request SR-R1-1 (to lab-sql, D9)

The port the router calls, one call per method. PostgreSQL is the authority, and the clock is `infrx.now()`.

- `infrx.release_active(requested_model text) returns table(record jsonb /* lab.rollout_policy.1 */, policy_ref text, revisions jsonb /* {serving_ref: R62 pin} */, shadow_limit int)`.
  It returns only the running head revision for that alias. Each candidate revision is a pin (`like '%@%'`), and `shadow_limit >= 0`.
- `infrx.release_eligible(policy_id uuid, org_id uuid) returns boolean`. It is current (L2 grants/consent at
  `infrx.now()`), never cached, and defaults to deny.
- `infrx.record_rollout_assignment(record jsonb /* lab.rollout_assignment.1 */) returns void`.
  It inserts once on `request_id` (`on conflict do nothing`). It has no org, user or key column: the provider sees `cohort_digest` only.
- All three are granted to `infrx_runtime` only. Policy revisions are immutable, and start/pause/stop/rollback are CAS on
  a head row with a fence (D9 brief), so a rollback is a new revision and never an edit.

## Proposed rulings (unnumbered)

- **P-R1-a** With one candidate, F3 `assign` keeps every candidate subject when its weight rises (tested).
  With more than one candidate, raising an earlier candidate's weight shifts later candidates' bands, so a promised
  subject can move between candidates. Until F3/D9 decide otherwise, D9's CAS should refuse a weight change that
  moves any candidate's lower edge. That allows only growing the last candidate or appending a new one.
- **P-R1-b** A `session` cohort serves the baseline until a session unit is on the wire. Video and robot episode units
  need their extension contracts (R1 acceptance).
- **P-R1-c** A release-store outage at admission is a 503 `dependency_unavailable`, never a silent baseline.
