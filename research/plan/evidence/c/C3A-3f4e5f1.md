## Brief items → where

1. **Narrow ports, current-context authorization, cross-site protection, nothing trusted from the client.**
   - Key create/revoke → `public.api_keys` through the individual's OWN JWT (`supabaseKeyStore`; 0001 owner policies + 0004 column grants decide). The org is `account.orgId`, the creator `account.userId` (C0's `resolveConsumerContext`: verified + own consumer wallet); audience is the column default `consumer` (not writable by the browser role). Revoke/find are scoped `id + org_id + audience=consumer` and revoke also `revoked_at is null`.
   - Onboarding/grant retry → `public.claim_signup_grant(session user, 'app_onboarding', null)` through the service-role client, server-side only; the DB derives verification and owns idempotency (R71). No grant SQL in the App.
   - Supported privacy settings: **none is mutable in v1** — consumer capture is off (P-09 in `15-pending-inputs.md`; U2 brief: no trace-sharing/annotation consent until its permission and deletion path exists), `api_keys.trace_mode` is not browser-writable, and no settings write port exists. So there is deliberately no settings action; `createKey` refuses `trace_mode` other than `off` with `unsupported_parameter` ("content capture is not available for consumer keys"). U2 renders truthful static copy.
   - Operator actions → `operatorCommand` (session `is_operator`, required reason ≤500, required idempotency key, allowlisted fields per action, exact CREDIT decimal string for adjustments, no zero, no "set balance", actor = `operator:<session user>`), `runOperatorCommand(command, port)`. **No App-reachable audited port exists** (G6B's operations live in `infrx`, which PostgREST does not expose), so `operatorAction` answers `dependency_unavailable` with "use the audited operations CLI" — never a silent success (WR-C3A-3).
   - Cross-site: every mutating action (and `signOut`) checks `sameOrigin(headers())` (Origin host must equal `x-forwarded-host`/`host`), on top of Next 16's own server-action Origin check.
   - Inputs are allowlisted (`badInput`, reused from C1): a smuggled `org_id`, `role`, `audience`, `amount`, `created_by`, `actor`, `unit` is `invalid_request` before any write.
2. **Idempotency/conflicts, one-time plaintext, no optimistic success.**
   - Double-click/concurrent/in-process retry: `createKey` with an `idempotency_key` single-flights per (individual, key): one insert; the replay returns the key's CURRENT metadata with `secret: null, replayed: true`; a different payload under the same key is `idempotency_conflict`; a failed attempt is forgotten so its retry can write. The secret is never stored (the memo holds a promise of the summary only).
   - Lost response: fixed copy "If a new key appears in your list, revoke it - its secret cannot be shown again". ponytail ceiling: the replay memory is per process; a cross-instance retry after a lost response mints a second key (revocable). Durable replay = WR-C3A-3(b).
   - Revoke is idempotent (a second click answers the first `revoked_at`), tenant-scoped and allowed while suspended (R33).
   - Grant: concurrent callbacks/claims resolve in the DB (one entitlement); `granted` vs `already_granted`; denials (`identity_reused`, `rollout_hold`, `retired`) are `{status:"held"}` with no reason (no enumeration); `unverified` → `forbidden`; outage/config failure → `dependency_unavailable`, never a grant; a row for another user or a non-string amount → `internal_error`.
   - Server actions revalidate only after an ok result (`/api-keys`, or the layout after a grant): the UI re-reads committed state.
   - DB error text never reaches a caller (fixed messages; `42501` → `forbidden`, else `dependency_unavailable`).
3. **Real DB role boundaries and callback retries; operator distinct from consumer; no duplicated grant SQL.** See the real-DB table below. Operator commands are a separate function with operator authority, reason, idempotency key and session actor.
