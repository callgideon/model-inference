## What B3 does (CHECKPOINT-IDEM)
- **B3.a `receive(body, signature, keys, ledger, store)`**: `infrx.checkpoint_event.1` = provider, `key_id`, checkpoint id, external run ref, training `step`, artifact `{uri, digest}`, `issued_at`. HMAC-SHA256 of the **raw body** under the key the id names (`sign`; stdlib, no new dependency; keys are `secrets.token_bytes` in the test world only) with `compare_digest`; an unsigned/undecodable body, an unknown key, a forged or tampered body → `invalid_api_key`. **Provider binding**: the event's provider and its external run ref's provider must both be the key's. **Replay window**: `|store clock − issued_at| ≤ 300 s` both ways. The external run must resolve for the provider (D7). Then the ledger keeps the event once per checkpoint id (another body = conflict) and D7 the receipt + ONE outbox event; a replay inside the window is the same receipt; the same id with other bytes is `idempotency_conflict`.
- **`subscribe`**: a pinned suite (dataset, harness, evaluator spec whose digest must be its ref's, seed, max_cases) on one external run, a CREDIT `run_limit` within a CREDIT `limit` total, `max_active`, `policy` latest_only|every; the subscriber must be a current `run_evaluation` member (WR-B-4's `may_schedule`); the owner is the subscriber.
- **B3.b `on_checkpoint(checkpoint_id, …)`** (the `checkpoint_received` handler): registration once (`received` only): the URI scheme must have a registry adapter, the bytes must hash to the signed digest, and parse as safetensors (8-byte header length, JSON header, every tensor's offsets inside the file) → `validated`, else `rejected` with the reason in the ledger; a rejected checkpoint is a `skipped/rejected` decision per subscription and is **never deployed**. Per subscription, once: `latest_only` → `superseded` if a higher step was received and not rejected; queued limits past the total → `budget`; `max_active` unfinished runs → `CapacityExhausted` (nothing recorded; the relay releases the event); otherwise a **dev** deployment (the `Deployer` port, idempotent per checkpoint, pulled by digest), then B1 `freeze` as the owner (L2 re-checked; D7 re-checks the grant) → `queued` with the run id; a refusal is a visible `forbidden`/`not_found` skip. The run id is a v4-shaped sha256 of `subscription:checkpoint` and `created_at` is the event's, so a redelivery after a crash anywhere between receipt and dispatch is the same record, ref and D7 run. The checkpoint ends `evaluated`; nothing publishes or promotes.
- **B3.c lineage**: receipt (D7) → event + registration (ledger, D7 state) → decision + run id (ledger) → run/attempts/results (D7).

## Proposed ruling (propose; the coordinator numbers)
- (B3) A checkpoint event is `infrx.checkpoint_event.1`, authenticated by HMAC-SHA256 over its raw body under the provider-registered key its `key_id` names, bound to that provider (event and external run), accepted only within ±300 s of the store clock; one receipt and one outbox event per checkpoint id. A checkpoint is registered (supported registry, signed digest, safetensors shape) before any deployment; a rejected one never deploys. Each (subscription, checkpoint) gets exactly one decision: queued, or skipped with `rejected`/`superseded`/`budget`/`forbidden`/`not_found`; `latest_only` compares training steps, never arrival order, and a rejected step supersedes nothing; at `max_active` unfinished runs the event is deferred undecided. The run id is the v4-shaped sha256 of `subscription:checkpoint` and its `created_at` the event's `issued_at`, so a redelivery is the same run. Evaluation targets a dev deployment only; nothing is published or promoted.

## Open issues
- A higher step received but not yet registered supersedes a lower one; if it is then rejected, nothing is evaluated for that pair until another checkpoint arrives (documented edge; a later event re-decides nothing already skipped).
- The registry fetch holds the artifact in memory (ponytail comment; the checkpoints unit's 4 GiB bound); real adapters stream the hash (WR-B3-3).
- `created_at` determinism (a redelivery's same ref) is proved by the crash drills (same run id and one D7 run), not by a mutant: the D7 fake does not compare a second record under the same run id.
- A registry outage raises out of the handler (the relay records the error and redelivers); there is no per-event attempt cap in the Lab outbox (0029 counts `attempts` but nothing stops on it) - a lab-sql follow-up if wanted.
