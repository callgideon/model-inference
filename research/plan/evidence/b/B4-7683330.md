## Design (one line each)

- Port `EvaluationPort` (LAB_EVALS): catalog (datasets, H1 harness revisions, servings, evaluators by immutable ref), runs, experiments, subscriptions, launch, cancel, subscribe. Records are the backends' JSON verbatim: `Run` = D7 `lab_run_json`, `Report` = B2 `infrx.eval_report.1`, `Decision` = B3 ledger decision + D7 receipt state. Default = `unavailable` on every call (fails closed); `LAB_EVALS_PREVIEW=1` and `NODE_ENV!=production` = the labelled in-memory fake.
- Capabilities (contracts/v2 ROLE_CAPABILITIES): every role reads; `run_evaluation` (developer, administrator) launches, cancels, subscribes. The actor is always `requireProviderWorkspace()`'s.
- Launch = baseline + candidate over one frozen suite (dataset, H1 harness picked by ref, evaluator, seed, max_cases), one factor (serving), a CREDIT run limit (8-decimal F3 amount) and B2's protocol predeclared (confidence in (0.5,1), margin ≥ 0, min_cases ≥ 2, metric basis, required slices `name margin min` lines). The form mints `experiment_id` (`crypto.randomUUID()` at render): a resubmit is the same experiment, another body under it a conflict. Success lands on `/experiments/<id>`, which shows the runs `queued · waiting for a worker` from the records — never an action-local "done".
- Progress: every count out of all the run's cases (`done`, `failed`, `skipped`, `pending+leased` = not finished), attempts by state, costs one line per unit. Cancel offered only on queued/running runs to `run_evaluation` roles; the backend's answer is the redirect's `?refused=` reason.
- Comparison: B2's decision and reasons, overall + every required slice (paired n, clusters, needed minimum, diff, interval at the declared confidence, margin, verdict, `improved` only when B2 says so; insufficient = "—"), observed per run (mean over all cases, missing/universe, errored, not comparable, costs per unit, latency), cost delta per unit (only units both runs carry), digests of report/runs/universe/protocol. Numbers are printed as carried (no rounding).
- Export `GET /experiments/<id>/report`: the stored B2 report verbatim, `attachment`, `private, no-store`; 404 foreign/unknown, 409 before the report exists, 503 unavailable.
- B3: subscription rows (pinned suite, CREDIT per run / in total / at once, policy copy) with one decision per checkpoint (queued + run id, skipped + reason, rejected receipt, not decided). Copy states evaluation never publishes or promotes.

## Wiring / interface requests

- **WR-B4-1 (→ lab-api)** `/lab/v1/evaluations` in the `/lab/v1/control` style (lab_auth actor per call, `{data:[...]}`, `{refusal}` + 401/404/403/422/409/503, `no-store`, mounted only under a default-off `LAB_EVALS` switch):
  - `GET catalog` (read_aggregate_health) → `{datasets:[{ref,label}], harnesses:[{ref,harness_id,version,adapter}], servings:[{ref,label}], evaluators:[{ref,label}]}` (provider's own, D7 `lab_resolve`-able; H1 revisions by `revision_ref`).
  - `GET runs` → D7 `lab_run_status` objects verbatim. `POST runs/{id}/cancel` (run_evaluation) → D7 `lab_cancel_run`, **409 when the run is already terminal** (see open issue 1).
  - `GET experiments` → `[{experiment_id, created_at, protocol, baseline: Run, candidate: Run, report: B2 report | null}]`. `POST experiments` (run_evaluation, 202) body = `Launch` in `port.ts`: two B1 `freeze` calls as the session user (`may_schedule`), run ids derived from `(experiment_id, baseline|candidate)` so a resubmit is the same D7 run, the evaluator spec resolved from `evaluator_ref`; B2 `compare` runs in a worker once both runs are terminal and stores the report. Nothing executes in the request.
  - `GET subscriptions` → B3 `Subscription` minus `evaluator`/`owner_user_id` + `decisions:[{checkpoint_id, step, receipt, state, reason, run_id}]`. `POST subscriptions` (run_evaluation) → B3 `subscribe` with `subscription_id` from the form.
  - Then the Lab gets `lib/services/evaluation/http.ts` replacing `UNAVAILABLE` in `evaluationPort()` (one line) and J01–J03 rerun against it.
- **WR-B4-2 (→ lab-sql)** schema: an experiments table (provider, experiment id, protocol, two run ids, stored B2 report + digest); a provider-scoped subscription/decision listing for the B3 ledger (WR-B3-1); `created_at`/`updated_at` in `lab_run_json` for the timeline.

## Ruling proposal (unnumbered)

LAB-EVALS-UI: the Lab shows evaluation state only from backend records (D7 run status, B2 report, B3 decisions) verbatim; every progress count is out of all the run's cases; a comparison shows every required slice, its interval and verdict, missing/errored/unscored cases and costs per unit exactly as B2 reports them (no rounding, no cross-unit total); `improved` only when B2 sets it; a launch or subscription carries a form-minted id so a resubmit is the same record; launch/cancel/subscribe need `run_evaluation`; nothing runs in a Next.js handler.

## Open issues

1. D7 `lab_cancel_run` (0029:522) updates the state unconditionally: a `succeeded`/`failed` run can be flipped to `cancelled`. The UI offers cancel only on queued/running, but the route or lab-sql must refuse a terminal run (409).
2. After a cancel, D7 keeps the in-flight case `leased` (real fixture); the UI shows it as not finished, which is accurate.
3. Not done in B4 (deliberately, owner/inputs elsewhere): a harness version **editor** (B4.a) — only H1 revision selection; browser (Playwright) tests — E6L owns `apps/lab/tests/e2e/`; a run timeline beyond experiment `created_at` and receipt states (needs WR-B4-2); multi-factor experiments (one serving factor per launch); a "resume" control (B1 resume is worker-side; reload shows durable progress).
4. Integration unclaimed until WR-B4-1 lands (fake-driven UI; real backend shapes proven on b3).
