## 1. Per-item disposition

### B1 — R41 leak through `feedback.submit`

Confirmed and fixed. A feedback entry now carries the same internal `by_operator` flag as a ledger
row, and **every** path projects it through `visibleFeedback`: `feedback.list`, `traceDetail.feedback`,
`calibration.list`, the value `feedback.submit` itself returns, and the **replay** — which was its own
hole, since the idempotency record held the raw entry. An operator session still sees the principal.
The entry stays a customer signal (`author_role: "customer"`, R19); only who pressed the button is
withheld.

The traces *list* was the reason the principal reached a list view at all: the fake was returning its
whole stored trace, feedback array included. It now projects to `TraceListItem` field by field, and a
conformance case pins the row's exact field set — the nonblocking item and this leak were one bug.

Cases: the R41 sweep now submits ordinary feedback from **both** operator sessions, asserts
`author_role: "customer"` and `author_principal: platform` in the customer's list and in the
customer's own replay of the same key, and asserts an operator reading the same entries still sees the
real principal. Mutants `R41-03` (projection removed), `R41-04` (entry not marked), `R41-05` (list row
is the stored trace).

### B2 — suspension cases all used the organization with no accounting

Confirmed. `ids.otherOrgId` is the all-free tenant: no holds, no settled rows, so nothing there could
detect a suspension that released a hold or rewrote a settlement. A new case suspends **and** restores
`ids.orgId` — which has both — and deep-compares usage rows (`cost`, `settlement_state`, `max_hold`,
`usage_certainty`), the ledger, `balances`, `usageSummary` and the operator's view of the wallet on
either side, after first asserting the harness really has a hold and a settled row. Mutants `SUSP-07`
(releases holds), `SUSP-08` (rewrites settled as `released_free`), `SUSP-09` (zeroes settled cost).

### B3 — `adminOrgs` hiding organizations from a member-operator

Fixed: the case asserts `operatorMember` sees exactly the same org ids **and** the same balances as
`operator`. Mutant `ROLE-06`.

### B4 — the runner could still report a false kill

Confirmed, and this was the important one. `classify()` looked at the exit code and the case *name*,
never at **why** the case failed, and never read `kills_by`. Now:

- a kill requires a declared case failing **on an assertion**;
- a declared case failing by exception is a **runner error**, unless the mutant declares
  `kills_by: "throw"` — including the suite's own `settle()` wrapper message, which is a thrown error
  wearing an assertion's clothes;
- a `kills_by: "throw"` declaration whose case now fails on an assertion is a runner error, so the
  declaration cannot rot;
- **"every case failed" is a runner error**: a copy that breaks everything has demonstrated nothing
  about any invariant;
- collateral failures are printed with the kill (`[+N collateral]`).

Both reproductions are self-tests: a crash in the harness factory (`SELF-FACTORY-CRASH`) and a
declared case failing by exception rather than assertion (`SELF-EXCEPTION-KILL`). The old V03 edit is
a self-test too, expecting **killed** — it now dies on an assertion in the per-field idempotency case,
and if that case ever weakens the classifier will refuse the kill rather than report one. **12
self-tests, 12 passed.**

Running the stricter classifier immediately found two mis-declarations of my own, which is the point
of it: `MONEY-04` claimed `kills_by: "throw"` but dies on an assertion (declaration removed), and the
role/suspension matrix made its assertions *inside* a `settle()` closure, so a genuine failure was
reported as a thrown error (restructured — only the probe call goes inside `settle`). `kills_by:
"throw"` now applies to exactly two mutants: **GRANT-04, MONEY-03**.

## 4. Limits (unchanged except where noted)

- Still fake-only, and the corpus is mine; R40 rightly makes the reviewer's corpus the criterion.
- Two invariants remain unexpressible through `ConsoleServices` and are documented as fake-only: the
  idempotency record committed with its effect, and the label id/clock sequences.
- The runner does not typecheck, so a mutant may be type-invalid while runtime-valid.
- `idempotency_expired` and the read-path overflow branch remain unreachable from outside.
- R41 now covers three actor fields (`LedgerEntry.actor`, `ConsentHistoryEntry.changed_by`,
  `FeedbackEntry.author_principal`). Any *new* field naming a principal must be added to the
  projection deliberately — the sweep will catch it only if the harness's operator sessions write it.
