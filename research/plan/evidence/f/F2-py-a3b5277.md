## B1 — the regression, and where the guard belongs

My r7 pass moved the "one loss per capture" guard out of `_count` into its call sites. Two
routes out of the capture lifecycle then counted twice, and the reviewer measured 3,914 of
124,416 sequences affected:

- **(a)** `open(rid, ORG_A, full, None)` → `abandon` (or a context exit) → `finish` →
  `{'abandoned': 2}` **and a queued row**. `_close` counted via `_discard`, then `finish`
  still routed every no-op capture into `_finish_no_op`, which counted again and checked
  neither `closed` nor `counted`. This is G's ordinary order: a `finally` that abandons,
  then a late `finish`.
- **(b)** a `full` capture that breached the budget (or took a non-bytes part) and then
  finished with a mode-mismatched envelope → `{'memory_budget': 1, 'malformed': 1}`: the
  new live-path branch called `_discard` with no `lost` guard.

**Root fix, as ruled:** `_count` is idempotent per capture — it returns once the capture
has contributed its single loss. The guard is back in the one place every route passes
through, so no present *or future* route can double count; that is the whole reason it does
not belong at the call sites. A closed capture now answers what the first call answered,
queues nothing and adds nothing.

## R42 — an off-mode capture is silent

Before this pass every off-mode request counted `{'malformed': 1}` on the ordinary
lifecycle (open → add → finish), and a case asserted that count. That reports a
platform-wide 100% loss rate for exactly the customers who asked for no tracing, while 02
keeps off-mode jobs out of the loss and coverage figures and G is told not to branch on the
mode. Now an off-mode capture is silent in **every** state — including abandoned-then-finished,
which the property test caught while it was being written. `finish` answers
`TraceOfferResult.dropped`, documented as "nothing stored": it is the honest *result*, and
the `dropped` **counter** does not move, because no record was dropped. No enum value was
added. Only an `offer` of an off-mode envelope — which has no capture to speak for it —
stays a counted caller bug. The case, the README G1/T1 notes and the `ports.py` docstring
all say this.

## R42 deliverable — the property test

`infrx/contracts/conformance/sequences.py`, exported as
`run_tracesink_sequence_properties(factory)` (plus an async `tracesink_sequence_properties`
for callers already in an event loop) so T1's real spool sink runs the same lattice, and as
the conformance case `trace_bounds__every_bounded_capture_sequence_holds_the_invariants`
(lengths 1–3, exhaustive) so every adapter's ordinary run covers it.

**It is exhaustive, not sampled**: 12 operations × lengths 1–4 × 3 opened modes × 2 deadline
states.

```
trace sequence properties: 135720 sequences, 530568 operations (exhaustive); len 1: 12, len 2: 144, len 3: 1728, len 4: 20736 in 4.4s
```

The first version took minutes because `add over budget` allocated a 248 MiB string from
the default profile; the lattice runs against a 4 KiB budget and one event loop, which is
why the whole product fits in 4.4s and needs no seed caveat.

Asserted after every sequence: nothing raises; bytes never negative; no bytes leaked after
close + flush; ≤ 1 loss count per capture; ≤ 1 row per capture; a closed capture never
queues a row; opened `off` never stores and never counts; opened `minimal` never stores
content; content declared but absent always reports *and* counts a loss; nothing counted
under `none`; no row's `content_bytes` exceeds the bytes `add` actually charged; a second
`finish` returns the first result.

Four mutants declared, as ruled: `count_is_not_idempotent`,
`live_mode_mismatch_discards_unguarded`, `closed_no_op_capture_queues_a_row`,
`off_capture_counts_a_drop`. The first two are killed **only** by the lattice case — no
one-off case reaches those routes, which is precisely the gap R42 closes.
