## B1 — the no-op capture trusted the envelope over itself

This was code r5 introduced: `finish` on a no-op capture called
`sink._offer_metadata(envelope)` and consulted nothing about the capture. The envelope
therefore decided what was stored, which turns the trace mode into a client-supplied
field — the thing R12 exists to prevent. `_finish_no_op` now decides from the capture:

| Branch | Behaviour | Mutant |
|---|---|---|
| identity | `(request_id, org_id)` must match, exactly as on the accumulating path → else dropped, `malformed` | `no_op_finish_skips_the_identity_check` |
| opened `off` | queues nothing, whatever arrives (01: no trace row at all) | `off_capture_queues_the_envelope` |
| opened `minimal` | only a metadata-only `minimal` envelope is stored; another mode, or any content, is dropped `malformed` | `minimal_capture_trusts_the_envelope_mode` |
| opened `full`, never accumulated | honest **metadata**: content stripped, `content_complete` false, and exactly one counted loss — `abandoned`, the same fact `reap` records. `loss_reason: none` is not an option (02: a loss is marked *and* counted) | `no_op_full_capture_keeps_its_content`, `no_op_full_capture_reports_no_loss` |

`trace_bounds__a_no_op_capture_trusts_itself_not_the_envelope` covers all five
reproductions (a)–(e), each of the five opened/envelope mode pairs, the identity mismatch
and the honest minimal case.

Two related holes closed in the same place:

- **`offer` is metadata-only** (R27): an envelope carrying content never went through the
  accounting, so it is dropped `malformed` rather than queued as a capture nobody charged.
  The exported cases now put content where it belongs — in captures — which is what R27
  intended all along. Mutants `offer_accepts_content`, `minimal_content_queued`.
- **A live capture may not claim more content than it charged.** `finish` refuses an
  envelope whose `content_bytes` exceeds the charge (a *lost* capture is the honest
  exception: its charge was released on purpose and its envelope is stripped). Mutant
  `finish_accepts_uncharged_content`.

Three duplicate guards were removed to get there — `_enqueue`'s uncharged-content branch
and `_offer_metadata`'s content check, both dead once `offer` and `finish` each own their
rule — which is what turned two equivalent mutants into killable ones.

## B2 — m20b survived, and the evidence claimed it killed

`metadata_drop_keeps_its_charge` deleted the *shared* release line, and its only named
case drove `trace_queue_max=1`, so it died through the `queue_full` branch while a finish
dropped for `metadata_budget` kept its content charge. Fixed on both sides:
`trace_bounds__a_dropped_finish_releases_its_charge` gained a metadata-exhaustion phase
(exhaust the reserve, open a full capture, `add(1000)`, finish → dropped,
`{'metadata_budget': 1}`, **0** bytes charged), and `charge_released_only_on_queue_full`
is a mutant specific to the drop reason. The claim is corrected in `F2-py-4657d02.md`, the report that made it.

## Nonblocking applied

- `dur_settle__one_unsettleable_job_does_not_stop_the_sweep`'s `... == 0 or True` is a
  real assertion (the reaped job's settlement state and debit), with mutant
  `reaped_job_keeps_its_hold`.
- `recover` no longer returns exception objects: the unsettleable job is reported only
  through the store's documented `unsettleable` view, so
  `tuple[TerminalOutcome | IndexEvent, ...]` is true of what it returns.
- `harness.py` documents the hook signatures a case relies on, including
  `reap(grace_s: float = 60.0)` — called both as `reap()` and `reap(-100.0)`.
- The README's R37 row and the G1 note describe the fixed behaviour.
- A T1/G1 note: **the sink does not dedupe by request** (`finish` then `offer` of the same
  envelope queues two rows). Projection dedupe by stable event id is what protects counts,
  per 02; that lives in T's projection, not in the sink.

## Port and record changes

None to the records. `TraceSink`/`TraceCapture` behaviour is unchanged in shape from r5 —
`open(request_id, org_id, mode, deadline_at)`, the context manager, `reap(grace_s)`. The
**semantics** of a no-op capture's `finish` and of `offer` changed here, and the port text
was only brought into line with them in the r7 pass (`F2-py-<r7>.md`): at this SHA
`ports.py` still said a no-op `finish` "behaves as `offer`", which understated the rule.
