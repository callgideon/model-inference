
## Corrections (r6 review, fixed in the following pass)

Two claims in this report were wrong, both about code r5 itself introduced:

1. **"`finish` on a no-op capture behaves as `offer`" was the defect, not the fix.** It
   called `sink._offer_metadata(envelope)` without consulting the capture, so the
   **envelope** decided what was stored - which makes the trace mode a client-supplied
   field, exactly what R12 forbids. Five consequences the r6 review reproduced: a `full`
   capture with no deadline discarded its content with `loss_reason: none` and no counter
   (02 requires a loss to be marked *and* counted); a `minimal` capture accepted a `full`
   envelope **with content**; an `off` capture queued a row (01: off produces none); no
   identity check, so another tenant's envelope was accepted on the no-op path while the
   accumulating path dropped it; and a content-carrying envelope was stored as
   `content_complete=True` although every `add` had returned False. `_finish_no_op` now
   decides from the capture's own mode, identity and state, with one mutant per branch.
2. **`metadata_drop_keeps_its_charge` was reported killed but was not the corpus mutant
   m20b.** It deleted the *shared* release line, and its only named case drove
   `trace_queue_max=1`, so it died through the `queue_full` branch while a finish dropped
   for `metadata_budget` kept its charge. The case now has a metadata-exhaustion phase and
   `charge_released_only_on_queue_full` is a mutant specific to the reason.

Also corrected in the same pass: `offer` was not metadata-only (an envelope carrying
content was queued without ever being charged), `recover` returned `DomainError` objects
inside a tuple annotated `tuple[TerminalOutcome | IndexEvent, ...]`, one assertion in
`dur_settle__one_unsettleable_job_does_not_stop_the_sweep` was `... == 0 or True`
(vacuous), and the README's R37 row still described the pre-fix no-op behaviour.
