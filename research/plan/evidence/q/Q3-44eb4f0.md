## What was built (cumulative)

`infrx/scheduling/reconcile.py` defines `Reconciler(store, index, now)`:

- **`drain()`** indexes first and acknowledges second (`acknowledge_dispatch(…, worker_id=)`, so D2's OB-1b fence can refuse a late ack). It acknowledges only what the index took. A full index stops the drain and hands the refused row and the rest back at once. On any other index failure, the rows after it go back, and the failing row keeps its claim until `redelivery_s`. The scan is bounded to `batch × max_batches` rows per call. The gauge `outbox_lag_s` holds the oldest waiting age and is 0 when nothing waited.
- **`reconcile()`** reads the index, then the snapshot. It removes dead candidates and re-reads the snapshot after any removal. It enqueues missing jobs. It rebuilds when the index refuses a wanted event it has already acknowledged, and reads members a second time so a concurrent delivery is not mistaken for that case. Gauges: `missing_index`, `missing_lag_s`, `dead_candidates`, `rebuilds`.
- **`rebuild()`**: snapshot, rebuild with no caps applied, then top up from a second snapshot read after the rebuild. This closes Q2's hole. If the top-up is `blocked` (an ack landed inside the rebuild), it runs once more.
- **`switch(new)`**: rebuild the new index, repoint the drain, then top up from a snapshot read after the swap.
- **`run(stop)`**: reconcile on the first tick. Each step fails on its own: a failed pass stays due and never stops the drain. Failures are counted in `metrics["errors"]`.
- Caps: both adapters resolve an explicit argument first, then `PilotSettings.max_index_items/max_index_bytes`, then Q1's constants.

## Failure drills

- **SIGKILL** (unchanged mechanism): `docker kill --signal KILL infrx-q3-valkey`, `docker start`, wait for PONG; a sentinel key must be gone. In dr13's shape, `rebuild()` returns 3, dispatches each once, and never dispatches the finished job. In the concurrent drill (run 2), every loop that touched the server during the outage felt it and retried. The worker holding its lease across the kill waits on the kill and may feel nothing (printed as `'gpu-slow': 0`). All 24 jobs `succeeded` with one lease each, and every row was acknowledged.
- **Lost ack**: an ack lost before commit gives one redelivery (deliveries == 2) and no second candidate; an ack lost after commit gives none.
- **Persistent reconcile failure** (DUR-1): every snapshot fails and the drain still delivers.
- **Full index / index outage** (DUR-6): rows are handed back at once, and the failing row waits its claim out.
- **A second relay's fence** (OB-1b): the late ack is refused and the row is re-sent.
- **Interleavings**: `Interleave` at n=1 (fence, requeue, stale-snapshot delivery), n=2 (switch before the swap; an ack inside the rebuild) and n=3 (switch after the swap).

## Limits

1. **Not integrated.** D2's functions run through a fake of `0012` at `30d614d`, not PostgreSQL: there is no `skip locked` concurrency and no real transaction timing. Nothing in a request path runs the relay yet.
2. **Cross-process races.** Several relays or reconcilers on one index are safe but not perfect. A pass can remove a live candidate that another process just delivered; the fresh snapshot repairs it in the same pass, or the next pass does. A spurious rebuild resets fairness and never loses a job.
3. **Rebuilds reset fairness.** W2's loop acknowledges unconditionally (request 3). Also, until D3's reaper writes a **new** dispatch event id when it requeues (FID-5: at `30d614d` no SQL writes a dispatch row outside `admit` and `prepare`, while the contract fake's `recover()` does write one), a preparing job whose lease expired keeps only its original, index-acknowledged event. Every pass then reports it blocked and rebuilds until it is re-prepared: one rebuild per lost lease per pass, never a lost job. `reconcile__a_job_redispatched_during_the_pass_keeps_its_new_candidate` and the differential's `recover` op run on the fake's semantics.
4. **The snapshot is unbounded** (bounded only by admission capacity). Since DUR-1, a snapshot that keeps failing no longer stops the drain.
5. **Single-server Valkey only.**
6. **Kills are process-wide.** The drill SIGKILLs this lane's own container, so the final runs were sequential.
7. **No performance claim.** `members()` is one `HGETALL` bounded by the item cap.
8. **The differential's stream** (HON-2) never takes `switch`, the `run` loop, capacity deferrals (default caps), a mid-batch index outage, or a future `available_at`. Each has its own two-adapter cases. Its counters count operations that reported a key, not summed quantities.
9. **Fake rules Q3 cannot observe** (FID-3): no Q3 row has a future `available_at` (D2 writes `available_at = v_now`), so a fake that ignored it would pass (review F1). The drain never re-acknowledges an acknowledged row, so the "newly acknowledged" count is unobserved (F9). `gc_outbox`'s tombstone window and `attempts` are not mirrored.
10. **A poison row** (the index keeps rejecting it for a reason other than capacity) is retried once per `redelivery_s`. It does not block the rows behind it, and it is not recorded with `record_dispatch_error` (D2 OB-7), so operators see it only in the relay's error count and log.
11. **Order on PostgreSQL** (FID-2): `dispatch_pending` and the snapshot break an `available_at` tie on a random uuid, so after a rebuild FIFO within a tenant holds only by `available_at`.
