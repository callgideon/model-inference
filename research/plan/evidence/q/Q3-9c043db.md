## What was built

`infrx/scheduling/reconcile.py` defines `Reconciler(store, index, now)`. The store is anything that provides D2's `dispatch_pending`, `acknowledge_dispatch` and `dispatch_snapshot`, which `PgJobStore` already has. The index is either adapter, and both adapters gain `members()` (event_id → job_id, covering pending and in flight).

- **`drain()`** writes to the index first and acknowledges second, and only acknowledges what the index actually took. A `capacity_exhausted` refusal or an index outage leaves the row unacknowledged, so the store redelivers it after `redelivery_s`. The scan is bounded to `batch × max_batches` rows per call, and D2's `claimed_at` stamp acts as the checkpoint. It exports the `outbox_lag_s` gauge.
- **`reconcile()`** reads the index and then the snapshot. It removes dead candidates (jobs that no longer want dispatch) and takes a fresh snapshot after any removal. Missing jobs are enqueued again. If the index refuses a wanted event because it already acknowledged it (a worker acked a candidate whose claim never reached the store), the pass rebuilds. A second membership read keeps a concurrent delivery from being mistaken for that case. It exports the `missing_index`, `missing_lag_s`, `dead_candidates` and `rebuilds` gauges.
- **`rebuild()`** takes a snapshot, rebuilds with no caps applied, then tops up from a second snapshot read after the rebuild. This closes Q2's hole: a delivery acknowledged behind a stale snapshot would otherwise be lost, because the outbox will never repeat it.
- **`switch(new)`** rebuilds the new index before anything points at it, then repoints the drain, then tops up from a snapshot read after the swap. That catches any dispatch the drain delivered into the old index during the switch.
- **`run(stop)`** is the relay loop. It reconciles on its first tick, keeps a failed pass due and retries it on the next tick, and counts failures in `metrics["errors"]`.
- **Caps (item 5).** `MemoryScheduler` now resolves its caps the same way `ValkeyScheduler` already did: an explicit argument first, then `PilotSettings.max_index_items/max_index_bytes`, then Q1's constants.

## Failure drills

- **SIGKILL.** `vkharness.kill_and_restart()` runs `docker kill --signal KILL infrx-q3-valkey`, then `docker start`, then waits for PONG. A sentinel key written before the kill is asserted gone after it, which proves the data was lost.
  - In dr13's shape, the durable state before the kill is 3 queued jobs, 1 succeeded job and 4 acknowledged rows. After the kill the index depth is 0, and `rebuild()` returns 3. Those 3 are dispatched once each, and the finished job is never dispatched.
  - In the concurrent drill, every loop hit connection errors and retried: 89 relay errors, and 39–40 per worker. All 24 jobs `succeeded`, each with one lease, and no row was left unacknowledged.
- **Lost ack.** An ack lost before commit gives exactly one redelivery (deliveries == 2 per row) and no second candidate. An ack lost after commit gives no redelivery.
- **Interleavings.** `Interleave` runs an action between reading a snapshot and using it. It is used to reproduce: a stale snapshot followed by a delivery; a claim landing between snapshot and rebuild (the fence case); a requeue plus delivery landing between snapshot and removal; and a delivery into the old index during a switch.
- **Cleanup.** Test namespaces are left in the disposable server, as in Q2. The container is removed at the end (see Cleanup).

## Limits

1. **Not integrated.** The D2 functions are exercised through a fake that reproduces the SQL. It is not PostgreSQL: there is no `skip locked` concurrency and no real transaction timing. Nothing in a request path runs the relay yet.
2. **Cross-process races.** Several relays or reconcilers on one index are safe but not perfect. A pass can remove a live candidate that another process just delivered; the fresh snapshot repairs this within the same pass, or failing that the next pass. A spurious rebuild resets fairness state and never loses a job.
3. **Rebuilds reset fairness.** A pass rebuilds when a worker acknowledged a candidate whose claim never reached the store. W2's loop acknowledges unconditionally, so a database outage during claims will trigger rebuilds (see integration request 3).
4. **The snapshot is unbounded.** `dispatch_snapshot` returns every non-terminal job wanting dispatch, bounded only by admission capacity. `rebuild` crosses Valkey in one command (Q2 limit).
5. **Single-server Valkey only.** Replication and clusters were not tested.
6. **Kills are process-wide.** The drill SIGKILLs this lane's own container, so a second process sharing `infrx-q3-valkey` at the same moment would see the outage too. Q runs are sequential.
7. **No performance claim.** `members()` is one `HGETALL` bounded by the item cap.
8. Neither `tests/d` nor the console targets were run successfully in this worktree, as detailed above.

## Handback and integration requests

1. **D2 / D3 store methods.** `Reconciler` needs exactly `dispatch_pending(*, limit, worker_id, redelivery_s)`, `acknowledge_dispatch(event_ids) -> int` and `dispatch_snapshot() -> tuple[IndexEvent, …]`, all present on `PgJobStore` @ 8728aec.
   - D2's `infrx/state/outbox.py::OutboxRelay` duplicates `drain`, and its `rebuild` lacks the post-rebuild top-up, which leaves Q2's hole open. Replace it with `infrx.scheduling.Reconciler`, or make it delegate to `Reconciler`.
   - D3's reaper should write a **new** `prepare_dispatch` or `inference_dispatch` row (a new event id) whenever it re-dispatches work. Reusing an event the index has already acknowledged forces a rebuild.
   - Run `tests/q/test_reconcile.py` against `PgJobStore` once D2 merges: `rig.world` swaps `FakeDispatchOutbox` for the store.
2. **G2 / composition root.**
   - Construct `index = ValkeyScheduler(connect(limits), now, limits=limits)` and `relay = Reconciler(store=pg_jobstore, index=index, now=lambda: datetime.now(timezone.utc))`.
   - Run `asyncio.create_task(relay.run(stop))` for the process lifetime and set `stop` on shutdown.
   - Give workers `relay.index`. After `relay.switch(new)`, repoint the workers and drop the old index.
   - Export `relay.metrics` (`outbox_lag_s`, `missing_index`, `missing_lag_s`, `dead_candidates`, `rebuilds`, `errors`).
3. **W (worker loop).** When `JobStore.claim` fails without a domain answer (the database is unreachable), do not acknowledge the candidate; let its visibility return it. This avoids the rebuilds in limit 3. Also treat `InternalError` from Q2's `_CLAIM_ATTEMPTS` as retryable.
