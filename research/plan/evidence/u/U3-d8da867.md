## What U3 delivers (brief items → implementation)

1. **Authorized operator views, separate route.** `/admin` (existing route, `notFound()` before any read unless `session.isOperator`). Every read uses the operator's **own** cookie session (`createClient()`), never the service key; each relation is guarded in SQL by `public.is_operator()`, so a consumer JWT reads its own rows or none (DB-proven, U3-DB02). Not the provider Lab: no provider/trace/eval content.
2. **Health / reconciliation visibility.** Sections, each an independent `Result` (a failed or malformed section says "Unavailable", never an empty table, zero or fixture): consumer accounts (exact CREDIT balance/reserved/available, reconciled `available = total − reserved`, suspension state, signup-grant received or not); the 24 h unknown-usage queue (both regimes, each in its own unit, with the DB `reconcile_after`); wallet drift (0006 detector's drifting rows); the newest audit entries (closed `AUDIT_ACTIONS` vocabulary).
3. **Reasoned credit adjustment/grant, suspension, key revocation — audited, idempotent, no balance editing.** Three forms (adjust CREDIT: signed exact decimal; suspend/restore; revoke a consumer key) call C3A's shared `operatorAction` → `consoleActions.operator` (Origin check, session operator flag, allowlisted input, required reason and idempotency key). U3's `operatorRpcPort` maps each command to ONE `public.operator_*` RPC (WR-U3-1) that re-checks `is_operator()` in the DB, derives the actor from the JWT (a form/command actor is never sent), and runs the existing audited `infrx` operation (`grant_credit` `operator_adjustment`, `set_suspension`, `revoke_key`) — no new grant/hold/settlement SQL. A form keeps its idempotency key across every failure and rotates it only after a committed answer; the outcome says "Committed", "Already applied … nothing changed twice", "Refused: …", or "Not confirmed … same idempotency key"; after a commit the page re-reads (router.refresh) so balances/suspension/audit show the committed state.
4. **Crafted URLs / RPC.** Page 404 for non-operators; server action refuses without the session flag; the DB refuses the RPC for consumer, anon and service-role JWTs and for a session that *claims* operator authority the DB does not grant (U3-DB03, U3-DB09).
5. **Minimal approved rate publication.** Deliberately **not** a console form: P-01 is decided and enacted by the coordinator with the audited `publish-card` CLI ([15-pending-inputs.md](../../15-pending-inputs.md) P-01, 2026-09-25). The page states that truthfully and links the published catalog (Models). The one-time signup grant is likewise not an operator control (A2's claim flow; a held grant is the CLI's `grant`): the port refuses `grant_initial` without any call (U3-P03). Unknown-usage release is the CLI's `reconcile` (the page names it); no fake toggles.

## Proposed rulings (coordinator numbers them)

- The App's operator writes go through `public.operator_*` RPCs executed with the operator's own JWT: operator authority and the audit actor are decided in the database (`is_operator()`, `operator:<auth.uid()>`); the App holds no service key for operator work. The legacy `ConsoleServices.adminGrant/adminSetSuspension/adminSetEntitlements` (USD `promotional`) stay unimplemented and unused by the consumer App.
- Console idempotency keys are namespaced (`app-operator:<operation>:<key>`) apart from CLI keys; a reused key with another target or payload is `idempotency_conflict`; a concurrent retry is a replay.
- Rate publication, the one-time signup grant and unknown-usage release remain CLI-only operator operations in v1; the console states this rather than offering controls.
