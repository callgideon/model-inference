## Real-database oracle (how the UI is checked against the ledger)

`credit_world.py` reuses the D harness (labelled/locked container, `seed_admission`, the real `admit`/`claim`/`terminalize`) — no grant/hold/settlement SQL is written. Ten threads race CONSUMER_1's wallet through settled ×4, cancelled-with-usage, unknown (published, no usage → `held_unknown`), free (`invalid_media`), absorbed (`deadline_exceeded`), running and queued; a legacy USD grant and job; CONSUMER_2's own job; then an operator adjustment leaves room for two holds and six admissions race (2 admitted, 4 refused 402). `credit-pg.test.ts` then runs **the App's unchanged `postgrestCreditReads`** against a PostgREST double that renders each call as PostgREST's SQL (`json_agg` of the select / RPC) and executes it via `psql` as role `authenticated` with a JWT subject (both claim forms), and compares with owner-run durable queries:

- P01 wallet = Σ ledger, reserved = Σ active holds; card reconciles; wallet reads **low** at `0.00000001 credits` with the 402 guidance.
- P02 Spent = −Σ `inference_debit`; ledger walk at page size 2 visits every entry once; Σ = balance.
- P03 usage walk at page sizes 1/2/7 across identical timestamps = exactly the org's jobs; Σ settled CREDIT charged = Spent; Σ held/unknown holds = Reserved; no charge shown for any non-settled job; USD rows say USD; all five settlement states present.
- P04 legacy statement = Σ `public.credit_ledger.delta_usd`, labelled USD, rollout hold shown.
- P05 CONSUMER_2's session: own wallet only; none of CONSUMER_1's jobs; C1's wallet id → empty ledger and `0` credits-in; C1's org legacy statement → `forbidden` (42501).
- P06 window: 24h inside → all rows; 7d eight days later → none.

### Open issue found in this round (not a review finding)

- **The ledger page is still a top-N sort over the whole wallet.** `console_credit_ledger` is `security_barrier`, so PostgreSQL keeps it as a subquery and cannot drive `ORDER BY created_at desc, entry_id desc LIMIT n` from `credit_ledger_wallet_created_idx`. Without `actor`, a page at 10k entries takes 6.5–8.4 ms (plan: Limit → Sort (top-N heapsort) → Subquery Scan → Seq Scan, 10,002 rows). At 100k it takes 84 ms (it was 13.5 s with `actor`). C0's `credit_ledger_page` reads the same view and has the same limit. Fixing it is SQL (D10): a `console_credit_ledger_page(p_wallet, p_after_at, p_after_id, p_limit)` SECURITY INVOKER function that selects from `infrx.credit_ledger` with the owner guard inside, so the Limit sits on the index scan. This is proposed as **WR-3(c)**, for when wallets reach tens of thousands of entries. At 10k entries the measured cost is single-digit milliseconds, so D10 sets the priority.
