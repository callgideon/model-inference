### Decisions worth reviewing

1. **The new relations live in schema `infrx`, not `public`.** Supabase grants `anon`,
   `authenticated` and `service_role` ALL PRIVILEGES on everything in `public` and keeps
   doing so through default privileges, so a relation created there is browser-reachable
   until a migration remembers to revoke it. A separate schema is deny-by-default;
   `0004` revokes explicitly anyway. Consequence: PostgREST exposes only `public`, so
   `infrx` is unreachable over the Supabase REST API and **must not** be added to
   `db-schemas`. Everything the console reads is a `public` view (`0005`).
2. **A pinned plain `postgres` image plus a documented shim**, not a
   `supabase/postgres` image. What `0001_init.sql` depends on is the `auth` schema,
   `auth.uid()`, three roles and Supabase's default grants — a dozen lines, auditable in
   the diff. The Supabase image is a multi-gigabyte pull this host does not have and
   would still need `request.jwt.claims` set by hand to exercise RLS. The
   default-privileges block is the part that matters: without it the role matrix would
   pass vacuously, which is the trap the contracts README warns about (note 1).
   Differences from production are listed in the shim's header; no migration touches one.
3. **The clock has two independent barriers.** `infrx.now()` reads its offset from
   `infrx_test.clock`, which (a) only `infrx/state/test_clock.sql` creates, and that file
   is not in `apps/app/supabase/migrations/` so no deploy applies it, and (b) is not even
   looked for unless `current_database()` matches `infrx\_%` (08 §8's task-local names).
   Production is Supabase's `postgres`, and a session cannot rename the database it is
   connected to; it short-circuits on the name test and pays no subtransaction per call.
   Proven both ways: movable in `infrx_d1`, ignored in `prodlike_d1` **with the fixture
   installed and its offset set**.
4. **Eleven RPC signatures, no bodies.** `infrx.{admit, prepare, claim, heartbeat,
   append, cancel, terminalize, grant_credit, accept_feedback, reserve_judge,
   record_submission}(jsonb) returns jsonb`: SECURITY DEFINER, fixed `search_path`,
   EXECUTE revoked from PUBLIC/anon/authenticated and granted to `service_role` alone,
   each body raising `feature_not_supported` naming its owner (D2: admit, prepare;
   D3: claim, heartbeat, cancel; D4: append; D5: terminalize, grant_credit;
   D6: accept_feedback, reserve_judge, record_submission). One uniform canonical-JSON
   signature, so a body can be filled in without moving the grants. `grant` is
   `grant_credit` because `grant` is a reserved word.
5. **Deviations from `06`, deliberate.** `capacity_reservations` is keyed
   `(request_id, kind)` with no `scope` column: the kinds **are** the scopes
   (`records.ReservationKind`). Active scope counters are partial indexes, not a counter
   relation, because 02 forbids counting a reservation twice and two sources can
   disagree. `staged_media` is one relation for staged refs and uploads (an upload is its
   `created` state), keyed `(org_id, handle)` per the contracts README. No PostgreSQL
   `traces` relation: T owns that projection.
6. **Tenant coherence is a foreign key, not a trigger.** `jobs` carries
   `unique (request_id, org_id)`, so `job_media` and `feedback` reference `(job, org)`
   together and R55's "the organization comes from the job row" is enforced by the
   database rather than by every caller.
7. **The console read surface is owner's-rights views with their own predicates.**
   **`[corrected in round 2 — the masking below keyed on `by_operator`, which fails open
   for all history and for the deployed console's own writes; it is now proven
   membership. See §Round 2, B2.]`** A
   `security_invoker` view would be denied `infrx` and there would be nothing to grant
   short of opening the schema, so each view in `0005` carries the same
   `is_org_member`/`is_operator` guard the existing `org_balance`/`org_usage_summary`
   functions use, plus `is_service_client()` for a server action holding the platform
   key. Operator principals are masked **in SQL** (R41/R50), so a customer session reads
   `platform` even if a caller forgets to project; `public.feedback` excludes calibration
   labels for every viewer (R49) and labels are read only through
   `public.calibration_labels`, which is operator-only.

## Failure drill

**Injection 1 — the ledger-precision mutant against real history.** Seed the current
schema with positive and negative ledger history, then apply a `0003` whose money
expansion says `numeric(20,2)`:

```
durable state BEFORE the pilot migration:
   ('-0.000001', 'adjustment')   ('-12.345678', 'usage')   ('25.000000', 'purchase')
   ('100.500000', 'grant')       ('-0.123456', 'usage')
durable state AFTER the mutated migration:
   ('0.00', 'adjustment')        ('-12.35', 'usage')       ('25.00', 'purchase')
   ('100.50', 'grant')           ('-0.12', 'usage')
  check_upgrade_preserved FAILED: ledger delta changed: -0.000001 -> 0.00
```

An adjustment of a hundredth of a cent became zero and a usage debit was rounded against
the customer. With the shipped `numeric(20,8)` the same drill leaves every value equal and
only the text form gains trailing zeros, which is what the check asserts.

**Injection 2 — a migration that runs twice (the deploy-retry case).** The migrations are
not idempotent by design (the Supabase CLI applies each file once and records it); what
matters is that a refused retry changes nothing:

```
  applied once: wallets=3 ledger_sum=113.03086500
  re-apply refused: 0003_pilot_durable_schema.sql failed to apply: relation "price_versions" already exists
  after the refused retry: wallets=3 ledger_sum=113.03086500 reconciliation_drift_rows=0
```

Each file executes as a single implicit transaction, so a failure part-way through leaves
the database as it was: no duplicated wallet import (the import is
`on conflict (org_id) do update`, idempotent in itself), no drift, no half-built relation.

**Injection 3 — a security-definer helper that reads `current_user`.** `is_service_client()`
was written SECURITY DEFINER first. Inside a definer function `current_user` is the
function's owner (`postgres`, a superuser), so `pg_has_role(current_user, 'service_role',
'usage')` answered **true for every caller** and the read-surface check reported every view
leaking, including to `anon`:

```
public.wallets: anon sees rows
public.console_ledger: anon sees rows
public.operator_audit: a member session sees operator rows        (… 18 lines)
```

Fixed by making it SECURITY INVOKER (it needs no privilege of its own). This is the
failure the read-surface check exists for, and it was caught before the code was
committed rather than in review.

**Cleanup:** every drill database and the container were removed; `docker ps -a` afterwards
showed only other sessions' containers.

## Migration, rollback and retention notes

**Order and locks.** `0003`, `0004`, `0005`; all additive. The two
`alter column … type numeric(20,8)` statements rewrite `credit_ledger` and `usage_events`
under `ACCESS EXCLUSIVE`, milliseconds at pilot size and the only blocking step;
`create trigger credit_ledger_append_only` and the `add constraint` statements take brief
exclusive locks. Nothing is dropped or renamed, so a gateway of the previous version keeps
working: the columns it writes are untouched and every new column is nullable or defaulted
(`settlement_regime` defaults to `'legacy'`, which is what an F1-era insert should be).
`0005` narrows two existing grants (`api_keys` table UPDATE → `(name, revoked_at)`), which
is the only behaviour change visible to the console; both console key actions are covered
by positive controls in the matrix.

**Reversibility.**

| Change | Rollback |
|---|---|
| `0005` | fully reversible: `drop view` ×10, `drop function public.org_wallet_summary(uuid)`, `drop function public.is_service_client()`, `grant update on public.api_keys to authenticated`, and drop the added columns/constraints on `api_keys`, `usage_events` and `infrx.judge_runs`. |
| `0004` | fully reversible: `drop function infrx.<name>(jsonb)` ×11, `alter table … disable row level security`, and restore `grant update on public.organizations to authenticated` (0001's state). |
| schema `infrx` and its 21 relations | `drop schema infrx cascade` — **only while no job has been admitted**; afterwards it destroys accepted jobs, holds and journal rows, which 06 forbids ("no destructive downgrade of accepted job/ledger data"). The supported path is to stop admitting and leave the schema in place. |
| `organizations.suspended*`, `credit_ledger` provenance columns, `usage_events` outcome columns | `alter table … drop column` is safe; no historical value lives in them. Drop the matching constraints and indexes first. |
| `numeric(20,8)` on `delta_usd` / `cost_usd` | **not reversible** in general: narrowing back would round any pilot-era row. Only safe while every row still fits, and never necessary — the wider type is a superset. |
| `models.limits` extension | remove the added keys with `limits - 'max_output_tokens' - 'max_context_tokens'`; existing keys were never overwritten (`jsonb_build_object(...) || limits` keeps what was there). |
| the wallet import | re-derivable at any time by re-running the import statement (`on conflict do update`). |
| append-only triggers | `drop trigger` restores editability. |

**Retention.** `stream_chunks` are pruned at `expires_at` (`JOURNAL_CHUNK_TTL_S`, 1 h);
`staged_media` at its `expires_at` (GC must respect `job_media` references);
`idempotency` at `expires_at`, null while the referenced work is active and set to
terminal + `IDEMPOTENCY_TTL_S` (24 h) after; `outbox` rows are retained after
acknowledgment (an acknowledgment marks, it never deletes) and are the projection audit
trail. `jobs`, `attempts`, `credit_holds`, `capacity_reservations`, `credit_ledger`,
`usage_events`, `feedback`, `consent_history`, `audit_entries` and `judge_*` are
**accounting and audit records**: 06 is explicit that the 13-month trace retention does not
authorize deleting the ledger/usage/idempotency evidence reconciliation needs, so nothing
here expires them. D1 adds no TTL job; whoever adds one owns the reconciliation argument.

**Sizing, measured** on the 3 000-job seeded database (`pg_table_size` /
`pg_indexes_size` / `n_live_tup`, PostgreSQL 16.14):

≈ **4.3 KB of durable PostgreSQL per completed request** with two journal chunks and one

nothing. At 64 concurrent jobs the journal's own 1 GiB global budget
(`JOURNAL_TOTAL_BYTES`) binds before table growth does: 100 000 requests of permanent
accounting is ≈ 250 MB.

## For D2–D6 (from the reviewer's round-2 list, recorded, not fixed)

Nothing in the database prevents a **double move**: a settlement that both updates
`wallets.ledger_total` and inserts a ledger row would drift by the delta — which is why
`ledger_total` is no longer writable by the platform role at all (above), so D5 **must**
move money by inserting the ledger row. Two-org ledger transactions in opposite order will
deadlock: D5 locks in `org_id` order. A bulk ledger load is O(n²) on the wallet row. Still
accepted by the schema, each a state machine's business: a usage debit plus a negative
adjustment on one request; a ledger debit larger than the job's debit, or for a
non-terminal job; `reserved_total` above `ledger_total`; `entitlement_version` and
`result_expires_at` rewritable; non-terminal jobs deletable; feedback rewritable.

For C2 (the coordinator carries it): `usage_summary`/`usage_daily` as **rendered SQL** fail
with `sum(text)` — C must call the RPCs, always with non-NULL `p_from`/`p_to` (NULL gives
zero rows); `operator_audit.org_id` equals `target_org_id` and is nullable; an
operator/service call with a NULL `p_org` returns a zero row whose `org_id` is NULL;
`console_usage_daily`'s limit applies after a full-window aggregate, so the work it does is
not bounded by the row cap.
