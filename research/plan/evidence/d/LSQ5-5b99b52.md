### (1) E8L-F1 / WR-E8L-2: one serving-ref identity for a rollout candidate

Bug (`research/plan/evidence/e/E8L-2334e6a.md` "E8L-F1"): 0043's `release_active` read a
candidate's `lab:serving:<provider>:<id>@sha256:<d>` with `<id>` = **serving_version_id**
and `<d>` ignored. L3's `operations.serving_ref` (R188, `08-contracts-v1-encoding.md`:361)
names `<id>` = **deployment_revision_id** and `<d>` = the JCS (RFC 8785) digest of the served
revision. The two identity spaces disagree, so `emergency_rollback` records a D9 decision R2's
`_converge` never recognises as "the candidate" - the alias never rolls back (E8L's k06).

Fix, additive migration `0045_lab_serving_ref_identity.sql` (0043 untouched):
- `infrx.lab_rfc3339(timestamptz)`: RFC 3339 the way Python's `datetime.isoformat()` writes it
  (no fractional seconds at microsecond 0, else exactly six digits) - `to_char`'s `US` format
  code is already zero-padded to six digits.
- `infrx.lab_serving_ref_digest(serving_version_id)`: the sha256 hex of the JCS bytes of the
  `ServingRevision` that id names, built field-for-field from `infrx.serving_versions` +
  `infrx.model_versions` + `public.models` (0043's own `_SERVING` join,
  `apps/infrx-api/infrx/state/operations.py`), matching `ServingRevision.model_dump(mode="json")`
  including `schema_version` (2, `infrx/contracts/v2/records.py`) and `CapabilityRecord`'s own
  defaults (`billing_meter`, `api_family`, `stream_input`, `tools`, `structured_output`, its own
  `schema_version`) the way pydantic validation fills them when the stored `capability` jsonb
  omits them (the CHECK on that column only requires `billing_meter`/`api_family`).
- `infrx.lab_serving_ref(deployment_revision_id)`: the deployment's full current ref, or null.
- `release_active` now resolves a candidate's id as a `deployment_revision_id`, looks up its
  serving revision's label and model (still requiring `provider_org_id = o.provider_org_id` and
  `sv.model_id = v_model`, as before), and refuses (`state_conflict`) unless the recomputed
  `infrx.lab_serving_ref` of that deployment equals the candidate's ref **verbatim** - identity
  and digest in one comparison, per the ruling.

Verified byte-for-byte against `infrx.lab.control.operations.serving_ref` for two field
combinations (every optional field null, zero-microsecond timestamp; every optional field set,
two weight shards, every `CapabilityRecord` flag non-default, a microsecond timestamp) - built
the same row in a scratch database and a Python `ServingRevision`/`DeploymentRevision` from the
same values, both times `MATCH: True` (scratch scripts, not committed; the reproduction is in
the migration's own header comment).

Fixture updated to match (owned: `tests/d/test_d8_requests.py`): the candidate serving version
`W['serving_2']` now has an actual deployment (`W['deployment_2']`, private/dev on

### (2) endpoint_alias oracle (LSQ5-m1/m2, R195)

Lens findings from the coordinator's session record: **m1** - `endpoint_alias` has no oracle
when two aliases share one prod endpoint (0007 lets two models' public deployments sit on one
endpoint; nothing FKs an endpoint to a model). **m2** - the fake answers for an endpoint the
alias has moved off.

Both were real: `infrx/state/lab_control.py`'s `_ENDPOINT_ALIAS` ordered by `l.version desc`,
but `version` is scoped to ONE alias, so comparing it across two different aliases' listings is
not "newest" (m1: the H2/"order asc" mutant note in LSQ4's evidence was about this same
ambiguity). `infrx/lab/control/fakes.py`'s `endpoint_alias` compared each alias's OWN latest
version number after checking only that ANY of that alias's listings ever touched the endpoint
- not that its CURRENT listing does - so it could name an alias whose newest listing has since
moved elsewhere (m2).

Ruling (proposed, unnumbered - "propose, never number" per the brief): **an endpoint's alias is
the newest LISTING (by `created_at`, ties broken by `public_model_id` then `version`, both
descending) whose OWN row names a deployment on that endpoint** - never a per-alias "any
listing ever" check, and never compared across aliases by `version`.

- SQL: `_ENDPOINT_ALIAS` now orders `l.created_at desc, l.public_model_id desc, l.version desc`.
- Fake: added `_listing_log: list[Listing]` (global, insertion order, across every alias) to
  `FakeControl`; `list_now` appends to it; `endpoint_alias` walks it backwards for the first
  listing whose own deployment is on the endpoint. This is the fake's honest analogue of
  `order by created_at desc` (the fake has no clock column on `Listing`).
- New oracle test, `tests/d/test_l3sql_reads.py::check_endpoint_alias_orders_across_aliases_by_
  time_not_by_either_ones_version`: a second alias's v1 listing on the SAME prod endpoint,
  published (an explicit later `created_at`, since the test clock is frozen) after the first
  alias's v2 - the second alias must win despite 2 > 1.
- `l3r_alias_any_endpoint` (existing) re-anchored to the smaller literal that survives the
  ordering change; a new `l3r_alias_by_version_not_time` mutant reverts the ordering to
  `l.version desc` alone, named by the new check.

Verified: `tests/l/control` + `tests/l/access` unchanged (51 fake, 85 total incl. `[pg]` on
`l3`) - the fake fix changes no existing answer, only the ambiguous cross-alias case nothing
before this lane exercised.

## Fix round (handback `c217bab6`, review `research/plan/evidence/coordinator/updates/LSQ5-20260929T0030Z.json`)

Two findings, both fixed.

**0-F1 (blocking): the endpoint_alias oracle never implemented LSQ5-m2.** The section above
("(2) endpoint_alias oracle") and this evidence file's own text claimed m2 ("answer nothing for
an endpoint the alias moved off") was fixed alongside m1. It was not: `_ENDPOINT_ALIAS`'s m1 fix
(order by `created_at desc` instead of `version desc`) still let a STALE listing win, because a
catalog listing is never deleted or moved (0007 keeps it as history) - an alias that republishes
to a new deployment on a different endpoint leaves its old listing behind, and nothing in the
m1-only query checked whether that old listing was still its own alias's CURRENT one. The
proposed ruling this lane wrote at the top ("the newest catalog listing... whose OWN row names a
deployment on that endpoint") was itself the gap: read literally, an alias's old row still
"names a deployment on that endpoint" forever, so it can keep winning after the alias moves off,
as long as nothing else has since claimed the old endpoint. `fakes.py`'s `endpoint_alias` had the
structurally identical gap (walked `_listing_log` backwards for the newest listing touching the
endpoint, never checking it was still that alias's current version).

Fix (no new migration; `_ENDPOINT_ALIAS` is a Python-level query constant in
`infrx/state/lab_control.py`, not SQL in a migration file): both stores now additionally require
the candidate listing to be its own alias's current (max-`version`) listing -
`and l.version = (select max(v.version) from infrx.catalog_listings v where
v.public_model_id = l.public_model_id)` on the SQL side, `current[-1] is listing` (against
`self.listings[alias]`) on the fake side. The proposed ruling is narrowed accordingly (see
below). New oracle test, `tests/d/test_l3sql_reads.py::check_endpoint_alias_answers_nothing_
for_an_endpoint_the_alias_moved_off`: a fresh alias publishes v1 on one endpoint, then v2 on a
DIFFERENT endpoint (two brand-new endpoints, isolated from every other check's fixtures so
ordering in `CHECKS` doesn't matter) - the old endpoint must answer `None`, the new one the
alias. New mutant `l3r_alias_ignores_superseded` (the correlation predicate replaced with
`where false`, so the "current version" subquery always returns `NULL` and no listing ever
qualifies) is named by exactly that check; a first attempt at this mutant (`where true`, an
uncorrelated global max) survived because the isolated single-check database this lane's mutant
harness rebuilds per case happened to make the global max coincide with the per-alias max - a
reminder that a mutant against a correlated subquery needs a data shape (or, here, an
unconditional `where false`) that cannot coincide by accident, not just "looks like a real bug".

**0-F2 (major): 0045's own comment cited a regression test that did not exist.** The migration's
header names `tests/d/test_d9_rollout_serving_ref.py` as the safety net against
`ServingRevision`/`CapabilityRecord` field-set drift; that file did not exist anywhere in the
repo, so the byte-for-byte verification this lane did when writing 0045 (per its own text,
"scratch scripts, not committed") had no committed guard. Written now: it builds the same row
two ways - a real `ServingRevision` read back through `PgCatalogDirectory.serving_revision`
(the exact path every production caller, including `operations.serving_ref`, uses; nothing here

the way a hand-rolled comparison could) and `infrx.lab_serving_ref_digest` on the same
`serving_version_id` - and asserts the two sha256 hex digests match, for the two field
combinations the migration's comment already claimed were checked (every optional field null,
`adapter_digest`/`runtime_image_digest` NULL, one weight shard, a zero-microsecond `created_at`;
every optional field set, two weight shards, every `CapabilityRecord` flag non-default, a

review's own finding that there is no live bug today - only that the promised net was missing.
No migration or comment edit needed: the comment's claim is now true.

## Proposed ruling, narrowed (0-F1; supersedes the unnumbered one above)

"An endpoint's alias is the newest catalog listing - by `created_at`, ties broken by
`public_model_id` then `version`, both descending - that is BOTH (a) the newest such listing and
(b) its own alias's CURRENT listing (the highest `version` under that `public_model_id`). A
listing an alias has since superseded never answers for an endpoint, no matter how recently it
was written or how long ago the alias moved off - `catalog_listings` rows are permanent history,
not a live index of what an endpoint currently serves." (LSQ5-m2, corrects the unnumbered
ruling above, which lacked clause (b) and so still permitted exactly the bug 0-F1 reports.)
