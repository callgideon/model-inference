## The migration vs U3's proposal

RPC names, argument lists, answer shapes (`{replayed, unit, amount}`, `{replayed, suspended}`, `{replayed}`), error codes (42501 `forbidden: …`, `invalid_request`, `not_found`, `idempotency_conflict`), view names and columns are the proposal's; `operator-postgrest.test.ts` passes 9/9 unchanged. Deviations, each with its failing proof on the proposal as written (the proposal applied as 0025 with these tests: 4 failed, 6 passed):

| # | Deviation | Why | Proof on the proposal verbatim |
|---|---|---|---|
| 1 | Views revoked `from public, anon, authenticated, service_role` (the proposal omitted service_role), then SELECT to authenticated, service_role | Supabase's default ACL gives service_role ALL on a new public view. `operator_wallet_drift` is auto-updatable (single relation down to `infrx.credit_wallets`), so the platform key could UPDATE/DELETE `credit_wallets` rows through it with the owner's rights - writes 0006 took from service_role. | `service_role: update public.operator_wallet_drift set kind = kind -> None` (succeeded); privileges `('public.operator_wallet_drift', 'service_role', 'INSERT', True)` |
| 2 | `operator_set_suspension` and `operator_revoke_key` take `pg_advisory_xact_lock(hashtextextended(v_key, 0))` before the key lookup; the suspension's `exception when unique_violation` block is removed (unreachable once same-key calls serialize) | R143: "a reused key with another target or payload is idempotency_conflict; a concurrent retry is a replay". | 3 | Static REVOKE/GRANT statements instead of the DO loop with `execute format` | no dynamic SQL where a static statement does | - |
| 4 | 0024-style header: objects, ORDER, ROLLBACK, re-runnable note; comments | D10 convention | - |
