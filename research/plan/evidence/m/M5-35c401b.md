## What was built

* **Authority (point 1).** `MediaUploads(objects, uploads=<UploadRepository>, content=<ContentLifecycle>)`. Nothing about an upload is kept in the process: no ticket dict, no `refs` entry per finalized upload, no lock per upload. The ref a ticket names is rebuilt from `(org, digest, profile)` with M's key builder; the repository stores no path. `ProcessUploads` (the port in this process's memory, refusal for refusal) is the default only where nothing durable is composed, and the executable negative control. A declared MIME, duration or digest is never a fact: size, digest and container are measured from the stored bytes.
* **Create.** `UploadConstraints.parse` (F2C's trust boundary) plus the v1 mediastore rule that a null `max_bytes`/`accepted_mime` is refused. The repository mints the handle and the window; the destination stays `infrx-upload:<handle>`.
* **PUT (point 2).** Measure the body, `acknowledge_put` (owner, open window, the ticket's cap, one set of bytes per handle), register the destination content row, then write the destination write-once. A foreign, closed, oversize or other-bytes PUT stores nothing; a retry after a lost acknowledgement is the same receipt and a no-op write.
* **Finalize (point 2).** `resolve` first: a finalized ticket is the idempotent answer (and a destination rewritten behind the store is `409`); otherwise, under the preparation pool's gate, HEAD (refuse above `MAX_MEDIA_BYTES` unread), download, `acknowledge_put` with what was measured (this recovers a lost PUT acknowledgement and returns the constraints), refuse declared size/digest/type BEFORE anything is copied (abort durably), probe (`media_refused` on failure), register the source row, write the content-addressed source, then `complete`. A crash between the source write and the commit is finished by any process's retry (write-once no-op). In-process single flight per `(org, handle)`; across processes `complete` decides (the same source answers the same ticket). Every object I/O is between short repository calls.
* **Use (point 3).** `resolve_owned`/`materialize` of an upload handle go through the repository: foreign/unknown `404`, from `expires_at` `410 upload_expired`, unfinalized `404` (R99(a)), object gone or replaced `404`. `attach` of an upload ref checks the tenant's content-addressed source object and its digest, not the ticket window: a job admitted inside the window stays attachable and preparable after it (the relay's `_resume`), and another tenant's same-bytes object binds nothing.

## E1C's question: is the Idempotency-Key consumed by an upload-handle refusal?

**No.** A request refused before admission (unknown, foreign, unfinished or expired upload handle: 404/410) is refused in `prepare_request`, before `lookup`'s mapping could exist and before `admit`: it is not a job, holds nothing and records nothing under the key (R91: a key maps only an admitted job; R21: nothing is settled for it; consistent with R106, which is about a job that exists). So the key stays free: the same key with a corrected handle is admitted FRESH (no `Idempotency-Replayed`), the same refused body under the key is simply evaluated again (not a replayed refusal - once the upload completes, that same keyed body is admitted), and only after admission does the key replay (a changed body is then `409 idempotency_conflict`). Test: `tests/m/test_upload_wiring.py::test_upload_restart__a_refused_upload_reference_does_not_consume_the_idempotency_key` (shared job store across composed gateways). E1C's quarantine-and-never-rebill policy is safe under this; it may also retry the item under the same key with a corrected handle.

## Proposed ruling text (coordinator numbers it)

"**Upload tickets across processes (M5).** The ticket authority is F2C's `UploadRepository`; a gateway keeps no per-upload state. (a) A PUT records its receipt before the destination is written, write-once; a refused PUT stores nothing and a retried one is a no-op. (b) Completion measures the destination, refuses declared size/digest/type before anything is copied, probes, writes the content-addressed source and only then commits; a crash between the write and the commit is completed by any retry; the first completion's bytes are the handle's forever. (c) Resolution of an upload handle is the ticket's: foreign or unknown 404, from `expires_at` 410, unfinalized 404 (R99(a)'s 'otherwise indexed' `invalid_request` arm is retired), the object gone 404. (d) Ticket expiry bounds new use only: an admitted job's upload ref binds by its tenant's content-addressed source object and survives the window. (e) A request refused before admission for its upload reference does not consume its idempotency key."
