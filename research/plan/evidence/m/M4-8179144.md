* **Harness** (`tests/m/perf/harness.py`). Per clip, against the real `MediaFetcher`,
  `MediaPreparation` and `probe`: retrieval over a real loopback TCP socket (an
  `http.server` subprocess; the fetcher resolves a public documentation address and a
  transport connects that pinned request to 127.0.0.1, so every byte crosses httpx and the
  fetcher's cap, digest and copy); probe time; materialization (URL and `data:`);
  preparation with the processing cache cold (miss), warm (hit) and after expiry; the
  event loop's worst stall during each operation; `tracemalloc` high-water in a separate
  pass; the MEDIA-PARITY facts; and for refused media the outcome, time and bytes read
  first. 7 repeats per timing (p50 needs ≥ 6, `bench.py`'s rule); p50 and max reported,
  never a p95. Clip set: E1's 64-clip corpus and its 4 negatives, `sop-synth-v1`'s 12, a
  synthetic size ladder (16 MiB, 32 MiB, exactly the 64 MiB cap, cap + 1), and two
  over-cap real encodes rendered by the pinned ffmpeg (150 s, 720p, 3 Mb/s, 56,510,882 B;
  one header-first, one media-first).
* **3a** `fetch.py`: the digest is updated per chunk and the body is copied once.
* **3b** `store.py`/`prepare.py`: the full-body digests in `materialize` and `prepare` run in
  `asyncio.to_thread` (hashlib releases the GIL).
* **3c** `fetch.py`/`store.py`: a `data:` URL's payload is sliced once and decoded with
  `binascii.a2b_base64(strict_mode=True)` (exactly what `b64decode(validate=True)` calls,
  minus its ASCII re-encoding copy); the decode runs in a worker thread so its digest is off
  the loop.
* **3d** `fetch.py`/`probe.py`/`prepare.py`/`store.py`: `MediaFetcher.fetch(url, early=)`
  shows the head of a download to the caller at 1 MiB and each time it has doubled (≤ 7
  looks to the cap). `MediaPreparation.refuse_early` probes a **complete leading `moov`**
  (`probe.probe_header`; a `moov` still arriving is answered from its box header alone,
  without copying the prefix) and applies the same `MediaProfile.check`; a refusal is tagged
  `reason="header"` for the operator log. Whatever the header does not settle is left to the
  whole-object probe in `facts`, so this only refuses sooner, never accepts: a `Probed` from
  the header is read from bytes the whole-object probe reads identically, and a second
  `moov`/`mvhd` later in the file is itself a whole-object refusal (`duplicate-header`).

### Measured, not taken

* **The prepared-copy write.** After 3b, the remaining 27–28 ms of loop stall in a 64 MiB
  cache miss is `ProcessingCache.put` writing the local file. Moving it to a thread needs
  two changes for safety — a per-call temporary name (today `{path}.{pid}.part`, which two
  concurrent same-key writes in one process would share) and the index update kept on the
  loop (M3's GC iterates `entries`) — so it is left as is: a candidate, with this number.
* **The `data:` decode itself.** After 3c the remaining `data:` stall (~250 ms at the cap) is
  the slice and `a2b_base64`, which hold the GIL in one C call; a thread does not help and
  chunked strict decoding changes refusal semantics unless padding is policed per chunk.
  The gateway's JSON parse of the same 85 MiB body (G's) costs the loop as well and is not
  measured here. Large clips are better sent as URL or upload.
* **Preparation concurrency.** Not tuned. `PREPARATION_CONCURRENCY` stays 2; a sweep on a
  shared 16-CPU development host would say nothing about the 8-vCPU pilot box.

## Limits

1. **This is not the pilot box.** Every number is from a shared 16-CPU development host
   under load average 13–31; the pilot is an 8-vCPU g6e.2xlarge whose absolute numbers will
   differ. The ratios that do not depend on the host — high-water 3.0× → 2.0× (URL) and
   3.67× → 2.33× (`data:`), 56.5 MB → ~1 MB read before an early refusal — should carry;
   stalls and walls must be re-measured there. **Pending P-04's target via E1B**, which
   this lane is not authorized to run on.
2. **The E1B bottleneck was not profiled**, because E1B has not run (its protocol is
   predeclared, every cell pending P-04/W3/I2B). What was profiled is the media layer's own
   cost. S2M §1.6's one surviving finding — per-request video handling is the bottleneck at
   1080p — concerns **decode inside the engine**, which this layer does not do in profile v1
   (no transcode; `mm_processor_kwargs` from the measured duration). Nothing here can move
   that number; it is W4's and a separately versioned profile's.
3. **Retrieval is loopback only.** TTFB and MiB/s are the fetcher's ceiling on this CPU,
   not a network figure; the early-refusal saving in wall time grows with the real link
   (≈ 55 MB not sent), which is unmeasured.
4. **The whole object is still held in memory** (≤ 64 MiB, M2's design): the write-once
   `put_if_absent` takes bytes and a media-first file needs its end before anything is
   known. Peak is now ~2× the body for a URL; 1× would need a streaming object-store port
   and a staging key the probe can refuse from — a port change, not proposed.
5. **Early refusal covers ISO base media only.** Neither corpus has a WebM or Matroska clip,
   so no measurement would support one; WebM is still refused by the whole-object probe.
   Only the URL path benefits — an upload is already stored and a `data:` URL is already in
   memory.
6. **The harness's store doubles are not S3.** The in-memory double's own digest runs off
   the loop during timing; a real adapter's `PutObject`/`GetObject` time is not in these
   numbers (M1 limit 2, pending).
7. **The upload finalize digest (`uploads.py`) still runs on the loop** (~0.8 ms/MiB here,
   same cost class as 3b). The harness does not exercise uploads, so it was left unmeasured
   and unchanged rather than changed without a before/after.
8. **Probe vs decoder, not vs the engine.** The parity oracle agrees with ffprobe on 76 real
   clips (all H.264 MP4 from one encoder); no engine has decoded a prepared artifact, and no
   HEVC/AV1/VP9/MOV/WebM real clip was available (M2 limit 2, narrowed but not closed).
9. **`make check` was not run as written** — see Test runs; the M, contracts, ordering and
   full M mutant suites were.
