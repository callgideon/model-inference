## Design (P3.a/b/c)
- **P3.a the manual bundle (the real workflow).** `prepare` validates the config (strict: objective `sft|preference`, adaptation `full|lora` — LoRA is how weights adapt, not an objective; base model, hyperparameters, environment), checks the export (N2's or P1's) is of this dataset, reads the training gate now (train ids and dev = validation ids still under a training grant; the rest listed in `omitted`; no trainable train sample → `Forbidden`), publishes the `lab.external_run.1` in D7 (purpose `training`, connector, `submit_key`, PROVIDER_USD budget with the named payer), and writes the bundle write-once at `lab/<provider>/training/<run>/bundle.json`: dataset ref, config, train, dev, omitted, the export's id/sha256, the external run ref, and a **pin** of the frozen holdout `{size, sha256(canonical sorted ids)}` — the holdout itself never ships. A replay is the same bytes; changed inputs a `Conflict`. The ledger run is created `prepared`.
- **P3.b connectors and one paid job.** `ManualConnector` (always advertised: the provider trains on its own compute, job id `manual:<key>`); `HttpConnector` speaks the protocol `POST /jobs` (Idempotency-Key) / `GET /jobs?key=` / `GET /jobs/<id>` / `POST /jobs/<id>/cancel` and is used only when its name is in `advertised` (default `{manual-bundle}` until P-11) and the run was prepared for it. `submit`: a `prepared` run re-reads the rights (current `run_evaluation` member on the L2 clock; every bundled id still under a training grant), reserves once per `submit_key` (D6J), moves prepared → submitting, calls the connector with the key: a 4xx is `failed` (reservation released); any other outcome (timeout, 5xx, crash) is `ambiguous` with the reservation held. A resume of `submitting` (a dead worker) moves it to `ambiguous`; an `ambiguous` run is reconciled **only** by `lookup(submit_key)`: found → `submitted`, not found → stays `ambiguous`. Nothing ever re-enters `submitting`, so no resume posts twice. `poll` settles a finished job's provider-reported PROVIDER_USD cost exactly, or `None` (unknown) when not reported exactly — never an estimate; provider training metrics are ignored. `cancel`: prepared → cancelled without the connector; submitted → the connector's cancel (a refusal raises, the run stays submitted) and the reported cost; ambiguous → `StateConflict` (reconcile first).
- **P3.c checkpoints and eligibility.** `import_checkpoint` requires the artifact under the run's prefix, records a D7 receipt (a redelivery = the first outcome, noted once in the ledger; the same id with other bytes = D7's `idempotency_conflict`), then rejects (`rejected` receipt, reason noted, never evaluated): a run not `submitted`/`completed` (`run_cancelled` for a late checkpoint, `run_prepared`), `missing_artifact`, `digest_mismatch` (bytes changed under the key), `incompatible` (not an `infrx.checkpoint.1` descriptor object, or another base model/adaptation). A valid one is `validated` and queued through B3 for evaluation on split `holdout` with the bundle's holdout pin. A crash between the receipt move and the note keeps the receipt's state. `approve` (a current developer-or-above) makes a candidate eligible — not public, not promoted — only for a validated checkpoint of **this** run whose evaluation **succeeded** on the bundle's dataset, split `holdout` and holdout pin; anything else is `StateConflict`.

## Oracles
- TRAIN-RECOVER: manual bundle → checkpoint → held-out evaluation → eligible (acceptance round trip); late checkpoint after cancel, never-submitted run, missing/tampered/incompatible artifacts rejected and never evaluated (even if B3 evaluated one anyway, it is not eligible); ambiguous submit (503 after accept in process; timeout after accept over TCP) and a worker crash mid-submit never post twice; a definite refusal fails and releases; explicit connector capability (automatic hidden by default, a run only through its own connector); eligibility only on the succeeded frozen-holdout evaluation of the same run (failed, other split, other holdout, other dataset, other run refused); training metrics never promote.
- PIPELINE-LINEAGE: bundle → external run record (D7) → receipt (D7) → evaluation run (B3) → eligibility note name each other; the holdout pin binds evaluation to the frozen holdout.
- PIPELINE-BUDGET / DATA-RIGHTS: one reservation per submit key, held while unknown; reported cost exact or unknown; the training gate read at bundle and again at submit (a grant narrowed to provider_sharing refuses the submission with no reservation and no post); USD only (PROVIDER_USD with the named payer), no CREDIT anywhere.

## Proposed ruling (propose, never number)
- P3 training: the manual bundle connector is the only advertised connector until P-11; a bundle carries train/dev ids under a current training grant and only a size+digest pin of the frozen holdout; a submission is at most once per `submit_key` — any outcome other than a success or a definite 4xx refusal is `ambiguous` and is reconciled only by lookup (not found stays ambiguous, reservation held); provider cost settles as reported or as unknown, never estimated; a checkpoint is rejected when its run is not submitted/completed or its artifact is missing, altered or incompatible, and a candidate is eligible only on a succeeded evaluation of its own run's pinned frozen holdout — training metrics never promote.
