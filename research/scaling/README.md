# research/scaling/ — index and reading guide

## 1. What this is

Fact-checked research on **running this repo's five models at scale**: cluster hardware, serving stack, admission control, throughput, autoscaling, cold start, cost, reliability, reference architectures, and how commercial inference providers solve the same problems — each with its own verification log. It assumes the per-GPU and per-model numbers already established elsewhere in `research/` (weight memory, KV/state, fit, throughput, cost) and **links to them rather than re-deriving them**; `01`–`09` and `12` are the independent studies, `10-blueprint.md` assembles them into one platform for this repo's hardware, and `11-playbook.md` condenses all of it into decision tables and checklists.

**Research date: 2026-09-19**, pinned in every document. Infrastructure software in this space moves on a ~3-month cadence; re-pin before you buy.

**Repo context assumed throughout:** five models — `deepseek41f`, `deepseek41fnvfp4`, `qwen3827b`, `kimik3`, `marlin2b` — on 8×B300 HGX nodes (268 GB/GPU as deployed, 2,144 GB/node) with local NVMe, plus AWS `p6-b300` nodes for burst.

## 3. Reading order

1. **New to this tree?** Read `10-blueprint.md` first — it states the "five sentences" the whole platform reduces to — then `11-playbook.md` alongside it as the quick-reference.
2. **Need the reasoning behind a blueprint decision?** Go to the numbered document `10` cites for that section — `01`–`09`, `12` are independent and readable in any order, but `01` (hardware) and `02` (serving stack) are the foundation the rest assume.
3. **Operating a live fleet?** Start at `11-playbook.md` §2 (checklists) and §3–4 (alerts, engine flags); drop into the numbered doc only when a rule needs its derivation.
4. **Evaluating build-vs-buy?** `07-cost-engineering.md` and `12-inference-providers.md` §5–6 together.

## 4. The documents, 01–12

**[`01-bare-metal-cluster.md`](01-bare-metal-cluster.md) — bare-metal GPU cluster foundation.** Everything below the inference engine: silicon layout and NVLink/fabric topology, OS/driver stack, orchestration choices, cluster networking, weight distribution, an observability baseline, and security/multi-tenancy basics. Key takeaways: Kimi-K3 needs whole-node gang scheduling (its 1,560.9 GB checkpoint alone), one copy of all five models sums to 2.40 TiB and sets the NVMe floor per node, and RoCEv2 is defensible only at small (4-node) scale. Worked example (§8): a reference bill of materials and cluster layout at two sizes — **4 nodes (32 B300)**, the smallest cluster that holds one replica of every model with N+1, and **16 nodes**, where the document's P2P weight-delivery, quota and fabric decisions start paying for themselves.

**[`02-serving-stack-and-routing.md`](02-serving-stack-and-routing.md) — serving stack, gateways and routing.** The five-layer stack (client → gateway → router → engine → hardware) and who owns what at each layer, the engine serving surfaces as of this date, routing algorithms from round-robin to KV-event-driven prefix routing, gateways (Gateway API Inference Extension, Agent Router), multi-model/multi-tenant serving, and streaming/cancellation semantics. Worked example (§8): a per-model routing verdict for all five models on 8×B300 — KV-aware/prefix-precise for DeepSeek-V4.1-Flash, token-load/power-of-two for Qwen3.8-27B, least-loaded + hard session affinity for Kimi-K3 (nothing to route *within* its one whole-node replica), plain least-outstanding-requests for Marlin-2B (video prompts have no shared prefix).

**[`03-concurrency-and-admission-control.md`](03-concurrency-and-admission-control.md) — handling concurrent requests robustly.** The request lifecycle inside an engine, capacity limits and how to set them, admission control and backpressure, SLO-aware scheduling, failure handling under load, long-context/multimodal concurrency, and a fill-in-the-blank concurrency test plan template. Worked example (§8): DeepSeek-V4.1-Flash on **2×8×B300 (16 GPUs)** under a **5× burst** — TP4, 4 replicas, Engram tables host-offloaded, DSpark γ=5, with the full admission-queue and prefill-backlog arithmetic shown step by step.

**[`04-throughput-and-utilization.md`](04-throughput-and-utilization.md) — maximising throughput and GPU utilisation.** Utilisation metrics that matter (MBU/MFU and their DCGM traps), batching at the cluster level, filling idle capacity, memory tiering for KV (G1–G4/L1–L3), kernel- and engine-level knobs, and MoE-specific cluster patterns (wide-EP, EPLB). Worked example (§8): a utilisation plan for this repo's nodes — decode tok/s/GPU and tok/s/node for every model's recommended shape, quoted entirely from [`../matrix/pairs.json`](../matrix/pairs.json) with no new arithmetic.

**[`05-autoscaling-and-predictive-scaling.md`](05-autoscaling-and-predictive-scaling.md) — autoscaling, predictive scaling and capacity planning.** Why CPU-style HPA is wrong for inference, which signals lead and which lag, Kubernetes mechanisms (HPA/KEDA/Knative), predictive scaling, scale-down/thrash/when zero is legal, and multi-model fleet scheduling. Worked example (§8): a per-model scaling policy table — Marlin-2B and Qwen3.8-27B scale to zero with a cron floor, DeepSeek-V4.1-Flash gets a predictive p90 forecast at a 15-minute horizon, Kimi-K3 gets **no reactive autoscaling at all** (queue depth drives admission, not replica count).

**[`06-cold-start.md`](06-cold-start.md) — cold start: boot, weight loading, warm-up and pre-warming.** The anatomy of a replica cold start, weight-loading fast paths (NVMe/S3/P2P-RDMA), compile/JIT/CUDA-graph caches, snapshot/restore (and why it doesn't work yet for multi-GPU TP), pre-warming strategies, and rolling updates. Worked example (§8): a cold-start budget on an 8×B300 node — per-model weight-load time at 10/20 GB/s NVMe, 3 GB/s S3 and P2P RDMA; every figure is `est.` because **no model in this repo has a measured end-to-end cold start** (its own open question 1).

**[`07-cost-engineering.md`](07-cost-engineering.md) — reducing inference cost.** The cost model of a fleet, utilisation levers in cost terms, caching economics, model-level levers (routing, distillation, prompt compression), hardware levers (power capping, GPU choice), and the FinOps loop. Worked example (§9): $/1M output tokens for all five models on 8×B300 at 30/60/85 % goodput and the `low` GPU-hour tier, against each model's vendor-API price — Marlin-2B is cheapest ($0.026 at 85 %), Kimi-K3 the most expensive even against its own $15/1M vendor price.

**[`08-reliability-and-operations.md`](08-reliability-and-operations.md) — reliability, observability and day-2 operations.** SLOs for inference, failure modes and detection (Xid/SXid catalogues, silent failures that emit no error), recovery, the observability stack, change management, and benchmarking as an operational discipline. No numbered worked example; its equivalent is **ten runbooks** (§8) for named incidents — Xid 79, NCCL hang, KV OOM storm, 429 storm, slow weight load, hot node, stuck rolling update, cache-hit collapse, quality regression, IB degradation — and a fill-in benchmark-plan template (§6.4).

**[`09-reference-architectures.md`](09-reference-architectures.md) — reference architectures and case studies.** Published production architectures with numbers (DeepSeek, Character.AI, Baseten, Mooncake and others), open-source stacks end-to-end on Kubernetes, Slurm-based serving, topology patterns, anti-patterns seen in the wild, and a decision matrix (workload × model class → stack). Worked example (§7): **three blueprints on 8×B300 nodes** — Blueprint A (4 nodes / 32 GPUs), B (16 nodes), and C (64 nodes) — sized for all five models with per-pool GPU counts, replica counts and aggregate tok/s and $/1M, all `est.` from `pairs.json`.

**[`10-blueprint.md`](10-blueprint.md) — the inference platform for this repo.** Assembles `01`–`09` and `12` into one target architecture: the five-layer stack, the software bill of materials, a per-model serving profile, two request-path walkthroughs (an interactive DeepSeek-V4.1-Flash request and a Kimi-K3 agent/tool loop), the scaling policy, a cost projection, provider-derived techniques adopted, and a phased rollout plan. No number here is new — every figure is carried from a linked document or is one stated multiplication on carried figures. Its own key takeaway is the **five sentences** it reduces to: five pools behind one gateway; nothing PD-disaggregated at 4 or 16 nodes; weights live on every node's NVMe; autoscale on queue/backlog/KV, never CPU/GPU utilisation; and the money is in utilisation, not silicon (30 %→85 % goodput on DeepSeek-V4.1-Flash is worth 2.83×, for free).

**[`11-playbook.md`](11-playbook.md) — decision rules and checklists.** The condensed operator's guide to `01`–`09` and `12`: decision tables (when to PD-disaggregate, TP vs DP, which router, when to scale to zero, buy vs rent vs API, which KV tier, workload × model class → stack), five operational checklists (bring up a node, deploy a model, before a launch, during an incident, monthly FinOps review), the 20 metrics worth alerting on, the 15 engine flags that matter most per model (with this repo's recommended value for each), and a glossary. Every number is quoted, not derived — if a row disagrees with its source, the source wins.

**[`12-inference-providers.md`](12-inference-providers.md) — how optimized inference providers build their platforms.** Reverse-engineers **28 commercial inference operators** — the GPU-seconds/serverless-container business (Modal, fal, Wafer, Baseten, RunPod, Replicate, Beam, Cerebrium, Northflank, Anyscale, Cloudflare, Hugging Face...) and the per-token model-API/custom-silicon business (Together, Fireworks, DeepInfra, Novita, Groq, Cerebras, SambaNova, DeepSeek, Moonshot, Mistral...) — for what transfers to a single-tenant bare-metal cluster and what is an artefact of being a multi-tenant public business. Worked example (§6): a **ranked "what transfers" list**, leverage-ordered against this repo's five models — PD disaggregation, KV-aware routing + tiered KV store, and concurrency-based autoscaling with asymmetric windows rank #1–#3; per-head KV compression (unproven on MLA/KDA/GDN) ranks last.

## 5. How this connects to the rest of `research/`

`research/scaling/` never re-derives a weight-memory, KV, fit, throughput or cost formula — every one of those lives in [`../METHODOLOGY.md`](../METHODOLOGY.md) and is cited by section. The per-GPU facts (HBM, bandwidth, attention-kernel and quantization support) come from [`../gpus/`](../gpus/); cross-model topic references (flash-attention, quantization formats, engine support, cloud pricing, serving optimizations) come from [`../cross-cutting/`](../cross-cutting/); the audited per-(model, GPU) throughput/latency/cost numbers this tree's worked examples quote come from [`../models/<exp>/`](../models/) and the generated [`../matrix/`](../matrix/) grids, above all [`matrix/pairs.json`](../matrix/pairs.json). [`../README.md`](../README.md) is the parent index for that numeric tree; this document is the parallel index for the operational layer built on top of it.

## 6. Top 15 open questions across `research/scaling/`

Consolidated and deduplicated from each document's own Open-questions section; each one is load-bearing for at least one number elsewhere in the tree. Full detail and resolution method are in the named document.

1. **DSpark/MTP speculative-decoding acceptance rates are synthetic, not measured** — swings every `$/1M output` figure by up to 3–3.5×. [`10` §9.1](10-blueprint.md#9-risks-and-open-questions)
2. **Replicated vs. sharded KV cache accounting differs 4–8× and no engine doc states which applies** — `pairs.json` and the per-model guides already disagree by exactly 4× and 8× on two pairs. [`10` §9.1](10-blueprint.md#9-risks-and-open-questions), [`03` OQ](03-concurrency-and-admission-control.md#open-questions)
3. **No end-to-end cold-start measurement exists for any of the five models** — every §8 figure in `06` is `est.` arithmetic on other models' published stage timings. [`06` OQ1](06-cold-start.md#open-questions)
4. **Achieved MBU on Blackwell spans roughly 8×** (0.054–0.70 across two anchors) and no per-GPU-generation MBU/MFU measurement exists in this tree; every throughput table's target band is a planning default. [`04` OQ1](04-throughput-and-utilization.md#open-questions)
5. **Every Qwen3.8-27B and Marlin-2B row is `confidence: estimate`** — no throughput, TPOT or TTFT measurement exists for either on any datacentre GPU, and Marlin's `--hf-overrides` remap has never been run anywhere. [`10` §9.1](10-blueprint.md#9-risks-and-open-questions)
6. **Peak prefill throughput `V_P` is unmeasured for every (model, B300, parallelism)** — the DeepSeek prefill-backlog scale-up threshold uses llm-d's default, not a derived value. [`05` OQ4](05-autoscaling-and-predictive-scaling.md#open-questions)
7. **No published comparison of prefix-affinity routing against a well-tuned token-load baseline exists** — every measured routing gain in `02` is against round-robin or random. [`02` OQ2](02-serving-stack-and-routing.md#open-questions)
8. **Prefix-affinity routing on hybrid linear-attention models (Qwen3.8-27B, Kimi-K3) is unmeasured** — most of their layers hold recurrent state, not KV, and no benchmark covers cross-replica routing for that case. [`02` OQ9](02-serving-stack-and-routing.md#open-questions)
9. **Whether vLLM's PD path preserves DSpark for DeepSeek-V4.1-Flash is unanswered** — NVIDIA's SGLang recipe refuses it under disaggregation; this decides whether the DeepSeek pool can be disaggregated at all. [`09` OQ3](09-reference-architectures.md#open-questions)
10. **B300 HBM per GPU: 288 GB (NVIDIA HGX AI Factory RA, a primary source) vs. 268 GB (`METHODOLOGY.md` §8 pin, as-deployed)** — unreconciled; every capacity figure in this tree uses 268 GB. [`01` OQ1](01-bare-metal-cluster.md#open-questions)
11. **Local NVMe sustained read bandwidth on this repo's 8×B300 nodes is unmeasured** — it sets cold-start time and MTTR for every model; one `fio` run would close it. [`08` OQ1](08-reliability-and-operations.md#open-questions)
12. **Client-disconnect → engine-abort mapping is undocumented** across vLLM/SGLang/TRT-LLM — on agentic traffic with high abandonment this is directly wasted, unmeasured GPU time. [`02` OQ3](02-serving-stack-and-routing.md#open-questions)
13. **Dynamo's DeepSeek-V4.1-Flash and Kimi-K3 recipes are day-0 GB200/GB300 snapshots, not B300 HGX** — router mode, `max-running-requests` and DCP settings are read across to a different NVLink-domain scale without validation. [`02` OQ11](02-serving-stack-and-routing.md#open-questions), [`10` §9.3](10-blueprint.md#9-risks-and-open-questions)
14. **No measured goodput-`U` for a dedicated inference fleet was found anywhere** — the 30/60/85 % scenarios throughout `07` and `09` are brackets, not forecasts. [`07` OQ3](07-cost-engineering.md#open-questions)
15. **The 8×B300 server price ($600k), node draw (15.5 kW) and colo rate ($180/kW-month) are all estimates**, carrying every absolute cost figure in `07` and `10`'s cost projection at roughly ±25 % — the *ratios* are robust, the totals are not. [`07` OQ1](07-cost-engineering.md#open-questions), [`10` §9.2](10-blueprint.md#9-risks-and-open-questions)
